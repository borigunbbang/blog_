## 1. 같은 질문, 다른 맥락 — 답의 근거는 어디서 오는가

**왜?** 같은 질문을 했는데 어제와 오늘 답이 다르다면, "모델이 변덕을 부렸다"고 보기 전에 이번 호출에서 모델에게 **무엇을 읽혔는지**부터 확인해야 한다. 답의 재료가 달랐을 가능성이 훨씬 크다.

**무엇?** 앞 단원의 지시가 "모델이 무엇을 해야 하는지 정하는 계약"이라면, 맥락은 "그 판단에 필요한 자료를 이번 호출에 어떻게 보여 줄지 정하는 입력 구성"이다. 한 번에 넣을 수 있는 분량에는 한도가 있고, 이를 **컨텍스트 창(context window)**이라고 한다.

> 💡 **컨텍스트 창**: 책상 위에 펼쳐 둘 수 있는 종이의 양이 정해져 있다고 생각하면 된다. 모델은 이번 호출로 책상에 올라온 글만 읽을 수 있다. 창보다 큰 입력은 전달되지 않고, 창에 올라오지 않은 과거 내용은 이번 답에서 존재하지 않는 것과 같다. 분량은 토큰으로 센다.

```
┌──────────── 컨텍스트 창 (최대 분량) ────────────┐
│ 질문·지시 (예: 반품 문의)                       │        ┌───────────────────┐
│ 근거 자료 (예: 정책 문서)                       │  ←──── │ 지난 대화·문서     │
│ ┄┄ 출력이 쓸 자리 (예: 답변 초안) ┄┄           │        │ (창 밖 저장소)     │
└─────────────────────────────────────────────────┘        └───────────────────┘
입력과 출력이 같은 창의 한도를 나눠 쓴다. 창 밖 자료는 넣어야만 이번 답에 존재한다.
```

### 컨텍스트 창의 세 가지 성질

1. **창은 유한하다** — 입력과 출력이 같은 한계 안에서 자리를 차지한다. 입력을 더 넣으면 출력이나 다른 자료의 자리가 줄어든다. 그래서 컨텍스트 엔지니어링은 많이 넣는 기술이 아니라, 필요한 재료와 **출력 예산**(답에 남겨 둘 자리)을 함께 남기는 일이다.
2. **창은 매 호출 새로 구성된다** — 대화가 사람의 기억처럼 모델 안에 남아 있는 게 아니다. 다음 요청 때 앱(모델을 감싼 서비스 프로그램)이 필요한 메시지와 자료를 다시 넣는다. 대화가 매끄럽게 이어져 보여도 그 연속성은 앱이 조립한 결과다.
3. **창은 저장소가 아니다** — 오래 보관하고 찾는 일은 파일, 데이터베이스, 문서 저장소, 대화 로그 같은 모델 밖 장치가 맡는다.

> 💡 **검색 인덱스**: 책 뒤의 "찾아보기"처럼 어떤 단어나 주제가 어디 있는지 미리 정리해 둔 목록. 전체를 뒤지지 않고 빨리 찾는다.

### 창과 저장소를 구분한다

| 구분 | 컨텍스트 창 | 저장소 |
|---|---|---|
| 역할 | 이번 호출에서 읽는 범위 | 자료를 오래 보관하고 필요할 때 찾는 장치 |
| 예 | 이번 질문 + 넣어 준 자료 | 고객 지원 기록, 정책 전문, 프로젝트 결정, 과거 대화 원문 |

⚠️ 창에 넣었다고 저장된 것이 아니고, 저장소에 있다고 이번 답에 읽힌 것도 아니다. 이 구분이 흐리면 "긴 문서를 한 번 넣으면 계속 알고 있으리라" 기대하거나, "화면에 보이는 기록이 언제나 답의 근거"라고 착각한다.

실무에서는 원문은 저장소에 두고, 현재 질문에 필요한 부분과 **원문 주소**를 호출에 넣는다. 반품 판단이라면 정책 적용일, 수령일 기준, 예외 조항, 주문 상태의 출처를 따로 나눠 둔다. 요약할 때도 어느 버전의 어느 조항에서 왔는지 적어야 다음에 다시 확인할 수 있다.

🔑 저장 · 검색 · 입력 조립은 서로 다른 역할이고, 어느 하나가 나머지를 자동으로 대신하지 않는다.

### 답이 달라졌다면 확인할 것

모델이 "앞서 정한 형식을 따르겠습니다"라고 할 때 그 형식은 대화 이력, 시스템 지시, 메모리 요약, 프로젝트 파일 중 하나에서 **이번에 다시 읽힌 것**이다. 답이 달라졌다면:

- 지시문이 바뀌었나?
- 대화 요약이 갱신됐나?
- 검색으로 들어온 문서 버전이 달라졌나?
- 출력 예산이 줄었나?

**입력 조립표**(이번 호출에 무엇을 넣었는지)와 응답 원문을 함께 남기면 어느 재료가 판단을 바꿨는지 추적하고 재현할 수 있다. "정책을 보냈다"만 적으면 전문인지, 발췌인지, 최신본인지 알 수 없다.

🔑 컨텍스트 설계는 프롬프트 문장을 잘 쓰는 일이라기보다 **호출마다 같은 근거 조건을 관리하는 일**에 가깝다.

### 창이 넓어져도 읽히는 것은 다르다

긴 창은 더 많은 재료를 올릴 수 있게 해 줄 뿐, 모든 문장이 같은 정도로 답에 쓰인다는 보장은 없다. 긴 정책의 예외 하나가 중간에 묻히거나, 오래된 가정이 최근 정정과 함께 남을 수 있다.

🔑 "들어감"과 "읽힘", "보관"과 "회수"는 서로 다른 사건이다.

그래서 큰 창에서도 먼저 판단 조건을 적는다 — 답을 바꾸는 사실은? 그 원문은 어디에? 예외와 적용 시점은? 출력은 얼마나 필요한가?

### 순서와 경계가 근거를 보존한다

지시·질문·문서·도구 결과 사이에 `[정책]`, `[질문]` 같은 제목과 구분자를 두지 않으면, 어떤 문장이 규칙이고 어떤 문장이 인용 자료인지 헷갈린다.

- 문서에는 제목·발행일·버전·출처를 붙인다.
- 사용자가 말한 사실과 정책의 일반 규칙을 구분한다.
- 오래된 초안에는 "폐기" 또는 "참고" 표지를 붙인다.

도구가 가져온 결과는 **만들어진 시점**도 맥락이다. 재고·주문 상태처럼 바뀌는 사실은 지난 대화보다 방금 조회한 결과가 우선할 수 있지만, 정책의 적용일은 "최신"이라고 자동으로 현재 고객에게 적용되지 않는다.

## 2. 창을 나눠 쓰는 다섯 재료

컨텍스트를 다룬다는 건 "대화창 관리"가 아니라 **구성요소 전체의 자리 다툼을 설계하는 일**이다. 매 호출의 창에는 대화 이력뿐 아니라 시스템 지시, 도구 정의와 실행 결과, 검색 근거, 출력 스키마가 함께 들어온다.

> 💡 **출력 스키마**: 답의 모양을 정한 설계도. "답은 reply, evidence, question 세 칸으로 된 JSON"처럼 필드 이름과 형식을 정해 둔 것.

| 번호 | 재료 | 하는 일 |
|---|---|---|
| 1 | 지시 | 모델의 역할과 금지 사항을 정한다 |
| 2 | 문서 | 질문에 답할 근거를 준다 |
| 3 | 메모리 | 이전 작업에서 남긴 요약·결정 기록·사용자 선호 |
| 4 | 도구 목록 | 쓸 수 있는 도구의 이름, 매개변수, 설명 |
| 5 | 대화 이력 | 사용자와 assistant가 주고받은 메시지 |

```
[ 지시 | 문서 | 메모리 | 도구 목록 | 대화 이력 ]  ← 하나의 창을 나눠 씀
                    ↓
         남은 예산 안에서 출력 생성
```

한 칸을 늘리면 다른 칸과 출력 자리가 함께 줄어든다.
- 긴 시스템 지시·도구 정의 → 안전한 동작의 바탕은 늘지만 문서·이력 자리가 줄어든다.
- 과거 대화를 모두 유지 → 합의한 결정은 보존되지만 지금 답할 조항이 묻힐 수 있다.
- 새 문서를 넓게 → 근거 범위는 커지지만 오래된 메모리와 충돌할 가능성도 커진다.

⚠️ 메모리가 원문을, 도구 설명이 실제 결과를, 과거 대화가 최신 주문 상태를 대신할 수는 없다. 재료의 종류를 구분해야 충돌할 때 무엇을 다시 확인할지 판단할 수 있다.

### 예산표는 줄일 대상을 찾는 도구

| 칸 | 적는 것 |
|---|---|
| 입력 항목 | 지시, 도구 정의, 정책 문서 등 |
| 실제 토큰 수 | 그 항목이 차지하는 양 |
| 고정·가변 | 매번 같은지, 호출마다 바뀌는지 |
| 출처 | 어디서 왔는지 |
| 제거 위험 | 뺐을 때 무엇이 위험한지 |
| 확보할 출력량 | 답에 남길 자리 |

예: 고정 지시 8k는 유지하되 중복 예시 2k는 줄이고, 도구 정의 12k는 지금 안 쓰는 도구를 빼고, 대화 이력은 "최근 원문"과 "결정 메모"로 나눈다.

🔑 무엇을 넣을지는 곧 무엇을 뺄지의 판단이다.

## 3. 길수록 흐려진다

컨텍스트 창에 많이 넣는다고 모델이 모두 참고하는 건 아니다.

### Lost in the Middle — 중간에 묻히는 현상

긴 입력에서는 모든 부분이 같은 정도로 답에 활용된다는 보장이 없다. 정보가 너무 많으면 서로 영향력을 놓고 경쟁해서 중요한 정보의 힘이 약해진다.

Liu 외의 연구에서는 질문과 후보 문서는 그대로 두고 **정답 문서의 위치만** 처음·중간·끝으로 바꿨더니, 20개 문서 질의응답에서 정답이 중간에 있을 때 정확도가 양끝보다 낮았다.

- "중간 내용은 항상 안 읽는다"는 뜻은 아니다. 모델, 문서 구성, 질문 난이도에 따라 다르다.
- "관련 내용이 문서에 있다" ≠ "모델이 그 내용을 판단에 사용했다" → 실제 근거를 확인해야 한다.

### 고착 — 초반 가정이 계속 영향을 주는 현상

고객이 처음엔 "미개봉"이라고 했다가 나중에 "택을 제거했다"고 정정했는데, 이전의 "미개봉" 정보가 상태에 남아 있으면 잘못된 반품 판단을 내릴 수 있다.

- 대화 전체 유지 → 정정 전후가 모두 보존되지만, 무엇이 현재 사실인지 구분하지 않으면 충돌도 보존된다.
- 대화 요약 → 길이는 줄지만 정정 시점·원문 주소·미해결 조건이 사라지면 고착이 더 심해진다.

→ 긴 대화일수록 **최근 정정 + 현재 유효한 사실 + 미해결 조건**을 따로 관리한다.

### Context Rot (맥락 부패)

맥락이 길어지며 중요한 신호가 희석되어 답이 흔들리는 현상. 원인에 따라 처방이 다르다.

| 유형 | 의미 | 예시 | 대응 |
|---|---|---|---|
| Poisoning (오염) | 검증 안 된 이전 답변·추정이 사실처럼 재사용 | "반품 기간 14일"이라는 잘못된 판단이 상태에 남아 계속 반복 | 생성문 제외, 원문 재검증 |
| Distraction (주의 분산) | 무관한 정보가 핵심의 주의를 빼앗음 | 반품 질문에 보상 규정이 잔뜩 들어가 핵심 조항이 묻힘 | 불필요한 정보 제외 |
| Confusion (혼동) | 비슷한 근거가 섞여 어떤 조건을 적용할지 불분명 | "택 제거"와 "실제 착용" 예외 조항이 섞임 | 적용 대상·버전·범위 구분 |
| Clash (충돌) | 지시·근거가 충돌하는데 우선순위가 없음 | 기본 반품 규정과 승인된 예외 지시가 충돌 | 우선순위·최신성·권한 판단 |

> 💡 컨텍스트 엔지니어링은 자료를 많이 넣는 기술이 아니라, 현재 판단에 필요한 근거를 선택하고 그 근거의 상태·위치·출처를 관리하는 기술이다.

## 4. 맥락 전략의 지도

중요한 질문은 "무엇을 기억시킬까?"가 아니라 **"이번 호출에 무엇을 넣을까?"**다. 저장해 뒀다고 매번 다 넣을 필요는 없고, 이번에 뺐다고 삭제하거나 쓸모없다고 판단한 것도 아니다.

- 보관: 정보를 저장해 두기 / 검색: 필요한 정보 찾아오기 / 압축: 짧게 줄이기 / 조회: 저장된 정보 다시 가져오기 / 선택: 이번 호출에 넣을지 결정하기

전략은 두 축으로 나뉜다.
- **선택 연산** — 이번 호출에 무엇을 넣을까?
- **상태 정책** — 여러 턴에 걸쳐 무엇을 유지하고 다음 호출에 어떻게 다시 구성할까?

### 선택 연산

| 방법 | 하는 일 | 주의점 |
|---|---|---|
| 전체 투입 | 관련 문서를 통째로 넣음 | 잡음, 길이, 위치 문제 |
| RAG | 검색한 관련 조각만 넣음 | 검색 안 된 예외·최신 버전이 빠질 수 있음 |
| 압축 | 확인한 내용을 줄여서 넣음 | 부정·예외·미결정·출처가 빠질 수 있음 |
| 폐기 | 이번 창에서 불필요한 자료 제외 | 필요한 근거나 제외 이유까지 잃을 수 있음 |

- **전체 투입**: 조항을 빠뜨릴 가능성이 적고 원문과 비교가 쉽지만, 길고 무관한 내용이 많으면 중요한 내용이 묻힌다.
- **RAG**: 100페이지 반품 정책 대신 "택 제거 상품도 반품 가능?"과 관련된 조항 몇 개만 검색해 넣는다. 검색 결과가 나왔다고 필요한 근거가 모두 검색된 건 아니다.

```
문서 전체 → 여러 조각으로 나눔 → 사용자 질문 → 관련 조각 검색 → 검색된 조각만 넣음 → 답변 생성
```

- **압축**: 예외, 부정, 미결정, 출처가 빠지거나 왜곡될 위험.
- **폐기**: 실패한 검색 결과, 철회한 해석, 적용되지 않는 오래된 정보를 이번 호출에서 뺀다. 원본까지 삭제하는 건 아니다.

### 상태 정책

| 방법 | 하는 일 | 주의점 |
|---|---|---|
| 누적 | 이전 대화를 모두 다시 보냄 | 철회한 가정도 계속 남음 |
| 슬라이딩 윈도 | 최근 N개 턴만 보냄 | 오래된 금지·결정이 사라질 수 있음 |
| 요약 | 오래된 이력을 짧게 정리 | 필요하면 원문으로 돌아갈 수 있어야 함 |
| 러닝 서머리 | 같은 틀의 노트를 계속 갱신 | 갱신 전후와 철회 이유를 남겨야 함 |

러닝 서머리 틀 예시:

```
목표:
확정 사실:
가정:
미결정:
다음 행동:
```

잘못된 가정은 "이 가정은 철회됨"처럼 철회 사실과 이유도 남겨야, 틀린 내용이 나중에 다시 살아나지 않는다.

### 압축이 상태에 들어가면 위험하다

```
원문 → ❌ 잘못 압축 → ❌ 잘못된 정보가 상태에 저장 → 다음 턴에서도 사용 → 또 다음 턴에서도 사용 → 계속 유지
```

압축 과정의 오류가 이후 상태에 **고착**될 수 있으니, 압축본은 원문과 대조해 검증한다.

| 확인 항목 | 확인할 내용 |
|---|---|
| 사실 | 누가, 언제, 무엇을 확정했는가 |
| 부정 | 하지 말라는 내용이나 해당하지 않는 조건이 있는가 |
| 예외 | 기본 규칙을 뒤집는 조건이 있는가 |
| 미결정 | 아직 확인되지 않은 것이 무엇인가 |
| 출처 | 원문의 어디에서 왔는가 |

## 5. 실습 설계 — 같은 질문, 다른 맥락 (통제 실험)

**왜?** 맥락을 어떻게 주느냐에 따라 답이 달라진다는 걸 감이 아니라 근거로 확인하기 위해서다. 정책을 안 주면 일반론을 지어내고, 다 주면 핵심 조항이 묻히고, 일부만 주면 필요한 조항이 빠질 수 있다. 바꾸는 것을 **하나만** 두고 나머지는 고정하며, **채점 기준은 돌리기 전에** 정한다(결과를 보고 정하면 마음에 드는 답에 점수를 주게 된다).

**얻는 것**: 통제 실험의 틀, 항목별로 답을 평가하는 눈, 조건·모델·파라미터·로그를 남기는 습관, 실패에 이름 붙이기(오염·주의 분산·혼동·충돌).

**활용**: 챗봇의 정책·FAQ 투입 방식 시험, RAG 평가, 프롬프트 개선 전후 비교, 모델 교체 비교, 평가셋 만들기.

### 실험 설계

- **바꾸는 변수**: 입력 맥락의 범위와 출처 표식뿐. 질문·모델·버전·생성 파라미터·출력 형식·실행 장비는 고정.
- **고정 질문**: "고객이 상품을 수령한 뒤 12일이 지났고 택을 제거했습니다. 단순 변심으로 반품하려 하며 배송비가 누구에게 있는지 묻습니다. 확인된 정책만 근거로 답하고, 정책이 말하지 않는 사실은 단정하지 마세요." → 판단 지점 세 개: **수령일 · 택 제거 · 단순 변심 배송비**
- **네 조건 × 2회 반복 (총 8개 출력)**

| 조건 | 넣는 맥락 |
|---|---|
| none | 정책 없음 |
| full | 반품 정책 §1~4 전체 |
| selected | §1, §3 |
| selected_cited | §1, §3 + 제목·버전·절 표식 |

selected와 selected_cited는 문장이 같고 표식만 다르다. 표식이 사실성을 자동 보장하지는 않는다. 2회 반복은 충분한 통계는 아니지만, 한 번의 인상적인 답을 일반 성질로 선언하는 일을 줄여 준다.

### 채점 6항목 (형식은 기록, 나머지는 1/0)

| 항목 | 기준 |
|---|---|
| 형식 | JSON 파싱, reply·evidence·question 세 필드, 근거 없으면 evidence는 null |
| 정답성 | 수령 12일 사실과 정책의 기한·배송비 조항에 어긋나지 않으면 1 |
| 근거 일치 | 핵심 판단마다 실제 입력 조항·표식이 대응하면 1 (none은 0) |
| 무근거 주장 | 입력에 없는 사실을 단정했다면 0 |
| 충돌 처리 | 기본 규칙과 예외를 대조해 반영하거나 필요한 사실을 물었으면 1 (§3 택 제거를 자동 승인·거절하면 0) |
| 기권 | 근거가 없거나 미확인 사실이 있을 때 단정을 멈추고 질문하면 1 |

**기권 예시** — 정책에 배송비 액수가 없는데:
- 감점: `{"reply": "반품 가능하며, 배송비는 3,000원입니다.", "evidence": "정책 문서 1조"}`
- 득점: "반품 신청은 가능합니다. 다만 정확한 반품 배송비 금액은 정책 문서에 나와 있지 않아 확인이 필요합니다" + 질문, `"evidence": null`

**정답성과 근거 일치를 합치지 않는다** — none이 우연히 "14일 이내 반품 가능"이라고 맞혀도 출처가 없으니 근거 일치는 0. 반대로 `[반품 정책 v2.1 §3]`을 정확히 적었어도 그 절이 기한만 말한다면 배송비 판단의 근거 일치는 실패.

**기록표**: 조건, 반복, 모델·버전, 날짜, 파라미터, 원출력 로그 파일명, 토큰, 지연, 실패 유형, 필수 결정 회수율(세 판단 지점 중 몇 개). 토큰·지연은 품질 점수가 아니고, API가 주지 않는 값은 추정하지 않고 "제공되지 않음"으로 적는다.

## 6. 실습 따라하기 (ollama + langchain-ollama)

설계만으로는 실제 모델이 어떻게 답하는지 알 수 없어서 직접 8개 출력을 얻고 채점했다. 로컬 모델(ollama)은 비용 없이 반복 실험하기 좋다.

1. **준비**: `pip install langchain-ollama`
2. **서버 확인**: 터미널에서 `ollama run qwen3.5:2b` → 브라우저에서 `http://localhost:11434` 접속 시 "Ollama is running"
3. **코드 저장**: 수업에서 고친 수정본을 `day29_context_test.py`로 저장
4. **구문 검사**: `python -c "import ast, pathlib; ast.parse(pathlib.Path('day29_context_test.py').read_text(encoding='utf-8'))"` → 문법 OK
5. **실행·분석**: `python day29_context_test.py` → `context-lab-logs` 폴더 결과를 6항목으로 채점

### 노드 코드의 결함 찾기

- **첫 번째 코드**: `POLICY_SELECTED`에 이미 출처 표식(`[반품 정책 v2.1 §1]`, `§3`)이 들어 있어서, selected와 selected_cited가 표식 유무로 갈리지 않았다. 실험이 바꾸려던 변수가 분리되지 않은 것. → 수정본은 `POLICY_SELECTED`에서 표식을 걷어 내고 `POLICY_SELECTED_CITED`를 따로 정의해 연결.
- **두 번째 코드 (JSON 출력)**: 정책 상수를 "위 예시에서 정의한 상수"라며 정의하지 않아 새 폴더에서 돌리면 이름 오류. → `POLICY_FULL`·`POLICY_SELECTED`·`POLICY_SELECTED_CITED`를 파일 안에 직접 정의하고 selected_cited를 연결.

막힌 곳도 배운 것 — 터미널과 ollama 입력창 구분, 경로의 공백, `.py.txt` 확장자, 패키지 미설치는 실험이 아니라 **환경**에서 막히기 쉬운 지점이다.

### 실습 결과 — 직접 돌려 채점한 기록

**설정**: qwen3.5:2b(ollama 로컬), temperature=0, reasoning=False, 4조건 × 2회, 실행일 2026-10-08. 토큰·지연은 로그에 없어 "제공되지 않음".

**기준 정답**: 12일은 14일 이내라 반품 신청 가능. 택을 제거했으므로 착용 여부 확인 뒤 처리, 단순 변심 배송비는 고객 부담. none은 "근거가 없어 알 수 없다"가 기권 정답.

**실습 1 — 줄글 답** (각 조건 run1·run2 점수 동일)

| 조건 | 정답성 | 근거 일치 | 무근거 | 충돌 처리 | 기권 | 회수율 |
|---|---|---|---|---|---|---|
| none | 1 | 0 | 0 | 0 | 1 | 1/3 |
| full | 1 | 1 | 1 | 1 | 1 | 2/3 |
| selected | 1 | 1 | 0 | 0 | 1 | 2/3 |
| selected_cited | 0 | 0 | 0 | 0 | 0 | 1/3 |

- **none**: 정책이 없는데 "일반적으로 7일, 14일", "배송비는 원칙적으로 구매자 부담"처럼 일반론을 단정. "택"을 "택배"로 읽음. 정답성 1은 우연히 방향이 맞아서이고 근거 일치는 0.
- **full**: §2(배송비 고객 부담)와 §3(착용 여부 확인)을 번호까지 인용. §1(14일)은 인용하지 않았고 택/택배 오독이 남음.
- **selected**: §2가 없는데 배송비를 "명확히 알 수 없다"고 답함 — 가장 잘 된 기권. 반면 "택배 제거는 정상적인 절차"라며 §3 예외를 무력화.
- **selected_cited**: 표식은 정확히 인용했지만 "12일은 14일 기간을 초과"라는 비교 오류로 반품 불가를 단정. 표식이 정확해도 판단이 조항과 모순되면 근거 일치는 실패.

**실습 2 — JSON 답**

| 조건 | 정답성 | 근거 일치 | 무근거 | 충돌 처리 | 기권 | 회수율 |
|---|---|---|---|---|---|---|
| none | 0 | 0 | 1 | 0 | 1 | 0/3 |
| full | 0 | 0 | 0 | 0 | 0 | 1/3 |
| selected | 0 | 0 | 0 | 0 | 0 | 1/3 |
| selected_cited | 0 | 0 | 0 | 0 | 0 | 0/3 |

- **형식 점검**: 원문 그대로 `json.loads`는 8개 모두 실패(` ```json ` 코드펜스 때문). 펜스를 벗기면 8개 모두 통과. full 2개는 JSON 뒤에 설명 글이 붙음. 질문에 필드명을 안 적어서 모델이 `가능여부·근거·설명` 같은 키를 임의로 정함.
- **none**: 텍스트로는 "판단할 수 없다"고 기권했지만 같은 JSON에 `가능여부: false` → 말과 값이 모순. 코드가 값만 읽으면 "반품 불가"로 처리된다.
- **full**: §1을 인용하면서 "12일 뒤라 기간 위반" — 비교 방향이 뒤집힘. 배송비(§2)는 맞음, §3 언급 없음.
- **selected**: §3을 "착용 여부 확인 뒤 처리"가 아니라 "조건 미충족이라 불가능"으로 바꿔 읽음. 배송비 필드 없음.
- **selected_cited**: §1 표식만 반영, §3 빠짐. 실습 1과 같은 12일/14일 오류 재현. 0/3.

### 관찰

1. **"넣었다"와 "읽었다"는 다르다** — 12일/14일 비교 오류가 여러 조건에서 반복됐다. 맥락의 범위·표식을 바꿔도 사라지지 않았다. 2B 소형 모델의 한계로 보이지만 다른 모델로는 확인하지 않았다.
2. **같은 조건 2회 출력이 글자까지 같았다** — temperature=0에서는 2회 반복이 새 정보를 주지 못했다.
3. **표식은 사실성을 보장하지 않는다** — selected_cited가 selected보다 오히려 나빴다. 다만 표본이 작아 "표식이 해롭다"고 일반화하면 안 된다.
4. **비교 주의** — 실습 2는 출력 형식만 바뀐 게 아니라 질문이 짧아지고 지시문과 `[정책]`·`[질문]` 구획이 붙었다. 요인이 여럿이라 "JSON 요구 때문에 나빠졌다"고 단정할 수 없다.

> 오늘의 한 줄: 맥락을 줬다고 읽힌 것이 아니었다. 같은 정책을 줘도 모델은 12일을 14일 초과로 읽었고, JSON을 요구해도 순수 JSON이 나오지 않았다. 남은 일은 조건 하나만 바꿔 다시 돌리고, 채점표로 확인하는 것.

## 7. CLAUDE.md · AGENTS.md

코딩 에이전트가 세션을 시작할 때 자동으로 읽는 지시 파일. README가 사람에게 프로젝트를 소개한다면, 이 파일은 에이전트에게 프로젝트를 안내한다. 단, **적었다고 행동이 강제되지는 않는다** — 모델이 컨텍스트로 읽는 지시일 뿐이다.

예: CLAUDE.md에 "`data/raw/` 폴더의 CSV는 절대 덮어쓰지 마세요"라고 적어도, "결측치 정리해서 저장해줘"라고 하면 `df.to_csv("data/raw/sales.csv")`로 원본을 덮어쓸 수 있다. 규칙을 잊어서가 아니라 지금 요청과 맞물려 판단이 흔들린 것이고, 대화가 길어 규칙이 흐려졌을 수도 있다.

CLAUDE.md에는 **누가 썼는지 알고, 거의 매일 필요하고, 서로 안 부딪히고, 비밀이 아니고, 틀려도 되돌릴 수 있는** 규칙만 넣는다. 나머지는 문서나 사람 확인으로 보낸다.

### 넣으면 안 되는 내용

**외부에서 복사한 명령** — push가 `! [rejected] main -> main (fetch first)`로 거절되자 블로그에서 본 대로 "git push가 거절되면 `git push --force`로 올릴 것"을 적어 뒀다면? 이 오류의 진짜 뜻은 "팀원이 먼저 올린 코드가 있으니 먼저 받아오라"인데, 모델은 거절될 때마다 `--force`로 덮어써서 팀원이 밤새 만든 결제 기능이 사라진다.

**출처를 잃은 요약** — 회의에서 "이탈 고객 = 60일 미구매, 단 신규 가입 고객 제외"로 정했는데 기억나는 대로 "30일간 미구매"라고 적었다면, 모델은 매 세션 30일 기준으로 분석하고 발표 수치가 전부 틀어진다. 누가 언제 정했는지 없으니 확인할 원문도 없다. 4절에서 배운 압축의 위험이다.

### 맥락 파일의 세 가지 효과와 한 가지 비용

| 구분 | 내용 |
|---|---|
| 효과 ① 상태 보완 | 새 세션은 빈 창에서 시작하므로 매번 다시 설명하던 사실을 파일로 전달 |
| 효과 ② 일관성 | 검토된 같은 문장이 매 세션 같은 위치에 들어감 |
| 효과 ③ 캐시 이점 | 앞부분이 매번 같아서 재사용 비용이 줄어듦 |
| 비용: 상시 토큰 | 파일이 길수록 정책·코드·대화가 쓸 공간을 밀어냄 |

- 좋은 문장: "커밋 전 npm test를 실행하고 결과를 보고합니다"처럼 짧고 확인 가능한 문장
- 나쁜 문장: "품질을 높입니다"처럼 판정할 수 없는 문장

### 진짜 읽었는지 확인하는 법 (관찰 실험)

추측하지 말고 파일마다 도장을 찍어 직접 확인한다.

```
my-shop/
├── CLAUDE.md        # @AGENTS.md 와 [ROOT] 표식 규칙
├── AGENTS.md        # 팀 공통 규칙
└── payments/
    ├── CLAUDE.md    # [PAYMENTS] 표식 규칙
    └── charge.py
```

```
# 루트 CLAUDE.md
- 답변 맨 앞에 [ROOT]를 붙일 것

# payments/CLAUDE.md
- 답변 맨 앞에 [PAYMENTS]를 붙일 것
```

### 3층 구조: 규칙과 사실 분리

| 층 | 비유 | 들어가는 것 |
|---|---|---|
| 루트 AGENTS.md | 전 직원 행동 수칙 | "정책 문서만 근거로 답한다", "모르면 질문한다", "존댓말" |
| 하위 AGENTS.md | 부서별 수칙 | 결제팀: "카드번호 로그 금지" / 반품팀: "택 제거 상품 임의 거절 금지" |
| docs/ | 서류함 속 원본 서류 | 반품 정책 v3: "수령 후 7일" |

수칙에는 "어떻게 행동할지"만, 서류함에는 "무엇이 사실인지"를 둔다. 반품 기한이 바뀌면 서류함의 정책 문서 한 줄만 고치면 된다. 수칙에 "반품 기한 14일"이라고 직접 적었다면 정책이 바뀔 때마다 수칙도 찾아 고쳐야 하고, 하나라도 빠뜨리면 옛날 기준으로 안내한다.

## 8. 캐싱과 비용의 경제학

**캐시**: 한 번 읽은 내용을 저장해 뒀다가 다음에 더 싸고 빠르게 다시 읽는 기능. 매일 같은 교과서 1~3장을 읽고 숙제를 푸는 학생이, 다음 날엔 숙제만 새로 보면 되는 것과 같다.

- **cache write** (처음 저장): 일반 입력보다 약간 비쌈
- **cache read** (다시 읽기): 일반 입력의 약 10%
- 그래서 여러 번 반복할 때만 이득이다. 한 번 쓰고 끝나면 저장 비용만 더 든다.

⚠️ 캐시는 "싸게 읽기"지 "더 잘 읽기"가 아니다. 모델이 더 똑똑해지지 않는다.

### 예: 지금 쓰고 있는 Claude Code

메시지를 보낼 때마다 시스템 지침, 도구 설명, CLAUDE.md, 지금까지의 대화를 매번 앞부분에 똑같이 보내고, 새로 추가되는 건 방금 보낸 질문 하나뿐이다. 그래서 앞부분은 캐시에서 싸게 읽고 새 질문만 새로 처리한다.

**질문 내용만으로는 캐시를 깰 수 없다** — 질문은 맨 뒤에 붙기만 하니까 "캐시 깨져라"라고 입력해도 앞부분은 그대로다. 캐시를 깨려면 **앞부분을 바꾸는 행동**이 필요하다.

| 행동 | 캐시가 깨지는 이유 |
|---|---|
| 모델 변경 (예: Haiku로) | 캐시는 모델별로 따로 저장된다 |
| 커넥터 연결·해제 | 도구 목록이 앞부분에 들어가 있어서 도구가 바뀌면 앞부분이 바뀐다 |
| 한참 아무것도 안 하기 | 유효 시간(TTL)이 지나면 저장본이 사라진다 |
| /clear 또는 대화 압축 | 대화 기록 자체가 바뀌거나 요약본으로 대체된다 |

### 10시간 뒤에 질문해도 답이 똑같이 잘 나오는 이유

캐시가 사라져도 대화 기록이 사라지는 건 아니기 때문이다.

| | 대화 기록 | 캐시 |
|---|---|---|
| 무엇인가 | 주고받은 메시지 원문 | 그 원문을 미리 처리해 둔 결과물 |
| 어디에 있나 | 앱이 저장 | 모델 회사 서버에 임시 보관 |
| 10시간 뒤 | ✅ 그대로 있음 | ❌ 사라짐 |

10시간 뒤 질문하면 → 앱이 대화 기록 전체를 다시 보내고(원래도 매번 전체를 보낸다) → 서버에 캐시가 없으니 처음부터 다시 읽고 → 결과를 새로 캐시에 저장한 뒤 → 답한다. 내용은 캐시가 있을 때와 똑같다.

## 9. 마무리: 여섯 단계 판정 사슬

| 단계 | 쉬운 질문 | 관련 절 |
|---|---|---|
| ① 출처 | 이 자료, 어디서 왔어? | 1·2절 |
| ② 선택 | 꼭 필요한 것만 골랐어? 빼면서 놓친 예외는? | 3·4절, 실습 |
| ③ 배치·상태 | 어디에 놨어? 이전 대화의 틀린 가정이 남아 있지 않아? | 3·4절 |
| ④ 신뢰 | 외부 글을 지시로 착각하지 않았어? | 6·7절 |
| ⑤ 권한 | 읽을 수 있다고 행동까지 해도 돼? (환불, 메일 발송 등) | 6절 |
| ⑥ 비용 | 앞 다섯 개를 통과한 것만 캐시로 아끼기 | 8절 |

> 스스로 던질 질문: "지금 이 답에 필요한 최소한의, 믿을 수 있는, 확인 가능한 근거만 들어 있나?"

- 사슬이라서 하나가 끊기면 다 무너진다. 출처를 모르면 믿을 수 없고, 믿을 수 없으면 캐시할 이유도 없다.
- 오늘 실습 기록은 다음 평가 재료다. "좋았다, 나빴다"가 아니라 어떤 조건에서, 어떤 근거로, 어떻게 틀렸는지를 적어 둬야 다시 시험할 수 있다.
- 읽는 것과 행동하는 것은 별개다. 맥락을 잘 설계해도, 모델이 무엇을 실행해도 되는지는 따로 정하고 사람이 승인해야 한다.
