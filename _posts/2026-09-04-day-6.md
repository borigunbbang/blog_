## Database

데이터를 효율적으로 저장, 관리, 검색할 수 있도록 구조화된 데이터의 집합 (원하는 것을 빠르게 찾아주는 곳)

- **SQL**: 데이터베이스에 저장된 데이터를 관리하고 조작하기 위한 프로그래밍 언어. 기본적으로 관계형 데이터베이스 정보를 다루는 언어
- (참고) 어셈블리어: 기계어를 조금 더 편하게 보기 위한 언어

### 역사

SQL 등장 → NoSQL(Not only SQL)의 등장으로 용도에 따라 SQL과 NoSQL을 나눠 쓰게 됨

| | SQL | NoSQL |
|---|---|---|
| 생김새 | 엑셀 같은 표 | 유연한 문서/덩어리 (모양 자유) |
| 규칙(스키마) | 엄격하게 정해 둠 | 느슨하거나 없음 |
| 강한 곳 | 관계가 분명한 데이터, 정확성(돈·주문) | 대규모·빠르게 변하는 데이터 |
| 대신 포기 | 유연함이 덜함 | 표끼리 잇기(조인)·엄격한 거래 일부 |

**SQL 비유**: 카페 사장님이 "오늘 케이크 주문만 보고 싶어요"라고 했는데, 주문이 수백 건이라 눈으로 찾기 어렵습니다. 필요한 조건의 데이터만 골라 달라고 DB에 요청하는 말이 필요합니다. 그 요청을 쓰는 언어가 SQL입니다. → 데이터베이스에게 말을 거는 언어

## 관계형 데이터베이스 (RDBMS)

- 데이터를 표 형태로 나누어 저장하고 표와 표 사이의 관계를 이어 관리
- 행과 열로 구성된 표 구조 사용
- SQL 언어로 다룸, 압도적인 메인 표준

**표의 구조**

- ① 일대다(1:N) - 한쪽이 여러 개를 가진다
- ② 다대다(N:M) - 양쪽 다 여러 개를 가진다

## 작동 원리

### 색인 (인덱스)

- 자주 찾는 정보를 저장해놓은 것 (데이터를 복사해놓는 것이 아니라, 정보가 어디에 위치해 있는지 정도)
- 내용이 바뀌면 색인을 업데이트해야 함

### 마이그레이션

이미 데이터가 들어있는 DB의 구조를 안전하게 바꾸는 작업

> 딱 하나만 기억하세요 — 칸을 삭제하는 변경은 그 안의 데이터가 영구히 사라질 수 있습니다. 그래서 구조를 바꾸기 전엔 반드시 백업. 비전공자는 "느려지면 색인, 구조를 바꾸면 마이그레이션이라는 게 있다"는 감만 있으면 충분합니다.

## 트랜잭션 (묶음 처리)

데이터베이스에서 하나의 작업 단위로 묶인 여러 단계의 명령 처리 과정. 예) 출금·입금을 따로 하는 게 아니라 입출금으로 한 번에 묶어서 처리함

돈·재고·예약처럼 '동시에 두 번' 눌릴 수 있는 곳은 AI에게 "동시에 두 명이 마지막 하나를 요청하는 상황도 테스트하고 안전하게 처리해 줘"라고 요청

> 💡 **ACID 품질 안전 기준**
> - A(원자성) — 반쪽 실행은 없다. 전부 아니면 전부 취소.
> - C(일관성) — 규칙에 어긋난 상태로는 안 끝난다.
> - I(고립성) — 동시에 여러 명이 만져도 서로 꼬이지 않는다.
> - D(지속성) — 한번 됐다고 하면, 정전이 나도 남아 있다.

## 설계 원칙 — 정규화

같은 정보를 반복적으로 적지 않기 위해 데이터베이스를 효율적으로 관리해야 함. **정규화**: 중복을 없애기 위해 표를 나누고, ID(번호)로 이어주는 작업.

이것도 AI가 알아서 해줍니다. 데이터의 '모양'을 그릴 때 "이 정보, 여기저기 똑같이 적히고 있진 않나?" 한 번만 의심해 보면 됩니다. (출처: Wikipedia, "Database normalization")

## 회원가입과 로그인

**원칙**

- 비밀번호 원문 저장 금지 (솔트 포함)
- 이메일 유일하게 가입 (같은 이메일 중복 없애기)
- 최소 수집 (개인정보 보호법) — 가입에 필요한 것 외엔 받지 않기

> 주의 — 인증은 직접 만들지 마세요. 로그인·비밀번호 재설정·소셜 로그인은 함정이 많아, 자작하면 사고로 이어지기 십상입니다. 검증된 Auth 서비스/라이브러리(예: Supabase Auth)를 쓰는 게 안전합니다.
>
> AI에게: "인증은 처음부터 만들지 말고 검증된 Auth를 붙여줘. 비밀번호는 해시로, 이메일은 유일하게."

### 쿠키

어떤 중요한 정보를 담을 수 있는 상자 같은 존재

**로그인 지속 방법**

- **세션 (서버가 기억함)**: 로그인 정보를 세션에 묶어서 저장한 후 쿠키라는 태그를 달아 내 컴퓨터에 보냄
- **토큰 (서버가 기억하지 않음)**: 세션 방식과 달리 인증서를 발급
  - 최초에 웹에 접속해 서버에 로그인 → 서버에서 인증서를 발급해서 내 컴퓨터로 넘김(서버에선 아무런 저장이 없음) → 나중에 웹에 접속할 때 인증서와 함께 서버에 보냄 → 서버에서 인증서가 진짜인지 가짜인지만 판단 → 로그인

**나에게만 저장되는 것들**

- 사용자 설정 (다크모드, 언어설정 등)
- 서비스 상태 (팝업 금지)
- 마케팅 상태

## 캐시

자주 쓰는 데이터를 메모리에 잠깐 두어 빠르게 꺼내 쓰는 것. 자주 쓰거나 빠르게 처리해야 하는 데이터를 빠른 저장소(메모리 등)에 임시로 올려두어 성능을 높이는 모든 기술.

- 그 명부를 찾을 때 느린 서류함(DB) 대신 '계산대 옆 빠른 메모장(Redis)'에 적어두고 순식간에 확인하는 방식
- 세션 저장소에서도 등장

**색인 vs 캐시**

- 색인(Index): "어디 있는지 위치(주소)를 빠르게 알려줄게!" (여전히 창고로 가긴 가야 함)
- 캐시(Cache): "자주 찾으니까 아예 물건(복사본)을 계산대 바로 옆에 꺼내둘게!" (창고에 갈 필요 자체가 없음)

## 보안

**SQL 주입**: 사용자의 입력값을 코드처럼 실행되게 만들어 공격하는 방식 → **파라미터화 쿼리**로 방어 가능. 데이터베이스 명령을 실행할 때 '명령어(SQL 문장)'와 '사용자 입력값(데이터)'을 완전히 분리해서 전달하는 안전한 작성 방식.

> AI에게: "DB에 넣는 값은 문자열로 이어 붙이지 말고, 파라미터화 쿼리(prepared statement)로 처리해줘. 사용자 입력을 그대로 신뢰하지 마."

**개인정보의 최소 원칙** — 덜 모으고, 조심해서 다룬다

1. 필요한 것만 모은다 (최소 수집) — "이메일 하나면 되는데 전화번호·생년월일까지 받고 있진 않나?"를 늘 자문 (출처: 국가법령정보센터, 개인정보 보호법 제3·16조)
2. 비밀번호는 절대 그대로 저장하지 않는다 — 해시로 바꿔 저장하고, 빠른 해시가 아니라 bcrypt·Argon2 같은 비밀번호 전용을 사용 (출처: OWASP Password Storage Cheat Sheet)
3. 민감정보(주민번호·카드번호)는 직접 다루지 않는 게 최선 — 결제는 결제대행사(PG)에, 본인확인은 인증 서비스에 맡기고 내 DB엔 저장하지 않음
4. 모을 때 밝힌 목적에만 쓴다 (목적 제한) — 다른 데 쓰거나 남에게 넘기려면 별도 동의 필요

## 백업 — 3-2-1 규칙

- **3벌** — 원본 1 + 사본 2, 최소 세 벌을 둔다
- **2종** — 서로 다른 매체 두 곳에 (예: 노트북 디스크 + 클라우드). 한 종류가 통째로 망가져도 다른 쪽은 살아남게
- **1벌은 다른 장소에(off-site)** — 화재·도난·랜섬웨어처럼 한 장소를 통째로 잃는 사고에 대비

## 오늘의 실습 — Todo 앱

**시작 프롬프트**

> 내 서비스에 데이터를 저장하려고 해. 나는 비전공자고 무료로 시작하고 싶어. 내가 저장할 것은 [예: 상품, 주문]인데, 어떤 표(테이블)와 항목(열)이 필요할지 스키마를 제안해줘. 무료 SQL 데이터베이스(예: Supabase, PostgreSQL) 기준으로 이 스키마를 만드는 방법을 알려줘. 접속 정보(비밀번호·키)는 코드에 넣지 말고 환경변수로 빼줘. DB에 값을 넣을 때는 파라미터화 쿼리로 처리하고, 비밀번호는 해시로 저장해줘.

**PRD (요구사항)**

- 무엇: 내 컴퓨터에서 도는 Todo(할 일) 앱
- 기본 기능(CRUD): 할 일 추가 / 목록 보기 / 완료 표시 / 삭제
- 저장: 데이터는 내 컴퓨터의 무료 DB에 저장 (껐다 켜도 남기)
- 추가로 넣고 싶은 기능: 오늘 할 일만 보기 / 날짜별 검색 / 단어 검색 / 반복 일정 추가 / 연속 일정 추가
- 규칙: 무료 도구만. 비밀값은 `.env`로. (로그인을 넣는다면 직접 만들지 말고 검증된 라이브러리로)

**DB 구조 설계 프롬프트**

> 위 PRD로 만들 Todo 앱의 DB 구조(어떤 표·열·관계)를 먼저 설계해서 구조도로 그려 보여줘. 내 커스텀 기능(마감일·태그 등)도 반영해서. 로컬 무료 DB(예: SQLite)를 쓸 거야.

**→ 나온 ERD(엔티티 관계도) 구조 설명**

4개의 표가 반복되는 할 일과 카테고리(태그) 기능을 갖추도록 서로 연결되어 있음:

1. **RECURRENCE_RULES(반복 규칙) → TODOS(할 일)** — 1:N 관계
   - `RECURRENCE_RULES`의 `id`가 `TODOS`의 `recurrence_id`로 연결됨
   - 예) `RECURRENCE_RULES`에 1번 규칙 "매주 월요일마다 반복"을 만들어두고, `TODOS`의 "청소하기", "분리수거하기"에는 `recurrence_id`에 숫자 1만 적어둠
   - 이유: 규칙 텍스트를 할 일마다 매번 적지 않고 규칙 번호만 참조(FK)해서 데이터 중복을 없앰
2. **TODOS(할 일) ↔ TODO_TAGS(중간 연결표) ↔ TAGS(태그)** — N:M 관계
   - `TODOS`와 `TAGS` 사이에 `TODO_TAGS`라는 중간 연결 표가 있음
   - 예) `TODOS` 1번="DB 공부하기", `TAGS` 10번="#공부", 20번="#중요" → `TODO_TAGS`에 (todo_id:1, tag_id:10), (todo_id:1, tag_id:20)으로 연결
   - 이유: 할 일 1개에 태그가 여러 개 붙을 수 있고, 태그 1개에도 할 일이 여러 개 속할 수 있어서 중간에 짝짓기용 표를 하나 더 둠

전체 흐름: `[반복 규칙 표(1번: 매주 반복)] → [할 일 표(100번: DB 공부하기 / 규칙 1번)] → [중간 짝짓기 표(할 일 100번 - 태그 10번)] → [태그 표(10번: #공부)]`
→ "매주 반복되는 100번 DB 공부하기 할 일에는 #공부 태그가 붙어있구나!"를 번호 연결선을 따라 정확히 읽어낼 수 있음

**작업 지시서**

> 이 PRD와 방금 합의한 DB 구조로 Todo 앱을 만들어 줘. 데이터는 로컬 SQLite 파일 하나(`todo.db`)에 저장하고, 브라우저에서 localhost로 열리게 해줘. `.env`·`todo.db`는 `.gitignore`에 넣어. 먼저 전체 계획을 보여주고, 각 단계 끝에 뭘 확인하면 되는지 알려줘.
