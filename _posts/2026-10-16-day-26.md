> State에 현재 정보를 담고, Node가 작업을 수행하며, Edge가 다음 이동 경로를 정한다. 이 요소들을 연결해 그래프를 만들고 `compile()`한 뒤 `invoke()` 또는 `stream()`으로 실행한다.

패턴을 고를 때 스스로 던질 질문은 다섯 가지다.

- 작업 순서가 정해져 있는가?
- 입력에 따라 다른 길로 보내야 하는가?
- 독립된 작업을 동시에 할 수 있는가?
- 하위 작업의 개수가 입력마다 달라지는가?
- 결과를 평가하고 다시 고쳐야 하는가?

## 1. LangGraph의 기본 구조

LangGraph는 LLM을 사용하는 애플리케이션의 여러 작업 단계를 그래프로 연결하고, 상태와 실행 흐름을 관리하는 프레임워크다. 여러 단계를 잇거나, 조건에 따라 다른 단계로 이동하거나, 결과가 충분할 때까지 반복하는 흐름을 만들 수 있다.

| 요소 | 쉬운 뜻 | 예시 |
|---|---|---|
| State | 노드들이 읽고 업데이트하는 공용 데이터(작업 정보와 결과) | 사용자 질문, 초안, 평가 결과 |
| Node | 실제로 작업을 수행하는 함수 | 질문 분류, 요약·글 작성, 평가, 도구 실행 |
| Edge | 작업이 끝난 뒤 어디로 갈지 정하는 연결 | 합격이면 종료, 불합격이면 수정 |
| START / END | 그래프의 시작점과 종료점 | START → 요약 → END |
| `compile()` | 정의한 그래프를 실행 가능한 형태로 준비 | `graph.compile()` |
| `invoke()` | 실행이 끝날 때까지 기다려 최종 결과 받기 | `app.invoke(input)` |
| `stream()` | 실행 중 단계별 업데이트 확인 | 디버깅, 루프 확인 |

```
State 준비 → Node 실행 → Edge에 따라 다음 Node로 이동 → END 도달 → 결과 확인
```

일반 엣지는 고정된 경로이고, **조건부 Edge**는 현재 상태나 분류 결과에 따라 다음 경로를 선택한다. 예를 들어 평가 결과가 '합격'이면 END로, '불합격'이면 수정 Node로 보낼 수 있다. 순환 Edge를 만들면 반복이 가능하지만 종료 조건도 함께 설계해야 한다.

> 💡 State는 공유 노트, Node는 일을 하는 담당자, Edge는 다음 담당자에게 넘기는 규칙이다.

## 2. Tool을 에이전트에 연결하기

Tool은 AI가 사용할 수 있는 개별 기능이다(계산하기, 파일 읽기, 날씨 조회 등). 개발자가 직접 함수를 만들어 Tool로 등록할 수도 있다. LLM은 어떤 도구를 어떤 인자로 쓸지 **선택**할 뿐이고, 실제 **실행**은 연결된 실행 단계가 맡는다. 호출하겠다는 판단과 실행은 별개다.

| 구성 요소 | 역할 |
|---|---|
| Tool 함수 | 실제로 수행할 기능 정의 (예: 숫자 두 개를 더하는 함수) |
| `llm.bind_tools(TOOLS)` | LLM이 사용할 수 있는 도구 목록을 알려 줌 |
| `ToolNode` | LLM이 요청한 도구 호출을 실제로 실행 |
| `tools_condition` | 도구 호출이 있으면 ToolNode로, 없으면 답변 경로로 보냄 |

```
사용자 요청 → LLM 판단(Tool 선택) → ToolNode가 실행 → 결과를 LLM에 전달 → 최종 답변
```

실행 결과로 바로 끝나지 않고, LLM이 결과를 다시 읽고 추가 도구를 호출할 수도 있다. 필요한 작업이 끝나면 최종 답변을 만든다.

### Tool과 MCP 구분

- **Tool**: AI가 호출할 수 있는 개별 기능 또는 작업 단위.
- **MCP(Model Context Protocol)**: AI 애플리케이션과 외부 도구·데이터를 연결하는 표준화된 통신 규약. MCP 서버는 여러 기능을 외부에 제공할 수 있고, 직접 만들 수도 남이 만든 서버를 연결할 수도 있다.

> 💡 Tool은 '계산기' 같은 도구 하나이고, MCP는 여러 도구를 AI 앱에 연결할 때 쓰는 공통 연결 규격이다. 둘은 경쟁 관계가 아니며, MCP를 통해 Tool을 제공할 수도 있다.

## 3. 워크플로와 자율 에이전트

| 구분 | 워크플로 | 자율 에이전트 |
|---|---|---|
| 다음 단계 결정 | 개발자가 경로와 규칙을 미리 설계 | LLM이 관찰·도구 결과를 보고 다음 행동 선택 |
| 적합한 일 | 예측 가능한 반복 업무 | 필요한 단계와 도구 사용 횟수를 미리 열거하기 어려운 일 |
| 장점 | 비용·테스트·디버깅을 통제하기 쉬움 | 예상하지 못한 상황에 맞춰 행동 가능 |
| 주의점 | 예외 상황을 미리 설계해야 함 | 비용·실행 경로가 불확실하고 원인 추적이 어려울 수 있음 |

> 핵심 판단 기준: 필요한 단계의 조합을 개발자가 미리 열거할 수 있는가?

- 사내 가이드 문서로 퀴즈 만들기, '문서 읽기 → 요약 → 요약 검사' → 경로가 명확하므로 워크플로가 적합하다.
- GitHub 저장소에서 버그 찾고 고치기 → 파일과 테스트 횟수가 상황마다 달라 자율 에이전트가 유용할 수 있다.

**권장 원칙**: 처음부터 복잡한 자율형 에이전트를 만들기보다 명확한 워크플로로 시작하고, 경로를 미리 정하기 어렵다는 근거가 생길 때 자율성을 늘린다. 그편이 관리와 디버깅에 유리하다.

## 4. 다섯 가지 패턴 한눈에 보기

| 패턴 | 언제 쓰나? | 핵심 구조 | 주의점 |
|---|---|---|---|
| 프롬프트 체이닝 | 단계와 순서가 정해져 있을 때 | 순차 Node + 중간 검사 | 단계가 늘면 지연시간 증가 |
| 라우팅 | 입력 종류에 따라 다른 경로가 필요할 때 | 분류 Node + 조건부 Edge | 분류 오류가 전체 결과를 망칠 수 있음 |
| 병렬화 | 독립된 여러 작업을 동시에 처리할 때 | Fan-out + Reducer/Fan-in | 호출 비용 증가, 결과 병합 필요 |
| 오케스트레이터-워커 | 하위 작업 수와 내용이 입력마다 달라질 때 | 계획자 + Send + 결과 통합 | 계획 품질에 좌우, 비용 예측 어려움 |
| 평가자-최적화자 | 평가 기준을 만족할 때까지 개선할 때 | 생성 ↔ 평가 반복 루프 | 비용 증가, 종료 조건 필수 |

```
순서가 정해져 있다             → 프롬프트 체이닝 (Prompt Chaining)
입력에 따라 경로를 고른다      → 라우팅 (Routing)
정해진 여러 일을 동시에 한다   → 병렬화 (Parallelization)
AI가 하위 작업을 계획한다      → 오케스트레이터-워커 (Orchestrator-Worker)
결과를 평가하고 고친다         → 평가자-최적화자 (Evaluator-Optimizer)
```

## 5. 패턴 ① 프롬프트 체이닝

하나의 큰 작업을 여러 단계로 나누고, 앞 단계의 결과를 다음 단계의 입력으로 넘기는 방식이다.

```
강의 노트 정리: 원문 정리 → 핵심 용어 추출 → 설명 초안 작성 → 최종 점검
글쓰기:        자료 요약 → 요약문 바탕으로 초안 작성 → 문장 다듬기
```

### Gate(게이트)

중간 결과가 다음 단계로 넘어가도 되는지 확인하는 검사다. 필수 항목 존재처럼 코드로 판정할 수 있는 조건은 LLM 대신 코드로 검사하면 빠르고 일관적이다. 통과하면 다음 단계로, 실패하면 수정 Node로 보내거나 재작업하게 한다.

- **장점**: 단계별 책임이 명확하고 중간 점검이 가능하다.
- **주의점**: 순차 실행이라 단계가 많으면 전체 지연시간이 늘어난다.

> 순서가 중요하고 각 단계의 결과를 다음 단계가 사용한다면 체이닝을 고려한다.

## 6. 패턴 ② 라우팅

입력을 먼저 분류한 다음, 분류 결과에 맞는 전문 경로로 보내는 방식이다.

```
사용자 입력 → 분류 → 개념 설명 / 코드 예제 / 실습 과제 경로
문의        → 분류 → 결제 문제면 결제 담당 / 기술 문제면 기술 담당 노드
```

### 구조화된 출력

분류 결과를 '개념설명', '코드예제', '실습과제'처럼 허용된 선택지로 제한하면 예상하지 못한 라벨로 인한 연결 오류를 줄일 수 있다. 하지만 형식을 제한할 뿐, LLM이 의미를 잘못 분류할 가능성까지 없애 주지는 않는다.

- **장점**: 각 경로에 맞는 프롬프트나 모델을 쓸 수 있다.
- **주의점**: 첫 분류가 틀리면 이후 단계가 모두 잘못된 경로로 간다.
- 입력이 여러 종류에 동시에 해당하면 우선순위 규칙, 다중 라벨, 병렬 실행을 고려한다.

> 라우팅은 모든 작업을 다 하는 것이 아니라 입력에 따라 적합한 경로를 선택하는 것이다.

## 7. 패턴 ③ 병렬화

서로 의존하지 않는 여러 작업을 동시에 실행하고 결과를 나중에 합치는 방식이다.

- 노트 품질 평가: 같은 노트를 정확성·가독성·예시 평가에 동시에 보내고 세 결과를 종합한다.
- 제품 조사: 같은 제품을 가격·품질·사용성 관점에서 각각 조사하고 합친다.

| 용어 | 뜻 |
|---|---|
| Fan-out | 하나의 흐름을 여러 하위 작업으로 나눠 보낸다 |
| Fan-in | 여러 하위 작업의 결과를 다시 모은다 |
| Reducer | 같은 State 키에 여러 결과가 들어올 때 어떻게 합칠지 정하는 규칙 |

### Reducer가 필요한 이유

같은 State 키에 여러 노드가 동시에 값을 쓰는데 병합 규칙이 없으면 `InvalidUpdateError`가 발생할 수 있다. 리스트 결과를 누적하려면 아래 같은 reducer를 쓸 수 있다. 실제 적용은 자료형과 목적에 맞춰야 한다.

```python
Annotated[list, operator.add]
```

- **장점**: 작업이 독립적이면 전체 대기 시간을 줄인다.
- **주의점**: API·토큰 비용이 늘 수 있고, 결과를 안전하게 합치는 방법이 필요하다.

> 개발자가 병렬로 할 작업을 미리 알고 있다면 병렬화를 고려한다.

## 8. 패턴 ④ 오케스트레이터-워커

중앙의 오케스트레이터(총괄)가 입력을 보고 하위 작업의 종류와 개수를 계획하고, 워커(작업자)들에게 일을 나눠 준 뒤 결과를 합치는 방식이다.

```
회의록 액션 아이템 처리: 3개 추출 → 워커 3개에 분배 / 10개 추출 → 10개에 분배
```

| 역할/용어 | 쉬운 뜻 |
|---|---|
| Orchestrator | 무엇을 몇 개의 하위 작업으로 나눌지 계획한다 |
| Worker | 할당받은 개별 작업을 수행한다 |
| Send | 이미 정의된 워커 Node에 작업별 입력/상태를 보내 여러 번 실행하게 한다. 새 Node 함수를 즉석에서 만드는 것은 아니다 |
| Map / Reduce | Map은 작업을 분배하고, Reduce는 결과를 모아 최종 결과를 만든다 |

### 병렬화와의 핵심 차이

| 병렬화 | 오케스트레이터-워커 |
|---|---|
| 개발자가 하위 작업 목록을 미리 정한다 | AI(총괄)가 입력에 따라 하위 작업을 동적으로 계획한다 |
| 예: 가격·품질·사용성 세 관점 조사 → 더 단순 | 예: 매번 개수가 다른 회의록 실행 항목마다 담당자 배정 초안 |

### 주의할 점

- 계획이 잘못되면 워커 결과의 품질이 떨어진다.
- 작업 범위가 겹치면 중복 결과가 생긴다.
- 작업 수에 따라 비용이 커지므로 작업 범위, 최대 작업(워커) 수, 근거 확인, 최종 통합 검사를 설계한다.

## 9. 패턴 ⑤ 평가자-최적화자

초안을 만든 뒤 평가자가 부족한 점을 지적하고, 최적화자가 피드백을 반영해 다시 작성하는 반복 패턴이다.

```
초안 작성 → 평가 → 합격이면 종료
                 → 불합격이면 수정 → 다시 평가
```

### 좋은 평가 기준 만들기

- '좋게 써라'보다 확인 가능한 규칙을 구체적으로 적는다.
- 형식·필수 용어·예시뿐 아니라 원래 주제와 핵심 의미가 유지되는지도 검사한다. 기준이 모호하면 결과가 엉뚱한 방향으로 수정된다.
- 코드나 테스트로 확인 가능한 조건은 코드 게이트(결정적 검사)로 처리해 비용과 오류 가능성을 줄인다.

### 무한 루프와 종료 조건

State에 반복 횟수를 기록하고, 최대 라운드에 도달하면 현재 결과를 보존한 채 사람에게 넘기거나 제한된 결과로 종료하는 경로를 설계한다.

> 💡 `recursion_limit`은 안전망이다. 그래프가 지나치게 많이 반복될 때 실행을 멈추는 장치이며, 한도에 도달하면 `GraphRecursionError`가 발생할 수 있다. 정상적인 종료 로직을 대신하게 해서는 안 된다.

### 비용

한 라운드에 생성 1회와 평가 1회가 필요하다면 3라운드에서 최대 6회의 LLM 호출이 발생할 수 있다. 실제 호출 수는 구현 방식에 따라 달라지므로 반복 횟수와 비용을 함께 고려한다.

## 10. State 업데이트 · 종료 조건 · 실행 방식

### State, Reducer, Send, recursion_limit 정리

| 개념 | 설명 |
|---|---|
| State | 노드들이 공유하는 데이터 구조. 각 노드는 State를 읽고 자신이 계산한 변경 사항을 반환한다 |
| Reducer | 같은 State 항목에 여러 노드가 기록할 때 덮어쓸지, 누적할지 정하는 병합 규칙. 메시지 누적처럼 리스트를 쌓을 때 필요 |
| Send | 실행 중 작업별 입력을 만들어 특정 노드에 전달. Orchestrator-Worker에서 하위 작업 분배에 자주 쓴다 |
| recursion_limit | 과도한 단계·반복을 막는 보조 안전장치. 초과 시 `GraphRecursionError` |

### invoke()와 stream()

| 방법 | 무엇을 확인하나? | 주요 용도 |
|---|---|---|
| `invoke()` | 실행이 끝난 뒤 최종 상태/결과 | 서비스에서 최종 결과가 필요할 때 |
| `stream()` | 노드별 업데이트 등 실행 중 정보 | 노드 순서, 반복 횟수, 중간 상태 디버깅 |

`stream()`으로는 어떤 노드가 실행됐는지, 반복이 왜 길어지는지, 어느 분기에서 예상과 다른 경로로 갔는지 볼 수 있다. Evaluator-Optimizer처럼 반복이 있는 그래프에서는 매 단계 결과를 stream으로 확인하면 문제를 찾기 쉽다.

### 실패를 다루는 원칙

1. 정상 종료 조건('조건을 만족하면 END로 이동')을 그래프 안에 명시한다.
2. 최대 반복 횟수에 도달했을 때 결과 보존·사람에게 넘기기 경로를 정한다.
3. `recursion_limit`은 설계 오류나 예상치 못한 루프에 대비한 추가 안전망으로 둔다.

> invoke()는 최종 결과 확인에, stream()은 실행 과정을 살펴보는 데 유용하다. 반복과 병렬 작업에서는 종료 조건과 State 병합 규칙을 특히 주의해야 한다.

## 11. LangSmith와 관찰 가능성

LangSmith는 LangChain·LangGraph 애플리케이션의 실행을 관찰하고 디버깅하는 도구다. 설정에 따라 각 실행의 입력·출력, 모델 호출, 프롬프트, 토큰 사용량, 실행 시간, 분기 선택 등을 추적할 수 있다.

| 개념 | 뜻 | 왜 유용한가? |
|---|---|---|
| Trace | 그래프 한 번의 실행 기록 | 문제가 발생한 실행을 다시 살펴볼 수 있다 |
| Node별 입출력 | 각 단계에서 전달한 값과 반환한 값 | 잘못된 결과가 어느 단계에서 생겼는지 찾기 쉽다 |
| 프롬프트 기록 | 모델에 실제로 전달된 지시와 입력 | 프롬프트 조립 문제를 확인할 수 있다 |
| 시간·토큰 정보 | 단계별 실행 시간과 사용량 | 느린 단계와 비용이 큰 단계를 찾을 수 있다 |

에이전트가 왜 엉뚱한 답을 냈는지 조사할 때는 최종 답변만 보는 것보다 각 단계의 입출력과 도구 호출 기록을 확인하는 편이 유용하다.

### 사용 시 주의

- 추적이 켜져 있으면 입출력과 프롬프트에 민감한 정보가 포함될 수 있다.
- 개인정보, API 키, 비밀 정보가 기록·노출되지 않도록 데이터 처리와 접근 권한을 확인한다.
- 키가 없어도 추적 없이 다른 학습은 이어갈 수 있다.

### 워크플로를 넘어 에이전트로 갈 시점

- 고정된 단계만으로는 다양한 예외 상황을 처리할 수 없다는 사례가 반복된다.
- 다음에 어떤 도구를 몇 번 써야 하는지 입력 전에 결정하기 어렵다.
- 새로운 정보나 환경 피드백에 따라 다음 행동을 바꿔야 한다.

이런 증거가 있어도 무제한 자율 실행을 바로 택하지 않는다. 도구 권한, 실행 한도, 검증 기준, 중단 조건, 사람에게 넘기는 조건을 함께 설계한다.

## 12. 자주 헷갈리는 점

- LangGraph는 State, Node, Edge로 그래프를 구성하는 프레임워크이지, 이 세 단어의 순서 자체가 정의는 아니다.
- Node는 실제 작업 함수이고, Edge는 다음 경로를 정하는 연결이다.
- Tool은 기능이고, MCP는 외부 기능을 연결하는 표준 방식이다.
- 병렬화와 오케스트레이터-워커는 모두 여러 작업을 동시에 돌릴 수 있지만, 작업 목록을 미리 정하는지, 총괄이 동적으로 계획하는지가 차이다.
- `recursion_limit`은 반복의 정상 종료 조건이 아니다.
- 구조화된 출력은 형식을 제한해도 분류 내용의 정확성까지 보장하지 않는다.

## 13. 복습

| 질문 | 정답 키워드 |
|---|---|
| LangGraph의 핵심 구성 요소는? | State · Node · Edge |
| Tool과 MCP의 차이는? | 개별 기능 vs 외부 도구 연결 표준 |
| 순서가 정해진 단계별 작업은? | 프롬프트 체이닝 |
| 입력 유형별로 다른 길을 선택하는 것은? | 라우팅 |
| 정해진 독립 작업을 동시에 실행하는 것은? | 병렬화 |
| 입력에 따라 작업 개수와 종류를 AI가 계획하는 것은? | 오케스트레이터-워커 |
| 결과를 평가하고 고쳐 쓰는 것은? | 평가자-최적화자 |
| 실행 중 단계별 업데이트를 확인하는 것은? | `stream()` |
| 그래프 실행 기록을 관찰하는 도구는? | LangSmith |
| 무한 반복을 막으려면? | 명시적 종료 조건 + 최대 라운드 + recursion_limit 안전망 |

### 복습 퀴즈

1. **회의록에서 액션 아이템이 몇 개 나올지 알 수 없고, 각 항목을 개별 처리해야 한다면?** → 오케스트레이터-워커. 하위 작업 수가 실행 전에 정해져 있지 않기 때문이다.
2. **평가자가 계속 불합격 판정을 내릴 수 있다면 무엇을 설계해야 하나?** → 명시적 종료 조건, 최대 반복 횟수, 한도 도달 시 결과 보존 또는 사람에게 넘기는 경로.
3. **병렬 작업들이 같은 State 키에 결과를 기록한다면 무엇을 점검해야 하나?** → 값이 충돌하지 않는지, Reducer 등 병합 규칙이 적절한지.
4. **recursion_limit 외에 별도 종료 조건이 필요한 이유는?** → recursion_limit은 안전장치라 정상 종료 로직을 대신하지 못한다.
5. **단계별 디버깅에는 invoke()와 stream() 중 무엇이 유용한가?** → `stream()`.

> 좋은 에이전트 설계는 LLM을 많이 연결하는 것이 아니라, 문제에 맞는 흐름을 선택하고 도구·상태·검증·관측·종료 조건을 함께 설계하는 것이다.
