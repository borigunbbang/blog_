## 1. 이번 노드의 핵심 질문

> **"AI가 처음부터 끝까지 다 만들게 할까?"가 아니라 "어디까지 AI가 하고, 어디서 사람이 고르고 확인하게 할까?"**

이번 메인 퀘스트는 **'AI 최신소식'을 입력하면 자료를 조사하고, 사용자의 선택을 받아 카드뉴스를 완성하는 웹 앱**을 만드는 것이다.

- AI가 후보 소식을 찾아도 **어떤 소식을 다룰지는 사용자가 고른다.**
- 카드별 기획을 **사용자가 확인한 뒤** 제작을 시작한다.
- 완성 후에도 **원하는 카드만** 고칠 수 있다.

| 용어 | 뜻 |
| --- | --- |
| **워크플로** | 입력부터 결과물까지 이어지는 작업의 흐름 |
| **에이전틱 워크플로** | AI가 조사 결과와 사용자 답변을 보고 **다음 행동을 스스로 판단**하고, 검색·파일 생성 같은 **도구를 쓰며** 이어 가는 흐름 |
| **PRD** | Product Requirements Document, 제품 요구사항 문서. 앱이 무엇을 해야 하는지 정리한 설계 문서 |
| **바이브코딩** | 원하는 동작을 자연어로 요청하고, 실행 결과를 보며 고쳐 가는 방식 |

> 이번 앱에서는 **사람의 선택과 검토도 워크플로의 일부**다. 사람이 끼어드는 지점을 빼먹은 게 아니라 **일부러 설계한다.**

노드 구성은 이렇다.

```text
1. 만들 앱의 흐름 이해
   ↓
2. 카드뉴스 형식·독자 정하기 (가설)
   ↓
3. PRD를 코딩 에이전트에 주고 바이브코딩
   ↓
4. 실행 엔진 연결 + 웹에서 질문·답변 이어 가기
   ↓
5. 'AI 최신소식'으로 실제 제작·검수
   ↓
6. [과제] 내 작업으로 워크플로 확장
```

## 2. 만들 앱: 일곱 단계 제작 흐름

```text
① 주제 입력 + 넓은 조사      'AI 최신소식' → 최근 7일 자료 조사 (기준 시각·기간 표시, 부족하면 기간 넓힐지 질문)
   ↓
② 정보 선택 [사람]           후보의 제목·요약·날짜·원문을 보고 1~3개 선택 → 이후 제작 범위가 됨
   ↓
③ 심층 조사 + 편집 판단      원문·근거 확인, 독자·형식·표지 문구 제안 (크게 갈릴 때만 질문, 받은 답은 다시 안 물음)
   ↓
④ 카드별 기획 검토 [사람]     5~8장의 역할·제목·핵심 문장·출처·그림 계획 = 스토리보드 → 수정 요청 또는 승인
   ↓
⑤ 이미지와 글자 제작          승인된 기획대로 이미지 생성, 글자는 이미지와 따로 배치
   ↓
⑥ 검수와 부분 수정 [사람]     사실·출처·가독성 확인, 지정한 카드만 고치고 나머지는 유지
   ↓
⑦ 승인과 내려받기 [사람]      카드별 PNG, 전체 ZIP, 출처·이미지 사용 기록
```

- **스토리보드**: 카드별 설계도 (역할·제목·핵심 문장·출처·그림 계획)
- 진행 중에는 지금 무슨 작업 중인지 **화면에서 보여야** 한다.
- **사용자 답변을 기다리는 상태는 오류가 아니라 정상 과정**이다.
- 검색·이미지 생성이 실패하면 **원인과 재시도 방법**을 보여 줘야 한다.
- **새로고침 뒤에도** 선택과 진행 상태가 이어져야 한다.

#### 한 줄로 기억하기

> **AI는 조사·제안·제작, 사람은 선택·승인·검수**

---

### 2-1. 시작 전 준비

| 준비 | 확인할 것 |
| --- | --- |
| 코딩 에이전트 + 터미널 + 브라우저 | 작업 폴더를 열 수 있는지 |
| 조사 엔진 1개 + Antigravity 이미지 작업자 | 계정·인증·도구 권한 |
| 짧은 시험 | 실제 검색·원문 읽기가 되는지, 이미지 한 장이 생성되고 열리는지 |
| 이용 한도·과금 | 처음엔 **소식 1개·카드 5장**으로 전체 흐름만 연결 |

> ⚠️ **코딩 에이전트에 로그인했다고 앱의 실행 엔진까지 인증된 것은 아니다.**
> ⚠️ **설치돼 있다는 것만으로 연결 성공을 판단하지 않는다.** 실제로 한 번 돌려 본다.

한도나 인증 문제로 막히면 **모의 자료로 화면 작업을 계속**하되, 실제 조사·생성은 **미완료라고 기록**한다.

#### 완료 기준 세 가지

1. 실제 자료로 카드뉴스 한 편 **내려받기**
2. 질문 대기와 실패 후 **재개** 확인
3. 내 작업에 맞게 바꾼 흐름 **실행**

→ 단계마다 화면과 결과 파일을 남겨 제출에 쓴다.

## 3. 헷갈리기 쉬운 쌍 ①: 코딩 에이전트 vs 실행 엔진(제작 에이전트)

이 노드에는 **AI가 두 군데** 나온다. 섞으면 전체가 헷갈린다.

| 구분 | 코딩 에이전트 | 실행 엔진 (앱 안의 제작 에이전트) |
| --- | --- | --- |
| 하는 일 | **앱의 코드를 만들고 고친다** | 완성된 앱 안에서 **조사·원고 작성**을 한다 |
| 예 | Claude Code 등 | Claude Agent SDK / Claude CLI / OpenCode CLI 중 하나 |
| 누구에게 질문하나 | **앱을 만드는 나**에게 ("구현 언어는 뭘로 할까요?") | **카드뉴스를 만드는 사용자**에게 ("어떤 독자에게 전달할까요?") |
| 질문·답이 남는 곳 | DECISIONS.md 등 설계 문서 | 앱의 저장소 (프로젝트 상태) |

```text
나 ──(PRD 전달·요청)──→ 코딩 에이전트 ──(코드 작성)──→ 웹 앱
                                                    │
                       사용자 ←──(질문·선택지)── 웹 앱 안의 실행 엔진 ──→ 조사·원고
```

#### 한 줄로 기억하기

> **코딩 에이전트 = 앱을 만드는 AI, 실행 엔진 = 앱 안에서 일하는 AI**

- 이미지 작업자 **Antigravity(agy)** 는 실행 엔진 선택과 **별도로** 이미지 생성만 맡는다.

## 4. 카드뉴스 형식과 독자 정하기

같은 AI 소식도 **누구에게 무엇을 전달하느냐**에 따라 카드 순서가 달라진다.

- AI를 처음 접하는 친구 → **용어와 변화의 의미**가 먼저
- 이미 도구를 쓰는 동료 → **바뀐 기능과 활용 조건**이 먼저

그래서 예쁜 템플릿보다 먼저 **독자, 핵심 메시지, 읽은 뒤 할 행동**을 정한다.

| 용어 | 뜻 |
| --- | --- |
| **캐러셀** | 여러 장을 넘겨 보는 게시 형식 |
| **후킹** | 첫 장에서 독자의 관심을 끄는 문구나 장치 |

### 4-1. 참고 형식 다섯 가지

강의는 각 자료를 **확인**(원문에서 확인한 구조)과 **적용**(이번 카드뉴스용 설계 제안)으로 나눠 보여 준다.

| 형식 (참고 자료) | 구조 | 어울리는 독자·적용 |
| --- | --- | --- |
| **단계 안내형** (질병관리청 손씻기) | 표지 → 효과 → 필요한 상황 → 단계 그림 → 마무리 | 처음 따라 하는 독자. "새 AI 기능, 이렇게 시작하세요" + 카드마다 동작 하나 |
| **체크리스트형** (강원대 연구노트) | 의미·요건·절차 → 번호 붙은 점검 항목 + 예/아니오 | 사용 전 조건을 확인하려는 독자. "사용 전 확인할 3가지" |
| **사진 중심 연속형** (Canva) | 사진 중심, 연속 배치 | 결과 이미지를 보고 싶은 독자. 이미지로 관심 → 조건 짧게 |
| **이야기형** (Canva) | 상황 → 불편 → 변화 → 활용 → 한계 | 변화의 의미가 궁금한 독자. 장마다 중심 문장 하나 |
| **목록형 / 비교형** (Adobe Express 가이드) | 튜토리얼·목록·통계·비교 등 | 여러 소식을 훑는 독자는 목록형, 차이를 판단하려는 독자는 비교형 |

- Canva 두 형식은 **분류와 제목만 확인**했고 카드 내부 배치까지는 확인하지 않았다고 강의가 밝힌다.

#### 할 일

> 위 자료에서 **두 형식**을 골라 **"어떤 독자에게 왜 맞는지"를 한 줄씩** 적는다.

- 이건 **조사 전 가설**이다. → 3절에서 PRD에 반영 → 5절에서 실제 소식을 고른 뒤 5.3에서 다시 판단한다.
- 앱은 두 형식을 **비교해 하나를 추천**하도록 만든다. 예: 목록형은 여러 발표를 짧게, 단계 안내형은 한 기능을 써 보게 하는 데 적합.

### 4-2. 편집 규칙

- 제목의 **'최신'은 조사 기준일과 원문 게시일로 뒷받침**한다.
- **확인하지 않은 기능이나 효과를 후킹 문장에 넣지 않는다.**
- 독자가 이미 명확하면 **같은 질문을 반복하지 않는다.** 결과가 크게 갈릴 때만 짧은 선택지를 보여 준다.

제작 에이전트에 편집 방향을 덧붙이는 요청 예시:

```text
AI를 처음 접하는 대학생에게 최신 AI 소식을 소개하고 싶어. 공식 발표의 날짜를 확인하고,
목록형과 이야기형을 비교해 추천한 뒤 카드 순서를 제안해 줘.
```

### 4-3. 이미지는 '저작권 없음'으로 뭉뚱그리지 않는다

| 구분 | 기록할 것 |
| --- | --- |
| CC0·퍼블릭 도메인 | 출처와 사용 조건 |
| 라이선스 허용 스톡 (예: Pexels) | 출처와 사용 조건 — **CC0와 조건이 다르다** |
| 생성 이미지 | 사용한 도구와 그 도구의 조건 |

> ⚠️ **생성한 그림을 실제 발표 현장이나 제품 화면을 찍은 것처럼 표시하지 않는다.**

## 5. PRD로 시작하는 바이브코딩

완성된 앱 코드를 따라 치는 대신 **PRD를 코딩 에이전트에게 주고, 내 선택에 맞는 앱을 만든다.**

### 5-1. 설계 키트

**카드뉴스 워크플로 설계 키트**를 내려받아 압축을 푼다. 완성 앱이 아니라 **앱을 만들기 위한 설계 문서 묶음**이다.

| 파일 | 역할 |
| --- | --- |
| **PRD.md** | 무엇을 만들지 (요구사항) — 코딩 에이전트가 **먼저 읽게** 한다 |
| **DECISIONS.md** | 내가 내린 결정과 이유 기록 |
| **API_SPEC.md** | 화면과 서버 사이의 약속 (입력·출력·오류) |
| **ACCEPTANCE.md** | 다 됐는지 확인하는 조건 목록 |

PRD가 요구하는 흐름:

```text
주제 입력 → 넓은 조사 → 사용자 정보 선택 → 심층 조사·편집 판단
   → 스토리보드 승인 → 이미지·글자 제작 → 검수·부분 수정·내려받기
```

> 핵심 차이: 사용자가 고를 때는 **작업이 기다리고**, 답을 받은 뒤 **앞선 제작을 이어 간다.** 문구를 한 번 생성하고 끝나는 화면과 다르다.

### 5-2. 첫 요청은 짧게, 결정은 기록하게

```text
PRD.md를 끝까지 읽고 이 카드뉴스 앱을 함께 만들어 줘. 구현 전에 아직 정하지 않은 것을
2~3개씩 물어봐 줘. 추천과 이유를 보여주고, 내가 답한 결정은 DECISIONS.md에 기록해 줘.
```

첫 질문에서 정할 것:

| 결정 | 선택지 |
| --- | --- |
| 구현 언어 | Python, TypeScript, Rust 등 다루고 싶은 것 |
| 실행 엔진 | Claude Agent SDK / Claude CLI / OpenCode CLI 중 **하나** |
| 기타 | 검색 수단이 내 계정에서 되는지, 카드 비율, 결과 보관 위치 |

- **SDK**: 코드에 연결하는 개발 도구 묶음
- **CLI**: 터미널 명령으로 실행하는 도구
- 잘 모르겠으면: `내 환경에서 사용할 수 있는 언어와 엔진을 비교해 줘. 연결에 추가 작업이 필요하면 함께 설명해 줘.`

그다음 4절의 형식 가설 두 개와 편집 규칙을 PRD에 반영한다. 키트 PRD에 이미 있는 규칙은 두고 **빠진 것만** 추가하게 한다.

```text
내가 고른 카드뉴스 형식은 [형식 1]과 [형식 2]야. 이 형식 가설과 다음 편집 규칙을 PRD.md와 비교해서
빠진 것만 추가해 줘: 두 형식을 비교해 하나를 추천하기, 제목의 '최신'은 조사 기준일과 원문 게시일로
뒷받침하기, 확인하지 않은 기능이나 효과는 후킹 문장에 넣지 않기. 추가한 내용은 DECISIONS.md에도 기록해 줘.
```

### 5-3. 작은 흐름부터: 모의 데이터 → 실제 엔진 → 제작

**API**는 웹 화면이 서버에 요청하는 약속이다. 예: 주제를 보내면 프로젝트가 생기고 → 조사를 시작하면 **작업 ID**가 돌아오고 → 화면은 그 ID의 진행 상태를 보여 준다. PRD의 API 표는 초안이므로, 선택한 언어에 맞게 API_SPEC.md에 정리시킨다.

```text
① 화면 연결 (모의 데이터)
   "주제 입력부터 후보 선택과 질문 답변까지 먼저 만들어 줘. API_SPEC.md에 연결 방식을 기록하고,
    모의 데이터는 화면에 표시해 줘."
   → http://127.0.0.1:8765 에서 입력·선택·답변, 새로고침 후 유지 확인
   ⚠️ 이때 보이는 후보는 예시일 뿐, 실제 최신 조사 결과가 아니다
   ↓
② 실제 엔진 연결
   "선택한 엔진으로 실제 조사와 답변 후 이어가기를 연결해 줘. 검색 실패를 표시하고,
    실제 연결을 확인한 결과를 기록해 줘."
   → 기간·출처가 보이는지, 선택과 답이 원고에 반영되는지
   ↓
③ 이미지: Antigravity로 실제 한 장 생성·파일 확인 → 전체 카드로 확대
   ↓
④ 글자 배치 · 부분 수정 · 내려받기 → ACCEPTANCE.md 조건 하나씩 확인
```

- 기본 포트는 PRD가 정한 **8765**. 이미 쓰고 있으면 안내받은 다른 포트.

> **한 번에 완성을 요청하지 않는다.** 작은 흐름을 실행하고, **실제로 본 문제**를 다음 요청에 담는다.
> 예: "버튼을 눌렀는데 계속 대기 중이다", "새로고침하면 선택한 기사가 사라진다"

### 5-4. 참고 구현 (비교용)

직접 만든 앱과 비교할 수 있게 **Python 참고 구현**이 제공된다. Claude CLI로 조사·원고, Antigravity CLI로 카드별 삽화를 만드는 버전이다. **SDK·OpenCode 연결까지 구현된 건 아니다.**

필요한 것: Python 3.11 이상, uv, 로그인된 claude·agy CLI. `pyproject.toml`과 `run.py`가 있는 폴더에서:

```bash
uv sync --locked
uv run playwright install chromium
uv run run.py
```

- `uv sync --locked`: 잠금 파일에 적힌 버전 그대로 라이브러리 설치
- `playwright install chromium`: 카드를 이미지로 렌더링할 브라우저 설치
- 포트가 겹치면 `uv run run.py --port 8766` → 브라우저도 8766으로

진행 순서: 후보 선택 → 독자 질문 → 기획 승인 → 이미지 제작 → 검수 → 최종 승인

참고 구현의 특징:

- 카드별 제목·본문에 맞는 삽화 생성, 최종 카드 **1080×1350**
- 글자와 그림을 **분리**해 배치
- **작업 진행 내역**을 펼치면 실제 검색어·원문 읽기·결과 수신이 보인다. 경과 시간과 서버 응답도 같이 본다. **초안 표시를 검증 완료로 해석하지 않는다.**
- 첫 카드 후킹은 **별도 호출**로 설계: 독자 관심 → 후보 문구 두 개 → 근거·과장 위험 비교 → 하나 선정 → 첫 카드 작성. 뒤 카드는 첫 카드가 만든 궁금증을 **실제 자료로 해소**한다.

> 참고 구현을 그대로 제출하지 않는다. **내 선택에 따라 무엇이 달라졌고 실제로 어떻게 동작했는지** 설명한다.

#### 참고 구현 ≠ PRD 통과

| 항목 | v5.1.5 참고 구현 | PRD 목표 → 내 앱에서 확인·보완 |
| --- | --- | --- |
| 독자 질문 | **항상** 묻는다 | 이미 알려 준 독자는 다시 묻지 않기 |
| 텍스트 수정 | 제목·본문을 바꾸면 삽화도 **다시 생성될 수 있다** | 텍스트만 고칠 땐 그림 유지 |
| 카드 수 | 5장 고정 (표지 → 변화 → 활용 → 조건·한계 → 요약·출처) | 보통 5~8장, 소식 2~3개·다른 형식이면 수와 순서가 달라지는지 |

> **참고 구현을 실행했다는 사실만으로 PRD 전체를 통과 처리하지 않는다.**

### 5-5. 다음 단계로 넘어가기 전 증거

| 확인 단계 | 남길 증거 |
| --- | --- |
| 화면 연결 | 모의 자료 표시, 후보 선택, 새로고침 후 유지되는 질문 화면 |
| 실제 엔진 연결 | 검색·원문 읽기 기록, 선택한 후보, 답변이 반영된 원고 |

## 6. 실행 엔진과 웹 질문 연결

### 6-1. 엔진은 셋 중 하나만

웹 앱은 주제·자료를 받고 진행 상황과 질문을 보여 주고, **실행 엔진은 조사와 원고 작성**을 맡는다. 세 가지를 다 설치할 필요는 없다.

```text
실행 엔진을 [Claude Agent SDK]로 연결해 줘. 필요한 질문은 웹에서 답하고 같은 제작을 이어 가게 해 줘.
엔진 호출 부분은 분리해 줘.
```

- **엔진 연결** = 웹 **서버**가 SDK를 쓰거나 설치된 CLI를 실행하는 것. **브라우저가 직접 명령을 실행하는 구조가 아니다.**
- **세션**: 앞선 대화와 작업 맥락을 이어 가는 단위. **세션 ID**: 그걸 구분하는 값.

| 엔진 | 앱에서 연결하는 방식 | 앞선 대화를 잇는 방식 |
| --- | --- | --- |
| **Claude Agent SDK** | 코드에서 `query()` 호출, 메시지 수신 | 저장한 세션 ID를 `options.resume`에 |
| **Claude CLI** | 서버에서 `claude -p` 실행, JSON 결과 읽기 | `--resume <세션 ID>` |
| **OpenCode CLI** | 서버에서 `opencode run --format json` 실행, JSON 이벤트 읽기 | `--session <세션 ID>` |

- SDK는 앱 안에서 질문 처리를 연결하기 좋고, CLI는 익숙한 도구를 서버에서 부르는 방법이다.
- ⚠️ CLI의 `--continue`는 **가장 최근 세션**을 고른다. 프로젝트가 여러 개면 **앱이 저장한 세션 ID를 명시**해서 이어 간다.

### 6-2. 앱이 저장해야 하는 것

엔진의 답변만 저장하면 안 된다. **어느 제작인지, 무엇을 기다리는지, 사용자가 뭘 골랐는지**까지 남겨야 한다.

| 저장 항목 | 예 |
| --- | --- |
| 식별 | 카드뉴스 프로젝트 ID, 제작 실행 ID |
| 엔진 | 선택한 엔진, 세션 ID |
| 진행 | 현재 단계 |
| 질문 | 질문, 선택지, 사용자 답변 |
| 결과 | 지금까지 만든 원고 |

### 6-3. 질문 → 대기 → 답변 → 재개

```text
running (제작 중)
   ↓  엔진이 질문이 필요하다고 판단
waiting_for_user  ── 질문·선택지를 저장하고 웹 화면에 표시
   │                  답변 전에는 다음 단계로 넘어가지 않음
   ↓  사용자가 답변 제출
running  ── 같은 제작 실행으로 복귀, 저장된 답변 + 엔진 세션을 연결해 이어 감
```

```text
질문이 생기면 제작 상태를 waiting_for_user으로 저장하고, 질문과 선택지를 웹 화면에 보여줘.
답변 전에는 다음 제작 단계로 넘어가지 마. 답변을 제출하면 같은 제작 실행의 상태를 다시 running으로 바꾸고,
저장된 답변과 엔진 세션을 연결해서 이어 가게 해 줘. 새로고침해도 질문이 남고,
제출 버튼을 두 번 눌러도 중복 실행되지 않는지 확인해 줘.
```

### 6-4. 헷갈리기 쉬운 쌍 ②: SDK의 질문 방식 vs CLI의 질문 방식

| 구분 | Claude SDK | CLI (Claude CLI / OpenCode) |
| --- | --- | --- |
| 질문을 받는 법 | **AskUserQuestion** — TypeScript `canUseTool`, Python `can_use_tool` **콜백**에서 질문을 받아 웹으로 보냄 | 앱이 정한 **need_input 규약** — 엔진이 "질문이 필요하다"는 구조화된 결과를 반환하면 앱이 검증해 질문 화면으로 바꿈 |
| 답을 돌려주는 법 | 사용자의 답을 **콜백에 반환** → 기다리던 SDK 실행이 그대로 이어짐 | 프로세스는 끝날 수 있음 → 답이 오면 **저장한 세션 ID로 다음 CLI 호출**을 새로 시작 |
| 주의 | 콜백 응답은 SDK가 요구하는 구조로 — 언어별 공식 예제 확인 | need_input은 **공식 CLI 필드가 아니라 이번 앱에서 정하는 약속** |

- **콜백**: 특정 상황이 오면 프로그램이 대신 불러 주는 함수
- 어느 쪽이든 **웹 화면과 답변 저장은 앱이 직접 만들어야 한다.**

need_input 예시 (앱이 정하는 형식):

```json
{
  "status": "need_input",
  "question_id": "audience-001",
  "version": 1,
  "question": "누구를 위한 카드뉴스인가요?",
  "options": ["AI 입문자", "업무에 AI를 쓰는 사람"],
  "multi_select": false
}
```

- `question_id`: 질문이 새로 생길 때마다 구분하는 값
- `version`: 어떤 질문 **버전**에 대한 답인지 확인 → 이미 답한 질문이나 **지난 버전의 답으로 새 작업을 시작하지 않게** 한다
- 프로젝트 ID와 함께 저장한다.

> CLI 방식에서 "이어 간다"는 건 **같은 제작과 대화를 이어 가는 것**이지, **같은 운영체제 프로세스가 계속 살아 있다는 뜻이 아니다.**

```text
CLI 출력 형식을 검사하고, 질문과 답변을 해당 세션의 다음 입력으로 전달해 줘. 잘못된 출력을 완료로 처리하지 마.
```

#### 엔진마다 출력 모양이 다르다

| 엔진 | 세션 필드 | 텍스트 위치 |
| --- | --- | --- |
| Claude CLI (JSON 결과) | `session_id` | 결과 JSON |
| OpenCode (줄마다 JSON 이벤트) | `sessionID` | 텍스트 이벤트의 `part.text` |

→ 두 엔진의 원시 출력을 **같은 JSON이라고 가정하면 안 된다.** 앱이 필요한 내용을 꺼낸 뒤 자기가 정한 need_input / 완료 결과로 해석한다.

필요할 때 확인하는 명령 (앱 서버가 쓰는 형태, 매번 직접 칠 필요는 없다):

```bash
# Claude CLI: 시작과 후속 답변
claude -p "카드뉴스 제작 요청" --output-format json
claude -p "질문: 독자 / 사용자 답변: AI 입문자" --resume "$SESSION_ID" --output-format json


# OpenCode CLI: 시작과 후속 답변
opencode run --format json "카드뉴스 제작 요청"
opencode run --session "$SESSION_ID" --format json "질문: 독자 / 사용자 답변: AI 입문자"
```

- 두 번째 줄마다 **질문과 답을 함께** 넣고, `$SESSION_ID`에 앱이 받은 실제 값을 넣어 같은 대화를 잇는다.

### 6-5. 헷갈리기 쉬운 쌍 ③: 새로고침 vs 서버 재시작

| 상황 | 무슨 일이 생기나 | 앱이 할 일 |
| --- | --- | --- |
| **브라우저 새로고침** | 화면만 다시 그림. **서버 작업은 살아 있을 수 있다** | 저장된 질문·상태를 다시 보여 주기 |
| **서버 재시작** | 메모리에서 기다리던 **SDK 콜백이 사라진다** | 저장한 질문·답변·단계로 **중단 상태를 보여 주고**, 재개 또는 재시도 |

> **세션 ID만 저장한다고 화면 상태와 작업이 자동 복구되지는 않는다.**

- 엔진을 **바꾸면** 기존 세션 ID는 새 엔진에서 못 쓴다. → 앱에 저장한 **자료·선택·현재 원고**를 새 엔진의 시작 맥락으로 넘긴다.
- 다른 프로젝트를 하나 더 열어 **질문과 세션이 섞이지 않는지**도 확인한다.

### 6-6. 질문과 재개를 직접 검증하기

인증을 일부러 망가뜨리지 말고 **테스트용 모의 오류**로 실패 경로를 확인해도 된다.

| 재현할 상황 | 기대 결과 |
| --- | --- |
| 독자 질문이 나온 뒤 새로고침 | 같은 질문·선택지가 남고, 답변 전 제작이 시작되지 않음 |
| 같은 답변을 두 번 제출 | 한 번만 시작, 중복 답변은 재실행 안 함 |
| 이전 질문 화면에서 뒤늦게 답변 | 지난 질문임을 알리고 현재 작업을 덮어쓰지 않음 |
| 생성 실패 후 재시도 | 원인 표시, 확정한 기획과 성공한 카드는 보존 |
| 서버 재시작 후 프로젝트 열기 | 저장한 질문·결과 복원, 중단 작업은 재개·재시도 가능 |

관찰 기록 다섯 칸:

```text
입력·조작 | 기대 결과 | 실제 결과 | 수정 후 결과 | 확인 방식(모의 오류 / 실제 엔진)
```

## 7. 'AI 최신소식'으로 제작과 검수

시작점은 정해 둔 모델이나 오래된 발표가 아니라 **실행 시점 기준 최근 7일의 소식**이다.

> 아래 요청문들은 **각 단계를 손으로 진행하라는 뜻이 아니다.** 앱이 자동으로 해야 할 동작이고, 빠졌거나 고칠 때 코딩 에이전트에게 줄 참고다.

### 7-1. 단계별로 무엇을 확인하나

| 단계 | 앱이 할 일 | 내가 확인할 것 |
| --- | --- | --- |
| **① 후보 고르기** | 검색 기준 시각·시간대·시작일·종료일 표시, 서로 다른 후보 **7~12개** (같은 발표 기사는 묶음, 모델·제품·연구·개발 도구로 다양하게). 각 후보에 제목·원문 링크·게시일·실제 발표일·선택 가치·불확실성. 부족하면 실제로 찾은 수를 알리고 **30일로 넓힐지** 질문 | 공식 원문 하나를 **직접 열어** 제목·날짜 대조. 요약만 있고 원문을 못 읽었으면 '검증 완료' 아님 |
| **② 심층 검증** | 후보 1~3개의 공식 발표 + 제품 문서·변경 기록 확인. 무엇이 달라졌나 / 누가 언제부터 쓰나 / 지역·계정·요금제 조건 분리 | '모두 사용 가능', '무료', '성능 향상' 같은 큰 문장을 근거와 대조 |
| **③ 독자·후킹** | **검증을 마친 뒤** 표지 문장 2~3개 제안, 방향이 크게 갈릴 때만 객관식 질문 (+자유 입력) | 표지만 읽었을 때 원문보다 기능·혜택을 **크게** 받아들이게 되지 않는지 |
| **④ 스토리보드·이미지** | 5~8장 스토리보드 (장마다 핵심 문장 하나·본문·이미지 역할·근거 링크), 확정 후 agy로 이미지 생성 | 요청을 보낸 것 ≠ 파일이 생긴 것. **파일이 실제로 열리는지** 확인 |
| **⑤ 글자·미리보기** | 제목·본문·출처를 **별도 텍스트 레이어**로, 모바일 미리보기 | 글자 크기·줄바꿈·여백·명암 대비 |
| **⑥ 최종 검수** | 내보낸 파일 기준으로 점검 | 모든 카드를 열어 순서·수량·잘림·한글·출처·조사 기준일 |

- 확인하지 못한 날짜는 **미확인**으로 표시한다. 최근에 쓴 소개 글이라고 **오래된 발표를 새 소식으로 분류하지 않는다.**
- 후보 목록에는 미확인으로 남겨도 되지만, **카드의 핵심 사실로 쓰기 전에는** 근거로 확인하거나 그 주장을 뺀다.

### 7-2. 헷갈리기 쉬운 쌍 ④: 확인한 사실 vs 발표 주체의 주장 vs 미확인

```text
선택한 후보의 변화와 사용 조건을 원문으로 검증해 줘. 확인한 사실, 발표 주체의 주장,
아직 확인하지 못한 내용을 나누고 근거 링크를 붙여 줘.
```

| 구분 | 예 | 카드에 쓰는 법 |
| --- | --- | --- |
| **확인한 사실** | 공식 문서에 적힌 출시일·대상 계정 | 근거 링크와 함께 사실로 |
| **발표 주체의 주장** | "기존보다 2배 빠르다" (회사 발표) | "OO사는 ~라고 밝혔다"처럼 **주장으로** |
| **미확인** | 날짜·조건이 자료마다 다름 | 원고 확정 **전에 불일치를 보여 주고**, 확인 전엔 쓰지 않음 |

- 공개 **예정**인 기능이면 제목과 본문에도 **예정**이라고 남긴다.
- **궁금증을 만드는 문장**과 **사실을 과장하는 문장**을 구분한다.

### 7-3. 이미지: agy로 생성하고 파일까지 확인

이미지 요청에 넣을 것: **장면, 공통 색감, 구도, 글자 올릴 여백, "이미지 안에 글자 없음"**

```text
이 스토리보드에 맞는 설명용 이미지를 agy로 생성해 줘. 장마다 색감과 그림체를 통일하고,
제목을 올릴 여백을 남겨 줘. 이미지 안에는 글자를 넣지 말고 실제 저장 파일을 확인해 줘.
```

- `generate_image`는 에이전트의 **이미지 생성·편집 도구**다. `agy image generate` 같은 별도 명령이 있는 게 아니다.
- 실제 제품 화면·발표 장면이 아닌 그림은 **설명용 생성 이미지**로 기록한다.
- 생성 실패 시 그 카드에 **오류와 재시도 버튼**을 보이고, 확정한 스토리보드와 **다른 카드 결과는 유지**한다.

#### Headless 실행과 권한

**Headless**: 대화형 화면 없이 요청을 실행하는 방식. 도구 권한을 대화로 받을 수 없어서 **작업이 거부될 수 있다.**

| 문제 | 대처 |
| --- | --- |
| 인증 실패 | 대화형 `agy`에서 로그인 확인 |
| 권한 거부 | `permissions.allow` 규칙으로 **필요한 도구만** 허용 후 재시도 |
| (승인한 시험 작업에서) | `--dangerously-skip-permissions` — **그 실행의 모든 도구 요청을 자동 승인** |

> ⚠️ `--dangerously-skip-permissions`는 이미지 도구에만 권한을 주는 게 아니다. 전역 설정은 안 바꾸지만, **작업 폴더가 보안 격리를 해 주는 것도 아니다.** 웹 서비스에서는 **필요한 도구만 허용하는 규칙**을 우선한다.

수동으로 확인할 때 (작업 폴더에서 먼저 `agy`로 인증 확인 → 종료 후):

```bash
agy -p '내장 generate_image 도구로 AI 소식을 설명하는 카드뉴스용 일러스트를 만들어 줘. 청색과 흰색, 단순한 구도, 위쪽 제목 여백, 이미지 안에 글자 없음. 현재 작업 폴더의 card-01.png로 저장하고 실제 저장 경로를 알려 줘.'
```

- `card-01.png`는 **자연어로 요청한 저장 위치**일 뿐이다. 반환된 경로와 파일을 다시 확인한다.
- `--output-format json`은 **CLI 응답 형식** 옵션이지 **이미지 파일 형식** 옵션이 아니다.

### 7-4. 왜 글자를 이미지와 따로 넣을까?

| 글자를 이미지 안에 그리면 | 글자를 별도 텍스트 레이어로 두면 |
| --- | --- |
| 오타·사실 수정 때 **이미지를 다시 생성**해야 함 | **글자만** 고치면 됨 |
| 한국어 줄바꿈·크기 조정이 어려움 | 모바일 크기에 맞춰 조정 가능 |

수정 요청은 **카드와 문제를 구체적으로 지목**한다.

- ❌ "더 예쁘게"
- ✅ "3번 카드의 본문이 길어. 핵심 조건을 유지하며 두 문장으로 줄여 줘"

- 이미지가 부적절하면 **그 카드만** 다시 생성, 텍스트만 고칠 땐 **기존 이미지 유지** (5-4의 참고 구현 차이와 대조)
- 수정 후에는 **기존 최종 승인을 해제**하고 새 버전을 다시 승인한다.

### 7-5. 최종 검수 기준 (내보낸 파일 기준)

미리보기가 괜찮아도 **내보낸 결과는 따로** 확인한다. 자동 게시는 하지 않고, 수업에서는 검수한 파일을 제출한다.

| 검수 대상 | 통과 기준 |
| --- | --- |
| 최신성과 사실 | 조사 기간 표시, 핵심 문장의 날짜·기능·조건을 원문에서 확인 가능 |
| 독자와 흐름 | 표지가 독자에게 필요한 이유를 전달, 카드마다 다른 메시지 |
| 생성 결과 | 이미지가 실제로 열리고, 생성 그림을 실제 화면·보도 사진처럼 설명하지 않음 |
| 편집과 가독성 | 제목·본문을 따로 수정 가능, 모바일에서 읽힘 |
| 실패와 재시도 | 인증·권한·생성 실패가 **완료로 표시되지 않음**, 재시도 가능 |
| 내보내기 | 확정한 카드가 빠짐없이 같은 순서로, 출처와 조사 기준일 포함 |

```text
내보낸 파일을 기준으로 누락, 글자 잘림, 출처, 날짜를 확인해 줘.
확인하지 못한 항목은 통과로 처리하지 말고 내가 확인할 부분을 알려 줘.
```

**제출 전 짝 교차 검수**: 원문 링크·완성 PNG·실행 기록을 보여 주고 → 짝이 핵심 문장 하나의 날짜·조건을 원문과 대조 + 모바일에서 읽기 어려운 카드 하나 지목 → 피드백 하나 반영 후 다시 확인. (혼자면 시간을 두고 같은 두 항목을 직접 점검)

### 7-6. 실제 제작 결과 예시

- 2026년 9월 8일 실행: 후보 10개 중 **WeatherNext 3**를 고르고, 일반 AI 뉴스 독자로 카드 5장 완성
- 마지막 카드의 수치 설명을 검토 후 수정 → **수정하지 않은 4장은 그대로 유지**되는 것까지 확인
- 처음 조사에서 **시간 제한에 걸린 과정**과 실제 검증 범위도 기록에 남겼다

→ 당시 예시일 뿐 지금도 최신 소식이라는 뜻이 아니고, 현재 참고 구현의 모든 기능을 검증한 예시도 아니다.

## 8. 왜 이 노드는 "확인"을 계속 강조할까?

노드 전체에서 같은 경고가 모양만 바꿔 계속 나온다. **에이전트가 "했다"고 보이는 것과 실제로 된 것 사이에 틈이 많기 때문이다.**

| 그럴듯해 보이는 것 | 실제로 확인할 것 |
| --- | --- |
| 코딩 에이전트에 로그인됨 | **실행 엔진**도 인증됐는가 |
| 도구가 설치돼 있음 | 실제 검색·이미지 생성이 **한 번 돌아갔는가** |
| 화면에 후보가 보임 | **모의 데이터**가 아니라 실제 조사 결과인가 |
| 검색 결과 요약이 있음 | **원문을 직접 열어** 날짜·제목을 대조했는가 |
| 이미지 생성 요청을 보냄 | **파일이 생기고 실제로 열리는가** |
| 종료 코드·응답 문장이 성공 | 결과 **파일까지** 있는가 |
| 초안이 화면에 표시됨 | **검증 완료**와 구분했는가 |
| 참고 구현이 실행됨 | **PRD 조건**을 하나씩 통과했는가 |
| 세션 ID를 저장함 | 화면 상태·작업이 **실제로 복구되는가** |

그리고 확인 못 한 것은 이렇게 다룬다.

```text
확인 못 함
   ↓
통과로 처리하지 않는다
   ↓
'미확인' / '미완료'로 표시하고 기록한다
   ↓
사람이 확인할 부분으로 넘긴다
```

> **"완료"는 에이전트의 말이 아니라 결과물로 판정한다.**

## 9. [과제] 나만의 워크플로로 확장하기

카드뉴스에서 만든 흐름을 **내가 자주 하는 작업**에 적용한다. 반복해서 겪는 **불편 하나**와 **확인 가능한 결과물 하나**를 고르면 시작하기 쉽다.

예: 회의 기록 → 실행 항목 / 학습 자료 → 복습 문제 / 여러 공고 비교 → 지원 준비 목록

### 9-1. 무엇을 가져오고 무엇을 바꾸나

| 재사용할 흐름 | 바꿀 것 |
| --- | --- |
| 자료 조사 → 후보 비교 → 선택에 따라 결과물 생성 | 카드 수·이미지 배치처럼 **카드뉴스에만 필요한 조건** |

### 9-2. 다섯 칸 설계

| 설계할 부분 | 정할 내용 |
| --- | --- |
| **입력** | 사용자가 무엇을 넣나? 결과에 **필요한 것만** |
| **AI 판단** | 무엇을 추리고 어떤 후보를 비교·제안하나? **판단 근거도 결과에서 보이게** |
| **사람 결정** | 목표·취향에 따라 결과가 갈리는 지점은? **이미 받은 조건은 다시 안 묻고**, 꼭 필요한 선택만 |
| **도구 행동** | 선택 뒤 실제로 무엇을 검색·작성·저장하나? 외부 전송·게시가 있으면 **실행 전 검토와 조건** |
| **검수와 산출물** | 어떤 상태면 쓸 수 있나? 원문 일치·누락·형식 확인과 수정 가능 |

#### 예시: 학습 자료로 복습 문제 만들기

```text
입력: 자료 + 학습 범위
   ↓
AI 판단: 핵심 개념과 문제 후보 제안
   ↓
사람 결정: 복습할 개념·난도 선택
   ↓
도구 행동: 문제와 해설 작성
   ↓
검수: 해설의 근거가 자료에 있는지 확인 → 수정한 문제 저장
```

→ 선택 화면은 **모든 단계가 아니라 학생의 결정이 필요한 곳에만** 둔다.

구현 요청 예시:

```text
카드뉴스 PRD를 학습 자료로 복습 문제를 만드는 워크플로로 바꿔 구현해 줘.
핵심 개념을 제안하고 내가 선택하면 문제와 근거가 있는 해설을 만들어 줘.
자료가 부족하면 부족한 부분을 표시해 줘.
```

- 결과가 기대와 다르면 코드 설명을 길게 요청하기보다 **실제 입력 / 기대한 결과 / 나온 결과의 차이**를 알려 주고 다시 실행한다.
- **정상 입력 한 번 + 자료 부족 입력 한 번**을 실행한다. 오류를 숨기거나 그럴듯하게 채우지 않고, 현재 상태를 보여 주고 입력 보완·재실행으로 이어지는지 본다.

### 9-3. 제출물

| 항목 | 내용 |
| --- | --- |
| 구현 결과 | 실행 가능한 앱·프로젝트 + 간단한 실행 방법 |
| PRD의 결정 | 해결할 불편, 기대 산출물, 사람이 결정하는 지점을 반영한 PRD |
| 실행 증거 | 실제 입력부터 선택·결과까지의 화면·기록·산출물 |
| 실패와 개선 | 기대와 달랐던 사례 하나 + 바꾼 점 + 다시 실행한 결과 (못 풀었으면 남은 문제와 다음 방향) |

제출 폴더 구성:

```text
제출 폴더/
├── README.md        실행 방법
├── PRD.md           요구사항
├── DECISIONS.md     선택 이유
├── API_SPEC.md      화면과 서버의 약속
├── 실행 화면·결과 파일
└── 검증 기록
```

- **카드뉴스 한 편의 검수를 끝낸 뒤** 확장을 시작한다. 새 앱을 크게 만들기보다 입력·판단·결과 중 필요한 부분만 바꾼다.
- 확장을 못 끝냈으면 **카드뉴스 완료 범위와 확장 미완료 범위를 따로** 제출한다.
- 기능 수보다 **다음 작업에서도 다시 쓸 수 있는 흐름**을 완성하는 데 집중한다.
- 다음 Day 40에서 여기서 발견한 사용자 결정·도구 권한·실패 사례를 **내 도메인의 자동화 설계**에 반영한다.

```text
사용자와 함께 만드는 카드뉴스 에이전트
│
├─ 설계 원칙
│   ├─ AI = 조사·제안·제작 / 사람 = 선택·승인·검수
│   └─ 기다림(waiting_for_user)도 정상 단계
│
├─ 두 종류의 AI
│   ├─ 코딩 에이전트 ── 앱을 만든다 (PRD → 질문 → DECISIONS.md)
│   └─ 실행 엔진 ── 앱 안에서 조사·원고 (SDK / Claude CLI / OpenCode 중 하나) + agy는 이미지 전담
│
├─ 만드는 순서 (바이브코딩)
│   └─ 모의 화면 → 실제 엔진 → 이미지 한 장 → 전체 제작 → ACCEPTANCE.md 확인
│
├─ 질문과 재개
│   ├─ SDK: AskUserQuestion 콜백으로 대기 → 답 반환
│   ├─ CLI: need_input 규약 → 세션 ID로 다음 호출
│   └─ 저장: 프로젝트·실행 ID, 세션 ID, 단계, 질문·답, 원고 (새로고침 ≠ 서버 재시작)
│
├─ 제작과 검수
│   ├─ 최근 7일 후보 → 원문 검증(사실 / 주장 / 미확인) → 독자·후킹 → 스토리보드
│   ├─ 이미지는 파일까지 확인, 글자는 별도 레이어
│   └─ 내보낸 파일로 최종 검수 + 짝 교차 검수
│
└─ 과제: 입력 · AI 판단 · 사람 결정 · 도구 행동 · 검수 다섯 칸으로 내 워크플로 설계
```

### 핵심만 기억하면

> **에이전틱 워크플로에서 사람의 선택과 검토는 빠진 부분이 아니라 설계한 부분이다.**

> **코딩 에이전트는 앱을 만들고, 실행 엔진은 앱 안에서 일한다. 두 질문은 묻는 대상도 저장되는 곳도 다르다.**

> **질문 → 대기 → 답변 → 재개가 끊기지 않으려면 앱이 상태(ID·단계·질문·답)를 직접 저장해야 한다. 세션 ID만으로는 복구되지 않는다.**

> **"했다"는 말이 아니라 결과물로 판정한다: 원문을 열고, 파일을 열고, 내보낸 결과를 연다. 확인 못 한 것은 통과가 아니다.**

> **한 번에 완성을 요청하지 말고, 작은 흐름을 돌려 실제로 본 문제를 다음 요청에 담는다.**

그리고 **Claude Agent SDK·Claude CLI·OpenCode CLI의 세부 옵션(`options.resume`, `--resume`, `--session`, 출력 필드 이름)은 지금 외울 필요 없이 "엔진마다 이어 가는 방법과 출력 모양이 다르다"는 것만 기억하면 된다.** 실제 구현할 때 코딩 에이전트가 공식 문서를 보며 맞춘다.
