## 1. 에이전트 팀 꾸리기 — 기본 개념

목표는 **매일 아침 AI 뉴스레터를 자동으로 보내는 에이전트**를 만드는 것이다. 필요한 작업은 뉴스 수집, 선별, 요약, 검수, 발행이다.

### 핵심 개념

| 개념 | 뜻 |
| --- | --- |
| AI 에이전트 | 주어진 목표를 달성하기 위해 도구를 사용하고 여러 작업을 수행하도록 만든 시스템 |
| 파이프라인(Pipeline) | 여러 작업을 정해진 순서대로 연결한 작업 흐름 (세탁기의 `세탁 → 헹굼 → 탈수`처럼) |
| 노드(Node) | 파이프라인에서 하나의 작업을 담당하는 단위 (수집 노드, 선별 노드, 요약 노드…) |
| 엣지(Edge) | 한 작업이 끝난 뒤 다음 작업으로 이동하도록 노드를 잇는 경로 |
| 그래프(Graph) | 노드와 엣지를 연결해 작업의 순서와 흐름을 표현한 전체 구조 |
| LangGraph | AI 에이전트의 작업 흐름을 그래프로 설계하고 실행하도록 돕는 프레임워크 |

그래프가 반드시 일직선인 것은 아니다. 상황에 따라 다른 노드로 이동하거나 특정 작업을 반복하게 만들 수도 있다.

```
수집 Node → 선별 Node → 요약 Node → 검수 Node → 발행 Node
```

### 왜 다섯 단계로 나누는가

하나의 AI에게 "뉴스를 찾아서 중요한 것만 요약하고 보내 줘"라고 한 번에 요청할 수도 있지만, 그러면 문제가 생겼을 때 원인을 찾거나 결과를 통제하기 어렵다. 작업을 나누면 다음 장점이 있다.

- **수정하기 쉽다**: 요약 결과가 나쁘면 요약 단계만 고친다.
- **검증하기 쉽다**: 잘못된 뉴스가 들어왔는지, 요약이 틀렸는지 단계별로 확인한다.
- **교체하기 쉽다**: 수집 방법을 바꿔도 다른 단계는 유지된다.
- **흐름을 통제하기 쉽다**: 검수를 통과한 뉴스만 발행하게 만들 수 있다.

단, 단계가 많아질수록 구현과 관리는 복잡해진다. 수집 방법도 마찬가지로 방법마다 장단점이 다르므로 목적에 맞게 골라야 한다. 이것이 **트레이드오프(Trade-off)**, 즉 하나를 선택해 얻는 장점 대신 포기하거나 감수해야 하는 부분이 있다는 뜻이다.

### 자동 실행의 구성

- **Discord**: 완성된 뉴스레터를 전달하는 메신저
- **GitHub Actions**: 정해진 시간이나 조건에 따라 코드를 자동 실행하는 기능

매일 아침 GitHub Actions가 실행되면 수집부터 발행까지 진행되고 결과가 Discord로 전달된다. 다만 한 번 설정했다고 영원히 정상 작동하지는 않는다. 실행 실패, API 오류, 인증 만료 등이 생길 수 있으므로 실행 기록을 확인하는 방법도 알아야 한다.

```
목표 설정 → 작업 분리 → 노드 연결 → 실행 → 검증
```

> 퀴즈: '뉴스 요약하기' 같은 개별 작업을 LangGraph에서 무엇이라 부르는가? → **노드(Node)**

## 2. 다섯 단계를 빈 노드로 세우기

핵심은 **각 기능을 먼저 완성하는 대신, 빈 노드 다섯 개를 먼저 연결해 전체 흐름을 만들고 하나씩 실제 기능으로 교체하는 것**이다.

1. **collect (수집)**: 뉴스 기사 수집
2. **pick (선별)**: 중요한 기사 5건 선택
3. **draft (작성)**: 각 기사 요약 작성
4. **verify (검수)**: 작성된 내용 확인
5. **publish (발행)**: 완성된 뉴스레터 게시

### 왜 빈 노드부터 만드는가

빈 노드는 실제 작업 없이 실행 로그만 남기는 함수다.

```python
def collect(state):
    return {"log": ["① 수집 실행"]}
```

다섯 노드를 먼저 연결하면 전체 흐름이 작동하는지 확인할 수 있고, 이후 노드를 실제 기능으로 바꿀 때마다 결과를 확인할 수 있다.

| 개발 방식 | 특징 |
| --- | --- |
| 기능을 모두 만든 뒤 연결 | 기능별 개발은 쉽지만 연결 단계에서 데이터 형식 문제가 발견될 수 있다 |
| 노드를 만들 때마다 그래프 재작성 | 유연하지만 매번 그래프 정의를 수정해야 한다 |
| 노트북 셀을 순서대로 실행 | 간단한 실험에 좋지만 병렬 처리·자동 실행으로 확장하기 어렵다 |
| **빈 노드로 뼈대부터 (이번 실습)** | 전체 흐름을 먼저 확인하고 단계적으로 구현한다. 대신 State를 처음부터 설계해야 한다 |

모든 상황의 정답은 없다. 일회성 실험이라면 노트북 셀 순차 실행이 더 편할 수 있다.

### State 설계

**State는 노드들이 작업 결과를 주고받기 위해 공유하는 데이터 저장 공간**이다. LangGraph에서 노드들은 State라는 딕셔너리를 공유하며, 앞 노드가 기록한 값을 다음 노드가 읽는다. 이번 실습에서는 `Brief` 클래스가 State 구조를 정의한다.

| 항목 | 의미 |
| --- | --- |
| `hours` | 뉴스를 수집할 시간 범위 설정값 |
| `collected` | 수집한 기사 목록 |
| `picked` | 선별한 기사 목록 |
| `drafted` | 요약문을 작성한 결과 목록 |
| `log` | 실행 과정과 결과 기록 |

노드끼리 직접 데이터를 넘기지 않고 **State라는 공용 공간을 통해 결과를 주고받는다.**

### 기사 데이터 형식 통일

출처마다 항목 이름과 형식이 달라서 통일하지 않으면 출처별 조건문이 늘어난다. 모든 기사를 다섯 항목으로 맞춘다.

| 항목 | 의미 |
| --- | --- |
| `title` | 기사 제목 |
| `url` | 기사 링크 |
| `source` | 기사 출처 |
| `at` | 게시 시각 |
| `summary` | RSS에서 제공한 짧은 요약 |

취재 노드에서 LLM이 요약하면 `headline`(뉴스레터 제목), `summary`(LLM이 새로 쓴 요약), `why`(선정 이유)가 추가된다. 이때 `summary`의 의미가 RSS 요약에서 LLM 요약으로 바뀐다.

### 리듀서(Reducer)

**리듀서는 State에 새 값이 들어올 때 기존 값과 어떻게 합칠지 정하는 규칙**이다. 기본적으로 노드가 반환한 값은 기존 값을 교체하는데, 여러 노드가 같은 항목에 쓰면 일부 결과가 사라질 수 있다.

```python
Annotated[list, operator.add]
```

이 코드는 새 리스트를 덮어쓰지 않고 **뒤에 이어 붙이도록** 지정한다.

| 항목 | 값을 쓰는 노드 | 리듀서 필요 여부 |
| --- | --- | --- |
| `collected` | 수집 노드 | 한 노드가 쓰므로 교체하면 된다 |
| `picked` | 선별 노드 | 한 노드가 쓰므로 교체하면 된다 |
| `drafted` | 여러 취재 워커 | 여러 작업자의 결과를 모두 합쳐야 한다 |
| `log` | 다섯 노드 모두 | 모든 실행 기록을 보존해야 한다 |

> 핵심은 리스트의 길이가 아니라, 그 항목에 값을 쓰는 곳이 여러 군데인지 여부다.

`verified` 항목은 이후 검수 결과용으로 추가된다. 노드는 자신이 수정한 항목만 반환하므로 State에 항목이 늘어나도 다른 노드를 고칠 필요가 없다.

### 코드에서 알아둘 세 가지

**① 노드는 자기가 바꾼 항목만 반환한다.** LangGraph는 반환된 항목만 반영하고 나머지는 유지한다.

```python
def verify(state):
    return {"log": ["④ 검수 실행"]}
```

**② `build()`는 노드 이름으로 함수를 찾는다.**

```python
g.add_node(name, globals()[name])
```

`globals()[name]`은 현재 노트북에서 그 이름으로 정의된 함수를 가져온다. 다음 섹션에서 `collect`를 같은 이름으로 재정의하고 `build()`를 다시 실행하면 새 함수가 쓰이므로, 그래프 뼈대 코드를 고치지 않아도 된다.

**③ State에는 단계 사이에서 공유할 값만 넣는다.** 프롬프트 문자열이나 HTTP 세션처럼 한 노드 안에서만 쓰는 값은 넣지 않는다.

### 실행 결과 해석

빈 노드 다섯 개를 실행하면 ①~⑤ 로그 다섯 줄이 순서대로 찍히고 기사 건수는 모두 0이다. 오류가 아니다. 노드가 순서대로 실행됐고 State가 전달됐으며, 아직 실제 기능이 없을 뿐이다. 이제 노드를 하나씩 교체할 때마다 건수가 0에서 벗어난다.

| 용어 | 뜻 |
| --- | --- |
| Node | 하나의 작업을 수행하는 함수 |
| State | 노드들이 결과를 주고받는 공용 데이터 공간 |
| Pipeline | 여러 단계를 연결해 데이터가 순서대로 흐르게 한 처리 과정 |
| Reducer | 여러 곳에서 들어오는 값을 합치는 규칙 |
| Worker | 특정 작업을 실제로 수행하는 단위 (여러 취재 워커가 기사별 요약 작성) |

> 퀴즈: `drafted`와 `log`에만 리듀서를 붙인 이유는? → `drafted`는 여러 취재 워커가 동시에 쓰고 `log`는 모든 노드가 한 줄씩 남기므로 합쳐야 하지만, `collected`·`picked`는 한 노드가 쓰고 다음 노드가 읽으므로 덮어쓰기가 맞다. (리스트 길이, `TypedDict` 제한, 실행 속도와는 무관하다.)

## 3. 자료 수집: 경로와 소스 고르기

정보를 가져오는 경로에 따라 데이터 안정성, 수집 가능 여부, 법적 위험, 유지보수 비용이 달라진다. 이번 실습은 **RSS·Atom 피드**를 선택했다.

### 정보를 가져오는 다섯 가지 경로 (사다리)

위쪽 방법을 먼저 검토하고, 쓸 수 없을 때 아래로 내려간다.

| 경로 | 설명 | 장점 | 단점 |
| --- | --- | --- | --- |
| ① 공식 API | 제공자가 공개한 통로. 요청하면 JSON 등 구조화 데이터 반환, 인증 키·호출 제한이 있을 수 있음 | 형식과 이용 조건이 명확 | API가 없을 수 있음 |
| ② RSS·Atom (선택) | 새 글의 제목·링크·게시 시각을 주는 XML 피드. 인증 없이 공개된 경우가 많고 형식이 오래 안정적 | 시간순으로 올라오는 뉴스 수집에 적합 | 제목·짧은 요약만 줘서 본문은 따로 가져와야 할 수 있음, 시각 형식이 소스마다 다름 |
| ③ 공개 데이터셋·아카이브 | 이미 수집된 데이터를 내려받음 | 과거 데이터 일괄 분석·실험에 편함 | 갱신 주기가 일·월 단위라 실시간 뉴스에 부적합 |
| ④ 서드파티 집계 서비스 | 여러 매체를 대신 모아 주는 상용 서비스 | 매체 연결 작업 감소 | 비용, 수집·필터 기준 통제 어려움, 서비스 종료 시 파이프라인 영향 |
| ⑤ 직접 스크래핑 | HTML을 가져와 필요한 부분 추출 | API·RSS가 없는 사이트에 사용 가능 | 화면 구조가 바뀌면 깨짐, `robots.txt`·이용약관 확인 필요, 유지보수 비용 큼 |

공개 RSS라고 모든 콘텐츠를 자유롭게 재사용해도 된다는 뜻은 아니다. 이용 조건과 저작권도 확인해야 한다.

> 퀴즈: '위 칸이 가능하면 아래로 내려가지 않는다'의 근거는? → 위 칸일수록 발행자가 가져가도 된다고 밝힌 통로라 형식 안정성과 법적 명확성을 함께 확보하기 쉽기 때문이다.

### 실습 데이터

- **출처**: TechCrunch, The Verge, OpenAI·DeepMind 공식 블로그, AI타임스, 전자신문, Hacker News 등 11곳
- **수집 방식**: RSS와 공개 API
- **규모**: 최근 24시간 기준 약 50~120건
- **사용 범위**: 제목, 요약, 원문 링크 중심. 기사 전문은 재배포하지 않음
- **특징**: 실시간 피드라 실행 시각마다 결과가 다름

중요한 것은 많이 모으는 것이 아니라 **실제로 뉴스레터에 쓸 수 있는 데이터를 주는 소스를 찾는 것**이다.

### RSS 소스마다 품질이 다르다

교안에서는 여섯 곳에 실제로 요청을 보내 세 가지를 측정한다.

1. **수집 건수**: 수백~천 건 넘게 주는 곳도, 최근 10건만 주는 곳도 있다. 하루 15건 발행하는 매체가 10건만 준다면 수집 사이에 글이 밀려나 누락될 수 있다. 따라서 **하루 발행량과 피드 제공 건수를 함께** 봐야 한다.
2. **요약 길이**: 한 문장부터 한 문단까지 다양하다. 길어도 전문을 대신하기엔 부족할 수 있고, 제목·짧은 설명만으로 요약하면 기사에 없는 내용을 지어낼 위험이 있다.
3. **최신 게시물**: 며칠간 새 글이 없는 소스는 24시간 필터에서 대부분 날 아무것도 못 가져온다. 게시 시각이 음수로 계산되기도 하는데, 날짜만 기록하거나 시각을 자정으로 처리하는 등 기록 방식 때문일 수 있어 반드시 오류는 아니다.

> 퀴즈: 10건만 주는 소스를 다룰 때 먼저 확인할 것은? → 그 매체의 하루 발행량. 10건보다 많으면 한 번 수집으로 그날 글을 놓칠 수 있다. (User-Agent 변경, `?limit=100` 추가, 관문 생략은 답이 아니다.)

### 1차 소스와 2차 소스

| 구분 | 의미 | 예시 |
| --- | --- | --- |
| 1차 소스 | 정보를 직접 발표하는 곳 | OpenAI·DeepMind·Hugging Face 공식 블로그 |
| 2차 소스 | 발표를 취재·분석해 전달하는 곳 | TechCrunch·The Verge·AI타임스 |

한 사건을 여러 매체가 반복 보도하므로, 모두 같은 기준으로 경쟁시키면 비슷한 기사가 여러 개 뽑혀 다양성이 떨어진다. 그래서 소스 목록에 `tier` 값을 둔다.

- **`tier: 1` 소스**: 선별 경쟁 없이 우선 통과시킨다.
- **관문 검사**: 1차 소스라도 본문 추출·접근 가능 여부를 확인한다.
- **면제 건수 제한**: 우선 통과시킬 글 수에 상한을 둔다.

공식 발표를 놓칠 가능성을 줄이면서 중복 보도나 관련성 낮은 글이 결과를 독차지하는 것도 막는다.

### 소스 채택 기준: 관문과 등급 평가

먼저 **관문**(반드시 충족할 최소 조건, 통과 못 하면 다음 평가 없음)을 보고, 통과한 소스끼리 **등급 평가**로 비교한다. 관문은 세 가지다.

| 관문 | 질문 | 이유 |
| --- | --- | --- |
| G1 본문 제공 | 요약할 만큼 내용이 충분한가? | 제목·짧은 요약만 있으면 모델이 없는 내용을 지어내는 **환각**이 생긴다. 원문 주소에서 본문을 추출할 수 있는지 확인한다 |
| G2 최근 게시 | 지금도 새 글이 올라오는가? | 멈춘 소스는 결과 없이 요청·처리 시간만 낭비한다 |
| G3 자동 수집 가능 | 프로그램으로 가져와도 되는가? | `403`은 접근 거부, `robots.txt`가 금지할 수 있다. 기술적으로 가능해도 허용되지 않으면 제외한다 |

### G1 본문 관문 실제 검사

각 소스의 최근 기사 세 건으로 RSS 요약과 원문 추출 결과를 비교한다.

- **RSS 요약 길이**: 대부분 수백 자로, 기준인 600자에 못 미치는 소스가 많을 것으로 예상된다.
- **원문 추출**: 기사 주소로 다시 요청해 `trafilatura`로 본문을 추출하고 600자를 넘는지 본다. 유료 구독·동영상 위주 기사는 실패할 수 있으며, 이런 사례를 찾는 것이 관문의 목적이다.

> RSS 수집과 원문 추출은 서로 다른 단계이며 둘 다 필요하다. RSS는 새 글이 올라왔다는 사실과 기본 정보를, 원문 추출은 요약할 만큼의 내용을 확보한다.

본문 검사는 소스마다 세 건씩 추가 요청을 보내 약 1~2분이 걸린다. 매일 돌리기보다 소스를 처음 채택할 때와 필요할 때 실행한다.

### 운영 중 확인할 지표

1. **본문 추출 성공률**: 발행 후보 중 본문이 기준 길이를 넘긴 비율. 1.0보다 낮아지면 소스의 페이지 구조 변경이나 접근 제한을 의심한다.
2. **소스별 기여 건수**: 최종 5건이 어느 소스에서 왔는지 기록. 한 달 내내 0건인 소스는 G2를 재확인하고 제외를 검토한다.
3. **본문 추출 소요 시간**: 갑자기 늘면 특정 소스 응답이 느려졌을 수 있다. 타임아웃이 없으면 요청 하나 때문에 전체가 멈출 수 있다.

이 세 숫자는 별도 도구 없이 실행마다 파일에 한 줄씩 기록해 추적할 수 있다. 추출이 실패하면 모델이 제목만 보고 요약해 문장은 자연스럽지만 내용이 부정확해진다. 그래서 사람이 결과를 읽는 것만이 아니라 **성공률 숫자를 지속적으로 확인**하는 것이 중요하다.

참고 자료: RSS 2.0 명세, Hacker News 검색 API(Algolia), trafilatura 공식 문서, Python `urllib.robotparser`(`robots.txt` 확인용).

> 자료 수집 단계에서는 안정적이고 허용된 경로를 고르고, RSS로 기사를 찾은 뒤 원문을 추출해 실제 요약에 쓸 수 있는지 검증한다.

## 4. 수집 노드 만들기 (collect)

비워 두었던 `collect` 노드를 구현한다. 하는 일은 세 가지다.

1. **글 수집**: 등록된 소스를 차례로 확인해 새 글을 가져온다.
2. **수집 기간 필터링**: 설정한 시간 범위 안의 글만 남긴다.
3. **중복 제거**: 같은 글이 여러 번 들어오지 않게 한다.

여기에 특정 소스의 오류가 전체를 멈추지 않도록 예외 처리를 더한다. `collect` 함수만 수정하고 State와 그래프 흐름은 그대로 둔다.

### 수집 기간(Time Window)과 cutoff

기본 수집 기간은 **24시간**이며 State의 `hours`로 설정한다. `hours`를 48로 바꾸면 함수 수정 없이 48시간치를 수집한다.

`cutoff`는 현재 시각에서 설정 시간만큼 거슬러 올라간 기준 시각이다. 현재가 10월 28일 오후 10시이고 `hours = 24`면 `cutoff`는 10월 27일 오후 10시다.

```python
if not at or at < cutoff:
```

`not at`(게시 시각이 없는 글) 또는 `at < cutoff`(기준보다 오래된 글)이면 제외한다.

### 중복 제거

주소에 추적용 매개변수가 붙으면 같은 기사도 다르게 보인다.

```
https://example.com/article/123
https://example.com/article/123?utm_source=newsletter
```

```python
key = e.link.split("?")[0]
```

`?`와 그 뒤를 잘라 비교 기준 주소를 만든다. 단, 이는 **주소가 같은 글**의 중복만 제거한다. 다른 언론사가 같은 사건을 보도하면 주소가 달라 중복으로 잡히지 않는다. 내용 유사성이 아니라 URL 기준이다.

### 개별 소스의 오류 처리

```python
except Exception:
    dead.append(name)
```

예외가 나면 실패한 소스 이름을 `dead` 목록에 추가한다. 그러면 전체 수집이 멈추지 않고 나머지 소스를 계속 처리하며, 어떤 소스에 문제가 있었는지도 나중에 알 수 있다.

> 작업을 계속 진행하는 것과 오류를 기록하는 것을 함께 해야 한다.

### 조용한 실패(Silent Failure)

**프로그램이 중단되지도, 오류 메시지를 남기지도 않지만 결과가 잘못 나오는 상황**이다. 10개 소스 중 하나가 실패했는데 기록이 없으면, 9개는 정상 수집되고 프로그램도 정상 종료되어 문제가 없어 보이다가 나중에야 특정 매체 뉴스가 빠졌다는 것을 발견한다.

조용한 실패가 생기기 쉬운 코드는 다음과 같다.

```python
continue        # 조건에 안 맞는 항목을 건너뛰고 다음으로

except:
    pass        # 오류가 나도 아무것도 하지 않음
```

이런 코드가 항상 잘못된 것은 아니지만, 결과에 영향을 주는 누락을 기록 없이 넘기면 발견이 어렵다. 그렇다고 모든 건너뛰기를 기록하면 로그가 너무 길어져 중요한 문제가 묻힌다. **최종 결과에 영향을 줄 수 있는 문제 중심으로 기록**한다. 이번 코드는 소스 하나를 통째로 못 가져온 경우를 `dead`에 남긴다.

### 그래프와의 연결

`build()`가 노드 이름으로 함수를 찾으므로, 새 `collect`를 정의하기만 하면 기존 수집 노드를 대신한다. 실행하면 `collect`의 건수는 0이 아닌 값이 되고 나머지 네 노드는 아직 0이다. 노드를 하나씩 채우며 결과를 확인하는 방식이다.

참고 자료: feedparser의 Common RSS elements(`entries` 항목 구성), Date Parsing(`published_parsed`가 비는 경우), MDN `URL.searchParams`(문자열 자르기보다 정확한 URL 매개변수 처리).

| 개념 | 의미 |
| --- | --- |
| `collect` | 뉴스 소스에서 글을 수집하는 노드 |
| Time Window / `hours` | 수집 시간 범위 / 이를 시간 단위로 정하는 값 |
| `cutoff` | 수집 기간의 시작 기준 시각 |
| `if not at or at < cutoff` | 게시 시각이 없거나 기준보다 오래된 글 제외 |
| `key = e.link.split("?")[0]` | URL의 `?` 뒤를 제거해 중복 비교 기준 생성 |
| `dead.append(name)` | 실패한 소스 이름 기록 |
| Silent Failure | 정상 종료되지만 결과가 잘못되는 상황 |
| `continue` / `except: pass` | 현재 항목 건너뛰기 / 오류를 처리 없이 무시 |

## 5. 중요도 선별: 구조 정하고 노드 만들기 (select)

수집한 뉴스 중 중요한 기사 5건을 고르는 `select` 노드를 구현한다. 이번 단계부터 언어 모델을 쓰므로 **OpenAI API 키가 필요하다.**

### API 키 관리

API 키는 외부 서비스에서 사용자를 인증하는 비밀 문자열로, 비밀번호처럼 노출되지 않게 관리해야 한다.

- **로컬 주피터**: 프로젝트 폴더 `.env`에 `OPENAI_API_KEY`를 두고 `load_dotenv()`로 불러온다.
- **Google Colab**: 왼쪽 보안 비밀 기능에 `OPENAI_API_KEY`를 등록하고 `userdata`로 읽는다.
- **임시 설정**: `os.environ["OPENAI_API_KEY"]`에 직접 넣을 수 있지만 노트북에 키가 남으므로 저장·공유 전에 지워야 한다.

### 개별 평가(Pointwise Scoring)의 문제

기사마다 독립적으로 1~10점을 매기고 높은 순으로 상위 5건을 뽑는 방식이다.

1. **점수가 특정 구간에 몰린다**: 모델이 실제로는 5~8점 정도만 쓰는 경우가 있다. 12건을 평가했는데 점수가 4~5종류뿐일 수 있다.
2. **동점 처리가 어렵다**: 5등 자리에 동점이 여럿이면 점수로 판단할 수 없어, 목록에 먼저 나온 기사를 고르는 식으로 중요도와 무관한 기준을 쓰게 된다.
3. **수집량이 늘면 동점이 많아진다**: 100건 이상을 평가해도 점수 범위는 1~10점이다. 일정 점수 이상을 모두 뽑으면 어떤 날은 3건, 어떤 날은 40건이 된다.

> 풀어야 할 문제는 각 기사의 점수가 아니라 **오늘 기사 중 가장 중요한 5건을 고르는 것**이다. 개별 평가와 상위 5건 선정은 다른 문제다.

### 기사 선정 방식 네 가지

| 방식 | 평가 방법 | 장점 | 단점 |
| --- | --- | --- | --- |
| Pointwise + Top-k | 기사별 점수 후 상위 N개 | 같은 기준으로 독립 평가, 병렬 처리에 적합, 날짜가 달라도 비교 가능 | 동점 다발, 기사마다 호출해 비용 증가 |
| Pairwise (토너먼트) | 두 건씩 비교해 이긴 쪽을 올림 | 상대적 중요도 직접 비교, 점수 몰림 회피 | 100건에서 승자 하나에만 최소 99회, 전체 순위엔 수백 회 호출 |
| Listwise | 전체 후보를 한 프롬프트에 넣고 5건 선택 | 한꺼번에 비교, 호출 1회로 비용·시간 효율 | 입력이 길어지고 일부 기사가 덜 고려됨, 출력 형식이 깨질 수 있음 |
| **Two-stage (채택)** | 묶음별 예선 후 본선 | 입력 부담과 상대평가의 균형, 예선 코드 재사용 | 예선 탈락 기사는 본선에서 재평가 불가, 중요 기사가 한 묶음에 몰리면 일부 탈락하는 '묶음 운' |

교안 예시는 후보 100건을 40건씩 세 묶음으로 나눠 묶음마다 8건을 통과시키고(예선 24건), 본선에서 24건을 비교해 최종 5건을 고른다. 예선 3회 + 본선 1회로 총 4회 호출 구조이며, 실제 호출 수는 묶음 구성과 구현에 따라 달라진다.

```
후보 100건 → [묶음1 40건 → 8건] [묶음2 40건 → 8건] [묶음3 → 8건] → 본선 24건 → 최종 5건
```

두 방식의 선정 결과가 대부분 겹칠 수도 있지만 묻는 질문이 다르다. 개별 평가는 "이 기사는 몇 점인가?", 상대평가는 "후보 중 어떤 기사가 가장 중요한가?"다. 상대평가는 동점으로 구분하기 어려웠던 기사들의 우선순위를 정하는 데 도움이 된다.

### Lost in the Middle(중간 정보 손실)

후보가 12건 정도면 한 번에 넣을 수 있지만 수백 건이 되면 프롬프트가 길어지고, 모델이 입력 중간보다 앞부분과 끝부분 정보를 더 잘 활용하는 현상이 생긴다. 이를 줄이려고 후보를 묶음으로 나눠 예선을 한다. 예선은 입력을 나눠 처리하고, 본선은 살아남은 후보를 함께 비교한다.

### 병렬화와 Sectioning

교안은 예선 구조를 Anthropic이 설명한 병렬 처리 패턴 중 **sectioning**과 연결한다. 입력을 여러 묶음으로 나누고, 각 묶음을 독립 처리한 뒤 결과를 합치는 방식이다.

```
입력 → 여러 묶음으로 분할 → 각 묶음 독립 처리 → 결과 통합
```

- 같은 코드를 묶음마다 재사용할 수 있다.
- 묶음별 작업을 병렬로 처리할 수 있다.
- 한 묶음이 실패해도 나머지는 계속 처리하도록 설계할 수 있다.
- 묶음 간 직접 비교가 없어 중요한 기사를 놓칠 수 있다. 그래서 예선 통과 기준을 최종 건수보다 넉넉하게 잡는다.

### 구조화된 출력(Structured Output)

"선정한 기사 번호를 쉼표로 구분해 출력하세요"라고 해도 모델은 `3, 7, 그리고 9번도 좋습니다.`처럼 답할 수 있고, `int(x)` 변환에서 오류가 난다.

**구조화된 출력은 응답의 항목과 자료형(스키마)을 미리 정해 모델이 그 구조로 답하게 하는 방식**이다. 예를 들어 `event`(사건 라벨), 선정 기사 목록, `reason`(선정 이유)을 지정한다. 교안은 `Pick`과 `Shortlist`를 `response_format`으로 지정한다.

> 구조화된 출력은 구조와 자료형을 보장하도록 돕지만, 사건 라벨이 정확한지나 선정 판단이 옳은지까지 보장하지는 않는다.

### 사건 라벨(Event Label)과 중복 기사

여러 매체가 같은 신제품 출시를 보도하면 URL이 달라 수집 단계 중복 제거로는 막을 수 없고, 모두 최종 선정될 수 있다. **사건 라벨은 기사가 다루는 사건을 짧게 나타낸 이름**이다. `회사 A 신제품 출시`가 두 번 나오면 같은 사건일 가능성이 있다.

| 방법 | 내용 | 한계 |
| --- | --- | --- |
| 프롬프트에 조건 추가 | "같은 사건을 다룬 기사는 하나만 선정하세요" | 지시일 뿐 결과를 보장하지 않는다 |
| 코드로 라벨 검사 | 최종 후보의 `event`를 `Counter`로 집계해 이미 뽑은 사건과 같으면 건너뛰고 다음 후보 선택 | 프롬프트보다 일관되게 관리된다 |

같은 방식으로 매체별 건수를 세면 특정 매체가 너무 많이 뽑히는 것도 제한할 수 있다.

### select 노드의 흐름

1. State에서 수집된 기사를 가져온다.
2. 후보를 여러 묶음으로 나눈다.
3. 묶음마다 모델로 우수 기사를 고른다.
4. 예선 통과 기사를 하나로 합친다.
5. 본선에서 비교한다.
6. 최종 5건을 선정한다.
7. 선정 건수와 로그를 남긴다.

그래프를 실행하면 수집 건수, 예선 통과 건수, 본선 최종 5건을 확인할 수 있다. 프롬프트로 중복 제외를 지시해도 중복이 남을 수 있으므로 `event` 라벨 검사 로직을 추가해야 한다.

### 선별 결과 검증 지표

1. **묶음별 통과 기준**: 각 묶음의 마지막 통과(8등)와 첫 탈락(9등) 기사를 기록한다. 수준 차가 크면 '묶음 운'이 작용하고 있을 수 있다.
2. **본선 탈락 사유**: '중복', '판단하기 어려움' 같은 사유가 반복되면 앞 단계도 개선이 필요할 수 있다.
3. **예선 통과 대비 최종 선정 비율**: 대체로 3분의 1 안팎을 기준으로 본다. 1에 가까우면 본선 후보가 부족하고, 너무 낮으면 예선이 너무 많이 통과시켜 본선 부담이 크다.

지표를 로그와 파일로 남기면 날짜별 비교가 가능하다. 또 최종 선정만 보면 중요한 기사가 예선에서 떨어졌는지 알 수 없으므로 **탈락 목록도 확인**해야 한다. 중요한 기사가 탈락 목록에 반복해서 쌓인다면 소식이 없던 게 아니라 예선 기준이 문제일 수 있다.

| 용어 | 뜻 |
| --- | --- |
| Top-k | 상위 k개를 선정하는 것 |
| Pairwise Comparison | 두 건씩 비교하는 방식 |
| Listwise Ranking | 전체 후보를 한꺼번에 비교해 순위를 정하는 방식 |
| Two-stage Ranking | 예선과 본선으로 나눠 선정하는 방식 |
| Lost in the Middle | 긴 입력에서 중간 정보가 덜 활용되는 현상 |
| Sectioning | 입력을 묶음으로 나눠 독립 처리하는 방식 |
| Schema | 데이터의 항목과 자료형 등 구조를 정의한 규칙 |
| Event Label | 기사가 다루는 사건을 짧게 나타낸 라벨 |
| Counter | 항목별 등장 횟수를 세는 파이썬 도구 |

> 퀴즈 1: Pointwise에서 12건에 점수 값이 5개뿐인 것이 왜 문제인가? → 정해진 개수를 골라야 하는데 개별 점수만으로는 경계의 동점 기사 우선순위를 정할 수 없기 때문이다. 점수 범위를 1~100으로 넓히거나 모델 설정을 바꾸는 것이 아니라 후보끼리 비교해 순위를 정하는 것이 해법이다.
>
> 퀴즈 2: 예선 묶음이 서로 모른 채 처리되면? → 묶음 간 비교가 없어 중요한 기사를 놓칠 수 있다. 대신 코드 재사용과 오류 격리가 가능하다. 그래서 통과 기준을 넉넉히 하고 탈락 기사도 확인한다.

## 6. 요약: 취재 노드 만들기 (draft)

제목과 링크만으로는 독자가 내용을 이해하기 어렵다. 링크에 접속해 본문을 가져오고 언어 모델로 요약하는 `draft` 노드를 만든다.

### 요약 결과의 형식

| 방식 | 설명 | 한계 |
| --- | --- | --- |
| Free-form Text | 하나의 문단으로 생성. 프롬프트가 간단하고 사람이 읽고 고치는 결과물에 적합 | 사실과 해석 구분, 부분 검사·수정, 재구성이 어려움 |
| **Structured Output (선택)** | 정해진 항목으로 나눠 생성 | 항목이 많아지면 출력 비용·시간 증가 |
| Grounded Generation | 각 문장과 원문 근거 구절을 함께 생성 | 출력이 길어지고 근거 구절도 따로 검증해야 함 |
| Prompt Chaining | 여러 단계로 나눠 모델을 차례로 호출 | 호출 횟수·비용·응답 시간 증가 |

생성 결과를 자동 검수할 예정이므로 Structured Output을 고른다.

| 항목 | 의미 | 검증 방법 |
| --- | --- | --- |
| `headline` | 카드에 표시할 제목 | 원문과 대조 |
| `summary` | 세 문장 요약 | 원문과 대조 |
| `why` | 이 소식이 왜 중요한지 한 문장 | 독자 관점에서 평가 |

`why`는 해석이므로 원문에 같은 문장이 없어도 적절할 수 있어, 원문 일치 여부로 검사하면 안 된다.

> 결과 항목을 나누면 각 항목의 목적에 맞는 검증 기준을 적용할 수 있다.

### 기사 본문 추출

제목만으로 요약하면 모델이 세부 정보를 지어낼 수 있다. 그래서 링크 접속 → 원문 본문 추출 → 모델에 전달 → 제목·요약·중요성 문장 생성 순으로 처리한다. G1 관문과 연결되며, 본문이 부족한 기사는 취재 단계에서 빠질 수 있다.

### 한국어로 요청했는데 영어로 나오는 문제

시스템 프롬프트와 스키마에 한국어로 쓰라고 명시했는데도 일부 결과가 영어로 나왔다. 모델이 입력 본문의 언어를 따라가는 경향 때문이다. 프롬프트는 요청 수단이지 결과를 보장하는 장치가 아니다.

해결책은 **코드로 확인할 수 있는 규칙은 코드로 검사하는 것**이다. 결과에 한글이 있는지 확인하되, 한 글자 포함됐다고 한국어 문장인 것은 아니므로 기준을 구체적으로 정한다. 조건을 어기면 다시 요청하거나 번역 단계를 추가한다.

> 퀴즈: 한국어로 쓰라고 했는데 영어가 나왔다면? → 한글 포함 여부를 코드로 검사하고 어기면 재요청하거나 번역 단계를 추가한다. 프롬프트를 더 세게 쓰기, 더 큰 모델로 교체, 영어 기사 전부 제외는 직접적인 처방이 아니다.

### Send로 기사 수만큼 작업 분배

기사 다섯 건을 순서대로 처리하면 앞 작업을 기다리느라 오래 걸리고, 처리할 기사 수도 매번 다르다. LangGraph의 `Send`는 실행 중에 특정 노드에 전달할 입력을 지정해 그 노드를 실행하게 한다. 조건부 엣지가 노드 이름 대신 `Send` 객체 목록을 반환하면 각 입력으로 같은 노드가 실행된다. **실행할 작업 수가 고정되지 않아도 된다**는 점이 중요하다.

### 팬아웃(Fan-out)과 팬인(Fan-in)

```
선정된 기사 목록
  → Fan-out: 기사별 작업으로 분배
  → 기사별 본문 추출 및 요약
  → Fan-in: 각 작업의 결과를 drafted로 통합
```

팬아웃은 하나의 작업을 여러 독립 작업으로 나누는 것, 팬인은 결과를 하나로 모으는 것이다. 합쳐서 병렬 처리(Parallelization) 또는 팬아웃·팬인 패턴이라 한다. 작업이 독립적이면 동시에 처리해 실행 시간을 줄인다.

### Worker와 Reducer

워커는 분배된 개별 작업을 수행하는 단위로, 여기서는 기사 한 건을 처리하는 `draft` 실행이다. `Send`의 두 번째 인자로 `{"item": 기사 하나}`를 넘기면 워커는 자기 기사만 받아, 다른 워커나 전체 진행 상황을 알 필요가 없다. 그래서 독립적으로 테스트하기 쉽고 서로 영향을 덜 준다.

다섯 워커가 각각 `{"drafted": [기사 한 건의 요약]}`을 반환하면, `drafted`에 걸린 리듀서가 이를 하나의 목록으로 이어 붙인다.

| 구성 요소 | 역할 |
| --- | --- |
| `Send` | 어떤 입력으로 몇 개의 작업을 실행할지 분배 |
| Worker | 전달받은 기사 한 건 처리 |
| Reducer | 여러 워커의 결과를 하나로 합침 |
| State | 그래프 노드들이 공유하는 데이터 구조 |

> Send가 작업을 펼치고, 워커가 처리하며, Reducer가 결과를 모은다.

### 모든 작업을 병렬로 하면 안 되는 이유

다른 항목의 정보가 필요한지가 기준이다.

| 함께 봐야 하는 작업 (한데 모아 처리) | 기사별 독립 작업 (병렬 적합) |
| --- | --- |
| 중복 판정, 상대평가, 매체별 기사 수 제한 | 본문 추출, 요약 생성, 기사별 검수 |

따라서 이 파이프라인의 **병렬 처리 전환점(Fan-out Point)은 선별이 끝난 직후**다.

### 본문이 부족한 기사

본문이 부족하거나 추출에 실패하면 워커가 빈 리스트를 반환해, 다섯 건을 뽑아도 네 건만 남을 수 있다. 교안은 추가 수집 없이 통과한 네 건만 발행한다. 실제 운영에서는 선정 수, 성공 수, 실패 수, 실패 원인을 로그로 남겨야 결과가 줄어든 이유를 알 수 있다.

## 7. 검수 노드 만들기 (verify)

문장이 자연스럽다고 내용이 정확한 것은 아니다. 원문에 없는 내용을 만드는 환각을 잡기 위해 요약이 원문에 근거하는지 검사하는 `verify` 노드를 만든다.

### 숫자 대조와 오탐(False Positive)

요약의 숫자가 원문에도 있는지 비교하는 것은 문자열 비교만으로 가능해 추가 모델 호출 비용이 없다. 하지만 원문 `three months` ↔ 요약 `3개월`, 원문 `$60 million` ↔ 요약 `6000만 달러`처럼 표기가 달라도 의미가 같으면 정확한 요약이 불합격된다. **실제로는 맞는 결과를 틀렸다고 판정하는 것**을 오탐(False Positive)이라 한다. 문제는 숫자 검사 자체가 아니라 문자열 일치만 보는 방식이다.

> 퀴즈: 위 사례를 환각으로 판정했다면? → 검사 코드는 문자열 일치를 정상적으로 확인했지만 그 방식으로는 번역·단위 변환을 다룰 수 없었다. 의미가 같은지 판단하는 방식으로 개선해야 한다.

### 요약 검수 방법 네 가지

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 검수하지 않기 | 추가 비용 없음, 발행량이 적고 사람이 볼 수 있으면 간단 | 오류를 자동으로 못 거름, 신뢰가 중요한 뉴스레터에서 오보 위험 |
| Rule-based Check (숫자·고유명사 문자열 비교) | 비용 없음, 같은 입력엔 항상 같은 결과 | 번역·단위 변환에 약함, 숫자·이름 없는 과장은 못 잡음 |
| **LLM-as-a-Judge (선택)** | 표현이 달라도 의미가 같으면 통과, 숫자 없는 과장도 탐지 | 추가 호출 비용·시간, 검수 모델도 틀릴 수 있음 |
| Grounded Generation | 요약과 근거를 직접 비교 | 출력·비용 증가, 원문 표현에 얽매임, 근거 구절 자체도 틀릴 수 있음 |

원문은 영어, 요약은 한국어라 문자열 비교로는 한계가 있어 LLM-as-a-Judge를 쓴다. 검수는 요약을 생성한 호출과 **분리**해야 한다. 자기가 쓴 내용을 스스로 검증하면 오류를 잘 못 찾는다.

### 검수 대상 항목

`headline`과 `summary`는 원문이 뒷받침하는지 대조하고, `why`는 독자 관점의 해석이라 원문 일치만으로 판정하지 않는다. 다만 `why`에 잘못된 인상을 주는 해석이 섞일 위험은 남는다. 교안 범위를 넘는 개선안으로 `why`도 별도 기준으로 검수하기, 사실과 해석을 구분해 쓰게 하기, 중요한 해석은 사람이 확인하기를 고려할 수 있다.

### 검수가 제대로 작동하는지 확인하기

1. **불합격 건수(`verify_fail`)**: 계속 0건이면 검수가 정말 작동하는지 의심한다. 너무 많으면 기준이 과하게 엄격하거나 요약 생성에 문제가 있다.
2. **재작성 후 합격률**: 재작성해도 계속 탈락하면 본문 추출 과정도 살펴본다.
3. **의도적으로 틀린 요약의 적발 여부**: 약 5억 달러를 약 50억 달러로 바꿔 넣어 본다. 통과하면 검수가 작동하지 않는다는 신호다.

> 검수 실패 0건은 검수가 완벽하다는 증거가 아니다. 실제 오류를 찾아낼 수 있는지 테스트해야 한다. (조용한 실패와 같은 맥락)

### 탈락 기사 처리

| 방법 | 장점 | 단점 |
| --- | --- | --- |
| 다시 작성하기 | 기사를 살릴 수 있다 | 비용 증가, 재시도 관리 복잡 |
| 취재 노드로 되돌아가기 | 그래프상 재실행 흐름이 명확 | 한 건 실패로 전체 단계가 재실행될 수 있음 |
| **버리고 기록하기 (선택)** | 구현이 단순 | 최종 발행 건수가 줄 수 있음 |

다섯 건 중 한 건이 추출 실패, 한 건이 검수 탈락이면 최종 세 건이 된다. 다섯 건을 채우려고 재작성하거나 추가 수집하지 않고, 통과한 것만 발행하고 실패 이유를 기록한다. 재시도를 넣으면 재시도 횟수, 비용 상한, 중복 처리까지 관리해야 하므로 단순한 구조를 유지한다.

### `drafted`와 `verified`를 분리하는 이유

`drafted`에는 결과를 이어 붙이는 리듀서(`operator.add`)가 걸려 있다. 검수 단계는 통과한 항목만 남겨야 하는데, 같은 키로 통과 기사만 반환하면 기존 목록에 계속 추가될 뿐 탈락 기사를 제거할 수 없다. 그래서 새 키 `verified`에 저장한다.

| State 키 | 역할 |
| --- | --- |
| `drafted` | 취재 워커들이 생성한 결과를 모아 둔다 |
| `verified` | 검수를 통과한 결과만 저장한다 |

키가 늘어도 각 노드는 자신이 바꾼 키만 반환하므로 다른 노드를 고칠 필요가 없다.

> 결과를 모으는 키와 통과 결과를 담는 키를 분리한다.

### 검수는 반드시 병렬이어야 하는가

기사별로 독립적이라 기술적으로는 병렬이 가능하지만, **할 수 있다는 것과 해야 한다는 것은 다르다.** 다섯 건 정도면 한 노드에서 차례로 검수한다. 구현이 단순하고, 동시 호출 부담이 줄며, 현재 처리량에는 순차로도 충분하다.

## 8. 발행 노드와 매일 아침 자동 실행 (publish)

```
수집 → 선정 → 취재·요약 → 검수 → 발행
```

### 발행 노드의 성격

수집·요약은 내부 데이터를 처리하지만 발행은 결과를 외부로 보낸다. 한 번 보내면 다른 사람 화면에 실제로 표시되므로 주의해야 한다.

- 검수를 통과한 기사 수만큼 그대로 발행한다.
- 통과한 기사가 없으면 `오늘은 조용합니다` 안내를 보낸다. 아무것도 안 보내면 정상 실행인지 중간에 멈췄는지 구분할 수 없기 때문이다.
- 기사가 부족해도 추가 수집이나 재시도를 하지 않는다.

### 발행 방법 비교

| 방법 | 특징 |
| --- | --- |
| 이메일 (SMTP, Resend 등) | HTML 메일, 정식 뉴스레터에 적합. 도메인 인증·발송 설정 필요 |
| Slack 웹훅 | 팀이 Slack을 쓰면 편리. 관리자 승인이 필요할 수 있음 |
| **Discord 웹훅 (선택)** | 웹훅 URL로 JSON을 보내 게시. 설정이 간단하고 Embed로 보기 좋게 구성. 구독자 관리·열람 통계 없음 |
| 정적 페이지 (GitHub Pages 등) | 링크 공유·과거 글 보관에 좋음. 새 글 알림 없음 |

빠르게 결과를 받아 보는 것이 목적이라 Discord를 골랐다. 실제 운영에는 이메일이 더 맞을 수 있으며, 그때는 `publish` 노드만 바꾸면 된다.

### Discord 웹훅 설정

웹훅(Webhook)은 특정 URL로 요청을 보내 외부 서비스에 메시지를 전달하는 방식이다.

1. Discord 서버를 만든다.
2. 채널을 만든다. (예: `#브리핑`)
3. 채널 설정에서 **연동 → 웹후크 → 새 웹후크**로 이동한다.
4. 웹훅 이름을 정하고 URL을 복사한다.
5. URL을 환경변수나 키 설정에 등록한다.

URL 형태는 `https://discord.com/api/webhooks/<숫자>/<긴문자열>`이다.

```bash
export DISCORD_WEBHOOK_URL="<WEBHOOK_URL>"
```

> 웹훅 URL 자체가 인증 수단이다.

URL을 아는 사람은 누구나 채널에 메시지를 보낼 수 있다. 공개 저장소에 올리지 말고, 노트북·코드 공유 시 노출되지 않게 하며, 유출되면 기존 웹훅을 삭제하고 새로 만든다. 또한 Discord 웹훅에는 중복 방지 기능이 없어 두 번 보내면 두 번 올라간다.

### 응답 상태 코드

| 코드 | 의미 |
| --- | --- |
| `204` | 요청 성공, 응답 본문 없음 |
| `400` | 보낸 JSON 형식이 올바르지 않음 |
| `401` | 인증 관련 오류 |
| `404` | 웹훅 URL이 잘못됐거나 삭제됨 |
| `429` | 요청 한도 초과. 응답의 재시도 시간을 확인 |

> `204`는 실패가 아니다. 성공했지만 돌려줄 본문이 없다는 뜻이다. 채널에 메시지가 올라왔는지로 확인한다.

### Embed로 메시지 구성

`content`는 하나의 긴 텍스트라 기사 여러 건을 이어 붙이면 읽기 어렵다. Embed는 제목·본문·링크를 카드 형태로 나눠 보여 준다.

| 생성 항목 | Embed 위치 |
| --- | --- |
| `headline` | 제목(`title`) |
| `summary` | 본문(`description`) |
| `why` | 본문 아래 강조 문구 |
| 기사 링크 | URL 또는 링크 필드 |

교안이 제시한 제한은 메시지당 Embed 최대 10개, 제목 최대 256자, 본문 최대 4,096자, 전체 Embed 텍스트 합계 최대 6,000자다. 넘으면 요청이 실패할 수 있으므로 발행 전에 길이를 확인하고 줄인다.

### Dry Run

`dry_run`은 실제로 보내지 않고 전송할 내용을 출력해 확인하는 시험 실행 모드다. 메시지 구조를 미리 확인하고, 형식을 고칠 때 시험 메시지가 쌓이지 않으며, 자동 실행 중 실수로 발행하는 것을 막는다. `dry_run=True`면 출력만, `False`면 실제 발행이다.

환경변수 `DRY_RUN`의 기본값은 `"1"`(시험 실행)이고 `"0"`이 실제 발행이다.

```python
os.environ["DRY_RUN"] = "0"
```

> 안전한 기본값을 쓰면 설정을 깜빡했을 때 실수로 발행되는 위험이 줄어든다.

### 필요한 데이터만 전달하기

State에는 `body`(원문 긴 본문)처럼 발행에 필요 없는 정보도 있다. 다 보내면 메시지가 불필요하게 길어지고, Discord 제한을 넘을 수 있으며, 무엇을 발행하는지 불분명해진다. 그래서 `publish`는 `verified`에서 필요한 항목만 골라 새 딕셔너리를 만든다.

> 내부 처리에 필요한 데이터와 외부 발행에 필요한 데이터는 다르다.

### GitHub Actions로 자동 실행

매일 아침 누가 노트북을 켜지 않아도 돌아가야 한다. GitHub Actions는 저장소에 정의한 작업을 GitHub 서버에서 자동 실행하는 기능으로, 별도 서버 운영이 필요 없고, 실행 기록·로그를 웹에서 보며, 예약 실행과 수동 실행이 모두 된다. 교안은 공개 저장소에서 무료라고 설명하지만 실제 사용량과 요금 조건은 계정과 GitHub 정책에 따라 확인해야 한다.

### 노트북을 파이썬 파일로 옮기기

```
my-newsletter/
├── graph.py
├── run.py
├── requirements.txt
└── .github/
    └── workflows/
        └── daily.yml
```

| 파일 | 역할 |
| --- | --- |
| `graph.py` | State, 노드 다섯 개, `build()`, `run()` 등 파이프라인 구성 |
| `run.py` | `graph.py`를 불러와 파이프라인을 한 번 실행 |
| `requirements.txt` | 필요한 라이브러리 목록 |
| `daily.yml` | Actions가 언제 무엇을 실행할지 정의 |

옮길 때 주의할 점은 다음과 같다. 정의를 빠뜨리면 `NameError`가 난다.

1. `!pip install` 같은 노트북 전용 명령은 지우고 라이브러리는 `requirements.txt`에 적는다.
2. `build()`, `Brief`처럼 여러 번 정의한 것은 마지막 정의를 남긴다.
3. 정의가 사용 위치보다 먼저 나오게 순서를 맞춘다.
4. `Pick`, `Shortlist`, `Draft`, `SYS`처럼 다른 셀에서 정의한 항목도 빠뜨리지 않는다.

### run.py와 진입점(Entry Point)

```python
import os
import sys
from graph import run

if __name__ == "__main__":
    if "--dry-run" in sys.argv:
        os.environ["DRY_RUN"] = "1"

    out = run()

    for line in out["log"]:
        print(line)
```

**진입점**은 프로그램 실행이 시작되는 지점이다. `if __name__ == "__main__":` 아래 코드는 파일을 직접 실행할 때만 돈다. `import graph`로 구성 요소를 가져오기만 할 때 뉴스레터가 의도치 않게 발행되는 일을 막고, `python run.py`로 실행할 때만 파이프라인이 돈다. `print(line)` 로그는 Actions 실행 기록에서 볼 수 있다.

### API 키는 GitHub Secrets에

API 키나 웹훅 URL을 코드에 적으면 안 된다. 저장소의 `Settings → Secrets and variables → Actions`에서 `New repository secret`으로 등록한다.

| 이름 | 값 |
| --- | --- |
| `OPENAI_API_KEY` | 발급받은 OpenAI API 키 |
| `DISCORD_WEBHOOK_URL` | Discord 웹훅 URL |

등록한 Secret은 다시 열어 보는 것이 아니라 덮어쓰는 방식으로 관리된다. 키가 한 번 커밋되면 커밋을 지워도 Git 이력에 남을 수 있으므로 안전하다고 여기면 안 된다. GitHub는 로그에 그대로 찍힌 Secret을 가려 주지만 변형해 출력하면 가려지지 않을 수 있으므로 비밀값을 로그에 출력하지 않는다.

### daily.yml 워크플로

경로는 `.github/workflows/daily.yml`이다.

{% raw %}
```yaml
name: 매일 브리핑

on:
  schedule:
    - cron: "30 22 * * *"
  workflow_dispatch:
    inputs:
      dry_run:
        description: "발행하지 않고 로그만 남기기"
        type: boolean
        default: false

jobs:
  publish:
    runs-on: ubuntu-latest
    timeout-minutes: 20

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - run: pip install -r requirements.txt

      - name: 브리핑 생성·발행
        run: python run.py ${{ inputs.dry_run && '--dry-run' || '' }}
        env:
          OPENAI_API_KEY: ${{ secrets.OPENAI_API_KEY }}
          DISCORD_WEBHOOK_URL: ${{ secrets.DISCORD_WEBHOOK_URL }}
          TZ: Asia/Seoul
```
{% endraw %}

| 설정 | 의미 |
| --- | --- |
| `schedule` / `cron: "30 22 * * *"` | UTC 매일 22:30 = 한국시간 다음 날 오전 7시 30분(UTC가 9시간 느림). 예약 실행은 정각 시작이 보장되지 않고 지연될 수 있다 |
| `workflow_dispatch` | Actions 탭의 `Run workflow` 버튼으로 수동 실행. `dry_run` 옵션으로 다음 날 아침을 기다리지 않고 시험해 볼 수 있다 |
| `timeout-minutes: 20` | 응답을 기다리며 너무 오래 도는 것을 막고, 넘으면 중단 |
| `env` + Secrets | 키와 URL을 코드에 적지 않고 환경변수로 전달 |

> 자동 실행은 실행 시각뿐 아니라 수동 실행, 실행 시간 제한, 비밀값 관리까지 함께 설정해야 한다.

### 한 회차의 실행 흐름

1. `cron` 시각이 되거나 `Run workflow`로 시작한다.
2. GitHub 서버에 실행 환경을 준비하고 저장소를 내려받는다.
3. `requirements.txt`의 라이브러리를 설치한다.
4. Secrets를 환경변수로 전달한다.
5. `run.py`가 파이프라인을 실행한다.
6. 검수된 기사를 Discord로 발행한다.
7. 실행 로그가 Actions에 남는다.

확인 장소는 **Discord 채널**(메시지 도착 여부)과 **Actions 실행 페이지**(성공·실패와 로그)다. 일회성 실행 환경 안에서 만든 파일은 환경과 함께 사라질 수 있으므로 결과를 확인할 경로를 따로 마련해야 한다.

### 실제로 실행해 보기

1. 필요한 파일을 커밋·푸시하고 저장소의 `Actions` 탭으로 간다.
2. 왼쪽에서 `매일 브리핑` 워크플로를 고른다.
3. `Run workflow`를 누르고 `dry_run`을 체크해 실행한다.
4. 실행 기록에서 `브리핑 생성·발행` 단계 로그를 확인한다.
5. 문제가 없으면 `dry_run`을 끄고 다시 실행한다.
6. Discord 채널에 브리핑이 왔는지 확인한다.

> 퀴즈: `workflow_dispatch`를 넣는 이유는? → 수동으로 즉시 실행해야 수정 사항을 빠르게 테스트할 수 있다. `dry_run`으로 확인한 뒤 실제 발행으로 넘어간다.

### 자동 실행이 멈추지 않았는지 확인하기

1. **실패 알림**: Actions 실패 알림을 이메일로 받는다.
2. **하트비트(Heartbeat)**: 기사가 0건이어도 `오늘은 조용합니다`를 보낸다. 정해진 시각에 정상 작동을 알리는 신호로, 도착하면 최소한 발행 단계까지 돌았다는 뜻이고, 안 오면 파이프라인이 멈췄을 수 있다.
3. **실행 기록 확인**: Actions 탭의 성공·실패 표시와 로그를 본다.

추가로, 예약 실행은 워크플로 파일이 기본 브랜치에 있어야 하며, 교안에 따르면 공개 저장소가 60일간 활동이 없으면 예약 워크플로가 비활성화될 수 있으니 안내 메일과 Actions 탭을 확인한다.

> 자동화는 실행 코드를 만드는 것에서 끝나지 않는다. 정상 실행 여부를 확인할 방법까지 만들어야 완성이다.

| 용어 | 의미 |
| --- | --- |
| Webhook | 특정 URL로 요청을 보내 외부 서비스에 작업을 전달하는 방식 |
| HTTP Status Code | 요청 처리 결과를 알려 주는 상태 코드 |
| Embed | Discord에서 제목·본문·링크를 카드로 보여 주는 기능 |
| `dry_run` | 실제 전송 없이 결과를 확인하는 시험 실행 모드 |
| Scheduler / `cron` | 정해진 시각에 작업을 실행하는 장치 / 반복 일정 표현 형식 |
| `workflow_dispatch` | 워크플로 수동 실행 설정 |
| `timeout-minutes` | 작업 최대 실행 시간 |
| Secrets | 비밀값을 안전하게 보관하는 기능 |
| Entry Point | 프로그램 실행이 시작되는 지점 |
| Heartbeat | 시스템이 정상 작동 중임을 알리는 신호 |

## 9. 정리와 회고

다섯 개의 빈 노드를 먼저 만들고 실제 코드를 하나씩 채웠다. 노드 사이 데이터는 State로 정의했고, 수정할 때마다 전체를 실행해 단계별 처리 건수를 확인했다. 각 단계에서 여러 방법을 비교해 목적에 맞는 것을 고른 과정이 중요했다.

| 단계 | 핵심 |
| --- | --- |
| 뼈대 | State(공통 데이터), 노드(작업 함수), 로그(실행 기록)로 전체 흐름부터 확인 |
| 수집 | 본문 확보·최근 게시·자동 접근 세 관문, RSS 외 원문 본문 추출, 실패 소스 기록으로 조용한 실패 방지 |
| 선별 | 점수 매기기보다 상대 순위 문제. 2단계 상대평가로 예선 통과를 넉넉히 잡음 |
| 요약·검수 | `headline`/`summary`/`why` 구조화 출력으로 항목별 기준 적용. 프롬프트는 정확성을 보장하지 않으므로(언어 지시 미준수, 숫자 변환 오탐) 별도 검수하고 검수가 오류를 잡는지도 확인 |
| 발행·자동 실행 | Discord 웹훅, GitHub Actions, `dry_run`, 하트비트로 '소식이 없어서 조용함'과 '멈춰서 안 옴'을 구분 |

### 남아 있는 한계와 개선 방향

| 한계 | 개선 방향 |
| --- | --- |
| 평가셋(Evaluation Set)이 없다. 몇 건을 눈으로만 봐서 수정 전후 비교나 품질 유지 확인이 어렵다 | 같은 입력으로 결과를 비교할 평가셋을 만든다 |
| 사람의 발행 전 승인(Human-in-the-loop)이 없고, 난이도와 무관하게 모든 단계에서 같은 모델을 쓴다 | 발행 전 사람 승인 단계 추가, 작업별 적절한 모델 선택 검토 |
| 실행 기록이 누적되지 않아 매번 해당 실행 로그를 열어 봐야 한다 | 실행 결과를 지속 저장해 소스별·단계별 성과를 비교 |
| 독자·중요도 기준이 프롬프트에 직접 들어 있어 설정과 코드가 섞여 있다 | 분야별 기준을 코드와 분리 |
| 수집이 RSS에 의존해 RSS 없는 분야에 적용하기 어렵다 | 다른 수집 방식 추가 (교안은 스크래핑 단계를 다시 구현해야 한다고 설명) |

| 용어 | 의미 |
| --- | --- |
| Evaluation Set | 결과 품질을 평가·비교하기 위해 준비한 입력과 기준 데이터 |
| Human-in-the-loop | 사람의 검토나 승인을 작업 흐름에 포함하는 방식 |

### 회고: 내 분야로 옮긴다면

질문은 "오늘 만든 다섯 단계를 내 분야로 옮긴다면 가장 크게 고칠 단계와 그대로 쓸 단계는?"이다.

AI·음향 분야 자료를 정리하는 서비스에 적용한다면 가장 크게 바꿔야 할 단계는 **수집과 선별**이다. 뉴스는 RSS로 제목과 본문을 가져올 수 있지만 음향 분야는 공식 문서, 기술 자료, 프로그램 업데이트 등 자료 종류가 다양하고, 무엇이 중요한지 판단하는 기준도 일반 뉴스와 다르다. 반면 **요약·검수·발행**의 기본 구조는 그대로 쓸 수 있다. 정해진 형식으로 요약하고, 원문 근거를 검수하고, 통과한 결과를 원하는 채널로 보내는 흐름은 다른 분야에도 통한다.

> 자동화 프로그램은 만드는 것에서 끝나지 않는다. 결과를 평가하고 오류를 확인하며 필요에 따라 개선할 수 있어야 한다.
