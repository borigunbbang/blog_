모델이 도구를 호출하는 구조와 MCP를 배우고, Colab MCP를 직접 연결해 본 뒤 작업 방식을 Skill로 남기고 내 작업에 맞게 바꾸는 내용을 8개 강의 순서대로 정리했다.

## 1. [이론] 에이전트가 도구를 쓰는 방식과 MCP

### 1.1 오늘 할 일

금요일 오후, 팀에서 이런 부탁을 받았다고 하자.

> 이번 주 프로젝트 진행 상황을 정리해 주세요. 다음 주에 누가 무엇을 챙겨야 하는지도 알고 싶어요.

Claude Code는 터미널에서 AI와 대화하며 파일 작업과 도구 실행을 맡기는 앱이다. AI는 보고서를 읽기 좋게 구성하고 문장을 다듬는 데 익숙하다. 그런데 빠진 것이 있다. **우리 팀에서 이번 주에 실제로 무슨 일이 있었는지**다. 누가 어떤 기능을 만들었는지, 배포까지 끝났는지, 다른 팀의 답변을 기다리고 있는지는 요청 문장만으로 알 수 없다.

업무 기록을 읽을 때도, Colab 노트북에서 코드를 실행할 때도 모델은 도구에 작업을 요청하고 그 결과를 받는다. 이 노드는 업무 기록을 읽는 예로 이 구조를 보고, 실습에서는 Colab MCP로 같은 구조를 직접 확인한다.

1. Colab MCP를 설치해 바로 써 본다.
2. 도구 목록, 호출 기록, 실제로 실행된 곳을 펼쳐 MCP가 어떻게 동작하는지 파헤친다.
3. 반복되는 작업 방식을 작업 지침인 Skill로 남기고 내 방향에 맞게 고친다.

### 1.2 기록을 전달하는 두 장면

| 장면 | 방법 | 맞는 경우와 한계 |
|---|---|---|
| 붙여 넣기 | 파일 내용을 대화창에 직접 붙여 넣는다 | 기록이 몇 줄이고 한 번만 정리하면 될 때 충분하다. 하지만 매주 반복하거나 기록이 공유 표나 여러 프로젝트에 나뉘어 있으면 자료를 모으는 작업부터 반복해야 한다 |
| 조회 기능 제공 | AI에게 "필요한 주의 기록을 가져오는 기능"을 준다. 사용자는 보고 싶은 주를 말하고, 프로그램이 그 주의 기록을 읽으며, AI는 읽어 온 기록을 바탕으로 답한다 | 지난주와 이번 주를 비교하는 요청도 처리할 수 있다 |

> 중요한 변화는 AI가 더 그럴듯한 문장을 쓰게 된 것이 아니라, **대화 밖의 자료를 실제로 가져오는 동작**이 생겼다는 것이다.

그렇다면 AI는 이런 조회 기능을 어떻게 알고 쓰게 될까?

### 1.3 도구 정의: 이름·설명·입력 스키마

도구를 쓰려면 실제로 실행할 기능과, 모델에게 줄 도구 정의가 함께 있어야 한다.

> 💡 **도구 정의(tool definition)**: 모델이 도구를 고를 때 읽는 이름, 설명, 입력 스키마의 묶음.
>
> 💡 **입력 스키마(input schema)**: 도구가 받을 입력의 이름과 형식, 허용하는 값을 정한 규격.

모델은 파일을 읽는 코드를 받는 것이 아니라 아래와 같은 도구 정의를 받는다. 표의 "필요한 입력"과 "준비된 값"이 입력 스키마에 해당한다.

| 도구 정의 항목 | 예시 도구의 내용 |
|---|---|
| 이름 | `get_weekly_records` |
| 설명 | 지정한 주의 가상 제품팀 업무 기록을 읽는다. 보고서 작성이나 완료·진행·위험 판정은 하지 않는다 |
| 필요한 입력 | `week`: 조회할 주를 나타내는 글자로 된 값 |
| 준비된 값 | `week-one`, `week-two` |
| 반환할 자료 | 주차, 팀 이름, 기간 시작일, 보고 기준일, 업무 기록 목록 |

도구 정의는 조회 기능의 **사용법**일 뿐, 업무 기록 자체가 들어 있는 것은 아니다. "기록을 읽을 수 있다"는 정의만 받은 상태에서는 TASK-102의 개발이 끝났는지 아직 알 수 없다. 실제 내용은 조회한 뒤에 도착한다.

### 1.4 모델의 도구 호출과 앱의 실행

사용자가 "첫째 주 기록을 읽고 진행 상황을 알려 줘"라고 요청했다고 하자. AI 앱은 사용자 요청과 사용 가능한 도구의 정의를 모델에게 전달한다. 모델이 만드는 응답은 사용자에게 보여 줄 문장일 수도 있고, 도구 이름과 입력을 담은 요청일 수도 있다. 모델이 만드는 이 요청을 **도구 호출(tool call)**이라고 한다.

다음은 설명용 메시지 예시다(특정 앱의 실제 실행 로그는 아니며, 앱마다 표시 항목과 화면은 다를 수 있다).

```
[모델에게 전달]
사용자 요청: 첫째 주 기록을 읽고 진행 상황을 알려 줘.
도구 정의: get_weekly_records는 지정한 주의 업무 기록을 읽음
필요한 입력: week
준비된 값: week-one, week-two

[모델이 생성한 도구 호출의 예]
사용할 도구: get_weekly_records
이번 입력: week = week-one

[조회 프로그램이 반환한 기록의 일부]
업무: TASK-102 · 로그인 안내 문구 개선
상태: 개발 완료
배포일: 기록 없음
메모: 코드 작성은 끝났으며 다음 배포를 기다린다.
```

도구 호출만 만들어진 시점에는 아직 기록을 읽지 않았다. 앱이 그 도구 호출을 실제 조회 프로그램의 실행으로 연결하고, 반환된 결과를 모델에게 전달해야 한다.

요청에서 답변까지의 흐름을 표로 옮기면 다음과 같다. 등장하는 것은 사용자, AI 앱(요청·실행·결과를 잇는 쪽), 모델(도구 선택·답변 생성), 조회 프로그램(실제 업무 기록 읽기) 넷이다.

| 단계 | 보내는 쪽 → 받는 쪽 | 오가는 것 |
|---|---|---|
| 1 | 사용자 → AI 앱 | 첫째 주 상황 요청 |
| 2 | AI 앱 → 모델 | 요청 + 도구 정의 |
| 3 | 모델 → AI 앱 | 도구 호출(도구와 입력을 선택) |
| 4 | AI 앱 → 조회 프로그램 | 조회 실행 요청: `get_weekly_records`, `week = "week-one"` |
| 5 | 조회 프로그램 → AI 앱 | 첫째 주 기록 반환 |
| 6 | AI 앱 → 모델 | 도구 결과 전달 |
| 7 | 모델 → AI 앱 | 기록에 근거한 답변 |
| 8 | AI 앱 → 사용자 | 답변 표시 |

> **핵심: 모델은 도구 호출을 만들고, 조회 프로그램이 실제 기록을 읽는다.**

이 표는 한 번의 조회로 답할 수 있는 경우다. 실제 에이전트는 필요한 자료에 따라 추가 조회를 이어 갈 수 있다. 프로그램이 돌려주는 것은 조회 결과이지 최종 평가가 아니다. 모델은 반환된 메모를 읽고 "로그인 안내 문구 개선은 코드 작성이 끝났지만 아직 배포를 기다리고 있습니다"처럼 답변을 구성한다. 도구 정의만 읽었을 때와 달리, 이제 실제 업무 기록에 근거한 문장을 만들 수 있다.

### 1.5 모델별 도구 호출 형식의 차이

모델마다 도구 이름과 입력을 출력하는 방식은 다를 수 있다. 앱은 사용하는 모델에 맞게 그 차이를 맞춰 주고, 도구 호출을 실제 기능의 실행으로 연결한다. MCP를 쓴다고 모든 모델의 호출 표현이나 도구 선택이 같아지는 것은 아니다.

### 1.6 MCP의 정의와 세 역할

기록을 조회하는 기능을 다른 AI 앱에서도 쓰려면 어떻게 해야 할까? 앱마다 기록 파일을 읽는 코드를 새로 만들면, 저장 위치나 조회 조건이 바뀔 때마다 여러 구현을 고쳐야 한다. 대신 기록 프로그램이 제공하는 기능과 입력 스키마를 공통 방식으로 알려 주고, 앱들이 그 방식에 맞춰 호출하게 할 수 있다. 이 연결 약속이 **MCP(Model Context Protocol)**다.

| 용어 | 뜻 |
|---|---|
| 프로토콜 | 프로그램들이 메시지를 주고받을 때 따르는 규칙 |
| MCP | 앱과 도구를 제공하는 프로그램 사이의 공통 약속. 기록을 어느 파일에서 읽을지는 여전히 기록 프로그램의 몫이다 |
| 컨텍스트(context) | 모델이 이번 응답을 만들 때 참고하도록 제공받는 정보. MCP로 연결한 도구 정의가 컨텍스트에 들어온다 |

연결했다고 모델이 업무 기록을 이미 읽은 것은 아니다. 실제 실행은 서버가 맡고, 앱이 모델의 요청과 서버의 결과를 이어 준다.

```
호스트 (Claude Code / OpenCode) — 대화, 모델 사용, 연결과 실행 관리
 ├─ 업무 기록 서버용 클라이언트 ──MCP 메시지──▶ weekly-records 서버 (주차에 맞는 기록 파일 읽기)
 └─ 문서 서버용 클라이언트     ──MCP 메시지──▶ 문서 서버 (확장 예)
```

- 클라이언트는 **서버 하나당 하나씩** 생긴다.
- 클라이언트와 서버가 같은 컴퓨터에서 실행되어도 이 구분은 그대로다. "어디에서 실행되는가"와 "어떤 역할을 하는가"는 서로 다른 질문이기 때문이다.

| 역할 | 이번 이야기의 구체적인 대상 | 하는 일 |
|---|---|---|
| 호스트 | Claude Code처럼 사용자가 대화하는 AI 앱 | 모델에게 도구 정의와 실행 결과를 전달하고, 필요한 실행 허용을 처리한다 |
| 클라이언트 | 호스트 내부의 MCP 연결 구성 요소 | 연결된 서버에 요청을 보내고 결과를 받는다 |
| 서버 | 업무 기록을 읽는 weekly-records 같은 프로그램. 실습에서는 colab-mcp | 도구를 제공하고, 실제 작업을 실행해 결과를 돌려준다 |

### 1.7 MCP로 얻는 것: 여러 앱, 원격 서버

- 한 번 만든 조회 기능을 같은 약속을 지원하는 여러 앱에서 쓸 수 있다. 앱마다 서버를 등록하는 방법은 달라도 기록을 읽는 코드를 다시 만들 필요는 없다.
- 기록의 저장 위치가 바뀌어도 도구의 이름, 입력 스키마, 반환 형식이 같다면 서버의 조회 코드만 고쳐 계속 제공할 수 있다.
- 서버는 내 컴퓨터에서 실행할 수도 있고 원격 컴퓨터에 배포해 둘 수도 있다. 두 경우 모두 앱은 기능의 사용법을 알고, 입력을 보내 결과를 받는다.

원격 서버를 쓸 수 있는 이유는 앱이 서버의 구현 코드를 직접 실행할 필요가 없기 때문이다. 앱은 도구 정의를 받아 호출하고, 서버가 보내 준 결과를 읽으면 된다. 구현 코드와 원본 자료는 서버 쪽에 남고, 요청에 대한 결과만 앱으로 전달된다. 원격 서버를 쓰려면 접속할 주소와 접근 권한이 있어야 한다.

| 서버 위치 | 앱에 알려 줄 연결 정보 | 실행되는 곳 |
|---|---|---|
| 로컬(내 컴퓨터) | 서버를 시작할 실행 명령 | 앱이 내 컴퓨터에서 서버 프로그램을 실행한다 |
| 원격(다른 컴퓨터) | 서버의 URL | 이미 실행 중인 원격 서버에 네트워크로 요청한다 |

> 원격으로 기능을 제공하는 일 자체는 MCP만의 기능이 아니다. MCP가 더하는 이점은 **여러 앱이 같은 약속으로 그 기능을 쓸 수 있다**는 것이다.

### 1.8 도구가 많아지면

도구 정의도 컨텍스트를 차지한다. 도구가 많아지면 호스트는 필요한 도구를 먼저 찾고 그 도구의 정의만 읽게 하는 기능을 둘 수 있다. Claude Code의 **Tool Search**가 그 예다. Tool Search는 사용하지 않을 도구의 정의를 줄이는 기능이지, 호출해서 받은 업무 기록 자체를 줄여 주는 기능은 아니다.

> **확인 질문**: 1.4의 설명용 메시지에서 "개발 완료"는 도구 정의에서 알게 된 내용일까, 실행 결과에서 알게 된 내용일까?
>
> **답**: 실행 결과, 즉 조회 프로그램이 반환한 기록에서 알게 된 내용이다. 도구 정의에는 `get_weekly_records`가 지정한 주의 기록을 읽는다는 사용법만 있고, TASK-102의 상태는 들어 있지 않다.

## 2. [실습] Colab MCP 설치하고 바로 써 보기

Claude Code에 계산을 부탁하고, Colab 노트북에 코드와 출력이 생기는지 확인한다.

1. 2.2에서 Colab MCP를 등록한다.
2. 2.3에서 노트북 연결을 허용한다.
3. 2.4에서 8, 10, 12의 평균을 구해 본다.

### 2.1 사전 준비: 실습 폴더와 준비물

| 준비물 | 설명 |
|---|---|
| Colab | 브라우저에서 Python 코드를 실행하는 노트북 |
| Colab MCP | 연결하면 Claude Code에서 노트북의 셀을 추가하고 실행할 수 있다 |
| Claude Code | 내 컴퓨터에서 실행할 수 있어야 한다 |
| uv | Python 도구를 설치하고 실행하는 프로그램. 설치하면 `uvx`도 함께 준비된다 |
| Git | 저장소의 프로그램을 가져오는 도구 |
| Chrome | Google 계정에 로그인해 둔다 |

uv나 Git이 없다면 각 공식 설치 안내에서 운영체제에 맞게 설치한 뒤 터미널을 다시 연다. 설치 여부는 Claude Code에 "uv와 Git이 설치되어 있는지 확인해 줘. 없으면 설치해 줘."처럼 요청해 확인할 수도 있다(새로 설치했다면 터미널을 다시 연다).

터미널에서 빈 실습 폴더를 만든다(macOS 터미널과 Windows PowerShell 공통, 한 줄씩 실행). 이후 Claude Code는 이 폴더에서 쓴다.

```bash
mkdir colab-practice
cd colab-practice
```

### 2.2 Colab MCP 등록하기

이 실습 폴더에서 쓸 MCP 서버로 등록한다. 아래 명령은 Claude Code가 내 컴퓨터에서 `uvx`로 Colab MCP 서버를 시작하도록 지정한다. 같은 폴더의 터미널에서 한 줄로 실행하며, macOS와 Windows에서 같다.

```bash
claude mcp add --transport stdio --scope project colab-mcp -- uvx --python 3.13 git+https://github.com/googlecolab/colab-mcp
```

| 부분 | 뜻 |
|---|---|
| `claude mcp add` | Claude Code에 MCP 서버를 등록한다 |
| `--transport stdio` | 표준입출력으로 통신하는 로컬 서버 |
| `--scope project` | 이 실습 폴더(프로젝트)에서만 쓰도록 등록한다 |
| `colab-mcp` | 등록할 서버 이름 |
| `--` 뒤쪽 | 서버를 시작할 실행 명령. `uvx`가 GitHub 저장소에서 Colab MCP를 받아 실행한다 |
| `--python 3.13` | 내 컴퓨터에서 MCP 서버를 실행할 Python 버전. 없으면 uvx가 준비한다 |

Claude Code에 이 명령을 보여 주고 현재 실습 폴더에 등록해 달라고 부탁해도 된다. 등록이 끝나면 다음 순서로 확인한다.

1. 같은 폴더에서 `claude`를 실행해 Claude Code를 시작한다.
2. 이 폴더를 신뢰할지 묻는 화면이 먼저 나오면 신뢰를 선택한다.
3. 프로젝트의 MCP 서버를 사용해도 되는지 묻는 화면에서 colab-mcp를 승인한다.
4. 대화 입력창에 `/mcp`를 입력하고 colab-mcp가 연결된 상태인지 확인한다.

### 2.3 노트북 연결 허용하기

Claude Code에 "Colab 노트북에 연결해 줘."라고 요청한다. Chrome에 Colab이 열리면 화면에 뜨는 "연결 허용" 창에서 **60초 안에** 연결을 허용한다.

- 연결 주소에는 연결용 토큰이 들어 있으므로 채팅이나 공유 문서에 붙이지 않는다.
- 연결에 실패하면 Claude Code에 연결을 다시 요청하고, 그래도 안 되면 Claude Code를 다시 시작한다.

### 2.4 평균을 구하고 노트북에서 확인하기

연결된 Colab 화면을 열어 둔 채 Claude Code에 요청한다.

```
8, 10, 12의 평균을 구하는 코드 셀을 추가하고 실행해 줘.
```

- 도구 실행 승인을 요청하면 셀 추가와 실행 요청인지 확인하고 허용한다.
- 노트북 연결 허용과 별도로, 계산을 맡는 실행 환경인 **런타임**도 연결되어 있어야 한다. 연결되지 않았다면 Colab 화면의 "연결" 버튼을 누른 뒤 다시 실행을 요청한다.
- Claude Code의 답변만 보지 말고 Colab 노트북으로 돌아가 눈으로 확인한다.

관찰할 것:

- 코드 셀에 입력값 8, 10, 12와 평균을 구하는 계산이 있다.
- 그 셀 아래에 출력 10.0이 생겼다. 출력에 "평균:" 같은 설명이 붙어 있어도 값이 10.0이면 된다.

**완료 조건**: 노트북에 평균을 구한 코드 셀과 출력 10.0이 함께 있다. 왜 이렇게 되는지는 3강과 4강에서 하나씩 펼쳐 본다.

## 3. [실습] 파헤치기: 모델이 본 것과 한 일

### 3.1 연결 뒤에 달라진 도구 목록

2강에서 만든 평균 계산 셀을 그대로 두고, 이번에는 Claude Code의 도구 목록과 호출 기록을 열어 모델이 어떤 안내를 보고 무엇을 요청했는지 확인한다. Claude Code에서 `/mcp`를 입력하고 colab-mcp의 도구 목록을 연다.

노트북 연결 전에는 연결을 여는 `open_colab_browser_connection` 하나만 보인다. 이 도구에는 보낼 입력이 없다. 연결을 마쳤다면 아래 일곱 도구를 찾아본다(비교하려고 연결을 끊을 필요는 없다).

| 이름 | 하는 일 | 필요한 입력 |
|---|---|---|
| `add_code_cell` | 지정한 위치에 코드 셀을 넣고 새 셀 ID를 돌려준다 | cellIndex, language(python·r·julia), code |
| `add_text_cell` | 지정한 위치에 마크다운을 쓸 수 있는 텍스트 셀을 넣는다 | cellIndex, content |
| `get_cells` | 노트북의 셀을 읽는다 | 선택: cellIndexStart, cellIndexEnd, includeOutputs |
| `run_code_cell` | 지정한 코드 셀을 실행하고 출력을 돌려준다 | cellId |
| `update_cell` | 지정한 셀의 내용을 새 내용으로 덮어쓴다 | cellId, content |
| `move_cell` | 지정한 셀을 다른 위치로 옮긴다 | cellId, cellIndex |
| `delete_cell` | 지정한 셀을 삭제한다 | cellId |

| 입력 이름 | 뜻 |
|---|---|
| cellIndex | 셀을 넣을 위치(몇 번째 자리인지) |
| cellId | 특정 셀을 가리키는 ID |
| code | 코드 내용 |
| content | 셀에 넣을 내용 |

화면에서는 도구 이름 앞에 서버 이름이 붙어 `mcp__colab-mcp__add_code_cell`처럼 보일 수 있다.

목록에서 `add_code_cell`과 `run_code_cell`의 설명을 열고 필요한 입력이 왜 다른지 비교해 본다. 아직 없는 셀을 만들 때는 위치와 내용이 필요하지만, 이미 있는 셀을 실행할 때는 어느 셀인지만 알려 주면 된다.

### 3.2 연결 뒤 도구가 늘어나는 이유

1. 노트북에 연결되면 서버가 "도구 목록이 바뀌었다"고 앱에 알린다.
2. 앱은 새 목록을 받아 모델이 쓸 수 있는 도구로 알린다.
3. Claude Code는 기본으로 도구 이름을 먼저 컨텍스트에 넣고, 쓰려는 도구의 설명과 입력 스키마는 필요할 때 불러온다(1.8의 Tool Search).

1.3에서 본 도구 정의가 바로 이 목록에 있는 이름, 설명, 입력 스키마다. 모델은 이제 "셀을 추가할 수 있다", "실행하려면 셀 ID가 필요하다"는 정보를 보고 요청을 만들 수 있다.

> 도구가 늘었다고 노트북의 내용까지 읽은 것은 아니다. 내용은 `get_cells` 같은 도구를 호출해 결과로 받아야 알 수 있다.

### 3.3 평균 계산의 호출 기록 펼치기

2강의 "8, 10, 12의 평균을 구하는 코드 셀을 추가하고 실행해 줘" 요청으로 돌아간다. Claude Code의 최종 답변 앞에는 도구 사용이 한 줄로 접혀 표시될 수 있다. **Ctrl+O**를 누르면 기록 보기가 열려 접혀 있던 MCP 호출의 입력과 결과가 펼쳐진다. 닫을 때는 **Esc**를 누른다.

> 💡 **호출 기록**: 어느 도구에 어떤 값을 보냈고 무엇을 받았는지 남긴 기록. 이름, 보낸 입력, 받은 결과를 차례로 찾는다.

아래는 실제 호출 기록의 셀 추가·실행 부분이다. code의 `…`는 생략된 코드다. 셀 ID는 실행마다 다르므로, 자신의 기록에서 셀 추가 결과의 ID와 실행 요청의 ID가 같은지 확인한다.

```
[add_code_cell에 보낸 입력]
cellIndex: 1
language: "python"
code: … scores=[8,10,12] …

[받은 결과]
{"newCellId":"chWhxVHOZkCD"}

[run_code_cell에 보낸 입력]
cellId: "chWhxVHOZkCD"

[받은 출력 중 평균]
평균: 10.0
```

- `add_code_cell`의 결과에는 평균이 아니라 `newCellId`(새로 만든 셀의 ID)가 있다.
- 이어지는 `run_code_cell`의 입력에 같은 값이 들어갔다면 방금 추가한 셀을 실행하도록 요청했다는 뜻이다. 모델은 셀 추가 결과를 받아 다음 요청의 입력으로 쓴 것이다.
- "실행하겠습니다"라는 답변만으로는 실행을 확인할 수 없다. `run_code_cell`에 보낸 셀 ID와 반환된 출력을 함께 봐야 한다.
- 도구 정의에는 평균을 계산한 결과가 없고, 실행 결과에 `평균: 10.0`이 있다.

**확인 질문**: 평균 10.0은 누가 계산했을까? 모델이 한 일과 코드가 한 일을 나누면 다음과 같다. 1.4에서 본 역할 구분을 호출 기록에서 확인한 셈이다.

| 주체 | 한 일 |
|---|---|
| 실행된 Python 코드 | 평균 10.0을 실제로 계산했다 |
| 모델 | 코드를 담은 셀 추가 요청과, 반환된 셀 ID를 넣은 실행 요청을 만들었다. 최종 답변은 그 결과를 바탕으로 작성한다 |
| 앱(Claude Code) | 요청을 도구로 보내고 결과를 모델에 전달했다 |

### 3.4 노트북의 셀과 출력 읽기

이제 셀을 더 만들지 않고, 앞에서 남긴 노트북을 읽어 본다.

```
Colab MCP의 get_cells를 includeOutputs=true로 호출해 줘. 셀을 수정하거나 다시 실행하지 말고,
평균 계산 셀의 코드와 저장된 출력을 읽어서 알려 줘.
```

- `includeOutputs`: 셀을 읽을 때 실행 출력도 포함할지 정하는 입력. true로 요청하면 코드와 출력을 함께 확인할 수 있다.
- `cellIndexStart`, `cellIndexEnd`: 읽을 셀 범위를 정할 때 쓰는 선택 입력.

관찰할 것:

- 호출 기록에 `get_cells`가 있고, 입력에 `includeOutputs: true`가 있다.
- 반환된 평균 계산 코드와 출력이 노트북 화면의 같은 셀과 일치한다.

> **주의**: 여기서 받은 출력은 새로 계산한 결과가 아니라 노트북에 남아 있던 출력이다. 값이 보인다는 사실만으로 코드를 다시 실행했다고 판단하면 안 된다.

| 한 일 | 확인한 호출 |
|---|---|
| 셀 추가 | `add_code_cell` (결과: newCellId) |
| 실행 | `run_code_cell` (입력: 같은 cellId, 결과: 출력) |
| 읽기 | `get_cells` (입력: includeOutputs: true) |

**완료 조건**: 대화에 `get_cells`로 읽은 코드와 출력이 남아 있고, 셀 추가·실행·읽기를 각각 어느 호출로 확인했는지 설명할 수 있다.

## 4. [실습] 파헤치기: 누가 실행했나

### 4.1 계산한 컴퓨터의 이름 확인하기

3강에서는 모델이 고른 도구와 호출 기록을 봤다. 이번에는 그 요청을 받아 Python 코드를 실행한 컴퓨터를 찾는다. 연결된 노트북을 그대로 두고 Claude Code에 요청한다.

```
Colab MCP로 현재 노트북에 import platform; print(platform.node())를 담은 코드 셀을 새로 추가하고 실행해 줘.
기존 셀은 바꾸지 마.
```

`platform.node()`는 Python이 실행되는 컴퓨터의 이름을 돌려준다. AI 답변만 읽지 말고 Colab 탭에서 새 코드 셀과 그 아래 출력을 확인한다. 이어서 내 컴퓨터의 터미널을 하나 더 열어 다음 명령을 실행한다(Windows에서도 같다).

```bash
hostname
```

| 화면 | 나오는 이름 | 출력 예 |
|---|---|---|
| Colab 셀 | 구글 서버에서 마련한 실행 공간인 컨테이너의 이름 | `3f237bd8c021` |
| 내 터미널 | 내 컴퓨터의 이름 | `내이름-MacBook.local` |

이름 자체를 맞추는 것이 아니라 두 출력이 서로 다름을 확인한다.

> 결론: 노트북의 Python 코드는 내 컴퓨터가 아닌 **Colab 런타임**에서 실행됐다.

### 4.2 MCP 서버 실행과 Python 계산의 위치

그렇다면 설치할 때 내 컴퓨터에서 실행한 `uvx`는 무엇을 했을까? 내 컴퓨터의 터미널에서 `claude mcp get colab-mcp`를 실행해 등록된 실행 명령을 확인한다. 여기에 보이는 `uvx`는 계산 셀을 실행하는 명령이 아니라 **MCP 서버 프로그램을 시작하는 명령**이다.

- Colab MCP의 브라우저 연결은 localhost, 즉 브라우저가 실행되는 컴퓨터 자신을 향한다. 그래서 MCP 서버와 브라우저는 같은 컴퓨터에 있어야 한다.
- 연결 주소에는 토큰이 들어 있으므로 전체 주소를 공유하지 않는다.
- 한 서버에는 노트북 하나가 연결된다.

| 구분 | 어디에서 무엇을 하나 |
|---|---|
| MCP 서버 프로그램 | 내 컴퓨터에서 uvx로 실행된다. Claude Code의 도구 요청을 받아 Colab 탭에 전달한다 |
| 서버와 Colab 탭의 연결 | 브라우저가 내 컴퓨터의 서버에 연결한다. 연결 주소에 든 토큰은 이 연결을 허용하는 값이다 |
| Python 계산 | 구글 서버의 Colab 런타임에서 실행된다. 방금 셀에 나온 이름이 이 실행 환경의 이름이다 |

```
모델 ──셀 추가·실행 요청──▶ 내 컴퓨터의 MCP 서버 ──전달──▶ Colab 탭 ──▶ Colab 런타임(Python 계산)
```

1. 모델은 셀 추가와 실행을 요청했다.
2. 내 컴퓨터의 MCP 서버가 이를 전달했다.
3. Python 계산은 Colab 런타임이 했다.

1.4에서 본 "모델은 도구 호출을 만들고, 앱과 서버가 실행한다"는 구분을 두 컴퓨터의 이름과 노트북 출력으로 확인한 것이다.

- 로컬 MCP 서버는 실행 명령으로 시작하지만, 원격 MCP 서버는 URL로 같은 MCP 약속에 따라 연결한다. 원격 서버를 쓰려면 그 서버의 주소와 접근 권한이 필요하다.
- 연결이 끊겨 노트북 도구가 실패하면 Claude Code에 Colab 연결을 다시 요청하고, 브라우저에서 60초 안에 연결을 허용한다. 그래도 안 되면 Claude Code를 다시 시작한다.

### 참고: 같은 Colab MCP 서버를 OpenCode에서 쓰기

OpenCode는 터미널에서 쓰는 코딩 에이전트 앱이다. 앱을 바꿔도 Colab MCP 서버 프로그램은 그대로 쓸 수 있다. uv와 Git이 설치된 같은 컴퓨터에서 진행한다. `opencode --version`으로 버전을 확인한다.

| V1 | V2 |
|---|---|
| `mcp` 안에 등록, `enabled: true` | `mcp.servers` 안에 등록, `enabled` 제거. `disabled`를 생략하면 연결 활성화 |

V1 프로젝트 설정 파일 `opencode.json` 예(기존 파일이 있다면 전체를 덮어쓰지 말고 colab-mcp 항목만 합친다):

```json
{
  "mcp": {
    "colab-mcp": {
      "type": "local",
      "command": ["uvx", "--python", "3.13", "git+https://github.com/googlecolab/colab-mcp"],
      "enabled": true
    }
  }
}
```

V2 형식:

```json
{
  "mcp": {
    "servers": {
      "colab-mcp": {
        "type": "local",
        "command": ["uvx", "--python", "3.13", "git+https://github.com/googlecolab/colab-mcp"]
      }
    }
  }
}
```

- `command`에는 실행할 프로그램과 그 뒤에 붙일 옵션을 차례로 적는다.
- `--python 3.13`은 내 컴퓨터에서 MCP 서버를 실행할 Python 버전이며, Colab 런타임의 Python 버전은 바꾸지 않는다.
- 설정 파일을 저장한 뒤 해당 프로젝트에서 OpenCode를 다시 시작한다.
- V1에서는 `opencode mcp list`로 연결 상태를 확인한다. V2에서는 같은 명령이나 OpenCode 안의 MCP 관리 화면(`/mcps`)에서 확인한다.

그다음 OpenCode에 "Colab MCP의 open_colab_browser_connection을 호출해서 브라우저의 노트북에 연결해 줘."라고 요청한다. 브라우저에서 연결을 허용한 뒤 위의 컴퓨터 이름 확인 요청을 실행한다. Claude Code에서 허용한 연결을 그대로 쓰는 것이 아니라, OpenCode가 시작한 서버에 새로 연결하는 것이다.

**완료 조건**: 노트북 셀 출력과 터미널의 이름을 근거로, MCP 서버·브라우저 연결·Python 계산이 각각 어디에서 이루어졌는지 설명할 수 있다.

## 5. [실습] Colab 작업 방식을 Skill로 남기기

### 5.1 결과와 규칙 구분하기

앞에서 Colab에 연결할 때는 브라우저에서 연결을 허용했고, 셀을 실행한 뒤에는 노트북에서 출력을 확인했다. 다음 노트북에서도 필요한 행동은 Skill에 남기고, 이번 계산의 결과는 노트북에 남긴다.

| 남길 내용 | 둘 곳 | 이유 |
|---|---|---|
| Chrome에서 Google 계정에 로그인한 상태로 진행한다 | Skill | 다른 노트북을 연결할 때도 필요한 준비다 |
| 연결 허용은 60초 안에 해야 한다고 먼저 알린다 | Skill | 연결 요청 전에 사용자가 준비할 수 있다 |
| Colab 런타임이 연결됐는지 확인한다 | Skill | 셀을 넣는 것과 코드를 실행할 준비는 다르다 |
| 새 셀을 추가하고 기존 셀은 덮어쓰지 않는다 | Skill | `update_cell`은 내용을 덮어쓰므로 이전 작업을 잃을 수 있다 |
| 결과는 노트북 출력으로 확인한다 | Skill | AI의 답변만으로는 실제 실행 여부를 알 수 없다 |
| 연결 주소는 공유하지 않는다 | Skill | 주소에 연결용 토큰이 들어 있다 |
| 8, 10, 12의 평균은 10.0이다 | 이번 노트북 | 이번 입력에 따른 결과이지, 다음 계산의 정답은 아니다 |

> 구분하는 방법: **다른 숫자를 계산해도 필요한 문장인지** 살펴본다. 계산 결과를 Skill에 고정하면 새 입력에도 예전 답을 쓸 수 있다.

### 5.2 AI와 Skill 초안 만들기

Skill은 AI가 필요할 때 읽어 쓸 작업 지침을 담은 폴더다. Colab MCP로 노트북을 다룰 때 반복해서 지켜야 할 규칙을 이 폴더에 저장한다. Colab을 실행한 대화에서 다음처럼 요청한다.

```
방금 Colab MCP로 작업한 방식을 다음 노트북에서도 쓸 수 있게 Skill로 만들어 줘.
연결 준비, 기존 셀 보존, 출력 확인, 연결 주소 보호를 규칙으로 담아 줘. 이번 숫자와 계산 결과는 규칙에 넣지 마.
이름은 colab-notebook으로 하고, .claude/skills/colab-notebook/SKILL.md에 저장해 줘.
```

- 새 대화라면 5.1의 표를 함께 제공한다.
- 초안에 평균 10.0이 고정되어 있다면 입력과 작업 규칙을 구분하도록 다시 요청한다.

### 5.3 완성 예제 읽기

AI가 만든 초안을 다음 예제와 비교한다. 연결부터 출력 확인까지 따라갈 수 있는지, 기존 셀을 보존하는 규칙이 있는지 읽어 본다.

```markdown
---
name: colab-notebook
description: Colab MCP로 브라우저 노트북에 셀을 추가하고 코드를 실행할 때 사용한다. 연결 준비, 기존 셀 보존, 실행 결과 확인에 적용한다.
---

# Colab 노트북 작업

사용자가 요청한 계산을 Colab MCP로 연결한 브라우저 노트북에서 수행한다.

- 연결 전 Chrome에서 Google 계정에 로그인한 상태인지 사용자에게 확인한다.
- 연결 허용은 60초 안에 해야 한다고 먼저 알린 뒤 연결을 요청한다.
- 연결 주소에는 토큰이 있으므로 대화나 공유 문서에 복사하지 않는다.
- 코드 실행 전 사용자에게 노트북 화면에서 런타임 연결 상태를 확인하고, 연결되지 않았다면 연결하도록 안내한다.
- get_cells로 현재 셀을 살펴보고 새 셀을 넣을 위치를 정한다.
- 코드는 add_code_cell로 새 셀에 추가하고 기존 셀은 보존한다.
- update_cell은 내용을 덮어쓰므로 사용하지 않는다.
- 추가한 셀의 ID로 run_code_cell을 호출한다.
- get_cells의 includeOutputs를 true로 지정하거나 노트북 화면에서 출력을 확인한다.
- 확인한 출력을 근거로 결과를 설명하고, 입력마다 계산을 새로 수행한다.
```

> **주의**: "update_cell을 쓰지 말라"는 문장은 도구를 없애는 설정이 아니라 AI가 따를 **규칙**이다. 그래서 실행 기록에서도 지켰는지 확인해야 한다.

### 5.4 파일 구성

이번 Skill은 참조 파일 없이 `SKILL.md` 하나면 충분하다. 규칙이 길어지면 `references` 폴더의 파일로 나눌 수 있다. 파일 이름은 대문자를 포함해 `SKILL.md`로 쓰고, 맨 위 두 `---` 사이에 이름과 설명을 적는다.

| 부분 | 하는 일 | 이 예제에서 지킬 규칙 |
|---|---|---|
| name | 불러올 이름 | 폴더명과 같은 colab-notebook을 쓴다. 소문자·숫자·하이픈으로 1~64자이며, 하이픈으로 시작하거나 끝내거나 연속해서 쓰지 않는다 |
| description | 언제 이 Skill을 쓸지 알려 준다 | 비우지 않고, 언제 쓸지 1~1,024자로 적는다 |
| 그 아래 본문 | 실제 작업 지침 | AI가 따라 할 작업 지침을 Markdown으로 쓴다 |

### 5.5 앱이 찾는 위치에 놓기

Claude Code로 연 실습 프로젝트 안에 다음 구조가 있는지 확인한다. 다른 폴더에 초안을 저장했다면 이 위치로 옮긴다.

```
실습 프로젝트/
└── .claude/
    └── skills/
        └── colab-notebook/
            └── SKILL.md
```

`.claude`처럼 점(.)으로 시작하는 폴더는 macOS Finder에서 기본으로 보이지 않는다(숨김 폴더). 터미널에서 숨김 폴더까지 보려면 macOS에서는 `ls -a`, Windows PowerShell에서는 `Get-ChildItem -Force`를 실행한다.

### 5.6 이름을 지정해 불러오기

같은 프로젝트에서 새 대화를 열고 입력한다.

```
/colab-notebook 8, 10, 12의 평균을 구하는 셀을 추가하고 실행해 줘.
```

연결을 요청받으면 허용하고, AI의 실행 기록과 Colab 화면을 함께 살펴본다. 파일이 제자리에 있는지, 앱이 그 파일을 읽었는지, 실제 작업에서 규칙을 지켰는지를 각각 확인한다.

| 확인할 것 | 살펴볼 곳 |
|---|---|
| Skill 파일이 제자리에 있다 | `.claude/skills/colab-notebook/SKILL.md` 경로와 파일 내용 |
| 앱이 Skill을 불러왔다 | colab-notebook의 로드 또는 본문 읽기 기록 |
| 규칙대로 처리했다 | 기존 셀을 덮어쓰지 않고 새 셀을 추가한 도구 기록과 노트북 화면, 실행된 셀의 출력 |

- 평균이 10.0이라고 답했더라도 출력이 없으면 실행 결과를 확인한 것이 아니다. `get_cells`의 includeOutputs를 켜서 읽거나 노트북 화면에서 출력이 남았는지 확인한다.
- Skill이 보이지 않으면 프로젝트 위치, 파일명, 이름과 설명을 확인한 뒤 `/reload-skills`를 실행한다. 이 명령은 세션을 시작할 때 없던 skills 폴더를 새로 만들었을 때 필요하다. 이미 있던 폴더 안의 Skill을 고치면 Claude Code가 다시 시작하지 않아도 반영한다.
- 그래도 안 되면 Claude Code를 다시 시작하고 새 대화에서 확인한다.

**완료 조건**: Skill이 로드된 새 대화에서 기존 셀을 보존하며 새 셀을 추가했고, 실행 출력까지 노트북에서 확인했다.

## 6. [실습] Skill을 내 방향으로 고치기

### 6.1 코드 앞에 설명 남기기

5강에서 만든 Skill에 설명 셀 규칙을 더한다. 계산값만 남은 노트북은 나중에 열었을 때 코드의 목적을 다시 읽어 내야 한다. 코드 앞에 무엇을 왜 하는지 적으면 실행하기 전에도 계산의 의도를 알 수 있다.

`.claude/skills/colab-notebook/SKILL.md`를 열어 해당 문장을 아래처럼 고친다. 파일 맨 위의 name과 description, 연결과 기존 셀 보호 규칙은 그대로 둔다.

```
[바꾸기 전]
코드는 add_code_cell로 새 셀에 추가하고 기존 셀은 보존한다.

[바꾼 뒤]
코드는 add_code_cell로 새 셀에 추가하고 기존 셀은 보존한다. 코드 셀 앞에는 무엇을 왜 계산하는지 한국어로 설명하는 마크다운 셀을 둔다.
```

- 내 파일의 문장이 예제와 다르면, 기존 셀을 보호한다는 뜻을 유지하면서 설명 셀 규칙을 덧붙인다.
- 실습 폴더 안에 `my-task` 폴더를 만들고, `my-task/README.md`에 실제로 바꾸기 전 문장과 바꾼 문장을 함께 적어 둔다. 6.4와 7강, 8강 과제에서 이 파일을 이어 쓴다.
- 설명 셀에는 "가장 큰 값과 가장 작은 값의 차이를 구합니다"뿐 아니라 "값들이 얼마나 퍼져 있는지 보기 위해서입니다"처럼 **이유**도 담도록 한다.
- Colab MCP의 `add_text_cell`은 마크다운을 지원한다. 설명과 코드를 각각 넣을 위치는 cellIndex로 정할 수 있으므로, 말로만 설명하는 대신 노트북 안에 설명 셀을 남길 수 있다.

### 6.2 새 대화에서 바뀐 규칙 확인하기

파일을 저장한 뒤 같은 실습 프로젝트에서 Claude Code의 새 대화를 연다. 앞 대화에서 직접 부탁한 설명 방식의 영향을 줄이고, 저장한 Skill이 다시 쓰이는지 보기 위해서다. 연결이 필요하면 앞에서처럼 Colab 연결을 허용한 뒤 요청한다.

```
Colab에서 8, 10, 12의 가장 큰 값과 가장 작은 값의 차이를 구해 줘.
```

이번 요청에는 설명 셀을 넣으라는 말을 보태지 않는다. 작업이 끝나면 노트북에서 새로 추가된 셀을 읽는다.

관찰할 것:

- 한국어 설명 셀이 코드 셀 앞에 있다.
- 설명 셀이 무엇을 왜 계산하는지 말한다.
- 코드 셀의 출력이 4다(12 − 8).

화면에서 순서가 잘 보이지 않으면 "get_cells로 방금 추가한 셀들의 순서와 내용을 보여 줘."라고 요청할 수 있다.

### 6.3 Skill이 쓰였는지 확인하기

결과가 맞게 나온 것과 Skill을 실제로 읽은 것은 **따로** 확인한다. 설명 셀이 생겼다는 사실만으로 Skill을 읽었다고 볼 수는 없다. Claude Code의 작업 기록을 Ctrl+O로 펼쳐 colab-notebook을 불러온 흔적과, 수정한 본문이 전달된 내용을 살펴본다.

Skill을 선택하지 않았다면 다른 새 대화에서 이름을 지정해 다시 요청한다.

```
colab-notebook Skill로 Colab에서 8, 10, 12의 가장 큰 값과 가장 작은 값의 차이를 구해 줘.
```

불러온 본문에도 새 문장이 있고, 새로 추가된 셀에도 그 규칙이 드러나는지 대조한다.

### 6.4 규칙 하나 더 고르기

내가 노트북을 다시 읽을 때 필요한 규칙을 하나 골라 같은 본문에 더한다. 예: "마지막에 결과를 한국어로 요약한 마크다운 셀을 둔다." 고른 규칙으로 무엇이 달라져야 하는지 `my-task/README.md`에 적은 뒤, 새 대화에서 같은 계산을 요청해 노트북에서 확인한다. 하는 일이 달라지면 Skill에 남길 규칙도 늘어날 수 있다.

### 6.5 결과가 다를 때

| 보이는 결과 | 다음 행동 |
|---|---|
| Skill이 안 불림 | 새 대화에서 colab-notebook 이름을 지정해 다시 요청한다 |
| Skill은 불렸지만 규칙을 안 따름 | 전달된 본문에 새 문장이 있는지 본다. 빠졌다면 `/reload-skills` 후 다시 요청한다. 문장이 있다면 어긴 규칙을 짚어 셀 추가를 다시 요청한다 |
| 기존 셀을 덮어씀 | 작업을 멈추고 원래 내용과 대조한다. `update_cell`은 내용을 덮어쓰므로, 기존 셀 대신 새 셀을 추가하도록 요청한다 |

**완료 조건**: 바꾼 Skill이 새 대화에서 불렸고, 한국어 설명 셀이 코드 셀 앞에 있으며, 변경 전후 문장이 `my-task/README.md`에 남아 있다.

## 7. [실습] 내 작업에 맞게 바꾸기

### 7.1 내가 반복하는 일에서 출발하기

지금까지 한 일을 정리하면 다음과 같다.

1. 만들어진 Colab MCP를 설치해 써 봤다.
2. 도구 목록, 호출 기록, 실제로 실행된 곳을 펼쳐 동작을 확인했다.
3. 매번 하던 말을 Skill로 남겨 내 방향에 맞게 고쳤다.

이제 매주 작성하는 문서 하나를 떠올린다(예: 학습자 피드백, 사용자에게 보내는 변경 안내). 6강에서 Skill 규칙 한 곳을 바꾸고 노트북 결과로 확인한 방법을 새 작업에 적용한다. 자료는 로컬 파일을 쓴다.

```
판단 기준을 파일에 적는다 → 기준 한 곳을 바꾼다 → 입력 한 건의 결과에서 한 문장의 근거를 확인한다
```

입력만 바꿔서는 원하는 결과가 나오지 않을 수 있다. 학습자의 답안을 넣어도 Colab 작업 방식만 담긴 Skill로는 교사가 알고 싶은 풀이의 부족한 부분을 짚지 못한다. **어떤 자료를 읽을지**와 **그 자료를 어떻게 판단할지**를 따로 정해야 한다.

| 용어 | 뜻 | Colab 실습에서 | 학습 피드백에서 |
|---|---|---|---|
| 데이터 | 이번에 처리할 사실 | 평균을 낼 숫자 | 문제와 답안 |
| 업무 지식 | 데이터를 어떻게 해석하고 결과로 표현할지 정하는 기준 | Skill의 규칙 | 피드백 기준 |
| 실행 기능 | 자료를 읽거나 계산하는 실제 동작 | Colab MCP 도구 | 로컬 파일 읽기 |

### 7.2 입력과 결과가 보이는 작업

"내 업무를 자동화한다"는 목표만 놓으면 시작할 곳이 너무 많다. 실제 자료 하나를 펼쳐 두고 "이 자료로 어떤 결과를 받고 싶은가"부터 생각하면 일이 구체적으로 보인다.

자기 작업을 고른다면 **입력 한 건, 원하는 결과, 바꿀 판단 기준 하나**를 적는다. 예: 변경 기록 한 건으로 안내문을 만들면서 "내부 작업명 대신 사용자에게 보이는 변화로 설명한다"는 기준을 적용할 수 있다. 이 절에서는 그 한 건을 끝까지 확인한다.

### 7.3 학습 피드백의 작은 설계

자기 업무 자료가 없다면 다음 문제와 답안을 그대로 써서 `my-task/input.md`로 저장한다(6.1에서 my-task 폴더를 만들지 않았다면 지금 만든다).

```
문제: 8, 10, 12의 평균을 구하고 계산 방법을 설명하세요.
학습자의 답안: 10입니다.
```

이 답안을 어떻게 보아야 하는지 정리한다.

| 판단 | 맞는지 | 이유 |
|---|---|---|
| 숫자 10은 맞다 | 맞음 | 평균은 10이다 |
| 계산 방법 설명이 있다 | 아님 | 문제는 설명을 요청했지만 답안에 없다 |
| "평균의 개념을 정확히 이해하고 있군요" | 잘못됨 | 답안에서 확인하지 못한 이해까지 추정한 것이다 |
| "평균을 이해하지 못했습니다" | 잘못됨 | 이 역시 근거가 부족하다 |

이 입력에 적용할 기준은 다음과 같다.

> 정답 여부와 풀이 설명을 구분한다. 풀이가 없으면 이해 여부를 단정하지 않고, 학습자가 자신의 계산을 설명할 다음 질문을 제안한다.

원하는 결과는 정답을 인정하면서 계산 방법을 묻는 피드백이다. 재사용할 지식은 "이 학생의 정답은 10"이 아니라 "정답과 설명을 구분해 피드백하는 기준"이다. 5강에서 평균 10.0이라는 결과 대신 작업 방식을 Skill에 남긴 것과 같은 생각이다.

### 7.4 바꿀 위치를 구분하기

기준을 둘 곳은 작업 종류에 따라 다르다.

- **Colab 노트북을 다루는 작업이라면**: 앞에서 고친 `.claude/skills/colab-notebook` 폴더를 `my-task/skill`로 복사하고 바꿀 규칙 문장 하나를 고른다. 원본 Skill은 그대로 둔다. 파일을 직접 읽도록 요청할 것이므로 복사본을 새 Skill로 등록할 필요는 없다.
- **Colab을 쓰지 않는 작업이라면**: 아래 기본안처럼 `my-task/criteria.md`에 기준을 적는다.

| 구분 | 이번에 둘 곳 | 바꾸는 내용 |
|---|---|---|
| 입력 | `my-task/input.md` | 자신의 자료 한 건 또는 위 문제와 답안 |
| 기준 | 복사한 Skill의 기준 한 곳 또는 `my-task/criteria.md` | 결과를 판단할 규칙 한 곳 |
| 실행 | Claude Code의 로컬 파일 읽기 | 기존 기능 사용 |
| 결과 | `my-task/result.md` | 새 입력에 기준을 적용한 결과 |

학습 피드백 기본안의 진행 순서:

1. `my-task/criteria.md`에 먼저 "정답이면 잘했다고 칭찬하는 피드백을 쓴다."를 적고 아래 요청으로 한 번 실행한다.
2. 결과에 답안에 없는 칭찬이나 이해를 덧붙인 문장이 있는지 확인한다.
3. 기준을 7.3의 피드백 기준으로 바꾸고 같은 답안으로 다시 실행한다.
4. 바꾸기 전 기준과 그때 나온 결과 한 문장은 뒤에서 작성할 README.md에 남긴다.

> 💡 학습자 답안이 로컬 파일에 있고 Claude Code가 그 파일을 읽을 수 있다면, 첫 피드백을 만들기 위해 새 MCP 서버를 추가할 필요는 없다. 반대로 Skill에 "답안을 읽으세요"라고 쓰는 것만으로 접근 기능이 생기지는 않는다.

### 7.5 AI와 필요한 부분 만들기

실습 폴더에서 Claude Code를 열고 다음처럼 요청한다(기본안의 경로).

```
my-task/input.md와 my-task/criteria.md를 읽어 줘.
입력 한 건에 기준을 적용해 피드백을 만들고 my-task/result.md에 저장해 줘.
입력과 기준 파일은 수정하지 마.
어떤 파일의 어느 내용을 근거로 썼는지 대화에 알려 줘.
새 서버나 외부 서비스 연결 없이 로컬 파일만 사용해 줘.
```

- Skill 복사본을 쓴다면 `my-task/criteria.md`를 실제 기준 파일 경로로 바꾸고, `my-task/skill/SKILL.md`도 함께 읽도록 요청한다.
- 기준 파일에는 적용할 기준만 남기고, 변경 전후 설명은 README.md에 둔다.
- Colab 작업이라면 마지막 줄(로컬 파일만 사용)을 빼고, 연결을 요청받으면 허용한다.
- 자기 작업을 쓴다면 "피드백"을 원하는 결과 이름으로 바꾼다.
- 기준 수정을 AI에게 맡길 때도 파일 경로, 바꿀 문단, 적용할 새 기준을 짚어 요청한다. 수정 뒤에는 해당 파일을 열어 지정한 곳만 바뀌었는지 확인한다.
- 파일을 만들었다는 답변만으로 결과를 확인한 것은 아니다. `my-task/result.md`를 직접 열어 읽는다.

### 7.6 결과의 한 문장에서 원인 찾기

결과에서 기준을 적용한 문장 하나를 골라 원본 입력과 나란히 놓는다. 기본안에서 "계산 과정도 잘 설명했어요"라고 썼다면 답안에는 그 근거가 없다. 잘못된 문장이 있다면 다음처럼 요청한다.

```
답안에는 계산 과정이 없는데 결과에는 잘 설명했다고 되어 있어.
사용한 입력과 기준을 확인하고, 정답 여부와 풀이 설명을 구분해 결과를 고쳐 줘.
```

| 확인할 곳 | 살펴볼 내용 |
|---|---|
| 입력 | 지정한 문제와 답안 한 건을 읽었는가 |
| 기준 | 바꾼 기준 파일을 읽었는가 |
| 결과 | 답안에 없는 설명이나 이해를 덧붙였는가 |

수정한 뒤에는 **같은 답안으로** 다시 확인한다. 처음부터 다음 학생의 답안으로 바꾸면, 결과가 달라진 것이 수정 때문인지 입력이 달라져서인지 알기 어렵다. 처음부터 맞았다면 받아들인 근거를 남기면 된다.

### 7.7 다음 사람이 이어 쓸 수 있는 결과물

`my-task/README.md`에는 다른 사람이 같은 입력과 기준으로 다시 요청할 수 있도록 다음을 적는다. 6.1에서 같은 파일에 적어 둔 Skill 변경 전후 문장은 지우지 않고 아래 항목과 나누어 둔다.

- 작업, 사용한 파일
- 바꾼 기준의 위치와 변경 전후 문장
- 실행 요청
- 결과 한 문장과 원본 근거

기본안에서 다음 문장을 얻었다면 이렇게 근거를 연결할 수 있다(실제 결과가 다르면 자신이 얻은 문장을 그대로 인용한다).

```
작업: 답안 한 건에 학습 피드백 작성
입력: input.md
기준: criteria.md
결과: result.md
바꾼 위치: criteria.md의 판단 기준 문장
변경 전: 정답이면 잘했다고 칭찬하는 피드백을 쓴다.
변경 전 결과 문장: (처음 실행에서 나온 문장. 예: 계산 과정도 잘 설명했어요.)
변경 후: 정답 여부와 풀이 설명을 구분합니다. 풀이가 없으면 이해 여부를 단정하지 않고, 계산을 설명할 다음 질문을 제안합니다.
실행 요청: (Claude Code에 보낸 요청)
확인한 결과 문장: 답안에 계산 과정이 없어 어떤 방법으로 구했는지 알 수 없습니다.
원본 근거: input.md의 학습자 답안 전체는 "10입니다."이며 풀이가 없습니다.
판정: 풀이가 없다는 판단은 답안과 일치합니다. 이해 여부는 판단하지 않았습니다.
```

결과물 파일 목록은 다음과 같다. Skill 경로와 기준 파일 경로 중에는 자신이 사용한 것만 남긴다.

| 파일 또는 폴더 | 담길 내용 |
|---|---|
| `my-task/skill/` 또는 `my-task/criteria.md` | 기준 한 곳을 바꾼 Skill 폴더 또는 기준 파일 |
| `my-task/input.md` | 사용한 입력 한 건 |
| `my-task/result.md` | 그 입력으로 만든 최종 결과 |
| `my-task/README.md` | 변경 위치와 전후 기준, 실행 요청, 결과 한 문장과 원본 근거 |

바꾼 기준, 입력 한 건, 결과 파일, 한 문장의 근거를 적은 README.md가 있으면 이 실습은 끝이다.

## 8. [과제] 내 작업에 맞게 바꾸어보기

7강에서 만든 `my-task` 폴더가 이번 과제의 결과물이다. 바꾼 기준 한 곳이 결과의 어느 문장에 어떻게 드러났는지를 다른 사람이 원본으로 확인할 수 있어야 한다.

### 8.1 과제의 목표

1. **바꾼 기준의 위치를 밝힌다.** Skill 또는 기준 파일에서 어느 문장을 어떻게 바꾸는지 변경 전후로 보여 준다.
2. **입력과 결과를 함께 남긴다.** 다른 사람이 같은 입력과 요청으로 다시 실행해 기준이 적용되는지 확인할 수 있게 한다.
3. **결과 한 문장의 근거를 원본에서 짚는다.** 결과 문장이 입력의 어느 부분에서 나왔는지, 입력에 없는 내용을 덧붙이지 않았는지 확인한다.

### 8.2 결과물

```
my-task/
├── skill/ 또는 criteria.md   # 기준 한 곳을 바꾼 Skill 폴더 또는 기준 파일
├── input.md                  # 사용한 입력 한 건
├── result.md                 # 그 입력으로 만든 최종 결과
└── README.md                 # 바꾼 위치와 변경 전후 기준, 실행 요청, 결과 한 문장과 원본 근거
```

- 자기 업무 자료를 썼다면 이름·연락처 같은 개인정보와 회사 내부 정보는 가리고 제출한다.
- API 키 같은 인증 정보와, 연결용 토큰이 들어 있는 Colab 연결 주소는 넣지 않는다.

### 8.3 평가 루브릭

각 항목은 결과물에서 다음이 확인될 때 충족이다.

| 항목 | 충족 조건 |
|---|---|
| 1. 바꾼 위치가 드러난다 | README에 바꾼 파일과 문장, 변경 전후 기준이 있고, 제출한 Skill 또는 기준 파일에 변경 후 문장이 실제로 들어 있다 |
| 2. 입력과 결과가 함께 있다 | input.md의 입력 한 건과 result.md의 결과가 짝을 이루고, README의 실행 요청만 보고 같은 요청을 다시 보낼 수 있다 |
| 3. 결과 한 문장의 근거를 원본에서 짚었다 | README가 인용한 결과 문장이 result.md에 있고, 그 근거로 든 내용이 input.md에서 확인된다 |

### 8.4 마지막 확인

- [ ] criteria.md 또는 skill/SKILL.md에 변경 후 문장이 실제로 들어 있다.
- [ ] README의 결과 문장을 result.md에서 그대로 찾을 수 있다.
- [ ] README의 실행 요청을 복사해 다시 보낼 수 있다.
- [ ] 개인정보와 인증 정보가 없다.
