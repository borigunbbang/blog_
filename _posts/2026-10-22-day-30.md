## 1. 이번 노드의 핵심 질문

> "채팅으로 일을 맡기는 에이전트를 내 컴퓨터에 띄우면, **무엇이 메시지를 받고, 무엇이 일을 하고, 어디까지 하게 둘 것인가?**"

OpenClaw는 **채팅으로 일을 맡기는 오픈소스 개인 어시스턴트**다. 채팅창에 부탁하면 스스로 파일을 찾아 읽고, Telegram 메시지에 대신 답하고, 정해 둔 시간에 반복 작업을 처리한다.

이 노드는 설치에서 시작해 아래 순서로 한 겹씩 쌓아 올린다.

```text
설치·온보딩 → WebChat 첫 메시지 → 세션 기록 확인 → Telegram 연결
   → 보안 경계 정하기 → (pi: 코어 이해) → 멀티에이전트 → 모니터링 → 자동화 → 확장 기능
```

| 절 | 내용 | 방식 |
|---|---|---|
| OpenClaw 나도 써보자 | 설치, 온보딩, WebChat 첫 메시지 | 실습 |
| 세션 기록 읽기 | 대화가 남기는 파일 확인 | 실습 |
| Telegram으로 부리기 | 봇 연결과 페어링 승인 | 실습 |
| 보안 | 파일·명령 범위, 대화할 계정, 외부 내용 처리 | 읽기 |
| pi | OpenClaw가 처음 쓴 에이전트 코어 | 읽기 |
| 멀티에이전트 | 바인딩, 에이전트별 분리, 병렬 작업 | 읽기 |
| 모니터링 | 토큰, 비용, 인증 상태 | 실습 |
| 자동화 | 예약 작업 만들고 지우기 | 실습 |
| 확장 기능 | 브라우저, 기기, 음성, 메일, 스킬 | 읽기 |

**실습 전 약속 세 가지**: 오늘 만든 연습 폴더 + 수업용 계정으로만 한다 / 봇 토큰은 채팅·화면 공유·메모·캡처에 남기지 않는다 / 끝나면 예약 작업을 지우고 Gateway를 멈춘다.

## 2. OpenClaw는 어디서 왔나: 이름이 세 번 바뀌었다

자료를 찾을 때 **예전 이름도 알아야** 기록을 놓치지 않는다. 그래서 강의는 이름 변천부터 짚는다.

| 이름 | 있었던 일 |
|---|---|
| Warelay | 출발점. WhatsApp 메시지를 연결하는 **게이트웨이** 프로그램 |
| Clawdbot | 바닷가재 마스코트 Clawd와 함께 붙은 이름. npm 설명은 "WhatsApp gateway CLI … with **Pi RPC agent**". 2026.1.4~1.24 사이 37개 버전 |
| Moltbot | 2026년 1월 Anthropic의 상표 문제 요청으로 변경. 1월 27일 커뮤니티가 수백 개 후보 중 선택. molt = 탈피 |
| OpenClaw | 2026년 1월 30일 정한 지금 이름. "New shell, same lobster soul"(새 껍데기, 같은 바닷가재) |

```text
Warelay ──→ Clawdbot ──→ Moltbot ──→ OpenClaw
(WhatsApp     (pi 코어를       (상표 문제로     (현재 이름)
 게이트웨이)    품은 게이트웨이)   개명)
```

**설치 환경에 남은 옛 이름**

| 운영 체제 | 처리 |
|---|---|
| Linux, WSL2 | 옛 서비스 이름 `clawdbot-gateway`를 자동으로 마이그레이션 |
| macOS | 옛 실행 설정이 지워지지 않고 남음. 진단 명령이 찾아서 알려 줌 |

> 💡 **한 줄로 기억하기**: 이름은 바뀌어도 코드와 커뮤니티는 이어진다. 검색할 땐 Clawdbot, Moltbot도 같이 찾는다.

## 3. 뼈대: Gateway · 채널 · 에이전트 런타임

OpenClaw를 이해하는 가장 중요한 그림이다. 세 부품이 각자 다른 일을 한다.

| 부품 | 하는 일 | 비유 (덧붙인 것) |
|---|---|---|
| **채널** (channel) | WebChat, Telegram 같은 메시지 서비스와 Gateway를 잇는 연결 | 접수 창구 |
| **Gateway** | 계속 켜 두는 중심 프로그램. 들어온 메시지를 **어느 세션·어느 도구로 보낼지** 정함 | 교환대(배차 담당) |
| **에이전트 런타임** | 모델을 호출하고 도구를 실행 | 실제로 일하는 직원 |

```text
[WebChat / Telegram]  ──메시지──→  [Gateway]  ──배정──→  [에이전트 런타임]
      채널                     어느 세션·도구로?            모델 호출 + 도구 실행
```

**왜 Gateway 한곳에서 정할까?** 채널이 늘어날수록 "이 요청을 어디로 보낼지"가 복잡해진다. 이 결정을 Gateway 한곳에 모으면 **각 대화가 어떤 세션으로 이어졌는지 기록**할 수 있다.

> 💡 **한 줄로 기억하기**: 채널은 입구, Gateway는 배정, 런타임은 실행.

## 4. 설치와 첫 메시지 (실습)

### 4-1. 연습 폴더와 Node 버전

```bash
mkdir -p ~/openclaw-lab && cd ~/openclaw-lab
pwd
node --version
```

- `-p`: 폴더가 이미 있어도 오류를 내지 않는다.
- 요구 버전: Node **24.16 이상 또는 26.1 이상**, 권장은 Node 26 (2026-10-17 기준). 맞지 않으면 억지로 바꾸지 말고 멈춘다.

> **주의: 폴더 이름만으로는 격리되지 않는다.** 연습 폴더에서 설치해도 설정·상태·자격 증명은 홈의 `~/.openclaw/`에 저장된다. 그래서 수업용 계정·키만 쓴다.

### 4-2. 설치와 온보딩

```bash
npm install -g openclaw@latest --allow-scripts=openclaw
openclaw --version
openclaw onboard --install-daemon
```

| 명령 | 하는 일 |
|---|---|
| `npm install -g openclaw@latest` | 공식 패키지 최신 버전을 전역 설치 |
| `--allow-scripts=openclaw` | 설치 때 자동 실행되는 스크립트(lifecycle script) 허용 |
| `openclaw onboard --install-daemon` | 대화형 첫 설정 + **데몬**(백그라운드 상시 실행 서비스) 설치 |

데몬은 macOS에선 LaunchAgent, Linux·WSL2에선 systemd 사용자 서비스로 설치된다.

### 4-3. 인증 경로 두 가지 ★

온보딩에서 고르는 이 선택이 뒤의 **모니터링 숫자 해석**까지 이어진다.

| 인증 경로 | 호출 방식 | 과금 |
|---|---|---|
| **API 키** (`ANTHROPIC_API_KEY`) | OpenClaw가 키를 들고 직접 호출 | 쓴 만큼 (종량 과금) |
| **claude-cli** | 같은 컴퓨터에 로그인한 Claude Code 세션을 대신 사용 | 구독 요금·한도에서 차감 |

> 💡 **한 줄로 기억하기**: 키를 OpenClaw가 들고 있으면 돈으로, CLI 로그인을 빌리면 구독 한도로 계산된다.

### 4-4. 진단 → WebChat 첫 메시지

```bash
openclaw doctor
openclaw gateway status
openclaw dashboard
```

- `doctor`: **마지막 줄만 보고 성공이라 판단하지 않는다.** 통과·경고·오류를 그대로 읽는다.
- 둘 중 하나라도 실패하면 거기서 멈춘다.
- WebChat은 Gateway가 `http://127.0.0.1:18789`에 열어 두는 대화 화면이다. `127.0.0.1` = 이 컴퓨터 안에서만 접속. 브라우저와 Gateway는 **WebSocket**(연결을 끊지 않고 계속 주고받는 방식)으로 통신한다.
- 첫 메시지는 무해한 한 문장: "이 메시지를 받았다면 연결 확인이라고만 답해 주세요."

**외부 접속은?** 포트를 열거나 주소를 추측하지 않는다. 원격 접속은 공식 문서가 **Tailscale**(내 기기들을 하나의 사설망처럼 묶는 도구)을 안내한다 (오늘은 안 함).

| 방법 | 하는 일 |
|---|---|
| Telegram 연결 | 에이전트가 메시지를 받을 **새 채널**을 연다 |
| Tailscale | 이미 떠 있는 **WebChat 화면**을 다른 기기에서 쓰게 한다 |

### 4-5. 설치 확인과 마무리

| 볼 곳 | 설치가 끝났다는 근거 |
|---|---|
| `openclaw --version` | 버전 |
| 온보딩 완료 화면 | 완료 표시 |
| `openclaw gateway status` | 실행 상태 |
| WebChat 첫 응답 | 응답 |

실습을 모두 마친 뒤 `openclaw gateway stop`으로 멈춘다(`openclaw daemon stop`은 예전 별칭). 멈춰도 `~/.openclaw/openclaw.json` 같은 설정은 남는다. 위치는 `openclaw config file`로 확인.

## 5. 세션 기록: "말한 것"과 "실제로 한 것"은 다른 줄에 남는다

### 5-1. 무엇이 어디에 남나

WebChat 직접 메시지는 기본적으로 **메인 세션**(`agent:<agentId>:main`, 하나로 이어지는 대화)으로 들어간다.

| 구분 | 위치 | 들어 있는 것 |
|---|---|---|
| 설정 | `~/.openclaw/openclaw.json` | 기본 설정 |
| 세션 기록 | `~/.openclaw/agents/<agentId>/agent/openclaw-agent.sqlite` | 대화 기록, 실행 상태 |
| 이전 형식 자료 | `~/.openclaw/agents/<agentId>/sessions/` | 보관·지원용 |
| 워크스페이스 | `~/.openclaw/workspace` | 파일 도구의 기본 작업 폴더 |
| 장기 메모 | 워크스페이스의 `MEMORY.md` | 오래 남길 사실·결정 |
| 날짜별 메모 | 워크스페이스의 `memory/` | `2026-09-04-제목.md` 형식 |

실습은 대화 전후로 `ls -la`를 찍어 **새로 생긴 파일·수정 시각이 바뀐 파일**을 비교하고, `openclaw memory status`로 메모 색인 상태를 본다. SQLite 내용을 여는 건 이 노드 범위 밖이다.

### 5-2. 답변 문장 vs 실행 기록 ★

| 줄 | 들어 있는 것 | 뜻 |
|---|---|---|
| assistant | `text` | 모델이 **말한** 문장 |
| assistant | `toolCall` | 모델이 **하겠다고 요청한** 도구 호출 |
| toolResult | `content`, `details` | **실제로 일어난** 일 |

```text
toolCall (id=abc) ──같은 toolCallId로 연결──→ toolResult (id=abc)
   "저장할게요"                                    실제 저장 결과
```

모델이 "파일을 저장했습니다"라고 말해도, **같은 toolCallId의 toolResult가 없으면 저장했다는 근거가 없다.**

> 💡 **한 줄로 기억하기**: 완료 여부는 답변 문장이 아니라 결과 줄로 판단한다.

## 6. Telegram으로 부리기 (실습)

### 6-1. 흐름

```text
BotFather에서 봇 생성 → 토큰을 Gateway 설정에 넣기 → Gateway 재시작
   → 연결 확인 → 휴대폰에서 첫 메시지 → 페어링 승인 → 대화 가능
```

1. Telegram에서 **@BotFather**(공식 봇, 핸들이 한 글자도 다르지 않은지 확인) → `/newbot` → 표시 이름, `bot`으로 끝나는 봇 이름 → 토큰을 안전한 곳에 보관.
2. 토큰이 대화에 남았다면 새 토큰을 발급하고 이전 토큰은 버린다.

```bash
openclaw config set channels.telegram.botToken "여기에_봇_토큰"
openclaw gateway restart        # 데몬 실행 중일 때
openclaw channels status --probe
```

- Telegram은 `channels login`으로 연결하지 않는다. **설정에 토큰을 넣고 Gateway를 시작**한다.
- 명령줄에 직접 넣은 값은 셸 기록(history)에 남을 수 있다.

| Gateway 상태 | 명령 |
|---|---|
| 데몬으로 실행 중 | `openclaw gateway restart` |
| 데몬 설치됐지만 멈춤 | `openclaw gateway start` |
| 데몬 없이 터미널 실행 | `openclaw gateway` |

### 6-2. 페어링: 아무나 봇과 대화하지 못하게

채널이 열려 있어도 바로 대화되지 않는다. 기본 DM 정책이 **페어링**이기 때문이다.

```bash
openclaw pairing list telegram
openclaw pairing approve telegram <코드>
```

- 대기 코드는 **1시간 뒤 만료**. 한 번 승인하면 이후엔 코드 없이 대화.
- 승인 안 된 계정 메시지에는 답하지 않는다.
- 계정은 **사람 이름으로 추측하지 말고** 승인 목록의 계정으로 구분한다.

| DM 정책 | 동작 | 맞는 경우 |
|---|---|---|
| pairing | 첫 메시지 계정을 대기 목록에 → 승인된 계정만 | 기본값 |
| allowlist | 숫자 Telegram ID를 넣은 계정만 | 소유 계정 하나만 쓰는 봇 |
| open | 모든 계정 | 도구를 강하게 제한한 공개 봇 |

**Discord·Slack**은 순서만 읽는다(지금은 이런 게 있구나 정도로 넘어가도 된다). 원칙은 같다: 토큰은 비밀, 대화할 계정 범위부터 제한.

## 7. 보안: 경계를 세 군데 따로 정한다

에이전트는 파일을 읽고, 명령을 실행하고, 채널 메시지를 받는다. 그래서 **세 종류의 경계**를 각각 정한다.

| 정할 것 | OpenClaw에서 정하는 곳 |
|---|---|
| 파일과 명령의 범위 | **권한 모드** |
| 채널에서 말을 걸 수 있는 계정 | **페어링, 허용 목록** |
| 외부 내용을 실행으로 옮기기 전 승인 | **읽기 전용 에이전트, 별도 승인** |

### 7-1. 권한 모드

`sessionRoot` = 세션이 파일 접근을 판단하는 기준 작업 폴더. 권한 모드는 이 폴더 안팎의 읽기·쓰기 범위와 **명령 실행을 누가 검토하는지**를 정한다. 에이전트는 그 모드에서 주어진 도구만 쓸 수 있다(쓰기 도구가 없으면 쓸 수 없다).

| 모드 | 파일 읽기 | 파일 쓰기 | 명령 실행 |
|---|---|---|---|
| read-only | 작업 폴더 안 | 도구 없음 | 거부 |
| guarded | 작업 폴더 안 | 작업 폴더 안 | 허용 목록 밖이면 **사람**이 승인 |
| workspace | 작업 폴더 안 | 작업 폴더 안 | **모델**이 검토, 애매하면 사람에게 |
| full | 제한 없음 | 제한 없음 | 승인 없음 (operator.admin 필요) |

- 자료 요약 작업 → **read-only**에서 시작. 파일 수정이 필요할 때만 guarded 검토.
- 권한을 넓히면 잘못된 요청이 들어왔을 때 **피해 범위도 같이 넓어진다.**

> 💡 **한 줄로 기억하기**: 필요한 만큼만 연다. 시작은 read-only.

### 7-2. 채널 계정 제한 (페어링의 보안적 의미)

페어링 = **채널 단계의 신원 확인**. 덧붙일 점:
- open 정책은 공개 봇에만, 그때도 도구를 강하게 제한.
- **DM 페어링 승인이 그룹 발신자 허용 목록으로 자동 확대되지 않는다.** 그룹은 따로 제한.

### 7-3. 외부 내용 ≠ 실행 허가 (프롬프트 인젝션)

웹 문서, 이메일, 채팅에는 명령처럼 보이는 문장이 섞일 수 있다. 이런 문장이 에이전트를 원래 작업보다 먼저 움직이게 만드는 것이 **프롬프트 인젝션**이다.

```text
외부 내용(웹·메일·채팅) ──→ [읽기 전용 에이전트가 요약] ──→ 판단 재료
                                                         │
                                         명령 실행·파일 변경은 별도 승인 후에만
```

- 외부 내용을 읽는 역할에는 **읽기 전용 도구**.
- 검색·웹 읽기·브라우저 도구는 **필요할 때만** 켠다.
- 음성 요청도 영향이 큰 행동 전에는 **말로 다시 읽어 주고 말로 승인**받는다. 말로 한 요청과 실제 실행에 다른 권한을 둔다.

> 💡 **한 줄로 기억하기**: 읽어 온 문서는 판단 재료일 뿐, 실행 허가가 아니다.

### 7-4. 실제 보안 권고 세 건이 보여 주는 것

| 권고 | 있었던 일 | 드러난 점 |
|---|---|---|
| 페어링 코드 권한 상승 | 채팅 명령 허용 발신자가 기기 페어링 코드를 만들어 operator·node 권한 기기를 등록할 수 있었음 | **대화 권한 ≠ 기기 등록 권한**인데 넘어갔다 |
| 명령 허용 목록 우회 | 인자 패턴 검사를 건너뛰어 실행 파일만 맞으면 다른 인자도 통과 | **명령 이름 제한 ≠ 인자 제한** |
| Gateway 자격 증명 유출 경로 | 모델이 지정한 loopback 주소로 요청 전달 시 자격 증명이 함께 전달될 수 있었음 | **모델이 정한 값이 자격 증명에 닿은** 경우 |

이건 피해 사고 보도가 아니라 **개발팀이 고친 뒤 스스로 공개한 권고**다(예: 첫 번째는 2026.5.4에서 수정). → **최신 버전 유지가 첫 번째 방어**라는 뜻이다.

## 8. pi: 작은 코어를 보면 무엇이 "바깥"인지 보인다

### 8-1. pi란

**pi** = 터미널에서 쓰는 작은 코딩 에이전트 CLI. 모델과 도구를 연결해 코딩을 돕고, 스크립트로 확장한다. 소개하는 이유: **pi 위에 내 필요에 맞춘 에이전트 도구를 만들 수 있기 때문**이다. 코어가 작으면 "코어에 있는 것 vs 바깥에 더할 것"을 나눠 볼 수 있다.

### 8-2. pi와 OpenClaw 비교

| 항목 | pi | OpenClaw |
|---|---|---|
| 화면 | TUI (터미널 안 화면) | WebChat, 채널 |
| 구독 로그인 | Claude Pro/Max로 OAuth | claude-cli |
| API 키 | 키 등록 | `ANTHROPIC_API_KEY` |
| 로컬 모델 | 로컬 Ollama | 이 노드에서 안 다룸 |
| 세션 기록 | `~/.pi/agent/sessions/` (JSONL) | `~/.openclaw/agents/` (SQLite) |
| 도구 제한 | `--tools` 옵션 | 권한 모드 |

- OAuth = 비밀번호를 넘기지 않고 로그인 권한을 맡기는 방식.
- JSONL = 한 줄에 JSON 하나. 첫 줄엔 세션 ID·시각·작업 폴더, 이후 줄엔 대화와 도구 호출 결과 → **화면 답변과 실제 호출을 따로 볼 수 있다**(5장과 같은 원리).

### 8-3. pi 위에 Gateway를 얹은 것이 OpenClaw

```text
[pi: 에이전트 코어] + [Gateway: 메시지 받기] = Clawdbot → … → OpenClaw
                       (초기엔 pi를 임베디드로 사용)
                              ↓
                  이후 자체 코어로 교체 (내장 런타임 이름: openclaw)
```

이름과 코어는 바뀌었어도 **코어 위에 채널과 기능을 조립하는 구조**는 그대로다. pi는 표준입출력(stdin/stdout)으로 요청·결과를 주고받는 **워커**로도 쓸 수 있다.

### 8-4. pi에 없는 것 = 설계 선택

| pi에 내장되지 않은 것 | 대신 쓰는 방법 |
|---|---|
| MCP 클라이언트 | 확장으로 더함 |
| 서브에이전트 | 확장이나 별도 구성 |
| 스케줄러 | OS 예약 기능이나 별도 확장 |

없는 게 결함이 아니라 **무엇을 코어에 둘지 고른 결과**다. OpenClaw는 채널·권한 모드·자동화를 한 도구에 담았고, pi는 바깥에서 조립하게 한다. → 도구를 비교할 때 **기능 유무 + 그 기능이 코어에 있는지 확장에 있는지**를 함께 본다.

### 8-5. 내 에이전트 도구를 만들 때 정할 다섯 가지

| 정할 것 | OpenClaw에서 본 곳 |
|---|---|
| 메시지를 어디서 받을지 | 채널 |
| 무엇을 할 수 있게 둘지 | 권한 모드, pi `--tools` |
| 어느 행동에 승인을 둘지 | 권한 모드, 페어링 |
| 모델을 어떻게 연결할지 | 온보딩의 인증 경로 |
| 세션 기록을 어디에 남길지 | `~/.openclaw/agents/`, `~/.pi/agent/sessions/` |

> 💡 **한 줄로 기억하기**: 에이전트 도구는 층을 조립한 것이다. 입구·권한·승인·모델·기록을 정하면 내 도구가 된다.

## 9. 멀티에이전트: 한 Gateway, 여러 에이전트

### 9-1. 챗봇 여러 개가 아니라 "라우팅 규칙"을 설계한다

실무에선 문의 담당, 코드 수정 담당, 자료 조사 담당처럼 역할이 나뉜다. OpenClaw는 **Gateway 하나 안에 서로 격리된 에이전트를 여럿** 두고, 들어온 대화를 담당 에이전트에게 보낸다.

```text
채널 메시지 → [바인딩: 받을 에이전트 고르기] → 에이전트 (자기 작업 폴더·자기 기록 안에서만)
```

### 9-2. 바인딩

**바인딩** = 채널 계정(Slack 워크스페이스 하나, WhatsApp 번호 하나 같은 단위)을 특정 에이전트에 연결하는 규칙.

```json5
{
  agents: {
    ownership: "explicit",
    entries: {
      main: { workspace: "~/.openclaw/workspace" },
      support: { workspace: "~/.openclaw/workspace-support" },
    },
  },
  bindings: [
    { agentId: "support", match: { channel: "discord", accountId: "support" } },
    { agentId: "main",    match: { channel: "discord", accountId: "*" } },
  ],
}
```

- `ownership: "explicit"`: 누가 어떤 대화를 맡을지 바인딩으로 명시.
- 첫 바인딩: Discord `support` 계정 → support 에이전트.
- 두 번째 `accountId: "*"`: 나머지 모든 Discord 메시지 → main.
- **어느 바인딩에도 안 맞으면 아무 에이전트도 못 받는다** → `AGENT_SELECTION_REQUIRED`. 그래서 "나머지 받는 에이전트"를 꼭 정해 둔다. (예전 `default: true`는 `openclaw doctor`가 새 형식으로 옮겨 줌)

### 9-3. 바인딩 vs 페어링 (헷갈리기 쉬운 쌍)

| | 바인딩 | 페어링·허용 목록 |
|---|---|---|
| 정하는 것 | **어느 에이전트가 받을지** | **누가 말을 걸 수 있는지** |
| 위치 | `bindings` | 채널 설정 |
| 한 줄 | 배정 규칙 | 출입 허가 |

### 9-4. 에이전트마다 분리되는 것

| 분리되는 것 | 내용 |
|---|---|
| 작업 폴더 | 다루는 파일이 처음부터 나뉨 |
| 상태 폴더 | 인증 프로필, 에이전트별 설정 |
| 대화 기록 | 에이전트별 SQLite 파일 |

- 기억·기록은 **기본으로 섞이지 않는다.** 함께 쓸 자료는 공유 문서로 따로 둔다.
- 상태 폴더를 같이 쓰면 인증·세션 상태가 충돌한다.
- **작업 폴더는 격리 장치가 아니다.** 폴더 밖을 막으려면 sandbox를 따로 둔다.

### 9-5. delegate: 자기 계정으로 대신 일하는 에이전트

**delegate** = 조직 안에서 **자기 이메일 주소·표시 이름**을 갖고, 사람으로 가장하지 않고, 정해진 권한 안에서 대신 행동하는 에이전트. "내 계정을 빌려주는 자동화"가 아니라 **권한 범위를 정한 보조 구성원 추가**다.

| 단계 | 할 수 있는 일 |
|---|---|
| 첫 단계 | 읽고 초안만. 승인 없이는 아무것도 밖으로 안 보냄 |
| 다음 단계 | 메일 발송·일정 생성을 delegate 자기 이름으로 |

권한을 넓히기 전에 도구 제한, sandbox, 감사 기록(audit log)부터. 넓은 위임 권한 하나가 유출되면 모든 사서함·캘린더가 뚫리므로 **최소 권한 원칙**.

### 9-6. standing orders와 병렬 전문 레인

**standing orders** = 에이전트에게 항상 적용되는 지시. 세 칸을 미리 적는다.

| 칸 | 적는 것 |
|---|---|
| 허용 | 해도 되는 것 |
| 승인 | 승인받아야 하는 것 |
| 중단 | 보이면 멈출 것 |

**병렬 전문 레인** = 연구·제작·검토처럼 **역할이 겹치지 않게** 나누고 **동시 실행 수를 정해 두는** 구성.

```json5
{
  agents: { defaults: { maxConcurrent: 4,
    subagents: { maxConcurrent: 8, delegationMode: "prefer" } } },
  messages: { queue: { mode: "collect", cap: 20, drop: "summarize" } },
}
```

- `maxConcurrent`: 동시 실행 한도.
- `messages.queue`: 몰리는 메시지를 모았다가 넘치면 요약해서 넘김.
- 에이전트 수를 늘리는 것보다 **역할 분리 + 처리량 한도**가 사고를 줄인다.

**agentToAgent**(에이전트끼리 서로의 세션에 접근)는 기본으로 켜져 있다. `allow`를 비우면 **모든 쌍이 접근 가능**하므로 필요한 상대만 적는다. 아예 막으려면 `enabled: false`.

```json5
{ tools: { agentToAgent: { allow: ["home", "work"] } } }
```

`openclaw agent --agent … --session-id …`는 특정 에이전트에게 **한 번 실행**을 시키는 별개의 명령이지, 에이전트 사이 대화를 여는 기능이 아니다. 역할 사이에 일을 넘길 땐 **대화를 통째로 공유하지 않고, 누구에게 무엇을 넘길지 정해서** 전달한다.

> 💡 **한 줄로 기억하기**: 바인딩으로 배정, 폴더·기록으로 분리, standing orders로 행동 규칙, 동시 실행 한도로 과부하 방지.

## 10. 모니터링: 얼마나 쓰고 있나

### 10-1. 토큰과 두 종류의 숫자

**토큰** = 모델이 주고받는 글의 양을 세는 단위. 입력·출력을 따로 세고 비용은 이 양으로 계산한다.

| 숫자 | 보여 주는 것 |
|---|---|
| 세션 단위 | 지금 대화가 얼마나 커졌나 |
| 전체 요약 | 지금까지 얼마를 썼나 |

### 10-2. 채팅에서 보기

```text
/status
/usage          (끄기 → 토큰 → 자세히 순서로 순환)
/usage tokens
/usage full
/usage cost
```

| 명령 | 보여 주는 것 |
|---|---|
| `/status` | 세션 토큰, 추정 비용, 제공사의 사용량 창(기간별 한도 사용량) 요약 |
| `/usage tokens` | 답변마다 입력·출력 토큰 한 줄 |
| `/usage full` | 모델, 추론 수준, 빠른/느린 처리, 컨텍스트 윈도우, 비용 |
| `/usage cost` | 세션 기록을 모아 계산한 로컬 비용 요약 |

실습 포인트: 대화를 몇 번 더 보낸 뒤 `/status`를 다시 보고, **입력·출력 중 어느 쪽이 빨리 늘어나는지** 본다. 이걸 보고 대화를 얼마나 이어 갈지 판단한다.

### 10-3. 명령줄에서 보기

```bash
openclaw status --usage     # Gateway 상태 + 제공자별 사용량·할당량
openclaw models status      # 인증 프로필 상태, 만료·끊김 확인
```

### 10-4. 왜 인증 경로를 다시 강조할까? ★

같은 화면의 숫자가 **인증 경로에 따라 뜻이 다르기** 때문이다.

| 인증 경로 | 화면의 숫자 | 계산하는 곳 |
|---|---|---|
| API 키 | 호출마다 계산한 **추정 비용(돈)** | OpenClaw (키를 갖고 있으니 직접 계산) |
| 구독 로그인 | **남은 한도 비율** | 제공사 |

어느 경로인지 모르고 숫자만 보면 **남은 한도 비율을 남은 돈으로 잘못 읽을 수 있다.** 4-3의 "누가 키를 들고 호출하나"가 여기서 다시 등장하는 이유다.

### 10-5. 운영용 도구 (지금은 이런 게 있구나 정도로 넘어가도 된다)

| 도구 | 한 줄 설명 |
|---|---|
| OpenTelemetry | 지표를 밖으로 내보냄 |
| Prometheus | 지표를 모아 봄 |
| audit | 누가 무엇을 승인했는지 이력 |
| 진단 번들 | 상태·로그를 압축 파일 하나로 (개인정보를 가려도 로그 요약이 있으니 비밀처럼 다룸) |

### 10-6. 사용량 · 진단 자료 · 제품 통계 구분

| 구분 | 해당하는 것 | 목적 |
|---|---|---|
| 내 사용량 관찰 | `/status`, `/usage`, `openclaw status --usage` | 내가 얼마나 쓰나 |
| 문제 분석 자료 | 진단 번들 | 문제 보고 |
| 제품 개선 통계 | 텔레메트리 | 제품 개선 (기본은 하루 한 번 업데이트 확인, 기능 통계는 동의 전까지 꺼짐) |

## 11. 자동화: 반복 작업 예약

### 11-1. automations는 모델이 아니라 Gateway의 스케줄러다

- **Gateway가 켜져 있어야** 예약 시간에 실행된다. 끄면 스케줄러도 멈춘다.
- 일정·실행 상태·기록은 공유 SQLite에 저장 → **재시작해도 예약이 남는다.**
- 결과는 채팅 채널, 웹훅, 기록으로 보낼 수 있다.
- `openclaw cron`은 같은 명령의 짧은 이름. 만들기·지우기·즉시 실행엔 **operator.admin** 권한 필요.

### 11-2. 실습 흐름

```text
목록 확인 → 3분 뒤 일회성 알림 → 5분마다 시보 → 실행 기록 확인
   → 대화로 예약 만들기(/loop) → 실습 뒤 작업 지우기 → 빈 목록 확인
```

```bash
openclaw automations list

date -u +%FT%TZ          # UTC 현재 시각 → 3분 뒤 ISO 시각 계산
openclaw automations create "<ISO시각>" --name "첫 알림" --session main \
  --system-event "3분 전에 예약한 알림이 도착했습니다"

openclaw automations create "*/5 * * * *" "지금 시각과 대기 중인 알림이 있으면 한 줄로 알려 줘" --name "5분 시보"

openclaw automations runs --id <job-id>
openclaw automations remove <job-id>
```

| 인자 | 하는 일 |
|---|---|
| `"<ISO시각>"` / `"*/5 * * * *"` | 일정 (항상 **일정 먼저, 할 일 다음**) |
| `--name` | 목록에서 알아볼 이름 |
| `--session main` | WebChat main 세션으로 보냄 |
| `--system-event "…"` | 프롬프트 대신 시스템 이벤트로 넣을 문장 |

**cron 표기식** (분 시 일 월 요일): `*/5 * * * *` = 5분마다, 나머지는 전부.

### 11-3. 일회성 vs 반복 (헷갈리기 쉬운 쌍)

| | 일회성 | 반복 |
|---|---|---|
| 실행 후 | 성공하면 **목록에서 자동 삭제** | 다음 실행 시각을 갖고 **목록에 남음** |
| 확인법 | 목록에서 사라졌는지 | 실행 기록에 횟수가 쌓이는지 |

**주의**: 5분 시보에는 `--session`이 없다. 세션을 안 정한 명령줄 작업은 실행마다 **새 세션(isolated)**에서 돌고, 전달 경로(채널·웹훅)가 정해져야 결과가 보인다. 그래서 WebChat에 안 나타날 수 있다 → **실행 기록으로 확인**한다.

### 11-4. 대화로 예약 만들기

| 방법 | 동작 |
|---|---|
| 반복 요청 알아채기 | 같은 부탁을 여러 번 하면 에이전트가 예약을 제안. cron이 아니라 **사람이 읽는 문장**("매주 평일 오전 7시에 … 이 방에 올립니다")으로 확인받고 생성 |
| `/loop` | 이 대화에 묶인 반복 작업 (소유자만) |

```text
/loop 5m 지금 시각을 한 줄로 알려 줘
/loop status
/loop stop
```

간격(5m)을 빼면 1분~1시간 사이에서 스스로 다음 실행을 정한다. `/loop`로 만든 것과 명령줄로 만든 것이 **한 목록에 같이 나온다** → 만드는 방법이 달라도 **스케줄러는 하나**다.

> 💡 **한 줄로 기억하기**: 예약은 Gateway가 돌린다. 만들었으면 반드시 지운다(켜져 있는 동안 계속 실행되므로).

## 12. 확장 기능: 기능 하나 = 범위·상태·권한이 함께 늘어난다

오늘은 켜지 않고 읽기만 한다. 기능을 더할 때마다 세 가지가 같이 늘어난다는 게 이 절의 축이다.

| 늘어나는 것 | 뜻 |
|---|---|
| 닿는 범위 | 새로 읽거나 다룰 수 있는 곳 (웹, 기기, 메일함) |
| 상태 | 그 기능이 남기는 기록 |
| 권한 | 그 기능에 허락해야 하는 범위 |

| 기능 | 하는 일 | 주의점 (보안 절과의 연결) |
|---|---|---|
| 브라우저 조작 | 페이지 열기·탭·스크린샷·클릭·입력·PDF | **웹 전체가 입력**이 된다 → 외부 내용 ≠ 실행 허가 원칙이 더 자주 적용 |
| 카메라·위치 노드 | 연결 기기의 사진, 위도·경도·고도·속도 | 실제 환경이 입력이 된다 → **기기 권한·노드 연결이 먼저** |
| Talk mode | 로컬 음성 인식+합성으로 음성 대화 | 소리 승인은 흘려듣기 쉽다 → 위험 작업은 **말로 정확히 재승인** |
| IMAP 메일함 감시 | 인증된 수신 메일을 **읽기 전용 reader agent**에 넘김 | 임의 메일을 주 에이전트에 바로 넣지 않음 → **가장 작은 권한의 별도 에이전트로 격리** |
| 모델 페일오버 | 문제 시 같은 제공자 안 프로필 교체 → 다음 모델로 | 실패를 없애는 게 아니라 **실패 후 순서**를 정함. 다음 모델·여러 프로필이 있어야 동작 |
| ClawHub 스킬 | 스킬 검색·설치 | **설치 가능 ≠ 안전**. 악성 표시는 거부하지만 감사 내용만 보여 주고 설치되는 것도 있음 → 문서 먼저 읽기 |
| iOS·Android 앱 | 휴대폰 카메라·위치·알림을 노드로 연결 | 휴대폰에서 에이전트에 닿는 경로가 하나 더 생김 |

```bash
openclaw skills search "calendar"
openclaw skills install @owner/<slug>
```

**공통 주의점 두 가지**
1. **experimental** 표시 기능은 미리 보기다. 형태가 빨리 바뀔 수 있으니 안정 경로가 있으면 그쪽 먼저.
2. 카메라·위치·음성·기기 조작은 권한과 노드 연결이 있어야 동작한다. **켜기 전에 그 권한을 줄 근거가 있는지** 먼저 확인.

## 13. 전체 흐름 한 번에 정리

```text
OpenClaw = 채팅으로 일을 맡기는 개인 어시스턴트
│
├─ 뼈대
│   ├─ 채널 (WebChat, Telegram) ── 입구
│   ├─ Gateway ── 어느 세션·도구로 보낼지 배정, 상시 실행
│   └─ 에이전트 런타임 ── 모델 호출 + 도구 실행
│
├─ 시작하기
│   ├─ 설치·온보딩 (인증 경로: API 키 = 돈 / claude-cli = 구독 한도)
│   ├─ doctor·gateway status ── 실패하면 멈춘다
│   └─ WebChat 127.0.0.1:18789 ── 외부에 열지 않는다
│
├─ 기록
│   ├─ 설정 / 세션 SQLite / 워크스페이스 / MEMORY.md ── 위치와 역할이 다름
│   └─ 답변(text) ≠ 실행(toolResult) ── 완료는 결과 줄로 판단
│
├─ 보안: 경계 세 가지
│   ├─ 권한 모드 (read-only → guarded → workspace → full)
│   ├─ 페어링·허용 목록 (누가 말을 걸 수 있나)
│   └─ 외부 내용 ≠ 실행 허가 (읽기 전용 에이전트 + 별도 승인)
│
├─ 구조 이해: pi
│   └─ 작은 코어 + 바깥에 조립 → OpenClaw도 pi + Gateway에서 출발
│
├─ 확장 운영
│   ├─ 멀티에이전트: 바인딩(배정) · 분리(폴더·기록) · standing orders · 동시 실행 한도
│   ├─ 모니터링: /status, /usage, openclaw status --usage (숫자 뜻은 인증 경로에 따라)
│   └─ 자동화: Gateway 스케줄러, 일회성 vs 반복, 쓰고 나면 지운다
│
└─ 확장 기능: 하나 더할 때마다 범위·상태·권한이 함께 늘어난다
```

> **핵심만 기억하면**
>
> 1. **채널은 입구, Gateway는 배정, 런타임은 실행이다.**
> 2. **모델이 "했다"고 말한 것과 실제로 한 것은 다르다. 결과 줄로 확인한다.**
> 3. **경계는 세 군데 따로 정한다: 파일·명령(권한 모드), 사람(페어링), 외부 내용(읽기 전용 + 승인).**
> 4. **사용량 숫자는 인증 경로를 알아야 읽을 수 있다: API 키면 돈, 구독이면 남은 한도.**
> 5. **기능·에이전트·예약을 더할수록 닿는 범위와 권한도 커진다. 필요한 만큼만, 쓰고 나면 정리한다.**
