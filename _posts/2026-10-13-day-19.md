Pro Tools 매뉴얼과 위키백과 등을 자료로, 터미널에서 직접 실행하는 RAG 챗봇을 만들었다. 과정에서 나온 질문과 정리 모음.

## 1. 검색 결과 개수 (top-k)

질문이 들어오면 22개 청크 전부와 점수를 매긴 뒤, 점수가 높은 순서대로 몇 개를 고를지 정하는 값.

```
질문: "바운스 어떻게 해?"
 1위 PT-009 최종 믹스 바운스 순서   0.78
 2위 PT-022 SOP: 납품 바운스 규칙   0.71
 3위 PT-010 클립을 파일로 내보내기  0.63
 ─── 여기까지 3개 ───
 4위 PT-012 단축키(Bounce Mix)      0.58
 …
(점수는 설명을 위한 예시)
```

| 개수 | 장점 | 단점 |
|---|---|---|
| 적게 (1~2개) | LLM이 헷갈릴 일이 적다 | 필요한 청크가 4위에 있으면 놓친다 |
| 3개 (가이드) | 균형이 맞다 | |
| 많게 (5개 이상) | 놓치는 게 줄어든다 | 관련 없는 청크도 섞인다. 작은 모델(qwen3.5:2b)은 그 내용까지 답에 섞기 쉽고, 입력이 길어져 답도 느려진다 |

2단계에서는 이 청크들이 그대로 LLM 입력에 들어간다. 그래서 **"몇 개를 보여 줄까"는 곧 "LLM에게 몇 개를 읽힐까"**와 같은 결정이다.

## 2. "관련 자료가 약함" 기준 점수 (threshold)

점수는 질문과 청크가 얼마나 비슷한지를 나타낸다. 코사인 유사도라서 1에 가까울수록 비슷하다. 1위 점수가 기준보다 낮으면 "자료에 이 질문의 답이 없을 가능성이 크다"고 보고 ⚠ 표시를 한다.

```
"바운스 어떻게 해?"   1위 0.78  → 관련 있음
"내일 날씨 어때?"     1위 0.42  → ⚠ 약한 근거 (0.55 미만)
```

이 기준이 중요한 이유: **검색은 항상 무언가를 1위로 돌려준다.** 날씨 질문에도 22개 중 가장 덜 엉뚱한 청크가 1위로 나온다. 기준이 없으면 LLM이 그 엉뚱한 청크로 답을 지어낼 수 있다. CLAUDE.md의 "모르면 지어내지 않기" 규칙을 지키는 장치가 바로 이 기준이다.

| 기준 | 결과 |
|---|---|
| 너무 높게 (예: 0.75) | 제대로 된 질문인데도 ⚠가 뜬다. 말투만 조금 바꿔도 점수가 떨어지기 때문 |
| 0.55 (가이드) | 물류 자료에서 관련 질문은 0.65 이상, 무관한 질문은 0.42~0.45로 나와서 그 사이에 둔 값 |
| 너무 낮게 (예: 0.35) | 날씨 질문도 통과해서 지어낸 답이 나올 수 있다 |

주의: 0.55는 물류 자료로 잰 값이다. Pro Tools 자료는 영어 메뉴 이름이 섞여 있어 점수 분포가 다를 수 있으니, 일단 0.55로 시작하고 관련 질문·무관한 질문의 점수를 실제로 재 본 뒤 조정한다.

## 3. 코드 구조와 실행 방법

- `src/ollama.mjs`: Ollama와 주고받는 일만 담당
- `src/ask.mjs`: 검색(1단계 search) → 프롬프트 조립 → `ollama.mjs` 호출 → 출처 출력까지 전체를 묶음

```bash
# 프로젝트 폴더로 이동
cd ~/Documents/Aifel/protools-rag

# 답변 받기 (2단계)
node src/ask.mjs "페이드 인은 어떻게 만들어?"

# RAG 없이 답변 받기 (비교용)
node src/ask.mjs "페이드 인은 어떻게 만들어?" --no-rag

# LLM에 보내는 프롬프트만 보기 (Ollama를 부르지 않음)
node src/ask.mjs "페이드 인은 어떻게 만들어?" --show-prompt

# 검색 결과 개수 바꾸기 (기본 3개)
node src/ask.mjs "페이드 인은 어떻게 만들어?" --k 5

# 검색만 하기 (1단계) — 여러 질문을 한 번에
node src/search.mjs "페이드 인은 어떻게 만들어?" "Slip 모드가 뭐야?"

# 하이브리드 검색
node src/search.mjs "Command+E 단축키는 뭐야?" --hybrid
```

### 일반 모드와 대화형 모드의 차이

"실행"은 터미널에 `node src/ask.mjs ...`를 입력하고 Enter를 누르는 것. 프로그램이 켜지고, 할 일을 마치면 꺼진다.

**일반 모드** — 켜질 때 질문 하나를 받고, 답한 뒤 바로 꺼진다.

```
$ node src/ask.mjs "Slip 모드가 뭐야?"     ← 실행 1번: 켜짐
🔎 … 💬 … 📚 … ⏱ …                         ← 답하고 꺼짐
$                                          ← 터미널로 돌아옴

$ node src/ask.mjs "Shuffle 모드가 뭐야?"  ← 질문하려면 명령을 다시 입력 (실행 2번)
🔎 … 💬 … 📚 … ⏱ …
$
```

질문할 때마다 명령 전체를 다시 쳐야 하고, 켜질 때마다 임베딩 모델을 처음부터 불러온다.

**대화형 모드** — 한 번 켜 두면 `exit`를 입력할 때까지 꺼지지 않는다.

```
$ node src/ask.mjs                         ← 실행 1번: 켜짐
질문> Slip 모드가 뭐야?
🔎 … 💬 … 📚 … ⏱ …
질문> Shuffle 모드가 뭐야?                 ← 명령 없이 질문만 입력
🔎 … 💬 … 📚 … ⏱ …
질문> exit                                 ← 이때 꺼짐
$
```

"실행 한 번에 질문 하나"는 "질문 하나마다 프로그램을 새로 켜야 한다"는 뜻이고, 대화형 모드는 한 번 켜 두고 여러 질문을 하는 것. 두 모드 모두 각 질문은 따로 처리한다.

## 4. 실습 정리 및 회고

- **자료**: Pro Tools 매뉴얼, 위키백과 등
- **주제**: 녹음 준비, 편집, 바운스와 익스포트, 단축키, SOP 규칙
- **설정**: 검색 결과 개수(top-k) 3개, 기준 점수 0.55

### 기준 점수를 0.55로 둔 이유

초보자는 전문용어를 모르고 쉬운 말로 물을 때가 많다. 실제로 "소리가 점점 커지게 시작하려면?"이라고 물으니 점수가 **0.596**으로, 용어를 쓴 질문보다 낮게 나왔다. 기준을 높이면 이런 질문을 놓친다.

반대로 "내 세션 지금 몇 BPM이야?" 같은 범위 밖 질문은 '세션'이라는 단어 때문에 **0.619**까지 올라갔다. 기준을 올려도 이런 질문은 거를 수 없었다.

→ 기준은 0.55로 두고, 범위 밖 질문은 **LLM에게 주는 규칙**으로 막았다.

### RAG 비교 실험

질문: "녹음 지연이 생기면 버퍼를 어떻게 바꿔?"

| | 답변 | 판정 |
|---|---|---|
| RAG 없음 | "버퍼를 늘려라" | 정답과 반대 |
| RAG 있음 | "버퍼를 줄여라" | 정답 |

답변 시간도 10~58초에서 **4~7초**로 줄었다.
