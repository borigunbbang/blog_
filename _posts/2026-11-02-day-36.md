## 1강. AI 분류 성능을 평가하는 방법

AI가 고객 문의를 제대로 분류했는지 확인하려면 먼저 평가 기준이 필요하다. 문의를 네 유형으로 분류한다고 하자.

| 유형 | 뜻 |
|---|---|
| SHIPPING | 배송 문의 |
| PRODUCT | 상품 문의 |
| RETURN_REFUND | 교환·반품·환불 문의 |
| OTHER | 그 외 문의 |

| 지표 | 뜻 | 예시 |
|---|---|---|
| Accuracy (정확도) | 전체 중 정답을 맞힌 비율 | 100건 중 90건 맞힘 → 90% |
| Precision (정밀도) | 특정 유형이라고 예측한 것 중 실제 그 유형인 비율 | 반품이라 분류한 10건 중 실제 반품 8건 → 80% |
| Recall (재현율) | 실제 그 유형 중 AI가 찾아낸 비율 | 실제 반품 20건 중 15건 찾음 → 75% |
| F1 Score | Precision과 Recall을 함께 고려한 점수 | 한쪽만 높고 다른 쪽이 낮은 문제를 드러낸다 |

### Macro F1과 Weighted F1

| 지표 | 계산 방식 |
|---|---|
| Macro F1 | 각 유형의 F1을 동일한 비중으로 평균 |
| Weighted F1 | 각 유형의 데이터 개수에 따라 가중 평균 |

배송 문의가 90건, 반품 문의가 10건이라면 Weighted F1은 데이터가 많은 배송 문의의 영향을 더 많이 받고, Macro F1은 두 유형을 같은 비중으로 평가한다.

> 정확도 하나만으로는 AI가 모든 유형을 골고루 잘 분류하는지 알기 어렵다. 그래서 여러 지표를 함께 쓴다.

## 2강. Confusion Matrix와 규칙 기반 분류

### Confusion Matrix (혼동 행렬)

어떤 유형을 맞혔고 어떤 유형으로 잘못 분류했는지 보여 주는 표다.

- 행: 실제 정답 / 열: AI 예측 / 대각선: 맞힌 결과 / 대각선 밖: 잘못 분류한 결과

| 실제 \ 예측 | 배송 | 반품 |
|---|---|---|
| 배송 | 8 | 2 |
| 반품 | 3 | 7 |

배송 10건 중 8건, 반품 10건 중 7건을 맞혔다. **행** 기준으로 보면 실제 정답 중 얼마나 찾았는지(Recall), **열** 기준으로 보면 그 유형이라 예측한 것 중 얼마나 맞았는지(Precision)를 볼 수 있다.

### Rule-based Classification (규칙 기반 분류)

AI 모델 없이 미리 정한 조건으로 분류한다.

```python
if "환불" in question:
    route = "RETURN_REFUND"
elif "배송비" in question:
    route = "SHIPPING"
```

한 문의에 여러 키워드가 동시에 있을 수 있어서 **규칙의 순서**가 결과를 바꾼다.

### Router Graph (라우터 그래프)

규칙 기반 분류기를 그래프의 한 단계로 연결한다.

```
고객 문의 → 문의 유형 분류 → 처리 경로 결정 → 유형에 맞는 처리
```

분류 방식을 바꿔도 전체 그래프 구조는 유지된다. 처음엔 규칙 기반으로, 이후 LLM 분류기로 교체할 수 있다.

## 3강. LLM 라우터와 확신도

### LLM Router

LLM이 질문의 의미를 이해해 유형을 분류한다. "주문한 신발이 아직 안 왔는데 언제 도착하나요?"는 키워드만으론 애매해도 LLM은 SHIPPING으로 분류할 수 있다.

| 구분 | 규칙 기반 | LLM 기반 |
|---|---|---|
| 판단 방식 | 미리 설정한 키워드 | 문맥과 의미 분석 |
| 장점 | 단순하고 예측 가능 | 다양한 표현 이해 |
| 단점 | 예상 못 한 표현에 취약 | 잘못 분류할 가능성 |
| 수정 방법 | 규칙 직접 수정 | 프롬프트와 예시 수정 |

### Confidence (확신도)와 Threshold (임계값)

```
route = SHIPPING
confidence = 0.85
```

확신도는 LLM이 자기 분류를 얼마나 확신하는지 반환한 값이다. 단, **실제 정답일 확률과 반드시 일치하지는 않는다.**

임계값을 0.7로 두면:

| 확신도 | 처리 |
|---|---|
| 0.9 | 정상 처리 |
| 0.8 | 정상 처리 |
| 0.6 | 상담원 이관 |

확신하지 못하는 문의는 무리하게 처리하지 않고 상담원에게 넘긴다.

### OTHER와 OUT_OF_SCOPE

- **OTHER**: 기존 유형 어디에도 명확히 해당하지 않는 **분류 결과**
- **OUT_OF_SCOPE**: 회사의 응대 범위를 벗어난 문의를 처리하는 **행동** (예: 이 상담 에이전트 담당이 아닌 홍대점 영업시간 문의)

## 4강. Prompt와 Few-shot으로 분류 개선하기

분류 프롬프트에 들어갈 것: **역할**(고객 상담 문의 분류기), **분류 기준**(각 유형의 정의), **출력 형식**(route, confidence 등), **주의사항**(판단 기준과 예외 조건).

| 구분 | 설명 |
|---|---|
| Zero-shot | 예시 없이 지시문만 제공 ("다음 문의를 배송, 상품, 반품 중 하나로 분류하세요.") |
| Few-shot | 몇 가지 질문과 정답 예시를 함께 제공 |

```
질문: 배송이 언제 오나요?        정답: SHIPPING
질문: 환불하고 싶어요.           정답: RETURN_REFUND
질문: 이 제품 소재가 뭔가요?     정답: PRODUCT
```

⚠️ **Few-shot 예시와 평가 데이터를 같은 것으로 쓰면 안 된다.** 이미 본 문제로 평가하면 실제보다 성능이 높게 나온다 — **데이터 누수(Data Leakage)**.

> 프롬프트와 예시를 조정한 뒤에는 반드시 별도의 평가 데이터로 성능을 확인한다.

## 5강. 매뉴얼 컨텍스트와 조회 도구 만들기

여기서부터는 분류를 넘어 실제 질문에 답하는 시스템을 만든다.

### 왜 매뉴얼을 전부 넣으면 안 될까

불필요한 정보까지 전달되고, 토큰과 응답 시간이 늘고, 질문과 무관한 정책을 답변에 섞을 수 있다. 배송 문의에 반품 배송비 정책까지 넣으면 잘못된 금액을 안내할 수 있다. 그래서 유형에 따라 필요한 매뉴얼만 골라 전달한다 → **Context Assembly (컨텍스트 조립)**.

| 구분 | 내용 |
|---|---|
| 공통 | 상담 원칙, 분류 기준, 응대 범위, 말투 |
| 주문 | 주문 및 구매 관련 정책 |
| 상품 | 상품 정보 관련 정책 |
| 배송 | 배송 관련 정책 |
| 교환·반품·환불 | 교환 및 반품 관련 정책 |

SHIPPING 문의라면 공통 + 배송 매뉴얼을 조합해 전달한다.

### 고정값과 조회값 구분

| 매뉴얼 고정값 (바로 사용) | 조회가 필요한 값 (상품·주문마다 다름) |
|---|---|
| 기본 배송비 2,500원 | 특정 상품의 재고 |
| 반품 배송비 5,000원 또는 2,500원 | 특정 주문의 배송 상태 |
| 배송 마감 시간 11:00 | 반품 진행 상태 |
| 지정 택배사 롯데택배 | 상품별 무료배송 기준 |
| | 재입고 확정 여부와 예정일 |

### Tool 만들기

매뉴얼의 [어드민 조회] 항목을 바탕으로 조회 함수를 만든다.

| Tool | 역할 |
|---|---|
| get_order_status | 주문 상태 조회 |
| get_product_detail | 상품 정보 및 재고 조회 |
| get_product_options | 상품 옵션 및 개별 구매 가능 여부 조회 |
| get_shipping_policy | 배송비 및 무료배송 기준 조회 |
| get_return_policy | 반품 가능 기간과 조건 조회 |
| get_return_status | 반품 진행 상태 조회 |
| get_restock_info | 재입고 정보 조회 |
| escalate_to_agent | 상담원 이관 |

### 조회할 때 주의할 점

- 데이터가 없으면 임의로 만들지 않는다.
- 존재하지 않는 상품 ID는 오류로 반환한다.
- 아직 확인되지 않은 정보는 `None`으로 반환할 수 있다.
- `$`로 시작하는 내부 교육용 정보는 고객 답변에 노출하지 않는다.
- 계산할 수 있는 값은 가급적 **코드에서** 계산한다. (무료배송 기준 100,000원, 구매 금액 59,000원 → 부족액 41,000원을 코드가 계산해 반환)

### 상품 ID를 찾는 과정

고객은 상품 ID보다 상품명을 쓴다. "캔버스화 배송비 얼마예요?"

```
상품명: 캔버스화 → 상품 ID 검색 → P4001 → 배송비 조회
```

강의의 상품 ID 추출 보조 함수와, 실제 서비스의 상품명 검색 기능은 구분해서 이해한다.

## 6강. 답변 생성과 Tool Calling

### 답변 생성기의 세 가지 입력

| 입력 | 역할 |
|---|---|
| 고객 문의 | 무엇을 질문했는지 |
| 매뉴얼 컨텍스트 | 어떤 정책과 기준을 따라야 하는지 |
| 조회 결과 | 실제 상품이나 주문 정보 |

### 답변 생성 프롬프트의 규칙

- 매뉴얼의 고정값은 그대로 사용한다.
- [어드민 조회] 항목은 조회 결과만 사용한다.
- 주문·반품 상태를 조회 없이 단정하지 않는다.
- 조회 결과가 null이면 아직 확인되지 않았다고 안내한다.
- 정보가 부족하면 주문번호나 상품명을 물어본다.
- 정중한 한국어로 1~3문장 정도로 짧게 답한다.

### 규칙과 절차의 차이

- **규칙(Rule)**: 반드시 지켜야 할 조건. 예: 상품명이 나오면 상품 검색을 한다.
- **절차(Procedure)**: 작업 순서. 예: 질문 분석 → 상품명 추출 → 상품 검색 → 상품 ID 확인 → 배송비 조회 → 답변 작성

실습에서는 단순 규칙보다 **구체적인 단계별 절차**를 줬을 때 다양한 표현에서도 도구 호출이 더 일관됐다.

### Tool Calling

AI가 필요한 도구를 판단하고 실행을 **요청**하는 방식. AI가 함수를 직접 실행하지 않고, **실행은 파이썬 코드가** 한다.

LangChain에서는 `@tool` 데코레이터로 일반 함수를 도구로 등록한다.

```python
@tool
def get_shipping_policy(
    product_id: str,
    order_amount: Optional[int] = None
):
    """
    상품 ID와 구매 금액을 이용해
    배송 정책을 조회합니다.
    """
    return result
```

| 요소 | 역할 |
|---|---|
| `@tool` | 함수를 AI가 사용할 도구로 등록 |
| Type Hint | 입력값의 자료형 지정 |
| Docstring | 도구가 어떤 기능을 하는지 설명 |
| `Optional[int]` | 정수 또는 None 허용 (별개 자료형이 아니라 타입 힌트) |

**전체 과정**

```
① AI에게 도구 목록 전달 (이름, 설명, 입력 형식)
② AI가 필요한 도구와 입력값을 요청
③ 파이썬 코드가 함수 실행 (실제 데이터 조회)
④ 조회 결과를 AI에게 전달 → 추가 도구 요청 또는 최종 답변
```

### LangGraph로 Tool Calling 구현

- **agent** 노드: AI가 판단하고 도구 호출을 요청
- **tools** 노드: 요청된 함수를 실제로 실행

| 조건 (Conditional Edge) | 이동 |
|---|---|
| Tool 호출 요청이 있음 | tools 노드 |
| Tool 호출 요청이 없음 | END |

tools 실행 후에는 다시 agent로 돌아가므로 도구를 여러 번 호출할 수 있다. 무한 반복을 막기 위해 **Recursion Limit**(반복 실행 한도)을 둔다.

### 상품 ID 추출 보조 함수

```
고객: 캔버스화 배송비 얼마예요? → 상품 ID 추출 → P4001 → get_shipping_policy("P4001")
```

- 상품 ID 추출: 어떤 상품인지 **식별**
- 배송비 조회: 그 상품의 **배송 정책 확인**

상품 ID 추출 함수는 Tool로 등록해도 되지만 꼭 그래야 하는 건 아니다. 개발자 코드가 미리 실행하는 일반 보조 함수로 만들어도 된다.

## 7강. 가드레일로 출처 없는 숫자 잡기

프롬프트에 "근거 없는 숫자를 쓰지 마세요"라고 써도 항상 지켜지지 않는다. 그래서 답변이 완성된 뒤 따로 검사한다 → **Guardrail (가드레일)**.

### 숫자의 출처

1. Tool이 반환한 조회 결과
2. 매뉴얼에 명시된 고정값
3. 허용된 한 단계 산술 계산 결과

이 중 어디에서도 근거를 찾을 수 없는 숫자는 위반이다.

```
① 답변에서 숫자 추출   (100,000 / 41,000 / 2,500)
② 숫자 출처 확인       (조회 결과, 매뉴얼 고정값, 허용 계산 결과와 비교)
③ 검사 결과            (모두 근거가 있으면 통과, 없으면 위반)
```

- **표기 정규화**: 100,000 / 100000 / 100,000원을 쉼표 등을 제거해 같은 값으로 비교한다.
- **작은 숫자 처리**: 2~3영업일, 1~3문장 같은 일반 표현의 숫자는 허용 목록을 둔다. 강의에서는 1,000 이상의 금액을 주요 검사 대상으로 삼았다.
- **계산 결과 처리**: 100,000 − 59,000 = 41,000처럼 조회 결과에 직접 없는 값도 한 단계 산술 계산이면 허용한다.

### 가드레일의 한계

- 숫자가 없는 잘못된 답변은 검사하지 못한다.
- 정상 답변을 위반으로 판단하는 **오탐**이 생길 수 있다.
- 잘못된 숫자를 놓치는 **미탐**이 생길 수 있다.

그래서 정답셋의 must, forbid 검사 같은 다른 평가 장치도 필요하다. 위반이 발견되면 답변을 다시 생성하거나 상담원에게 이관한다.

## 8강. 정답셋 평가와 전체 그래프 연결

### 정답셋 (Golden Dataset)

AI 답변은 표현이 다양해서 정답 문장과 똑같은지로 평가하기 어렵다. 그래서 답변이 지켜야 할 조건을 정답셋으로 만든다.

| 항목 | 의미 |
|---|---|
| action | 해야 할 행동 |
| tools | 반드시 호출해야 하는 도구 |
| must | 답변에 반드시 포함해야 할 사실 |
| forbid | 답변에 포함되면 안 되는 내용 |
| must_ask | 반드시 되물어야 하는 정보 |

상품을 특정하지 않은 배송비 문의라면:

```
action:   ASK
must:     2,500
forbid:   100,000 / 40,000 / 50,000
must_ask: 상품명
```

기본 배송비는 안내하되 상품별 무료배송 기준은 단정하지 말고 상품명을 물어야 한다는 뜻이다.

### 첫 번째 턴 34건 평가

정답셋은 34개 대화, 총 112턴이다. 첫 평가에서는 각 대화의 **첫 턴 34건**만 썼다. 뒤쪽 턴은 앞선 대화 맥락에 영향을 받기 때문이다.

| 행동 | 건수 |
|---|---|
| ANSWER | 22 |
| ASK | 8 |
| OUT_OF_SCOPE | 2 |
| CONFIRM | 1 |
| ESCALATE | 1 |

### 채점기 자체 검증

에이전트를 평가하기 전에 **채점기**가 제대로 작동하는지 먼저 확인한다. 정답셋의 모범 답안(reference) 34건을 채점기에 넣어 모두 통과하면 채점기가 의도대로 작동하는 것이다. 모범 답안이 실패한다면 에이전트보다 채점기부터 봐야 한다.

### 에이전트 평가

- 행동 판정 혼동표
- forbid 위반 건수
- 필요한 Tool 미호출 건수
- must 누락 여부

특히 **forbid 위반**이 중요하다. 조회 전에 근거 없는 숫자를 단정했다면 문장이 아무리 자연스러워도 실패다.

| 구분 | 확인할 항목 | 실패하면 |
|---|---|---|
| 능력 | tools, must | 필요한 정보를 제공하지 못함 |
| 안전 | forbid, action=ASK | 잘못된 안내를 할 수 있음 |

### 전체 LangGraph 연결

Router → Context Assembly → Tool Calling → Answer Generator → Guardrail을 하나의 그래프로 연결하고 조건부 엣지를 붙인다.

| 조건 | 처리 |
|---|---|
| 정상 문의 | 조회 및 답변 생성 |
| 상담원 이관 필요 | ESCALATE |
| 응대 범위 밖 | OUT_OF_SCOPE |
| 외부 채널 주문 | 범위 밖 안내 |
| 가드레일 위반 | 재생성 또는 상담원 이관 |

`StateGraph`는 각 단계를 노드로 만들고 조건부 엣지로 경로를 연결한다. 단, **LangGraph가 분기 기준을 알아서 정해 주지는 않는다.** 어떤 조건에서 어디로 갈지는 개발자가 먼저 설계해야 한다.

### 실제 고객 문의 40건 테스트

정답셋 34건만으로는 실제 문의 대응력을 알기 어려워, 실제 문의에서 무작위로 40건을 골라 정답 라우트 없이 실제 시스템처럼 처리하게 했다.

- **자동화율**: 이관이나 추가 질문 없이 답변까지 도달한 비율
- **조회율**: 답변한 문의 중 실제로 도구를 호출한 비율

발견한 문제:
1. **식별 정보 부족** — "이거 언제 와요?"처럼 주문번호나 상품 정보가 없으면 조회하기 어렵다.
2. **상품명 연결 문제** — 고객은 "원피스", "가방"이라 하지만 카탈로그엔 더 구체적인 상품명이 있다.
3. **확신도 부족** — 짧은 단답이나 이전 대화가 필요한 질문은 판단이 어려워 이관될 수 있다.

> AI 모델 성능뿐 아니라 실제 데이터 접근, 고객 표현과 상품 데이터의 연결도 자동화율에 영향을 준다.

### 멀티턴 대화와 Checkpointer

| 용어 | 역할 |
|---|---|
| Checkpointer | 대화 상태 저장 및 복원 |
| thread_id | 대화를 구분하는 ID |
| State | 현재 대화에서 유지되는 상태 |

같은 `thread_id`로 다시 호출하면 이전 대화 상태를 이어서 쓴다. 실제 서비스에서는 메모리 대신 데이터베이스 기반 Checkpointer를 쓸 수도 있다. 강의에서는 이전 턴의 상품명이나 주문번호를 다음 턴에서 활용하는지 확인했다.

## 9강. 전체 정리와 개선 과제

### 이번에 만든 것

- 문의 유형을 분류하는 라우터
- 확신도가 낮으면 이관하는 기능
- 유형에 맞는 매뉴얼 컨텍스트 조립
- 필요한 정보를 조회하는 Tool
- 조회 결과를 활용하는 답변 생성기
- 숫자의 출처를 검사하는 가드레일
- 전체 흐름을 연결하는 LangGraph
- 정답셋과 실제 고객 문의를 이용한 평가

### 발견한 세 가지 개선점

| 개선 과제 | 해결하려는 문제 |
|---|---|
| 엔티티 링킹 | 고객 표현과 실제 상품 카탈로그 연결 |
| 대화 상태 관리 | 이전 대화에서 필요한 정보 유지 |
| 되묻기 기준 | 검색과 추가 질문 사이의 판단 기준 개선 |

- **엔티티 링킹(Entity Linking)**: "원피스", "가방" 같은 표현을 실제 카탈로그 상품과 연결한다. 의미 기반 검색이나 카탈로그 검색 API가 개선 방향이다.
- **대화 상태 관리**: 이전 발화를 단순히 이어 붙이면 길어질수록 불필요한 정보가 섞이므로, 필요한 정보만 유지한다.
- **되묻기 기준**: 검색을 적극적으로 하면 조회 성공률은 오르지만 정보가 부족한데도 성급히 답할 위험이 있고, 너무 조심하면 대부분 되묻기만 한다. 검색할 조건과 되물을 조건을 더 명확히 해야 한다.

| Rule-based | 미리 정한 규칙으로 판단하는 방식 |
| Router | 입력을 분석해 처리 경로를 정하는 구성 요소 |
| LLM | 대규모 언어 모델 |
| Confidence | 모델이 반환한 확신도 |
| Threshold | 판단 기준이 되는 임계값 |
| Prompt | AI에게 주는 지시문 |

| Few-shot | 예시를 함께 제공하는 방식 |

| Tool | AI가 사용할 수 있도록 연결한 기능 |

## 꼭 이해해야 할 핵심 5가지

1. **AI가 판단하는 것과 실제 작업을 실행하는 것은 다르다.** AI는 Tool을 선택하고 실행을 요청할 뿐, 함수 실행은 파이썬 코드가 한다.
2. **AI에게 모든 정보를 주는 것이 좋은 방법은 아니다.** 질문에 필요한 매뉴얼과 조회 결과만 전달하는 컨텍스트 조립이 필요하다.
3. **AI가 모르면 답하지 않게 만들어야 한다.** 확신도가 낮으면 이관하고, 정보가 부족하면 되묻게 설계한다.
4. **AI가 만든 답변을 그대로 믿으면 안 된다.** 가드레일과 정답셋으로 근거와 품질을 검사한다.
5. **에이전트는 만들고 끝나는 게 아니라 평가하고 개선하는 시스템이다.** 실제 문의로 테스트하며 문제 지점을 찾아 고친다.
