같은 에이전트 루프를 감싼 여러 하네스를 일곱 기능으로 나눠 비교하는 프로젝트 노드다. 11개 강의 순서대로 정리한다.

## 1. 하네스의 일곱 기능과 비교 카드

### 하네스란

같은 코딩 에이전트를 써도 잘 되는 작업과 그렇지 않은 작업이 있다. 그 차이는 어디서 생길까?

> **하네스**는 모델이 일하는 동안 요청, 도구, 기록, 승인, 관찰(observation)을 연결하는 실행 환경이다.

```
요청 → [ 상태 → 모델 → 도구 → 관찰 → 상태 … ]
        └──────── 이 루프 전체를 하네스가 감싼다 ────────┘
```

같은 모델도 행동을 적는 형식, 남겨 둘 컨텍스트, 허용된 권한이 달라지면 다른 결과를 낸다. 그래서 결과의 차이를 모델의 답변 능력만으로는 설명할 수 없다.

### 기능 지도: 맡긴 일이 막히는 곳을 찾는 일곱 기능

이 노드는 하네스를 일곱 기능으로 나눠 보고, 이 분류를 **기능 지도**라고 부른다. 기능 지도는 맡긴 일이 멈춘 이유를 찾는 데 쓴다. 3강부터 9강까지 아래 순서대로 한 기능씩 다룬다.

| 기능 | 하는 일 |
|---|---|
| 행동 포맷 | 모델이 읽고, 고치고, 실행하는 행동을 실패하기 어려운 형식으로 적게 한다 |
| 컨텍스트 관리 | 긴 작업에서 무엇을 남기고 무엇을 줄일지 정한다 |
| 경험·스킬 축적 | 한 번 해결한 일을 다음 작업에 다시 쓴다 |
| 성찰(reflection) | 실행 결과를 살펴 다음 행동을 고친다 |
| 미니멀(단순성) | 필요한 구성만 남겨 운영 부담을 줄인다 |
| 권한·보안 | 읽기, 수정, 실행의 허용 범위와 승인 방식을 정한다 |
| 평가 루프 | 결과가 맞았는지 어떤 근거로 확인할지 정한다 |

기능 지도는 다음 세 질문을 차례로 던지며 쓴다.

1. 이 일은 **어디서 막히는가?** 행동이 애매한가, 컨텍스트가 넘치는가, 경험이 재사용되지 않는가, 승인이 많은가, 결과를 증명하기 어려운가
2. 그 병목을 줄일 **기능은 무엇인가?**
3. 그 기능이 실제로 작동했다는 **기록은 어디에서 확인**할 수 있는가?

이 세 질문으로 제품 설명을 보기 전에 맡길 일의 범위를 먼저 정한다. 10강에서 도구 후보를 줄일 때도 이 세 질문을 다시 쓴다.

### 기능 지도와 비교 카드

| 구분 | 무엇인가 |
|---|---|
| 기능 지도 | 맡길 일의 병목을 진단하는 일곱 가지 분류 |
| 비교 카드 | 도구 화면과 문서를 같은 방식으로 관찰하기 위한 여섯 칸짜리 기록 양식 |

기능 지도에서 컨텍스트 관리가 중요하다고 판단한 뒤에도, 카드에서는 그 도구의 상태와 주요 동작이 실제로 어떻게 보이는지 확인한다.

| 카드 칸 | 관찰할 내용 |
|---|---|
| 진입점 | 요청이 들어가는 화면, 명령, 연결 지점 |
| 상태 | 세션, 대화, 작업 기록이 남는 위치 |
| 주요 동작 | 읽기, 검색, 수정, 실행 중 화면에서 확인한 행동 |
| 권한 경계 | 읽기 밖의 행동 전에 승인이나 제한이 보이는지 |
| 1차 자료 | 실행 기록, 설정, 공식 문서처럼 나중에 다시 열 수 있는 근거 |
| 한계 | 이번 관찰만으로 확인하지 못한 범위 |

이후 강의에서는 주요 도구를 이 여섯 칸으로 소개한다. 한 기능만 살펴보는 도구(Hermes, 9강의 SWE-agent)는 그 기능에 해당하는 항목만 표로 정리한다.

### 근거 종류 표기

연구와 도구를 인용할 때 근거의 종류를 함께 적는다. 과제 보고서에서도 같은 표기를 쓴다.

| 표기 | 뜻 |
|---|---|
| [학술] | 학회·학술지 논문이나 arXiv에 공개된 연구 |
| [벤더] | 도구를 만든 회사나 개발자가 직접 보고한 수치와 설계 글. 독립적인 비교가 아니다 |
| [공식 문서] | 도구의 공식 문서나 저장소 README에 있는 기능·설정 설명 |

## 2. 코딩 에이전트 화면에서 하네스 신호 관찰하기

제품 설명만 읽지 않고, 지금 쓰는 도구가 요청을 받은 순간부터 화면에 무엇을 보여 주는지 직접 관찰한다. 관찰할 도구는 다음 둘 중 이미 쓰고 있는 하나다(수업 환경에는 둘 다 설치돼 있다).

| 도구 | 설명 |
|---|---|
| Claude Code | Anthropic이 만든 터미널용 코딩 에이전트. 터미널 안에서 저장소를 읽고, 파일을 고치고, 명령을 실행한다 |
| opencode | 오픈소스 터미널 코딩 에이전트. 여러 모델 제공자를 설정에서 골라 쓸 수 있다 |

이번 실습에서는 로그인 변경, 확장 연결, 파일 수정을 하지 않는다. 요청은 읽기 전용 작업 하나면 충분하다(예: 현재 작업 폴더의 파일 목록 읽기, 공개 문서 한 건 요약). 결과의 좋고 나쁨을 평가하지 않고, 요청이 들어가는 곳과 실행 범위가 화면에 어떻게 보이는지 찾는다.

### 설치 안내 (개인 컴퓨터에서 실습할 때)

**Claude Code** — Pro, Max, Team, Enterprise 플랜이나 Console(API) 계정이 필요하다. 무료 claude.ai 플랜으로는 쓸 수 없다.

```bash
# macOS, Linux, WSL
curl -fsSL https://claude.ai/install.sh | bash

# Windows PowerShell
irm https://claude.ai/install.ps1 | iex

# Windows 명령 프롬프트(CMD)
curl -fsSL https://claude.ai/install.cmd -o install.cmd && install.cmd && del install.cmd
```

- 설치 후 새 터미널 창에서 `claude --version`으로 버전을 확인한다. `claude`를 처음 실행하면 브라우저가 열리고 로그인을 진행한다.
- Windows에서는 Git for Windows를 함께 설치하면 Bash 도구를 쓰고, 설치하지 않으면 PowerShell로 명령을 실행한다. 그래서 시범과 다른 도구 이름이 보일 수 있다. ([공식 문서] Anthropic, Claude Code 설치 문서)

**opencode**

```bash
# macOS, Linux (Windows는 WSL에서 이 명령을 권장)
curl -fsSL https://opencode.ai/install | bash

# WSL을 쓰지 않을 때
scoop install opencode
choco install opencode
npm install -g opencode-ai   # Node.js 필요
```

설치 후 `opencode`를 실행하고 화면에서 `/connect`를 입력해 쓸 모델 제공자와 API 키를 등록한다. ([공식 문서] opencode, 설치 문서)

### 관찰 범위 정하기 — fixture

작업 폴더는 기존 작업 자료와 분리하고, 그 안에 간단한 fixture 하나만 둔다.

> **fixture**: 시험할 때마다 결과가 똑같이 나오도록 미리 준비해 둔 고정 자료를 가리키는 테스트 용어. 자료가 늘 같아야 달라진 것이 자료가 아니라 도구라고 말할 수 있다.

> 💡 **비유**: 요리 교실에서 매번 같은 재료를 미리 다져 두는 것과 비슷하다. 재료(fixture)가 그때그때 다르면 결과의 차이가 요리사(도구)의 실력 때문인지 재료 때문인지 구분할 수 없다. 다른 점은, 요리 재료는 매번 새로 준비하지만 fixture는 같은 파일을 그대로 다시 쓴다는 것이다.

- 공개 문서 한 건 또는 내용이 알려진 작은 텍스트 파일 한 건이면 충분하다.
- 비밀값, 개인 자료, 실제 저장소, 수정이 필요한 파일은 넣지 않는다.
- 관찰 메모에는 도구 이름과 버전, 작업 폴더 위치, fixture 종류를 먼저 적는다. 나중에 같은 화면을 다시 볼 때 어떤 조건에서 본 것인지 구분하기 위해서다.

### 화면에서 찾을 다섯 신호

| 신호 | 화면에서 볼 곳 | 연결되는 기능 |
|---|---|---|
| 입력 | 요청을 입력한 위치. 응답과 구분돼 남는지 본다 | 행동 포맷 |
| 도구 호출 | 도구가 파일 읽기나 검색 같은 행동을 알린 표시(도구 이름, 명령) | 행동 포맷 |
| 관찰 축약 | 긴 출력 일부를 접거나 요약한 표시 | 컨텍스트 관리 |
| 기록 위치 | 현재 대화, 세션 목록, 작업 기록, 로그 중 실행 결과가 남는 곳 | 경험·스킬 축적, 성찰 |
| 승인 신호 | 읽기 밖의 행동 전에 보이는 승인 창, 허용 선택지, 실행 예정 명령, 권한 설정 안내 | 권한·보안 |

- 입력과 도구 호출은 행동 포맷이 어떤 순서와 단위로 드러나는지 보여 준다. 요청 문장만 보이고 행동이 보이지 않으면 주요 동작은 확인하지 못한 것으로 적는다.
- 관찰 축약과 기록 위치는 화면에서 실제로 보이는 위치만 적는다.
- 승인 신호가 보이면 문구와 위치를 적고, 안 보이면 "이번 읽기 요청에서는 승인 신호를 확인하지 못했다"고 적는다.
- 확장 기능은 열거나 추가하지 않는다. 도구 연결, 플러그인, MCP, 설정 파일 같은 단서가 보이면 관찰한 사실과 확인하지 못한 범위를 나눠 적는다.
- 미니멀이 필요한지, 평가 루프가 어디서 이뤄지는지는 이 짧은 관찰로 결론 내지 않는다.

### 시범: Claude Code에서 파일 목록 요청 관찰하기

macOS의 Claude Code CLI 2.1.220에서 새 작업 폴더 `~/obs-lab`을 열고 실제로 실행한 기록이다. 폴더에는 공개 문서 한 건을 받아 둔 `notes.txt`만 있다. 버전 번호는 화면에 표시된 값을 그대로 적었다(Windows에서는 경로와 출력 형식이 다를 수 있으니 자기 화면 그대로 적는다).

**1. 요청 입력** — 대화창에 `이 폴더의 파일 목록을 보여 줘`를 입력한다. 요청 문장은 대화 흐름 안에 남고 응답 본문과 구분돼 표시된다. 결과 목록의 내용보다 요청이 들어간 화면의 위치를 먼저 본다.

**2. 도구 호출 표시** — 응답이 만들어지는 동안 도구 호출이 표시된다.

```
● Bash(ls -la /Users/admin/obs-lab)
  List files in obs-lab
```

Claude Code의 도구 목록 문서에는 파일 탐색용 Glob과 파일 읽기용 Read가 있지만, 이 요청에서 모델은 Bash의 `ls -la`를 골랐다. 화면에 나타난 도구 이름과 명령이 이번 실행의 사실이고, 어떤 도구를 쓸지는 모델이 판단했다. 버전과 운영체제에 따라 기본으로 켜진 도구가 다르므로 자기 화면에 나온 도구 이름을 그대로 적는다.

**3. 도구 결과**

```
total 8
drwxr-xr-x    4 admin  staff   128 Sep  2 01:36 .
drwxr-xr-x@ 171 admin  staff  5472 Sep  2 01:38 ..
drwxr-xr-x    4 admin  staff   128 Sep  2 01:37 .omc
-rw-r--r--    1 admin  staff    32 Sep  2 01:36 notes.txt
```

명령의 출력이 원본 그대로 돌아오고, 이 원본이 세션 기록에 남는다. 컨텍스트 관리는 이렇게 쌓이는 기록을 다룬다. 지금은 네 줄이라 그대로 두었지만 출력이 길어지면 관찰 축약이 적용될 수 있다. (`.omc`는 시범 환경에만 있는 상태 폴더다.)

**4. 최종 응답**

```
/Users/admin/obs-lab 내용:
- notes.txt — 32바이트 파일
- .omc/ — OMC 상태 디렉터리 (숨김)
```

요청 → 도구 호출 → 도구 결과 → 요약이 한 세션에 순서대로 남았다.

**5. 승인 창** — 이 실행에서는 나타나지 않았다. Claude Code는 `ls`, `cat`, `grep` 같은 읽기 전용 명령을 승인 없이 실행한다. ([공식 문서] Anthropic, Claude Code 권한 문서) 승인 창이 없었다는 사실은 적되, 설정 파일의 허용 규칙은 열어 보지 않았으므로 미확인으로 둔다.

**시범의 관찰 메모**

| 항목 | 기록 |
|---|---|
| 조건 | Claude Code CLI 2.1.220, 작업 폴더 `~/obs-lab`, fixture는 공개 문서를 받아 둔 notes.txt 한 건 |
| 입력 | 요청은 대화창에 들어가고 응답과 구분돼 남았다 |
| 도구 호출 | `Bash(ls -la)`가 표시됐다. 도구 목록의 Glob/Read가 아니라 모델이 Bash를 골랐다 |
| 관찰 | 원본 ls 출력 네 줄이 그대로 돌아왔다. 축약 표시는 확인하지 못했다 |
| 승인 | 이 읽기 요청에는 승인 창이 없었다. 설정의 허용 규칙은 미확인 |
| 기록 | 세션에 요청부터 요약까지 순서대로 남았다 |

이 메모에는 "이 도구는 읽기가 안전하다"는 해석을 쓰지 않는다. 안전하다고 판정하려면 권한 규칙을 확인해야 하는데, 이번에는 열어 보지 않았기 때문이다.

### 실습: 내 도구에서 관찰하기

```bash
# 1단계. 작업 폴더와 fixture 준비 (PowerShell, CMD, 터미널 공통)
mkdir obs-lab
cd obs-lab
# notes.txt를 만들고 공개 문서 몇 줄을 붙여 넣어 저장 → 이번 관찰의 fixture

# 2단계. 관찰 조건 적기 — 도구 이름·버전, 작업 폴더, fixture 종류
claude --version

# 3단계. 도구를 열고 읽기 요청 보내기 (opencode면 opencode 실행)
claude
# > 이 폴더의 파일 목록을 보여 줘
```

**4단계. 다섯 신호를 찾아 관찰 메모 쓰기** — 자기 화면에서 본 것만 채우고, 보이지 않은 신호는 "이번 실행에서 확인하지 못함"으로 적는다.

```
조건: 도구 ___ (버전 ___), 작업 폴더 ___, fixture ___
입력:
도구 호출:
관찰: (축약 표시가 보였는가)
승인: (승인 창이 보였는가, 설정의 허용 규칙은 확인했는가)
기록: (요청부터 요약까지 어디에 남았는가)
```

Claude Code에서는 `/permissions`로 현재 허용 규칙을 볼 수 있다. 승인 칸을 미확인으로 남겼다면 나중에 이 명령으로 확인한다.

### 사실과 해석 나눠 적기

기록에는 화면이나 로그에서 확인한 내용만 넣는다. 화면에 보인 연결이나 설정 단서는 확인한 사실로, 이번 실행에서 보이지 않은 기능은 한계로 구분한다. 같은 내용도 적는 방식에 따라 사실이 되기도 하고 해석이 되기도 한다.

> 파일 목록 요청에 승인 없이 읽기가 실행되었다. 관찰한 사실: 화면의 파일 목록. 미확인: 설정 파일의 권한 규칙

이 기록은 도구 전체를 판정하는 근거가 아니라, 짧은 실행 하나에서 보인 범위와 보이지 않은 범위를 나눈 것이다. 해석에 필요한 근거는 뒤의 기능별 강의에서 모은다.

## 3. 행동 포맷: 편집과 실행을 적는 형식

모델이 고칠 내용을 알고 있어도 변경 위치와 형식을 잘못 적으면 작업은 실패한다. **행동 포맷**은 바꿀 대상, 바꿀 내용, 실행 결과를 서로 확인할 수 있는 단위로 적게 해서 이런 실패를 줄이는 기능이다.

자유 문장으로 "이 함수를 고쳐 달라"고 하면 모델은 어디까지가 대상인지, 기존 내용과 교체 내용이 무엇인지 다시 추측해야 한다. 찾을 내용과 바꿀 내용을 묶은 편집 블록이나 실행 가능한 코드는 다음 행동의 모양을 좁혀 준다. Claude Code와 opencode에서 파일 변경과 명령 실행이 어떤 표시로 남는지 살피는 이유도 여기에 있다.

### 용어

- **SWE-bench Lite**: 실제 GitHub 이슈를 풀게 하는 벤치마크 SWE-bench(9강)에서 300문제를 골라 만든 축소판
- **ablation**: 구성요소를 하나씩 빼거나 바꿔 성능 차이를 보는 실험

### 행동 포맷을 비교한 연구와 도구

| 연구·도구 | 비교한 것 | 결과 (해당 조건) | 근거 |
|---|---|---|---|
| SWE-agent | 전용 인터페이스(ACI)에서 편집 기능을 뺀 조건 | 해결률 18.0% → 10.3% (SWE-bench Lite, GPT-4 Turbo) | [학술] |
| CodeAct | 행동을 JSON 도구 호출 대신 실행 가능한 Python 코드로 쓰게 함 | 17개 LLM에서 기존 형식보다 성공률 최대 20% 높음 | [학술] |
| Aider | 파일 전체를 다시 쓰는 whole 포맷과 바꿀 부분만 쓰는 diff 포맷 | gpt-3.5-turbo-0301 첫 시도 통과율: whole 46%, diff 30% | [벤더] |

### SWE-agent

프린스턴 연구진이 만든 연구용 코딩 에이전트다. 언어 모델이 쓰기 좋게 만든 전용 인터페이스를 **ACI(Agent-Computer Interface)**라고 부르고, ACI가 일반 셸보다 적합할 수 있다는 가설을 검토했다.

SWE-bench Lite ablation에서 기본 조건의 해결률은 18.0%, 편집 기능을 뺀 조건은 10.3%였다. 이 차이로 "인터페이스 설계가 해결률을 바꿀 수 있다"는 것까지는 말할 수 있다. 단, 같은 벤치마크와 구현 조건의 결과이므로 다른 모델과 편집 도구에서도 같은 크기의 차이가 난다고 보지는 않는다. ([학술] Yang et al., NeurIPS 2024, arXiv:2405.15793)

| 카드 칸 | SWE-agent |
|---|---|
| 진입점 | 이슈 설명과 저장소 환경이 ACI를 거쳐 모델의 작업 요청으로 들어간다 |
| 상태 | 검색, 파일 열람, 편집, 실행 관찰이 다음 판단에 필요한 형식으로 남는다 |
| 주요 동작 | 구조화된 edit 명령과 lint(코드 문법 검사) 피드백이 자유 셸 편집보다 좁은 편집 단위를 준다 |
| 권한 경계 | 논문의 ACI는 성능 실험용 인터페이스이며 실제 환경의 파일·명령 권한 정책을 보여 주지는 않는다 |
| 1차 자료 | NeurIPS 2024 논문이 ACI 구성과 SWE-bench Lite ablation 결과를 공개한다 |
| 한계 | 18.0%와 10.3%는 편집 기능을 뺀 해당 조건의 결과이며, 모델 세대와 작업이 바뀌면 차이도 달라질 수 있다 |

### CodeAct

행동을 실행 가능한 Python 코드 한 덩어리로 쓰게 하는 방식을 제안한 연구다. 예를 들어 여러 파일의 줄 수를 세는 작업이라면:

- **도구 호출 방식**: 파일 열기를 호출하고, 결과를 받고, 다시 줄 세기를 호출하는 식으로 여러 번 오간다.
- **코드 방식**: for 반복문과 함수 호출이 든 코드 한 덩어리를 쓰고 실행 결과만 받는다. 결과를 보고 코드를 고쳐 다시 낼 수도 있다.

흩어진 도구 호출을 코드 하나로 묶으면 모델이 계획 전체를 한 번에 표현할 수 있다는 것이 가설이다. 17개 LLM에서 기존 형식보다 성공률이 최대 20% 높았다. ([학술] Wang et al., ICML 2024, arXiv:2402.01030)

### Aider

터미널 안에서 파일을 편집하는 오픈소스 도구로, 변경을 자동으로 git 커밋한다. 편집 포맷은 두 가지다.

| 포맷 | 모델이 출력하는 것 | hello.py의 한 줄을 바꿀 때 |
|---|---|---|
| whole | 파일 전체를 새 내용으로 다시 쓴다. 바뀌지 않은 줄도 모두 출력한다 | 파일의 모든 줄을 다시 쓴다 |
| diff | 바꿀 부분만 search-replace(찾아 바꾸기) 블록으로 쓴다 | 바꾸기 전 줄과 바꾼 뒤 줄만 짝으로 적는다 |

Aider의 수치는 독립 비교가 아니라 Aider가 직접 만든 벤치마크 결과다. 측정 방식은 다음과 같다.

1. 133개 Exercism Python 작업을 풀게 한다.
2. 실패하면 테스트 오류의 앞 50줄을 다시 넣어 재시도하게 한다.
3. 성공 기준은 전체 테스트 통과다.

실패했을 때 개발자가 보는 것과 같은 테스트 오류를 돌려준다는 점에서 실제 개발 흐름과 비슷하다. 작성한 코드가 실제로 동작하는지 잰다는 점은 SWE-agent와 같지만, 작업 난이도와 채점 방식이 다르므로 두 벤치마크의 수치를 나란히 놓지 않는다. 같은 모델에서도 포맷에 따라 통과율이 갈렸지만, 다른 작업이나 모델에서도 whole이 diff보다 낫다는 뜻은 아니다. ([벤더] Aider, 자체 벤치마크)

```
Aider 편집 포맷의 흐름
1. 입력: 지정한 파일과 요청, 찾을 내용, 현재 컨텍스트
2. 편집 블록: search(찾을 내용) + replace(바꿀 내용)
3. 변경 제안 → 검토 뒤 반영
   (일치 여부와 실제 반영 범위는 변경 이력과 실행 기록으로 확인)
```

편집 블록은 변경 의도를 드러낼 뿐, 변경의 정확성이나 실행 안전을 보장하지 않는다. 그래서 대상 파일, 일치 결과, 테스트 결과, 승인 표시를 함께 본다.

| 카드 칸 | Aider |
|---|---|
| 진입점 | 터미널 대화에서 파일과 요청을 함께 받아 편집 대화를 시작한다 |
| 상태 | 대화, 지정 파일, 테스트 결과가 다음 응답에 쓰인다 |
| 주요 동작 | search와 replace를 한 블록에 써서 기존 문자열과 교체 문자열을 함께 나타낸다 |
| 권한 경계 | 파일 변경과 명령 실행의 허용 범위는 설치 버전, 설정, 실제 실행 기록에서 다시 확인해야 한다 |
| 1차 자료 | 공개 문서의 편집 포맷 설명과 자체 벤치마크. 독립적으로 재현한 결과는 아니다 |
| 한계 | 검색 문자열이 파일 내용과 그대로 일치하지 않거나 컨텍스트가 오래되면 구조화된 블록도 의도와 다른 변경을 낼 수 있다 |

### 포맷이 결과를 좌우하지 않는 경우

Aider 벤치마크에서 GPT-4는 whole과 diff의 결과가 거의 같았고, Aider는 비용 때문에 diff를 유지했다고 설명한다. 그러므로 포맷이 언제나 결과를 정한다고 말할 수 없다. 다음 조건에서는 포맷보다 다른 실패 원인이 더 클 수 있다.

- 모델이 어느 포맷으로도 수정 내용을 틀리지 않고 적는 경우
- 변경 범위가 아주 작은 경우
- 검색 문자열이 불안정한 경우

### 비교 실험: 포맷만 바꾸기

한 번의 결과로 일반 결론을 내지 않고 모델, 작업, 포맷 조건을 함께 적는다.

| 구분 | 내용 |
|---|---|
| 고정 | 작은 fixture 하나와 테스트 하나 |
| 바꾸는 것 | 같은 수정을 자유 텍스트로 요청하는 조건과 search·replace 구조 포맷으로 요청하는 조건 |
| 기록 | 대상 파일을 처음 맞힌 횟수, 변경 뒤 테스트 통과 여부, 재시도 횟수 |

이 실험은 요청 문장의 형식을 바꾸는 것이다. 하네스가 모델에게 요구하는 편집 포맷 자체를 바꾸려면 Aider처럼 포맷을 고를 수 있는 도구가 필요하다. Aider는 `--edit-format` 옵션으로 whole, diff 같은 포맷을 지정한다. ([공식 문서] Aider, 편집 포맷 문서)

## 4. 컨텍스트 관리: 남길 정보와 다시 찾을 정보

### 컨텍스트와 컨텍스트 윈도우

- **컨텍스트**: 모델이 한 번의 요청에서 입력으로 읽는 내용 전체
- **컨텍스트 윈도우(context window)**: 한 번에 넣을 수 있는 최대 크기

컨텍스트 윈도우가 크면 한 번에 읽을 수 있는 기록은 늘어나지만, 넓다고 해서 지금 필요한 정보가 눈에 잘 띄는 것은 아니다. 긴 실행에서는 명령 결과, 오류 메시지, 파일 내용, 중간 판단이 계속 쌓이고, 처음에 유용했던 단서도 새 관찰에 밀려 대화 위쪽으로 올라가 찾기 어려워진다.

> **컨텍스트 관리**는 다음 행동에 필요한 관찰과 저장소 구조를 골라 다시 보여 주어, 중요한 실패 조건이나 다음에 열 파일의 단서가 긴 이력에 묻히지 않게 하는 기능이다. 즉, 정해진 토큰 예산 안에 무엇을 넣고 지금 빠진 정보는 어디에서 다시 찾을지 정하는 일이다.

같은 크기의 컨텍스트 윈도우라도 무엇으로 채우느냐에 따라 다음 행동이 달라진다.

### 컨텍스트를 고르는 방법

무조건 줄이는 것이 목적이 아니라, 비용과 정확도를 함께 따져 넣을 양을 정하는 방법들이다.

| 방법 | 하는 일 | 근거 |
|---|---|---|
| 최근 관찰 유지와 과거 관찰 축약 (SWE-agent) | 최근 관찰 5개는 자세히 남기고 그 전 관찰은 줄여서 남긴다 | [학술] |
| repo map (Aider) | 파일 전체 대신 저장소의 뼈대만 담은 목록을 넣는다 | [벤더] 설계 글, 독립 성능 비교 아님 |
| 반복 검색 (RepoCoder) | 모델이 만든 코드로 다시 검색해 더 관련 있는 코드 조각을 찾는다 | [학술] |
| 검색해 다시 불러오기 | 요약하거나 뺀 정보를 필요할 때 다시 검색해 컨텍스트에 넣는다 | 근거 없음 (아래 비교 실험으로 확인) |
| 서브에이전트의 격리 컨텍스트 | 서브에이전트가 좁은 컨텍스트에서 따로 일하고 결과만 돌려준다 | [공식 문서] 구조 설명, 효과 비교 아님 |

**최근 관찰 유지 (SWE-agent)** — SWE-bench Lite에서 "최근 관찰 5개는 자세히, 과거 관찰은 축약"한 조건과 "전체 이력을 남긴" 조건을 비교했다. 최근 5개 조건 18.0%, 전체 이력 조건 15.0%로 3.0%p 높았다. 같은 작업과 모델에서 관찰을 고르는 방식만 바꿔도 결과가 달라졌다는 뜻이지, 5개가 모든 작업에서 가장 좋다는 뜻은 아니다. ([학술] Yang et al., NeurIPS 2024, arXiv:2405.15793)

**repo map (Aider)** — 큰 저장소의 파일을 전부 넣으면 컨텍스트 윈도우가 금방 넘친다. repo map은 어떤 클래스와 함수가 어느 파일에 정의돼 있는지 보여 주는 저장소 뼈대 목록이다. Aider는 파일 사이의 정의·참조 관계로 그래프를 만들어 파일 순위를 매기고, 기본 1천 토큰 예산 안에서 넣을 항목을 고른다. 모델은 이 목록을 보고 필요한 파일만 편집 요청에 첨부한다. ([벤더] Aider, 설계 글, 2023-10-22)

**반복 검색 (RepoCoder)** — 저장소에서 검색한 코드 조각으로 코드를 생성하고, 생성한 코드로 다시 검색해 더 관련 있는 조각을 찾는 반복 방식이다. ([학술] Zhang et al., EMNLP 2023, arXiv:2303.12570)

### Claude Code와 opencode 비교 카드 (컨텍스트 관리)

| 카드 칸 | Claude Code | opencode |
|---|---|---|
| 진입점 | 메인 대화가 터미널의 작업 요청을 받는다 | 현재 에이전트가 대화의 작업 요청을 받는다 |
| 상태 | 서브에이전트는 맡은 좁은 컨텍스트에서 작업하고 결과만 메인 대화에 돌려준다 | 에이전트별 대화 컨텍스트와 실행 단계가 분리돼 기록된다 |
| 주요 동작 | 조사를 맡긴 서브에이전트의 결과를 받아 메인 대화가 다음 행동을 정한다 | 에이전트별 steps 상한을 두어 한 대화가 끝없이 관찰을 쌓지 않게 한다. steps는 에이전트가 텍스트로만 답하도록 강제되기 전까지 반복할 수 있는 최대 횟수다 |
| 권한 경계 | 서브에이전트가 쓸 도구와 승인 동작은 해당 설정과 실행 기록에서 확인해야 한다 | 에이전트별 도구 설정과 단계 상한은 설정 파일과 실행 기록에서 확인해야 한다 |
| 1차 자료 | 공식 서브에이전트 문서, 설정 파일, 실행 기록. 문서는 설치 버전과 실제 권한 설정을 대신하지 않는다 | 공식 에이전트 설정 문서, 에이전트 설정 파일, 실행 기록. 설정 항목은 버전에 따라 다를 수 있다 |
| 한계 | 격리된 작업 결과가 메인 대화에 돌아오므로, 돌아온 결과가 충분한지는 작업마다 검토해야 한다 | 단계 상한은 관련 컨텍스트를 골라 넣는 규칙이 아니므로 검색과 요약의 품질은 따로 확인해야 한다 |

### 줄이는 것이 늘 답은 아닌 경우

검색이나 요약 뒤 다시 불러오는 방식이 항상 정확도를 높이지는 않는다.

| 방식 | 뜻 |
|---|---|
| RAG(검색 증강 생성) | 필요한 문서 조각을 검색해 컨텍스트에 넣는 방식 |
| long-context | 긴 원문을 그대로 넣는 방식 |

두 방식을 비교한 연구는, 예산이 충분할 때 long-context가 평균 성능에서 일관되게 RAG보다 높았고 RAG의 장점은 낮은 비용이라고 보고했다. ([학술] Li et al., EMNLP 2024 Industry Track, arXiv:2407.16833)

그러므로 원문이 컨텍스트 윈도우에 다 들어가는데도 비용 때문에 줄이려는 경우라면, 줄이기 전에 정확도가 얼마나 떨어지는지 먼저 따져 본다. 예산이 충분하고 원문 전체가 필요한 작업인지, 비용을 낮추려고 고르고 압축할 작업인지를 함께 판단한다.

Anthropic도 컨텍스트를 단순한 저장 공간이 아니라 요청마다 제한된 입력 예산을 나눠 쓰는 대상으로 설명한다. ([벤더] Anthropic Engineering, Effective context engineering for AI agents) 이 관점에서 실행 기록으로 다음을 확인한다.

- 요약이 필요한 단서를 버리지 않았는가
- repo map이 필요한 파일을 놓치지 않았는가
- 서브에이전트의 결과가 메인 대화에 충분히 돌아왔는가

### 비교 실험: 전체 이력 vs 요약 뒤 다시 불러오기

같은 모델과 같은 작업에서 전체 이력을 남긴 조건과 요약한 뒤 필요할 때 다시 검색해 넣는 조건을 비교한다. 나머지 조건은 같게 두고 **성공 여부, 사용 토큰, 다시 찾은 정보가 원문과 맞는지**를 기록한다. 그러면 어느 조건에서 요약이 도움이 되고 어느 조건에서 원문이 필요한지 확인할 수 있다.

## 5. 경험·스킬 축적: 지난 실행을 다음 실행에 쓰기

로그를 저장했다고 경험이 쌓인 것은 아니다. 다시 찾아 적용할 수 있는 형태여야 다음 실행에 쓸 수 있다. 작업 전체를 보관하는 일과 다음 작업에서 쓸 판단을 남기는 일은 다르다. 실패한 명령, 우연히 통과한 설정, 현재 작업에만 맞는 해결책까지 다시 불러오면 기록이 오히려 판단을 흐릴 수 있다.

경험이 다음 실행에 쓰이려면 세 조건을 갖춰야 한다.

1. 원문 기록에서 근거를 확인할 수 있다.
2. 필요할 때 검색할 수 있다.
3. 다음 행동으로 바꿔 적용할 수 있다.

### 경험을 다음 행동에 쓰는 연구

| 연구 | 남기는 것 | 다음 작업에서 하는 일 | 결과 (해당 환경) |
|---|---|---|---|
| ExpeL | 여러 경험에서 뽑은 판단(insight)과 성공 사례 | 비슷한 성공 사례를 검색해 함께 제공 | WebShop 평균 보상 0.701 (ReAct 0.665) |
| Voyager | 실행 가능한 코드 스킬 라이브러리 | 필요한 스킬을 검색해 검증한 코드를 조합 | 마인크래프트에서 고유 아이템 3.3배, 이동 거리 2.3배 |
| AWM | 과거 실행 궤적에서 뽑은 작업 절차(workflow) | 후보 workflow를 골라 현재 작업에 맞춰 사용 | Mind2Web 24.6%, WebArena 51.1% 상대 개선 |
| WikiSkill | 원문 궤적, 위키, 실행 스킬 세 층 | 세 층을 구분해 제공하고 위키로 스킬을 갱신 | 다섯 모델 모두 스킬 없는 조건보다 평균 정확도 상승 |

**ExpeL** — 경험에서 배우는 에이전트 연구다. 관찰과 성공·실패 경험을 그대로 다음 프롬프트에 쌓지 않고, 여러 경험에서 반복해 쓸 판단을 **insight**로 뽑아 저장한다. 새 작업이 오면 벡터 검색 라이브러리 FAISS에서 kNN(가장 가까운 k개 찾기)으로 비슷한 성공 사례를 찾아 함께 넣는다. 넣는 개수는 환경마다 다르다(WebShop 2개, HotpotQA 6개).

- GPT-4로 insight를 뽑고 GPT-3.5로 실행한 WebShop 조건에서 평균 보상 0.701로, 기본 에이전트 방식인 ReAct(추론과 행동을 번갈아 하는 방식)의 0.665보다 높았다.
- insight 목록은 모델이 관리한다. 새 insight를 추가하거나 고치고 찬성·반대 표를 매기며, 반대가 쌓여 중요도 점수가 0이 된 insight는 지운다. 다만 무엇이 틀렸는지도 모델이 판단하므로 틀린 insight가 걸러진다는 보장은 없다. ([학술] Zhao et al., AAAI 2024, arXiv:2308.10144)

**Voyager** — 마인크래프트 세계에서 스킬을 쌓는 에이전트 연구다. 자연어 메모 대신 실행 가능한 코드 스킬을 라이브러리에 남기고, 새 작업에서는 필요한 스킬을 검색해 이미 검증한 코드를 조합한다. 기존 방법보다 고유 아이템 3.3배, 이동 거리 2.3배, 기술 단계(milestone) 최대 15.3배 빠른 달성. 스킬 검색의 top-1 정확도(첫 번째 검색 결과가 맞을 비율)는 80.2%였다. 마인크래프트 환경의 결과이므로 다른 업무에서도 같은 재사용 효과가 난다고 보지 않는다. ([학술] Wang et al., arXiv:2305.16291)

**AWM(Agent Workflow Memory)** — 과거 실행 궤적(에이전트가 거친 행동의 기록)에서 다시 쓸 수 있는 작업 절차(workflow)를 뽑아 메모리로 남긴다. 다음 작업에서는 후보 workflow를 골라 제공하고, 에이전트는 그 절차를 현재 웹사이트와 작업에 맞춰 쓴다. Mind2Web과 WebArena에서 기준 방법보다 성공률이 상대적으로 24.6%, 51.1% 높았고, 작업·웹사이트·도메인을 바꾼 평가에서도 8.9~14.0점 높았다. 웹 탐색 환경의 결과이므로 웹 밖 작업에 같은 폭으로 적용된다고 보지 않는다. ([학술] Wang et al., arXiv:2409.07429)

**컴파운드 엔지니어링** — Every의 개발자 Kieran Klaassen은 이런 흐름을 컴파운드 엔지니어링(compound engineering)이라고 불렀다. ([벤더] Every, How I use Claude Code to ship like a team of five)

> 한 번의 실행 결과를 다음 실행의 입력으로 남기고, 검색·조합·검토를 거치며 작업 능력을 쌓는다. 단, 저장한 내용이 오래되거나 틀렸다면 다음 실행에도 같은 오류가 넘어갈 수 있다.

**WikiSkill** — Google Research가 2026년에 발표한 연구로, 에이전트의 경험을 위키로 쌓아 스킬을 개선한다. 세 층을 나눠 관리한다.

- **원문 궤적**: 판단의 근거를 확인한다
- **위키**: 여러 실행에서 얻은 지식을 쌓는다
- **스킬**: 실제로 실행할 절차를 둔다

다음 실행에서는 세 층을 구분해 제공하고, 위키에 쌓인 지식으로 스킬을 갱신한다. Figure 1 설명은 WikiSkill이 스킬 없는 조건과 기존 스킬 개선 방법(EvoSkill, SkillOpt)보다 일관되게 높다고 하고, 초록은 큰 모델일수록 대체로 이점이 크다고 보고한다. Table 1의 다섯 벤치마크 평균 정확도(스킬 없음 → WikiSkill)는 다음과 같다.

| 모델 | 스킬 없음 | WikiSkill |
|---|---|---|
| Qwen-3.5-4B | 26.2 | 38.5 |
| Qwen-3.6-27B | 39.4 | 63.3 |

한 모델로 만든 스킬을 다른 모델 계열에 옮겨 써도 효과가 있었다고 본문에서 보고한다. ([학술] Tang et al., arXiv:2608.27454) 강의의 개념 그림은 모델 크기(작음·중간·큼)마다 무스킬, EvoSkill, SkillOpt, WikiSkill의 평균 정확도를 막대로 보여 주며, 모델이 클수록 WikiSkill과 다른 조건의 차이가 커진다. 숫자 눈금이 없는 개념 그림이므로 실제 수치는 위 Table 1 값을 본다.

### 남기는 형태 네 가지

| 남기는 형태 | 다음 실행에서 하는 일 | 장점과 위험 | 먼저 확인할 질문 |
|---|---|---|---|
| 원문 궤적 | 당시 관찰과 행동의 근거를 다시 확인 | 검토하기 좋지만 길다 | 어느 지점까지 믿을 수 있는가 |
| 요약 | 긴 기록에서 현재 판단에 필요한 맥락을 압축 | 빠르지만 내용이 빠질 수 있다 | 중요한 실패 조건이 빠지지 않았는가 |
| insight | 여러 실행에서 반복된 판단을 검색해 적용 | 검색하기 좋지만 틀린 내용이 섞일 수 있다 | 반례와 갱신 날짜가 있는가 |
| 코드 스킬 | 검증한 절차를 실행 가능한 단위로 재사용 | 바로 실행할 수 있지만 오래된 절차를 그대로 반복할 수 있다 | 입력 조건과 되돌리는 방법이 있는가 |

실제 도구에서 이 구분을 보려면, 저장한 세션을 다시 찾아 현재 판단에 넣는 경로부터 확인한다.

### Hermes에서 확인할 항목

Hermes는 NousResearch가 만든 오픈소스 에이전트(MIT 라이선스)로, 대화 기록을 검색할 수 있는 형태로 남겨 다음 실행에서 다시 찾게 한다. 아래는 저장소 README에서 확인한 구조이며 성능 근거는 아니다. ([공식 문서] NousResearch, hermes-agent README)

| 확인 항목 | Hermes에서 보는 내용 |
|---|---|
| 과거 검색 | FTS5(SQLite 데이터베이스의 전문 검색 기능)로 과거 세션을 검색한다 |
| 진입점 | 여러 메시지 채널의 요청을 gateway 하나로 받는다 |
| 다음 컨텍스트 | 세션 이력, memory·user model, 활성 skills를 연결한다 |
| 확인 과제 | 어떤 기록이 어떤 조건에서 다시 들어오는지 설치본의 설정과 실행 기록으로 확인한다 |

Hermes에서 볼 것은 기록을 오래 보관한다는 점보다, 과거 세션을 찾아 현재 컨텍스트에 다시 넣는 경로다. 검색 결과가 현재 작업과 맞는지, 오래된 설정이 다시 실행되지 않는지, 기억과 스킬이 어떤 권한으로 작동하는지는 따로 점검해야 한다.

### Claude Code의 스킬

**스킬(skill)**은 SKILL.md 파일을 중심으로 지식, 절차, 템플릿, 스크립트를 묶은 폴더다. 필요한 내용만 단계적으로 불러오도록 만들 수 있고, Claude Code는 개인 또는 프로젝트의 스킬 폴더에서 스킬을 찾는다. ([공식 문서] Anthropic, Claude Code 스킬 문서)

스킬 파일을 추가했다고 경험 축적이 끝나지는 않는다. 어느 경험에서 왔는지, 언제 검토했는지, 어떤 작업에 적용할지를 함께 남겨야 한다.

### 메모리 오염(memory poisoning) 실험

ExpeL처럼 모델이 insight를 고르고 지우는 방식에서도 틀린 insight가 남을 수 있다는 점이 경험 기능에 대한 핵심 반론이다. 그럴듯하지만 틀린 insight 하나가 검색을 통해 여러 작업에 반복해 들어갈 수 있고, 실행 스킬은 그 판단을 더 빨리 행동으로 옮길 수 있다.

> 운영에서는 스킬을 얼마나 많이 모았는지보다, 틀린 지식을 찾아 고치고 되돌릴 수 있는지가 중요하다.

이 문제는 작은 주입 실험으로 확인할 수 있다.

| 구분 | 내용 |
|---|---|
| 고정 | 작업, 모델, 예산 |
| 조건 | 검증한 insight 또는 스킬을 넣은 조건과, 일부러 틀린 insight 또는 스킬을 넣은 조건 |
| 하나씩 바꿀 정책 | 출처 기록, 만료 기한, 반대 증거, 되돌리기 |
| 기록 | 성공률, 토큰, 오염 전파(틀린 내용이 다른 작업으로 퍼진 정도) |

### 미해결 질문: 남기는 형태만 바꾸면 무엇이 달라지는가

하나의 실행 궤적을 원문, 요약, insight, 코드 스킬 네 형태로 각각 준비한다. 같은 모델과 같은 작업에서 어느 형태가 다음 행동을 더 잘 돕는지, 토큰을 얼마나 쓰는지, 틀린 내용이 얼마나 퍼지는지 비교한다. 어떤 형태가 항상 가장 좋은지 정하려는 실험이 아니라, 내 작업에서 재사용하기 쉬운 형태와 검토하기 쉬운 형태가 어디서 갈리는지 찾는 실험이다.

## 6. 성찰: 실패 기록에서 다음 행동 고치기

> **성찰**은 실패한 실행 기록에서 다음 시도에 바꿀 행동 하나와 그 근거를 짧게 남기는 기능이다.

답을 길게 평가하는 글이 아니라 다음 행동을 바꾸는 짧은 피드백이어야 한다. 결과가 틀렸다는 문장만 길게 반복하면 다음 도구 호출과 검색 범위는 바뀌지 않는다.

### 성찰로 실패 기록 압축하기

**Reflexion** — 실패한 뒤 스스로 성찰 문장을 남겨 다음 시도에 쓰는 방식이다. 모델 가중치(모델이 학습한 값)를 바꾸지 않고 언어 피드백만으로 루프를 만들었다.

```
시도 → 오류 → 성찰 → 기억  (trial-error-reflection-memory)
```

- HotpotQA에서 이전 시도 기록(episodic memory)만 넣은 조건에 성찰을 더하자 정확도가 8%p 올랐다.
- 장기 기억에는 최근 성찰 1~3개만 남겨 다음 시도에 다시 넣었다. 모든 실패 기록을 보관하지 않고, 다음 행동을 고칠 근거만 줄여서 다시 넣는 설계다. ([학술] Shinn et al., NeurIPS 2023, arXiv:2303.11366)

**Generative Agents** — 스탠퍼드 연구진의 가상 마을 시뮬레이션 연구로, 기록 → 성찰 → 검색 → 다시 불러오기를 하나의 흐름으로 설계했다. 관찰을 memory stream(시간순 기억 목록)에 쌓고, 시간별 성찰로 의미를 묶고, 최근성·관련성·중요도로 찾아 계획에 다시 넣는다. 작업 성공률이 아니라 에이전트 행동이 그럴듯한지를 평가했으므로 코딩 하네스의 성능 근거로 넓혀 쓰지 않는다. ([학술] Park et al., UIST 2023, arXiv:2304.03442)

### 틀린 성찰도 기억이 될 수 있다

성찰이 항상 성능을 높이지는 않았다. Reflexion 저자들이 밝힌 결과는 다음과 같다.

- **MBPP**(Python 코딩 벤치마크): Reflexion 77.1%로 GPT-4 기준선 80.1%보다 낮았다.
- **WebShop**: 개선이 없었다.

실패 원인을 잘못 설명한 문장이 다음 시도에 다시 들어오면 틀린 교훈이 쌓일 수 있다. 그래서 성찰에는 정답처럼 보이는 결론보다 검증할 수 있는 행동을 남긴다. 다음 실행의 결과가 이 설명을 뒷받침하지 않으면 성찰을 고치거나 버린다.

| 결론만 남긴 성찰 | 검증할 행동을 남긴 성찰 |
|---|---|
| 검색이 부족했다. | 다음 시도에서는 오류가 난 파일의 호출 지점을 먼저 읽고, 그 뒤에만 검색 범위를 넓힌다. |

### Hermes에서 성찰이 남는 곳

Hermes README에는 성찰 기능이 따로 설명돼 있지 않다. 대신 5강에서 본 세션 이력, memory, skills에 성찰 문장도 남을 수 있다. 그래서 성찰 문장에는 **작성 시각, 근거가 된 실행 기록, 다음에 바꿀 행동**을 함께 연결한다. 그래야 검색으로 다시 들어온 문장이 어느 실패에서 나왔는지 확인하고, 틀렸을 때 지울 수 있다.

| 항목 | 내용 |
|---|---|
| 남는 상태 | FTS5로 찾은 과거 세션, memory, user model, 활성 스킬이 지속 상태로 남는다 |
| 주요 동작 | 과거 세션을 검색해 다음 요청의 컨텍스트로 다시 가져온다. 실패 기록만 골라 가져오는지는 README에서 확인하지 못했다 |
| 권한 경계 | README에 있는 command approval, DM pairing, container isolation의 실제 적용 범위는 설정과 실행 환경에서 확인해야 한다 |
| 1차 자료 | hermes-agent README와 공개 설정, 실행 기록을 대조한다 |
| 한계 | 성찰이 자동으로 정확해지거나 잘못된 기록이 자동으로 버려진다는 근거는 확인하지 못했다 |

### 미해결 질문: 성찰을 몇 개까지 남길까

Reflexion의 최근 1~3개 제한을 그대로 답으로 삼지 않는다. 같은 모델·작업·도구 예산에서 성찰을 1개, 3개, 전체로 남긴 조건을 비교한다. 성공률뿐 아니라 틀린 설명이 다음 시도에 재사용된 횟수와 성찰을 읽는 데 쓴 토큰도 함께 기록한다.

## 7. 미니멀: 도구와 프롬프트를 줄인 하네스

> **미니멀**은 기능을 적게 넣는 것 자체가 목표가 아니라, 작업을 끝낼 수 있는 가장 작은 루프의 조건을 찾는 기능이다.

기능 하나를 빼면 컨텍스트 비용과 설정 부담은 줄 수 있지만, 필요한 행동이나 안전 범위까지 빠질 수 있다.

### 작은 루프로 작업을 끝낸 사례

| 도구 | 구성 | 주장 | 근거 |
|---|---|---|---|
| mini-swe-agent | 100줄 규모. Bash만 쓰고 셸 상태와 선형 이력을 단순하게 다룬다 | SWE-bench Verified 74% 초과 | [벤더] README 자체 보고 |
| pi | read, write, edit, bash 네 도구. 시스템 프롬프트와 도구 정의를 합쳐 1,000토큰 미만 | 모델이 좋아질수록 복잡한 하네스가 덜 필요할 수 있다 | [벤더] 저자 에세이 |

**mini-swe-agent** — SWE-agent 팀이 만든 실험용 최소 에이전트다. 스스로를 "100줄 에이전트"라고 소개하며, Bash 말고는 도구를 쓰지 않고 셸 상태와 선형 이력(대화를 순서대로 쌓기만 하는 기록)을 단순하게 다룬다. README는 SWE-bench Verified에서 74%가 넘는 해결률을 보고하지만, 어떤 모델로 언제 측정했는지는 적혀 있지 않고 독립 논문도 확인하지 못했다. ([벤더] SWE-agent, mini-swe-agent README) 그래서 이 수치는 "풍성한 인터페이스보다 항상 낫다"는 근거가 아니라, 복잡한 기능을 빼도 작업을 끝낼 수 있다는 사례로 읽는다.

**pi** — 개발자 Mario Zechner가 혼자 만든 미니멀 코딩 에이전트다. 네 도구와 1,000토큰이 안 되는 시스템 프롬프트·도구 정의만으로 설계했다. 저자는 모델이 좋아질수록 복잡한 하네스가 덜 필요할 수 있다고 썼는데, 이는 설계 가설이며 독립 학술 근거는 확인하지 못했다. ([벤더] Mario Zechner, 저자 에세이, 2025-11-30)

| 카드 칸 | pi에서 확인할 내용 |
|---|---|
| 진입점 | 터미널에서 여는 대화형 코딩 CLI |
| 상태 | 세션 안의 대화와 도구 결과가 다음 판단으로 이어진다 |
| 주요 동작 | read, write, edit, bash 네 도구로 파일을 읽고 바꾸고 명령을 실행한다 |
| 권한 경계 | 권한 확인 기능(permission system)이 내장돼 있지 않아, 컨테이너 같은 외부 격리 환경에 권한 범위를 맡긴다 |
| 1차 자료 | 공식 저장소와 저자 에세이를 함께 확인한다 |
| 한계 | Terminal-Bench 2.0을 작업당 5회 실행했다는 언급은 있으나 측정 수치는 확인하지 못했다 |

### SWE-agent와 mini-swe-agent의 차이

3강의 SWE-agent를 여기서는 "풍성한 ACI"의 예로 다시 본다.

| 도구 | 묻는 것 |
|---|---|
| SWE-agent | 모델이 쓸 행동과 관찰을 인터페이스로 정교하게 만든다 |
| mini-swe-agent | 그중 필요한 부분이 현재 모델에서는 줄어들 수 있는지 묻는다 |

두 도구는 기능 수만 다른 것이 아니다. 같은 모델과 작업으로 고정하지 않으면 두 결과의 차이를 하네스의 효과라고 말할 수 없다.

### "미니멀이면 충분하다"는 아직 가설

mini-swe-agent의 수치와 pi의 주장은 모두 만든 쪽의 자체 보고다. 다음 작업에서는 작은 루프가 오히려 실패할 수 있다.

- 복잡한 ACI가 필요한 작업
- 긴 이력에서 관찰을 골라야 하는 작업
- 외부 격리로 해결되지 않는 권한 요구가 있는 작업

### 상용 도구에서 기능을 덜어 낸 사례

- Anthropic은 Claude Code의 시스템 프롬프트에서 80% 이상을 지웠는데도 코딩 평가에서 측정할 만한 손실이 없었다고 보고했다. 이전 모델의 최악 상황을 막으려고 넣은 규칙이 모델이 나아진 뒤에는 필요 없어졌고, 서로 충돌하는 지시가 지나친 제약이 됐다는 설명이다. ([벤더] Thariq Shihipar, Claude 블로그)
- Anthropic의 장기 실행 애플리케이션 개발용 멀티에이전트 하네스에서는, 모델이 나아진 것을 확인한 뒤 sprint(작업을 짧은 단위로 나눠 진행하는 구조)를 없애고 평가를 실행 끝에 한 번만 하도록 줄였다. ([벤더] Prithvi Rajasekaran, Anthropic Engineering)

두 사례 모두 현재 모델이 스스로 해내는 일을 시험해 보고 불필요한 장치를 덜어 낸 경우다.

### 미해결 질문: 모델이 좋아지면 격차가 줄어드는가

모델 세대가 오를수록 풍성한 ACI와 Bash만 쓰는 선형 이력 루프의 성능 격차가 줄어들까? mini-swe-agent의 74% 초과가 나온 모델·시점·작업 조건을 먼저 고정한 뒤, 같은 조건에서 두 루프의 성공률, 토큰, 실행 횟수, 권한 요청을 비교한다. 조건을 고정하기 전에는 숫자를 재현했다고 말하지 않는다.

## 8. 권한·보안: 허용 범위와 격리

파일을 읽는 능력, 명령을 실행하는 능력, 외부 메시지를 받는 능력은 서로 다른 위험을 만든다. **권한·보안** 기능은 이 세 행동의 진입점과 실행 범위를 나눠, 입력 하나가 곧바로 모든 도구 권한으로 이어지지 않게 한다.

### 차단 수치와 작업 결과를 함께 보는 연구

외부 문서에 숨긴 지시가 모델의 행동을 바꾸는 공격을 **프롬프트 인젝션(prompt injection)**이라고 한다. 아래 연구들은 이 공격을 얼마나 막는지와 함께, 막는 동안 작업을 얼마나 끝내는지를 다룬다.

| 연구 | 한 일 | 결과 (해당 조건) |
|---|---|---|
| Spotlighting | 외부 입력의 출처를 표시하는 변환을 적용 | 공격 성공률 50% 초과 → 2% 미만 |
| ToolEmu | 고위험 도구 사용을 에뮬레이션(흉내 내기)으로 평가 (도구 묶음 36개, 사례 144개) | 가장 안전한 에이전트도 23.9% 실패 |
| CaMeL | 권한, 데이터 흐름, 제어 흐름을 구조적으로 분리 | 설계 제안 |
| AgentDojo | 공격 성공률과 작업 완수율을 함께 측정 (작업 97개, 보안 테스트 629개) | 벤치마크 제안 |

- **Spotlighting**: 외부 입력에 출처를 표시하는 변환을 넣어 모델이 지시와 데이터를 구분하게 한다. 출처를 구분하면 공격을 줄일 수 있다는 근거지만, 저자 실험 조건의 결과이므로 모든 문서와 공격에 같은 효과가 난다고 보지 않는다. ([학술] Hines et al., arXiv:2403.14720)
- **ToolEmu**: 위험한 도구 사용을 실제로 실행하지 않고 언어 모델로 흉내 내어 안전성을 평가한다. 에뮬레이션 결과이므로 실제 컨테이너 격리나 다른 업무 환경의 실패율로 넓혀 읽지 않는다. ([학술] Ruan et al., ICLR 2024, arXiv:2309.15817)
- **CaMeL**: 외부 입력이 민감한 도구를 제어하지 못하게 하는 설계다. 민감한 데이터를 다루는 도구와 외부 입력이 만나는 곳에서 다음 행동을 무엇이 정하는지를 따로 관리하자는 접근이다. ([학술] Debenedetti et al., arXiv:2503.18813)
- **AgentDojo**: 많이 막으면 안전해 보이지만 작업도 끝내지 못할 수 있기 때문에 두 값을 함께 본다. ([학술] Debenedetti et al., NeurIPS 2024 Datasets and Benchmarks, arXiv:2406.13352)

### OpenClaw 비교 카드 (권한 경계)

외부 메시지가 들어오는 환경에서는 그 메시지를 어느 세션과 어떤 권한으로 연결하는지까지 확인해야 한다. OpenClaw는 Discord, Slack, Telegram 같은 여러 채널에서 상시 대기하는 오픈소스 에이전트다.

| 카드 칸 | OpenClaw에서 확인할 내용 |
|---|---|
| 진입점 | Gateway가 Discord, Slack, Telegram을 비롯한 여러 채널의 메시지를 받는다 |
| 상태 | Gateway가 채널 연결과 세션 라우팅(길 안내)을 관리하며, 에이전트·작업 공간·발신자별로 세션을 분리한다 |
| 주요 동작 | 상시 대기하는 Gateway가 들어온 메시지를 해당 세션과 에이전트로 보낸다 |
| 권한 경계 | pairing, allowFrom, 그룹 멘션 요구(requireMention)로 메시지를 보낼 수 있는 범위를 설정한다 |
| 1차 자료 | OpenClaw 공식 문서에서 구조와 설정을 확인한다 |
| 한계 | 이 권한 설계의 공격 방어나 작업 성능을 검증한 학술 근거는 확인하지 못했다 |

메시지를 보낼 수 있는 범위를 정하는 세 설정:

| 설정 | 하는 일 | 정하지 않으면 |
|---|---|---|
| pairing | 채널과 Gateway가 처음 연결될 때 어느 발신자와 짝을 맺을지(페어링) 정한다. 승인하면 그 발신자의 메시지가 정해진 채널을 거쳐 해당 세션으로 간다 | 기본 정책은 페어링되지 않은 발신자를 승인 절차로 분리한다. 이 정책을 바꾸거나 승인 없이 페어링을 허용하면 처음 보는 발신자가 믿을 수 있는 진입점인지 확인할 수 없다 |
| allowFrom | 페어링된 채널 안에서도 메시지를 보낼 수 있는 발신자 범위를 정한다. 목록 밖 발신자의 메시지는 에이전트 실행으로 이어지지 않는다 | 채널의 접근 규칙만으로는 허용할 발신자가 분명히 좁혀지지 않는다 |
| 그룹 멘션 요구 | 그룹 대화에서 에이전트를 멘션한 메시지만 처리하고 멘션 없는 메시지는 무시한다 | 일반 대화가 Gateway가 처리할 요청과 섞일 수 있다 |

세 설정은 메시지를 보낸 사람과 에이전트 호출 여부를 가리는 설정이다. 도구 실행이 허용된 뒤 피해 범위를 가두는 격리 환경과는 다른 단계에서 작동한다.

### Claude Code 권한 모드와 opencode 권한 규칙

**Claude Code 권한 모드** — 어떤 도구 행동을 자동으로 허용하고 어떤 행동을 승인 대상으로 둘지 정한다. 모드에 따라 파일 변경이나 명령 실행이 바로 실행되거나 승인 화면에서 멈춘다. 모드를 따로 정하지 않으면 기본 승인 흐름을 따르므로, 어떤 행동이 왜 승인 없이 실행됐는지는 설정에서 따로 확인해야 한다. ([공식 문서] Anthropic, Claude Code 권한 문서)

**opencode 권한 규칙** — 도구와 행동별로 `allow`(허용), `ask`(확인), `deny`(거부)를 정한다.

- 같은 행동에 규칙이 여러 개 맞으면 **마지막에 맞은 규칙**이 적용된다.
- **에이전트별 규칙이 전역 규칙보다 우선**한다. 그래서 특정 에이전트의 편집은 확인을 받고 다른 에이전트의 읽기는 허용하는 식으로 나눌 수 있다.
- 규칙을 정하지 않으면 전역 규칙과 기본 정책에 따라 판단되므로 작업별 예외가 어느 규칙에서 왔는지 읽기 어렵다. ([공식 문서] opencode, 권한 문서)

두 문서는 구조를 설명할 뿐 수치 실험 근거는 아니다.

### 권한과 격리

> 권한은 **누가 무엇을 허용할지**를 다루고, 격리는 **허용된 실행의 피해를 어디에 가둘지**를 다룬다. 하나가 다른 하나를 대신하지는 않는다.

| 구분 | 권한 | 격리 |
|---|---|---|
| 다루는 것 | 누가 무엇을 허용하는가 | 허용된 실행의 피해를 어디에 가두는가 |
| 작동 시점 | 실행 전 판단 | 실행된 프로세스가 닿는 파일·네트워크·운영체제 범위 |
| 예 | Claude Code 권한 규칙, opencode allow·ask·deny | Docker 컨테이너 같은 외부 격리 환경, Claude Code의 Bash 샌드박스 |

도구마다 두 가지를 배치한 방식이 다르다.

- **pi**: 내장 권한 체계가 없어 실행한 사용자의 권한으로 도구를 실행하며, 격리가 필요하면 Docker 같은 외부 환경에 맡긴다. ([벤더] Mario Zechner, 저자 에세이)
- **Claude Code**: 권한 규칙을 도구 안에 두어 행동의 허용과 승인을 먼저 다룬다. 여기에 더해 운영체제가 셸 명령이 닿는 파일과 네트워크를 제한하는 Bash 샌드박스도 제공한다(macOS, Linux, WSL2). ([공식 문서] Anthropic, 샌드박스 문서)
- **OpenClaw**: 에이전트·작업 공간·발신자별로 세션을 나눠 대화 상태가 섞이는 범위를 줄인다. 이 세션 분리는 컨테이너 격리와 같지 않으며, host(내 컴퓨터 자체)에서 실행하는 도구의 범위는 별도의 sandbox 정책과 실행 환경에서 확인해야 한다.

pi와 Claude Code는 같은 위험을 없애는 하나의 해법이 아니라, 권한 판단과 실행 환경을 서로 다르게 배치한 사례다. macOS `sandbox-exec`나 Docker의 구체적인 명령은 이 노드에서 다루지 않는다.

### 비교 실험: 허용 규칙 하나 바꾸기

권한 설정은 "안전하다"는 선언으로 끝나지 않는다. 같은 작업에서 허용 규칙을 하나 바꾸고 다음 값을 함께 기록한다.

- 처리된 요청 수
- 승인 횟수
- 막힌 정상 작업
- 의도하지 않은 도구 호출

외부 메시지를 받는 도구라면 허용되지 않은 발신자의 메시지와 멘션 없는 메시지가 실제로 어느 세션에도 들어가지 않는지도 확인한다. 권한을 촘촘히 할수록 공격을 덜 받는다고 바로 결론 내지 않는다. 정상 작업을 막은 비율과 어떤 설정이 그 차단을 만들었는지를 함께 남겨야 다음 설정을 바꿀 근거가 생긴다.

## 9. 평가 루프: 결과와 실행 궤적 나눠 확인하기

최종 패치(코드 수정본)가 맞았다는 사실만으로는 검색을 낭비했는지, 우연히 성공했는지, 권한을 과하게 썼는지 구분할 수 없다. 평가 루프는 두 가지를 나눠 확인한다.

1. 최종 패치가 작업을 해결했는가
2. 그 결과에 이른 검색·편집·실행 과정이 적절했는가

> 에이전트가 거친 검색·편집·실행을 순서대로 남긴 기록을 **실행 궤적(trajectory)**, 줄여서 궤적이라고 한다.

### 구성요소와 결과를 따로 측정하기

**SWE-agent의 ablation** — 검색, 편집, 관찰 형식처럼 인터페이스 구성요소를 바꾸고 결과를 비교할 수 있음을 보였다(3강 참고). 같은 모델이라도 무엇을 읽고 어떤 형식으로 행동했는지를 고정해야 구성요소 하나의 기여를 물을 수 있다. SWE-bench Lite와 논문의 실행 조건 결과이므로 다른 모델이나 저장소에서도 같은 기여를 한다고 보지 않는다. ([학술] Yang et al., NeurIPS 2024, arXiv:2405.15793)

**SWE-bench** — 실제 GitHub 이슈와 저장소로 코딩 에이전트를 측정하는 벤치마크다. 12개 Python 저장소에서 모은 문제 2,294개로 이루어지고, 최종 패치를 두 종류의 테스트로 채점한다. ([학술] Jimenez et al., ICLR 2024 Oral, arXiv:2310.06770)

| 테스트 | 확인하는 것 |
|---|---|
| FAIL_TO_PASS | 고치기 전에 실패하던 테스트가 패치 뒤에 통과하는지 (이슈 해결) |
| PASS_TO_PASS | 원래 통과하던 테스트가 패치 뒤에도 계속 통과하는지 (기존 기능 유지) |

문제를 푸는 루프와 채점하는 루프를 나눈 구조다. 다만 테스트 통과가 유지보수 품질 전체와 같지는 않고, 공개된 문제라서 모델의 학습 데이터에 섞였을 위험(contamination, 오염)도 남는다.

**SWE-bench Verified** — OpenAI가 SWE-bench 저자들과 함께 2024년 8월에 공개한 500개 문제 모음이다. Python 경험이 있는 개발자 93명이 문제를 검토해, 문제 설명과 테스트로 풀 수 있다고 판단한 문제만 남겼다. ([공식 문서] OpenAI, Introducing SWE-bench Verified) 이 검토는 "문제를 풀 수 있는가"에 대한 근거이지, 특정 하네스가 더 낫다는 근거는 아니다.

### SWE-agent에서 평가에 쓰는 기록

| 기능 | 확인할 기록 | 1차 자료 |
|---|---|---|
| SWE-agent 평가 루프 | 문제 설명·저장소, 궤적, 패치, 테스트 결과를 같은 실행 단위에 남겨 결과와 경로를 함께 검토한다 | SWE-agent 공개 저장소와 실행 기록, ACI 논문 |

궤적은 모델의 의도나 패치가 맞는지를 스스로 증명하지 않는다. 대신 어느 검색이 먼저 있었는지, 테스트 실패 뒤 무엇을 편집했는지, 어떤 명령이 실행됐는지를 1차 자료로 남긴다. 이 기록으로 다음을 다시 확인한다.

- 다음 행동을 바꾼 관찰이었는가
- 같은 탐색을 반복했는가
- 승인한 권한이 과도했는가

### 통과 결과만으로 부족한 이유

정적 벤치마크(문제가 고정된 벤치마크)의 테스트 통과는 장기 유지보수, 설명 가능성, 코드 검토, 의존성 변화 대응을 재지 못한다. 공개된 문제와 해답이 학습 데이터나 도구 설정에 섞였을 가능성도 비교를 흐릴 수 있다. 그러므로 결과 점수와 함께 **실행 환경, 모델, 권한 정책, 비용, 승인 횟수, 궤적**을 남기고, 실제 코드 검토는 따로 한다. 어떤 궤적 신호로 좋은 하네스를 가려낼 수 있는지는 아직 남은 질문이다.

## 10. 일곱 도구 비교표로 후보 고르기

> 표에서 빈칸이 적은 도구가 아니라, **내 병목 칸에 근거가 있는 도구**를 고른다.

먼저 내 작업에서 확인할 병목을 하나 정하고, 표에서는 그 병목에 해당하는 열을 읽는다. 도구 이름을 한꺼번에 외우려는 표가 아니다. Claude Code처럼 소스가 공개되지 않은 도구는 내부 구현을 확인할 수 없고, 공개 코드가 있는 도구도 설치 버전, 로컬 설정, 실행 기록 없이 안전하다고 증명할 수 없다. 그래서 이 표를 제품의 우열이나 안전 판정으로 읽지 않는다. 앞 강의에서 읽은 카드와 다시 확인할 근거를 한자리에 모은 표다.

### 기능별 비교표

| 도구 | 행동 포맷 | 컨텍스트 | 경험 | 성찰 | 미니멀 | 권한 | 평가 |
|---|---|---|---|---|---|---|---|
| Claude Code | 시범에서 Bash 도구 호출로 파일 목록 조회 | 서브에이전트 컨텍스트 격리 | skills 재사용 | 다루지 않음 | 시스템 프롬프트 80% 이상 삭제해도 코딩 평가 손실 없음(자체 보고) | 권한 모드로 자동 허용과 승인 대상 구분 | 다루지 않음 |
| opencode | 다루지 않음 | 에이전트별 컨텍스트 분리, steps로 반복 횟수 제한 | 다루지 않음 | 다루지 않음 | 다루지 않음 | 에이전트별 allow·ask·deny 규칙 | 다루지 않음 |
| Aider | whole과 diff 편집 포맷 | repo map으로 넣을 파일 선택 | 다루지 않음 | 다루지 않음 | 다루지 않음 | 허용 범위는 설치 버전·설정·실행 기록에서 확인 | 자체 벤치마크(133개 작업)로 측정 |
| pi | 네 도구를 호출하는 작은 루프 | 세션 안의 대화와 도구 결과를 다음 판단에 사용 | 다루지 않음 | 다루지 않음 | 도구 네 개, 1,000토큰 미만 프롬프트 | 내장 권한 확인 없음, 외부 격리에 맡김 | Terminal-Bench 2.0 실행 언급, 수치 미확인 |
| OpenClaw | 다루지 않음 | 에이전트·작업 공간·발신자별 세션 분리 | 다루지 않음 | 다루지 않음 | 다루지 않음 | pairing, allowFrom, 그룹 멘션 요구로 발신 범위 설정 | 다루지 않음 |
| Hermes | 다루지 않음 | 세션 검색, memory, 활성 skills를 다음 컨텍스트에 연결 | memory와 skills 재사용 | 별도 기능 없음, 성찰 문장이 세션 이력·memory에 남을 수 있음 | 다루지 않음 | command approval, DM pairing, container isolation 적용 범위는 설정에서 확인 | 다루지 않음 |
| SWE-agent | 검색·편집·실행 인터페이스(ACI) 제공 | 최근 관찰 5개 유지, 과거 관찰 축약 | 다루지 않음 | 다루지 않음 | 풍성한 ACI로 mini-swe-agent와 비교되는 쪽 | 논문은 권한 정책을 다루지 않음 | SWE-bench와 ablation으로 측정 |

> 💡 "다루지 않음"은 이 노드의 앞 강의에서 근거를 다루지 않은 칸이라는 뜻이지, 도구에 그 기능이 없다는 뜻이 아니다. 내 병목 칸이 "다루지 않음"이면 공식 문서와 실행 기록으로 직접 확인한다.

### 내 병목으로 후보를 두 개로 줄이기

표를 다 읽은 뒤에도 모든 열을 같은 무게로 비교하지 않는다. 1강의 세 질문으로 후보를 고른다.

1. 내 작업의 병목 기능을 하나 적는다.
2. 그 기능을 확인할 근거가 카드의 1차 자료에 있는지 확인한다.
3. 확인하지 못한 범위가 현재 작업에서 허용되는지 판단한다.

- 예: 컨텍스트가 병목이면 세션, 관찰 요약, repo map 중 내 작업에서 볼 수 있는 기록을 가진 도구를 남긴다.
- 예: 권한이 병목이면 문서의 기능 설명만 보고 남기지 않고, 현재 설정과 승인 기록을 확인할 수 있는 도구를 남긴다.

필요한 범위가 확인되지 않았다면 탈락이라고 단정하지 않고 다음 확인 대상으로 적는다. 이 과정을 거쳐 후보를 두 개로 줄인다. 비교표는 후보를 줄여 줄 뿐, 최종 판정에는 자기 환경에서 만든 실행 기록이 필요하다.

## 11. 과제 — 도구의 불편을 개선 가설로 바꿔 실험하기

앞 강의들의 비교 실험과 같은 방식으로, 지금 쓰는 하네스 도구의 불편 하나를 골라 실험으로 확인한다. 기준 도구는 Claude Code, opencode, Antigravity 등 실제로 쓰는 도구 중에서 고른다. 논문의 수치는 정답이 아니라 조건이 붙은 가설이므로, 자기 환경에서 재현하거나 반박할 근거로만 쓴다.

### 1단계. 지금 쓰는 도구의 불편 떠올리기

최근 작업에서 반복해서 멈추거나 되돌린 장면 하나를 고른다. 승인 요청이 너무 자주 나왔는지, 필요한 파일을 놓쳤는지, 기록이 길어져 중요한 조건을 잃었는지, 결과를 검토하기 어려웠는지를 행동과 결과로 적는다. "도구가 불편하다"처럼 넓게 적지 않고, **어떤 작업에서 어떤 입력 뒤에 무엇이 늦어지거나 잘못됐는지**를 적는다.

이 불편이 정말 하네스 기능에서 온 것인지도 함께 의심한다. 모델 선택, 작업 난이도, 저장소 상태, 네트워크, 자신의 요청 문장이 원인일 수도 있다. 뒤의 실험은 불편을 확인하는 데 그치지 않고 원인이 하네스 기능이었다는 설명까지 검토한다.

### 2단계. 불편을 개선 가설과 근거로 바꾸기

불편을 줄일 수 있는 하네스 기능 하나를 골라 **반증 가능한** 개선 가설로 쓴다.

> 반증 가능하다 = 결과가 반대로 나오면 가설이 틀렸다고 말할 수 있다는 뜻이다.

```
관찰: "승인 대기로 작업이 멈췄다"
  → 가설: "권한 규칙의 범위를 조정하면 완료 시간이 줄어든다"
```

3강(행동 포맷)부터 9강(평가 루프)까지 인용한 연구에서 가설을 뒷받침하거나 반박할 근거를 찾고, 비슷한 조건의 연구에서 원문 문장, 측정 수치, 연구가 검증하지 않은 것, 근거 종류를 옮겨 적는다. 근거 종류 표기([학술], [벤더], [공식 문서])를 숨기지 않으며, 벤더의 자체 보고는 독립적인 비교가 아니라는 점도 보고서에 남긴다.

### 3단계. 한 항목만 바꾸는 실험 설계하기

고정 조건, 조작 항목, 이중 측정, 사전 판정식이 분리돼야 불편의 원인을 다른 조건과 구별할 수 있다. 실험 설계 용어로는 고정 = 통제 변인, 조작 = 조작 변인, 측정 = 종속 변인이다.

| 구분 | 내용 |
|---|---|
| 고정 | 모델, 작업 묶음, 토큰 또는 시간 예산 |
| 조작 (하나만) | 관찰 개수 N(4강의 최근 관찰 개수), 편집 포맷, 권한 정책, 메모리 표현 중 하나. 실제로 바꿀 수 있는 항목만 고른다. Claude Code와 opencode에서는 권한 규칙과 메모리 표현(notes/ 같은 기록 파일)을 바꿀 수 있고, 편집 포맷은 Aider의 `--edit-format`처럼 포맷을 고를 수 있는 도구에서만 바꿀 수 있다 |
| 이중 측정 | 해결률과 함께 토큰, 승인 횟수, 시간을 측정 |
| 반론 | 예상 반론 하나 이상과, 그 반론과 가설을 구분할 통제 조건 |
| 사전 판정식 | 결과를 보기 전에, 어떤 수치면 가설을 지지하고 어떤 수치면 버릴지 정한 기준 |

### 4단계. 결과를 GitHub 보고서로 제출하기

실험을 실행한 뒤 GitHub 저장소에 Markdown 보고서를 올린다.

```
my-harness-experiment/
├── README.md         # 가설, 실험 설계, 결과, 다시 검토할 조건 요약
├── experiment-01.md  # 실험 보고서
├── traces/           # 수정 전후의 실행 기록
└── fixture/          # 고정한 작업 입력 원본
```

- README.md에는 가설, 실험 설계 표, 판정 결과, 재검토 조건을 요약하고 전체 내용은 experiment-01.md에 쓴다.
- 실행했다면 수정 전후(before·after)의 실행 기록(trace)을 traces/에 넣거나 링크한다. 실행하지 못했다면 그 이유와 사전 판정식을 남긴다.
- 불편의 실제 원인이 선택한 하네스 기능이었는지 돌아보는 문단을 넣는다.
- 가설과 다른 결과가 나왔다면 실패로 감추지 않고, 무엇이 원인 설명을 약하게 만들었는지와 다음 실험에서 고정하거나 바꿀 조건을 적는다.
- 저장소 URL을 LMS에 제출한다. LMS에서는 제출한 뒤에 수정할 수 없다.

**평가 기준**

- 가설이 반증 가능한가
- 고정, 조작, 측정이 분리되었는가
- 근거 종류를 구분해 인용했는가
- 불편의 원인이 하네스 기능이었는지 돌아보았는가

### 과제 진행 예시: 컴파운드 엔지니어링 실험

Claude Code에서 컴파운드 엔지니어링, 즉 한 번 얻은 경험을 다음 실행에 쌓아 성능을 올리는 접근이 실제로 효과가 있는지 확인한다. 5강의 ExpeL, Voyager, WikiSkill과 같은 방향의 주장이다.

> **가설**: 같은 작업을 다시 풀 때, 첫 시도의 기록을 notes/ 폴더에 남기고 다음 요청에서 그 기록을 참조하게 하면, 기록 없이 시작할 때보다 두 번째 시도가 빠르고 정확해진다.

**실험 작업 3개** (모두 fixture로 입력 고정)

1. **parse-log**: fixture 로그 파일 sample.log에서 오류만 골라 표로 정리하는 스크립트 parse.py 작성 (확인: test_parse.py)
2. **refactor-util**: fixture 유틸리티 util.py의 함수 3개에 타입 힌트와 독스트링(함수 설명문) 추가 (확인: test_util.py)
3. **fix-failing**: fixture 테스트 test_me.py의 실패 2건을 통과하도록 수정 (확인: test_me.py)

각 작업은 괄호 안의 테스트가 통과하면 끝난 것으로 본다.

**사전 준비** — 교안은 fixture 파일을 주지 않으므로 직접 만든다. 저장소의 fixture/ 폴더에서 Claude Code를 실행하고 다음과 같이 요청한다.

```
sample.log, util.py, test_me.py 실습용 fixture 만들어 줘. test_me.py는 실패 2건이 나오게 해 줘.
작업 확인용 테스트도 함께 만들어 줘. test_parse.py는 parse.py가 sample.log의 오류 줄만 골라
표로 출력하는지, test_util.py는 util.py의 함수 3개에 타입 힌트와 독스트링이 있는지 확인하게 해 줘.
두 테스트는 지금은 실패해야 해.
```

한 번 만든 fixture는 내용을 바꾸지 않는다. 입력이 같아야 조건 사이의 차이가 작업 난이도가 아니라 경험 기록 때문이라고 말할 수 있다. 작업이 util.py와 test_me.py를 고치므로 fixture/는 원본으로만 두고 시도할 때마다 복사해서 쓴다.

**실험 설계**

| 구분 | 내용 |
|---|---|
| 고정 | Claude Code, 같은 모델, 같은 세 작업, 같은 fixture |
| 조작 | 경험 기록 조건: 첫 시도 뒤 notes/에 접근법과 주의점을 남기고 다음 요청에서 참조하게 함. 대조 조건: 기록 없이 새로 시작 |
| 측정 | 두 번째 시도의 소요 시간, 수정 횟수, 테스트 통과까지의 시도 수, 토큰 |
| 사전 판정식 | 경험 기록 조건이 세 작업 중 두 개 이상에서 시간과 시도 수가 모두 적으면 가설 지지, 그 외에는 기각 |

**측정값을 세는 방법**

| 측정값 | 세는 방법 |
|---|---|
| 소요 시간 | 작업을 마친 뒤 `/usage`를 입력하고 Session 블록의 Total duration (wall)을 적는다 |
| 토큰 | 같은 Session 블록의 Usage by model 줄에서 input과 output 토큰 수를 적는다 |
| 수정 횟수 | 화면에 표시된 파일 편집·작성 도구 호출의 수를 센다 |
| 테스트 통과까지 시도 수 | 해당 작업의 테스트가 통과할 때까지 Claude Code에 요청을 보낸 횟수를 센다 |

`/usage`의 Session 블록은 `/clear`로 새 세션을 시작하면 0부터 다시 센다(v2.1.211 이상). 그보다 낮은 버전에서는 Claude Code를 새로 실행해야 0부터 센다. ([공식 문서] Anthropic, Claude Code 비용 문서)

**실행 절차**

1. 저장소 밖에 작업 폴더를 만들고, fixture/의 원본을 복사해 폴더 A(경험 기록 조건)와 폴더 B(대조 조건)를 만든다. 저장소 밖에 두면 작업 중 만든 파일과 notes/가 저장소의 fixture/ 원본, 보고서 파일과 섞이지 않는다.
2. 두 폴더에서 세 작업을 한 번씩 풀고, 작업마다 소요 시간과 시도 수를 기록한다.
3. 폴더 A에만 notes/를 만들고, 작업마다 접근법, 만난 오류, 해결 방법을 세 줄 이내로 적는다. 폴더 B에는 기록을 남기지 않는다.
4. 두 폴더의 작업 파일을 fixture/의 원본으로 되돌린다. 폴더 A의 notes/는 그대로 둔다.
5. 두 폴더에서 세 작업을 다시 풀게 하고 같은 지표를 기록한다. 폴더 A에서는 요청할 때 notes/의 파일을 함께 참조하라고 지시한다.
6. 두 조건의 기록을 나란히 놓고 사전 판정식에 넣는다.

> 💡 시도할 때마다 Claude Code를 새로 실행하거나 `/clear`로 대화를 비운 뒤 시작한다. 앞 시도의 대화가 남아 있으면 두 조건의 차이가 notes/에서 왔다고 말할 수 없다.

**기록 표** — 두 번째 시도의 결과를 채운다. 화면에서 확인하지 못한 값은 지어내지 말고 "미확인"으로 적는다.

| 작업 | 조건 | 소요 시간 | 수정 횟수 | 테스트 통과까지 시도 수 | 토큰 |
|---|---|---|---|---|---|
| parse-log | 경험 기록 | | | | |
| parse-log | 대조 | | | | |
| refactor-util | 경험 기록 | | | | |
| refactor-util | 대조 | | | | |
| fix-failing | 경험 기록 | | | | |
| fix-failing | 대조 | | | | |

**결과 보고** — 세 작업의 두 조건 기록을 표로 남기고 판정 결과(지지 또는 기각)를 함께 적는다. 기각돼도 실험이 실패한 것은 아니다. 어느 작업에서 기록이 도움이 되지 않았는지가 다음 실험을 설계하는 근거가 된다. 자기 도구의 불편에서 출발할 때도 작업을 fixture로 고정하고, 조작을 한 가지로 좁히고, 결과가 나오기 전에 판정식을 쓰는 흐름은 같다.
