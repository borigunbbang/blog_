## Claude SDK가 여기서 언급된 이유

이번 섹션은 "프롬프트나 생성 설정(온도, 추론 등)에 따라 AI의 답변이 어떻게 바뀌는가?"를 비교 실습하는 파트다.

- **Ollama**: 내 컴퓨터에서 직접 AI를 돌리며 `temperature`(창의성/무작위성), `top_k`(토큰 후보 수) 등 디테일한 설정을 마음대로 조절할 수 있다.
- **Claude SDK**: 코드로 Claude를 호출하는 편리한 도구지만, 이 실습에 필요한 일부 생성 옵션(temperature, top_k 등)을 외부 코드에서 직접 조절하기 어렵거나 제한적이다.

### 본문이 전하고자 하는 메시지

- **도구의 차이를 이해할 것**: 같은 프롬프트라도 Ollama로 로컬 모델을 부를 때와 Claude SDK로 외부 AI를 부를 때 조절할 수 있는 설정값(노브)의 범위가 다르다.
- **실험 기록 시 주의할 점**: 단순히 "모델이 달라서 결과가 다르다"고 적지 말고, "Claude SDK에서는 특정 옵션(예: temperature)을 조절할 수 없음"이라고 명확히 기록해야 공정한 비교 기준이 된다.

## 실습 1. 프롬프트 방식 비교

| 파일 | 프롬프트 방식 | 실제 프롬프트 | 기대 효과 |
|---|---|---|---|
| basic | 기본 질문 | "다음을 계산하세요: 25 × 14 - 87 ÷ 3" | 아무 장치 없이 모델이 원래 어떻게 답하는지 보는 기준점 |
| role_cot | 역할 부여 + 단계별 사고(CoT) | "당신은 꼼꼼한 수학 교사입니다. 연산 순서를 단계별로 검산하고…" | 과정이 길어지고 실수가 줄어드는지 |
| few_shot | 예시 제공 | "예: 18 × 5 - 12 ÷ 3은 90 - 4 = 86입니다. 같은 규칙을 적용하세요." | 예시와 비슷한 형식과 규칙으로 답하는지 |

- **CoT(Chain-of-Thought)**: 답만 말하지 말고 생각 과정을 단계별로 쓰게 하는 방법
- **Few-shot**: 질문 전에 예시 몇 개를 보여 주는 방법. 예시가 없으면 zero-shot

**비교 결과**
- basic: 간결
- role_cot: 예제에 맞는 풀이
- few_shot: 우선순위 원리에 맞는 풀이 진행 → 단계별 검토, 가장 긴 답변

## 실습 2. temperature 비교

질문 고정: **"9.11과 9.9 중 어느 쪽이 더 큰가요?"**

### temperature = 0.0

- 3번 실행 → 3번 모두 같은 값, 문장까지 같음
- 다만 소수점이 아니라 **날짜로** 비교함

### temperature = 1.5

3번 모두 답이 크게 흔들렸다.

- **1회차**: 9.11을 "11월 1일"로 읽는 등 날짜로 해석하다가 미국 독립전쟁, 추수감사절 같은 엉뚱한 이야기로 새고, 중간에 러시아어·중국어 글자까지 섞임. 결론도 "9월이 더 큽니다", "1일입니다"로 오락가락
- **2회차**: 9/11과 9/9를 날짜로 비교하며 존재하지 않는 "1997년 사건" 같은 사실을 지어냄. 결론은 "9.11이 더 큼"
- **3회차**: 9월을 "11월", "5월"과 뒤섞어 설명하다가 "9월 11일이 훨씬 더 큽니다"

→ temperature가 높으면 같은 질문에도 매번 다른 답이 나오고, 문장이 무너지며 환각이 크게 늘어난다.

## 실습 3. 조건 변형 실험

| 파일 | 조건 | 질문 뒤(또는 앞)에 붙인 지시 |
|---|---|---|
| m1_basic | 기본 (비교 기준) | 질문만 |
| m2_role | 역할 부여 | "당신은 꼼꼼한 수학 교사입니다." |
| m3_check | 단계별 검산 | "단계별로 풀고, 마지막에 답을 다시 검산하세요." |
| m4_example | 예시 제공 | "예: 3.25와 3.4 중 더 큰 수는 3.4입니다." |
| m5_vote | 셀프 다수결 | "세 번 풀고, 다수결로 최종 답을 정하세요." |
| m6_ban | 특정 단어 금지 | "'소수점'이라는 단어를 쓰지 말고 답하세요." |
| m7_json | JSON 출력 | `{"answer": ..., "reason": ...}` 형식으로만 답하기 |

**결과**

- m1_basic: 소수점 단위로 파악 → 9.9가 더 크다
- m2_role: 수학 교사 시점으로 소수점 정렬 비교 → 9.9가 더 크다
- m3_check: 소수점 왼쪽 정수 부분부터 자리 순서대로 비교
- m4_example: 예시대로 비교
- m5_vote: 날짜를 예시로 비교 — 숫자 크기 차이, 시간 분기 기준, 총 날짜 합계 세 가지 방법으로 풀어 최종 9.11이 더 큼 (오답)
- m6_ban: "양자가 같습니다" (오답)
- m7_json: 날짜로 비교

## 이번 실습에서 가져가야 할 핵심

**1. 채점 기준을 먼저 세운다 (Test-First)**
프롬프트를 쓰기 전에 무엇이 좋은 답인지 Pass/Fail 기준을 먼저 정한다. 기준이 없으면 "좀 나아진 것 같다"는 느낌으로 판단하게 되고, 기준이 있으면 "9개 중 3개 통과"처럼 숫자로 비교할 수 있다.

**2. 프롬프트는 부품을 하나씩 더하며 개선한다**
A→B→C로 한 번에 하나씩 조건을 추가해야 어떤 부품이 효과를 냈는지 알 수 있다.
- Claude: A에서 B로 넘어가며 배송일 환각과 다중 질문이 사라졌다.
- Ollama: C에서 JSON 형식은 완벽해졌지만, 주문번호를 묻지 않는 문제는 그대로 남았다.

부품이 효과를 내도 고쳐지지 않는 문제가 있다면, 그게 다음에 보강할 지점이다.

**3. 정보가 부족하면 LLM은 지어낸다 (환각)**
고객 질문에 주문 정보가 없었는데도 두 모델 모두 A에서 배송 기간을 만들어냈다. Ollama는 존재하지 않는 고객센터 전화번호까지 만들었다. "모르면 지어내지 말고 되물어라"는 규칙을 프롬프트에 명시해야 한다. 실제 서비스에서 가장 위험한 부분.

**4. 같은 프롬프트를 여러 번 돌려 재현성을 확인한다**
한 번 통과로는 부족하고 3회 모두 통과해야 믿을 수 있다. 단, 재현성이 높다고 정답인 건 아니다. Ollama는 3번 결과가 거의 똑같았지만 셋 다 틀렸다.

**5. 모델에 따라 같은 프롬프트의 결과가 달라진다**
Claude는 B부터 통과했지만, 작은 모델(qwen 2b)은 C에서도 통과하지 못했다. 모델이 작을수록 규칙을 더 구체적이고 명시적으로 적어야 하고, 모델을 바꾸면 테스트도 다시 돌려야 한다.

**6. 실험 환경을 기록해야 비교할 수 있다**
.json 파일에 모델, temperature, 프롬프트를 함께 남겼기 때문에 백엔드끼리 공정하게 비교할 수 있었다. 결과만 남기면 왜 달랐는지 설명할 수 없다.

**7. 사람이 보기 좋은 답과 코드가 처리할 수 있는 답은 다르다**
Claude의 C 결과는 내용은 좋았지만 ` ```json ` 코드블록에 감싸져 있어서 바로 파싱하면 실패한다. 서비스에 쓰려면 출력 형식까지 채점 기준에 넣어야 한다.

> 한 줄 요약: 기준을 정하고 → 프롬프트를 조금씩 고치고 → 여러 번 돌려 채점하는 반복이 프롬프트 엔지니어링의 표준 워크플로우.
