## 1. 메인 프로젝트: RAG 가이드 챗봇을 만들고, 배포하고, 평가하기

### 오늘 만들 제품

공개 자료를 근거로 답하고, 그 근거를 화면에 보여 주고, 답변 품질을 자동으로 판정한 결과까지 남기는 **RAG 가이드 챗봇**이다.

완성된 참조 구현은 모두의연구소 컨퍼런스 **모두콘**을 안내하는, 서버 없이 도는 RAG 챗봇이다.

- 임베딩과 검색은 브라우저에서 한다.
- 답변은 **로컬 Ollama**가 만든다. 서버가 답을 만들지 않고, 페이지를 연 사용자 컴퓨터의 Ollama(`qwen3.5:2b`)가 만든다.
- 답변마다 자동 판정이 붙는다.
- 처음 열 때 임베딩 모델을 내려받는다(첫 방문 1회, 약 200MB). Ollama가 실행 중이어야 답변이 시작된다.
- 원격 주소의 페이지가 사용자 컴퓨터의 Ollama와 통신하려면 CORS 허용 설정(`OLLAMA_ORIGINS`)이 필요하다. 설정 방법은 구현 단계에서 다룬다.
- 직접 확인: `suncreation.github.io/moducon-chatbot`

수업이 끝나면 내 도메인에 맞춘, 근거 기반 답변과 자동 판정을 갖춘 안내 챗봇이 하나 생긴다.

**기존 파이썬 실습과 다른 점 두 가지**

1. 파이썬 스크립트가 아니라 브라우저에서 동작하는 **타입스크립트 앱**으로 구현한다.
2. 완성 뒤에는 프롬프트와 검색 설정을 바꿔 가며, 직접 설계한 **루브릭(채점 기준표)**으로 성능을 측정하는 실험까지 한다.

### 학습 목표

- 내 도메인의 안내 챗봇을 PRD부터, 스스로에게 질문하며 기획한다.
- 공개 자료를 모으고 청크와 임베딩을 구성해 브라우저 벡터스토어를 만든다.
- 로컬 Ollama `qwen3.5:2b`의 스트리밍과 브라우저 임베딩을 묶은 RAG 파이프라인을 이해한다.
- 답변의 근거성과 거절을 판정하고, 사람 피드백과 함께 읽는다.
- 내 루브릭으로 프롬프트와 RAG 설정을 실험하고, 성능 변화를 표로 남긴다.
- 정적 앱을 배포한 뒤 수용 기준으로 동작을 다시 확인한다.

### 전체 모습: 소개, 검색, 판정

- 첫 화면은 단순한 대화창이 아니다. 행사 소개, 연혁, 프로그램, FAQ, 챗봇 상태를 함께 보여 주는 안내 공간이다.
- 질문이 들어오면 브라우저는 `onnx-community/embeddinggemma-300m-ONNX` 임베딩 경로로 질문과 공개 원문 **37개 청크**를 비교한다.
- **코사인 검색과 BM25 검색을 함께 돌린다.** 하나는 의미를, 다른 하나는 정확한 표기를 단서로 삼기 때문에, 한쪽만 쓰면 놓칠 근거를 서로 메워 준다.
- 선택된 청크는 본문뿐 아니라 ID, URL, 섹션 정보까지 그대로 달고 프롬프트에 들어간다.
- 로컬 Ollama의 `qwen3.5:2b`가 응답을 스트리밍하고, 화면은 답변 뒤에 필드 여섯 개짜리 판정 배지를 띄운다.
- **약한 근거 처리**: 최고 유사도가 0.55보다 낮으면 검색 결과를 버리지 않는다. 대신 근거가 약하다는 사실을 프롬프트와 UI에 드러내고, 모델은 단정하지 말고 자료의 한계나 답변 범위를 말해야 한다.

> 생성된 문장이 자연스럽다는 것과 출처가 있는 답이라는 것은 서로 다른 사실이다. 이 앱은 둘을 구분해서 보여 준다.

### 질문에서 판정까지 한 바퀴

| 순서 | 단계 | 내용 |
|---|---|---|
| 1 | 질문 | "모두콘은?" |
| 2 | 임베딩 | 768차원 |
| 3 | 하이브리드 검색 | 코사인 + BM25 |
| 4 | 근거 청크 | id · url · text |
| 5 | 프롬프트 조립 | 시간 맥락 · 약한 근거 주의 |
| 6 | Ollama 스트리밍 | qwen3.5:2b |
| 7 | 판정 배지 | 출처 칩 · 약한 근거 경고 · 판정 |

도식에서 왼쪽에서 오른쪽으로 가는 화살표는 데이터가 넘어가는 흐름이고, 아래로 꺾이는 화살표는 생성이 끝난 뒤에도 남는 검토를 뜻한다.

각 단계가 빠지면 이렇게 된다.

- 청크가 없으면 임베딩은 비교할 대상이 없다.
- URL이 없으면 사용자는 생성된 문장을 확인할 출발점을 잃는다.
- judge(판정기)가 없으면 답을 어떻게 읽어야 할지 알려 주는 별도 신호가 사라진다.
- 반대로 judge만 붙인다고 출처 없는 문장이 근거를 얻지는 않는다. **각 상자는 앞 상자의 결과물을 지켜야 한다.**

### 구현 열두 단계

기능을 급하게 붙이는 순서가 아니다. 뒤 단계가 앞 단계의 선택을 검증할 수 있도록 쌓아 올리는 순서다.

1. Vite, React, TypeScript로 정적 앱을 만들고 GitHub Pages용 상대 경로를 준비한다.
2. 모두콘 소개 화면을 만든다.
3. 공개 원문을 출처 URL이 붙은 사실 단위 청크로 수집한다.
4. 청크 JSON 스키마와 ID 규칙(MC-001부터)을 정한다.
5. 768차원 벡터를 만들어 정적 벡터스토어에 넣는다.
6. 브라우저 임베딩에는 WASM에서 동작하는 `no_gather_q4` 경로를 쓴다.
7. 모델과 자료의 캐시, 진행률 표시를 다룬다.
8. 코사인 + BM25 하이브리드 검색을 붙인다.
9. 시간 컨텍스트와 약한 근거 규칙을 넣어 프롬프트를 조립한다.
10. Ollama 상태 확인, 스트리밍, 취소 UI를 연결한다.
11. 출처 칩, 근거 모달, 검색 단계, 경고 배지를 화면에 보인다.
12. 선택 엔진, LLM-as-a-Judge, 사람 피드백, Pages 배포와 수용 기준 점검을 한 화면의 사용 경험으로 묶는다.

> 이 순서는 특정 도구의 정답이 아니다. **"질문이 들어온 순간부터 근거, 답변, 판정을 각각 관찰할 수 있어야 한다"**는 설계 원칙을 구현 순서로 옮긴 것이다.

**더 깊이 가 보기**: 기본 경로는 로컬 Ollama만으로 끝난다. 예시 구현에는 Gemini API를 쓰는 선택 엔진도 있어서, 무료 로컬 경로와 API 키를 넣는 경로를 비교해 볼 수 있다. 두 엔진을 나란히 두면 같은 질문에 대한 답변 리듬과 판정 결과가 어떻게 다른지 보이고, 이 비교가 나중에 판정 실험의 재료가 된다.

## 2. 바이브 코딩의 첫 문장: PRD를 스스로에게 묻기

### 에이전트에게 맡기기 전에 정할 것

에이전트에게 화면 구현을 요청하기 전에 PRD(제품 요구사항 문서)에 먼저 적어 둘 것이 있다.

- 방문자가 답을 보고 무엇을 확인해야 하는가
- 공개 자료로 답할 수 없는 질문이 오면 화면은 어떤 상태로 남아야 하는가

화면이 뜬다는 사실만으로는 성공을 판정할 수 없다. 그래서 **성공으로 읽힐 장면**과 **이번에 만들지 않을 기능**을 문장으로 못박아 둔다. 에이전트가 코드를 빨리 만든다고 해서, 그 코드가 무엇을 증명해야 하는지까지 정해 주지는 않는다. 요구를 받는 것보다 요구의 경계를 질문으로 정리하는 일이 먼저다.

> 💡 **바이브 코딩**: 요구를 말하면 에이전트가 화면과 파일을 만들어 주는 방식이다. 무엇을 성공으로 볼지 비워 둔 채 요청이 길어지면, 결과물은 빨리 나와도 검증할 대상이 사라진다.

- PRD는 에이전트에게 넘길 답안을 미리 써 두는 문서가 아니다. 만드는 사람이 아직 결정하지 못한 경계를 찾아내는 **질문지**다.
- 모두콘 안내 챗봇처럼 공개 정보로 답해야 하는 제품에서는 "답할 수 있는 질문"과 "답하면 안 되는 질문"이 똑같이 중요하다.
- 아래 여덟 질문은 정답을 채우는 양식이 아니다. 내 도메인의 경계를 탐색하는 질문이다. 아직 판단할 근거가 없는 칸에는 모른다고 적거나 `[결정 필요]`로 남긴다. 그 표시가 추가 조사나 에이전트의 확인 질문이 필요한 곳을 드러낸다.
- 비목표가 없으면 목표가 넓어질 때 검색 범위도 끝없이 넓어진다. 판정 기준이 없으면 에이전트가 만든 화면을 보고도 무엇이 빠졌는지 말할 수 없다.
- 이 항목들을 혼자 완벽하게 설계해도 되지만, 에이전트 도구에게 인터뷰를 받으며 구체화하면 더 풍부한 내용을 더 쉽게 쓸 수 있다.

### 목표는 기능 목록이 아니라 사용자의 변화

"모두콘 챗봇을 만든다"는 작업 목록으로는 쓸 수 있어도 제품 요구로는 부족하다. 사용자가 행사 소개를 읽고, 역대 정보를 찾고, 질문한 답의 출처를 열어 본다는 **변화**까지 적어야 소개 페이지, 청크, 검색, 생성 UI가 한 목표를 향한다.

모두콘 PRD의 목표에는 2018~2025년 소개, 검색 단계를 보여 주는 RAG, 출처 표시, 스트리밍, judge, 사람의 좋아요·싫어요 피드백, KST 상대시간 해석이 들어간다. 모두 화려한 부가 기능이 아니라, 사용자가 답을 믿을지 보류할지 판단할 근거를 주는 장치다.

| 스스로에게 묻는 질문 | 모두콘의 답 |
|---|---|
| ① 누구의 어떤 불편을 다루는가 | 행사 정보를 찾는 방문자가 공개된 사실에 닿도록 돕는다 |
| ② 사용자가 결국 무엇을 할 수 있어야 하는가 | 질문한 뒤 답변의 근거와 원문 출처를 확인한다 |
| ③ 제품의 한 문장 목표는 무엇인가 | 소개와 RAG를 이어 근거 있는 안내를 제공한다 |
| ④ 이번 범위에서 하지 않을 일은 무엇인가 | 로그인과 전문 DB 검색은 넣지 않는다 |
| ⑤ 무엇을 사실로 삼는가 | 공개 원문과 그 URL을 함께 보관한다 |
| ⑥ 답하지 못할 때 어떻게 하는가 | 근거가 부족하다고 밝히고 보수적으로 답을 줄인다 |
| ⑦ 사용자는 성공을 어떻게 알아보는가 | 스트리밍 답, 출처 칩, 판정 배지를 확인한다 |
| ⑧ 어떤 관찰로 수용 여부를 판정하는가 | 수용 기준의 질문과 화면 상태를 하나씩 확인한다 |

### 비목표는 안전장치다

비목표는 목표를 줄이겠다는 사과가 아니다. 이번 구현에서 **어떤 약속을 하지 않는지** 선언하는 안전장치다.

- 로그인, 전문 DB 검색, 다국어, 모바일 최적화, 서버 수집을 비목표로 적어 두면, 에이전트가 사용자 계정이나 서버 동기화가 필요한 것처럼 구조를 부풀리지 않는다.
- 정적 브라우저 앱이라는 선택과도 맞물린다. 공개 문서를 정적 파일로 두고 브라우저에서 검색하며 사용자의 로컬 Ollama를 부르는 구조에, 서버 측 계정 관리나 비공개 데이터 검색을 섞는 것은 목표를 넓히는 게 아니라 **다른 제품을 시작하는 일**일 수 있다.

### 수용 기준 읽는 법

> 💡 **수용 기준**: "좋은 챗봇"처럼 해석이 갈리는 표현을, 화면에서 확인할 수 있는 문장으로 바꾸는 장치다.

모두콘의 수용 기준은 다음과 같다.

- 소개에 출처를 표시한다
- "모두콘이 뭐야?"에 `[ID]` 근거가 붙은 스트리밍 답변을 보인다
- "내일 날씨"처럼 도메인 밖 질문에는 `refusal=true`로 답을 제한한다
- 모든 답변에 판정 배지를 보인다
- API 키가 없어도 로컬 자기평가를 시도한다
- 판정이 실패해도 기존 UI가 무너지지 않는다
- 상대시간 질문은 질문 시점의 KST로 해석한다
- 출처 칩에서 원문을 열 수 있다
- Ollama가 꺼졌을 때 배너와 재시도를 보인다
- CORS 설정 뒤에는 github.io 환경에서도 동작한다

이 기준들은 모델이 말을 잘하는지만 묻지 않는다. 근거가 실제로 있는지, 제품의 경계가 실제 UI까지 이어졌는지를 묻는다. 로컬 judge는 같은 2B 모델이 답과 판정을 모두 맡을 수 있으므로 **독립 평가가 아니다.** 교육용의 거친 신호로 읽어야 한다.

> 기준 하나는 기능 하나를 더하라는 명령이 아니다. 무언가 실패해도 사용자가 텅 빈 화면을 겪지 않게 하겠다는, 관찰 가능성에 대한 약속이다.

### 모두콘 PRD 발췌

모두콘 안내를 위해 실제로 세운 기획 결과물이다. 형식을 따라 하기보다, 앞의 질문을 내 도메인에 적용해 새 PRD를 채워야 한다. 도메인을 바꿀 때 행사명만 바꾸지 말고, 공개 자료의 범위와 도메인 밖 질문의 처리까지 함께 바꿔야 한다.

```markdown
# 모두콘 안내 챗봇 PRD

## 목표
- 2018~2025 모두콘의 공개 소개 정보를 안내합니다.
- 공개 문서를 검색한 단계와 출처를 드러내는 RAG 답변을 제공합니다.
- 답변을 스트리밍으로 표시하고, judge 결과와 좋아요·싫어요 피드백을 함께 기록할 수 있게 합니다.
- 상대시간이 들어간 질문은 KST 기준의 질문 시점 맥락을 사용합니다.

## 비목표
- 로그인과 사용자 계정 관리를 만들지 않습니다.
- 전문 데이터베이스 검색과 서버 수집을 만들지 않습니다.
- 다국어 지원과 모바일 최적화를 이번 범위에 포함하지 않습니다.

## 수용 기준
- 소개 정보에는 확인 가능한 출처가 표시됩니다.
- "모두콘이 뭐야?"에 [ID] 근거를 포함한 스트리밍 답변이 표시됩니다.
- "내일 날씨"에는 refusal=true로 도메인 밖 질문임을 드러냅니다.
- 모든 답변에는 판정 배지가 있으며, 판정 실패 뒤에도 UI가 유지됩니다.
- 출처 칩을 누르면 원문을 확인할 수 있고, Ollama가 꺼지면 배너와 재시도가 보입니다.
```

이 문서는 완성된 코드의 설명서가 아니다. 에이전트가 파일을 만들기 전에 반박하거나 확인할 수 있는 기준이다. "공개 문서", "도메인 밖", "판정 실패" 같은 표현은 구현 전에 예시 질문으로 검토해 두어야 나중에 서로 다른 해석이 쌓이지 않는다.

### 내 도메인의 PRD 초안 만들기

1. 모두콘을 기준점으로 삼고, 내가 안내하고 싶은 도메인을 하나 정한다. 자료를 공개 URL로 확인할 수 있어야 하고, 자료가 충분한지 확신이 없으면 그 불확실성 자체를 PRD의 조사 항목으로 남긴다.
2. 여덟 질문에 한 문장씩 답한 뒤, 그 답을 **목표 · 비목표 · 수용 기준** 세 제목 아래로 다시 배치한다. 답한 순서가 문서 순서와 같을 필요는 없지만, 빠진 답이 없는지 확인한다.
3. 수용 기준은 실제로 입력할 질문과 관찰할 화면 상태가 들어간 문장으로 바꾼다.
   - 예: 행사 안내 도메인이라면 "정확한 정보를 제공한다"보다 "소개 정보에 출처가 표시된다", "행사 밖 질문에는 근거 부족 또는 거절 상태가 드러난다"가 검증 가능한 기준이다.
   - 반대로 자료가 없는 주제에도 그럴듯하게 답하게 한다는 문장은 RAG의 목표와 맞지 않는다.

초안의 빈칸을 에이전트가 마음대로 채우게 두지 않는다. 아직 정하지 않은 항목은 `[결정 필요]`로 남긴다. **빈칸은 실패가 아니라, 에이전트가 확인 질문을 해야 할 곳을 보여 주는 표시다.**

### 첫 대화에서 에이전트에게 맡길 범위

PRD 초안이 생긴 다음에야 에이전트에게 첫 요청을 보낸다. 목적은 모든 파일을 한 번에 만들게 하는 것이 아니라, 에이전트가 **PRD의 모순과 빠진 판정 기준을 먼저 찾아내게** 하는 것이다.

- 에이전트는 누구를 위한 안내인지, 어느 공개 자료를 사실로 삼는지, 근거를 못 찾은 답을 어떻게 처리할지 되물어야 한다. 그 질문들이 코드를 만들기 전에 확인할 PRD의 빈칸을 가리킨다.
- 대괄호 부분을 내 도메인으로 바꾸고, 에이전트가 제안한 기능을 받아들이기 전에 비목표와 수용 기준에 다시 대조한다. 제안이 목표를 넓힌다면, 기능이 매력적인지보다 이번 약속에 필요한지부터 판단한다.

```
당신은 브라우저 기반 RAG 안내 챗봇의 제품 설계 검토자입니다.
아래 PRD 초안을 읽고 구현을 시작하지 말고 먼저 검토합니다.

도메인: [내 도메인]
목표: [사용자가 할 수 있어야 하는 일]
비목표: [이번 범위에서 하지 않을 일]
공개 자료 후보: [URL 또는 자료 종류]
수용 기준: [질문과 관찰 가능한 결과]

반드시 다음 순서로 답합니다.
1. 목표와 비목표가 충돌하거나 모호한 지점을 질문으로 제시합니다.
2. 공개 자료만으로 검증할 수 없는 수용 기준을 표시합니다.
3. 도메인 밖 질문, 근거 부족, 판정 실패의 처리 기준을 제안합니다.
4. 수정된 PRD 목차를 작성하되, 확인되지 않은 사실과 수치를 추가하지 않습니다.
5. 파일 생성이나 코드 작성은 제가 직접 요청할 때까지 하지 않습니다.
```

마지막 문장은 속도를 늦추려는 장식이 아니다. 설계와 구현을 나눠서, 검토 결과가 코드에 묻히지 않게 하는 경계다.

> PRD의 문장 하나하나가 나중에 채점 문항이 된다.

## 3. 자료 수집과 청크 설계

### 검색되는 자료와 답할 수 있는 자료는 다르다

행사 소개처럼 보이는 문장을 모아도, 원문 URL과 문단의 맥락이 없으면 사용자가 출처를 눌렀을 때 돌아갈 곳이 없다. 이런 문장은 검색 후보에서 빼고 원문 URL과 섹션을 다시 확인한다.

- 검색에 걸리는 문장과, 사용자가 근거로 확인할 수 있는 문장은 같지 않다.
- 자료를 많이 모으는 것보다, 답변의 한 문장이 어디서 왔는지 되짚을 수 있게 하는 일이 먼저다.
- RAG에서 자료를 모은다는 말은 웹페이지를 잔뜩 저장한다는 뜻이 아니다. 나중에 답변 문장과 이어 줄 수 있는 **공개 근거를 고르는 일**이다.

모두콘 챗봇의 **코퍼스(자료 묶음)**는 세 범위의 공개 문서로 만든 37개 청크다.

- 각 청크는 **최소 120자의 사실 단위**다.
- 본문만 떼어 두지 않고 원문 URL과 섹션을 함께 보관한다.
- 그래서 검색 결과가 "행사 정보와 비슷한 문장"에서 끝나지 않고, 사용자가 실제 출처로 돌아갈 수 있는 길이 된다.

**수집 단계에서 먼저 물을 것**

- 이 페이지에 질문의 답이 있는가?
- 그 답은 어느 시점의 어떤 공개 문서에 근거하는가?

**잘못 자르면 생기는 문제**

- 행사명이나 연도만 있는 페이지를 기계적으로 쪼개면, 검색은 되더라도 날짜·프로그램·소개처럼 서로 다른 사실이 한 청크에 섞여 생성 단계에서 엉뚱한 결론으로 이어진다.
- 반대로 한 문장씩 잘라 버리면 문맥이 사라져 질문과의 관계를 판단하기 어렵다.
- 최소 120자 기준은 글자 수가 품질을 보장한다는 뜻이 아니다. 따로 읽어도 이해되는 사실 맥락은 확보하면서, 검색 단위가 지나치게 넓어지지 않게 잡은 **출발점**이다.

### 청크는 본문이 아니라 출처를 가진 레코드다

청크 JSON은 검색용 텍스트 배열이라기보다 작은 데이터베이스에 가깝다. 다섯 필드가 함께 있어야 검색 순위, 화면의 출처 칩, 생성 프롬프트, 오류 조사가 모두 같은 대상을 가리킬 수 있다.

| 필드 | 뜻 | 예 |
|---|---|---|
| `id` | 청크를 식별하는 고정 이름. 답변의 근거를 가리키는 안정적인 표시 | `MC-001` |
| `text` | 최소 120자의 사실 단위 본문. 검색과 프롬프트에 들어감 | 모두콘 소개와 행사 사실을 담은 문단 |
| `url` | 본문을 확인할 공개 원문 주소 | 모두콘 또는 모두의연구소 공개 페이지 URL |
| `section` | 원문 안의 맥락이나 주제 | 2025 본행사 |
| `vector` | 본문을 임베딩한 검색용 값. 같은 임베딩 공간에서 질의와 비교 | 768차원 임베딩 배열 |

- `vector`만 보고 자료를 고르면 안 된다. 숫자 배열은 빠른 비교를 돕지만, 사용자가 확인할 수 있는 것은 원문과 인용된 본문이다.
- 코퍼스 벡터와 질의 벡터는 **같은 모델, 같은 공간**이어야 한다. 384차원 경로와 768차원 경로를 섞으면 배열은 있어도 비교라는 약속이 성립하지 않는다.

### 37청크의 범위부터 밝힌다

37청크는 아무렇게나 모은 글 묶음이 아니다. 범위를 먼저 정하고, 그 안에서 사실 단위로 나눈 결과다.

- 2025년 본행사
- 2018~2024년 역대 행사
- 모두의연구소 소개

운영 규칙은 이렇다.

- ID는 MC-001부터 차례로 붙인다. 새 자료를 더할 때도 기존 ID가 가리키는 원문은 바꾸지 않아야 검색 결과와 인용 기록을 비교하기 쉽다.
- `section`에 어느 행사인지 적어 두면, "역대 모두콘"처럼 넓은 질문에는 여러 연도의 근거를 모으고, 특정 연도 질문에는 그 맥락부터 점검할 수 있다.
- 연도마다 청크 수를 억지로 맞출 필요는 없다. 원문의 사실 밀도와 문단 경계에 따라 수가 달라질 수 있고, 자료가 부족한 연도는 부족하다는 사실을 남겨야 한다.
- 37은 현재 모두콘 구현에서 나온 규모일 뿐, 모든 도메인의 목표 숫자가 아니다. 내 도메인에서는 문서 수보다 **각 청크의 URL, 본문, 경계를 그렇게 자른 이유를 검토할 수 있는지**를 먼저 기준으로 삼는다.

### 경계를 자를 때 확인할 세 가지

1. **한 청크에는 중심 사실 하나.** 특정 연도 소개와 모두의연구소 일반 소개가 같은 원문에 붙어 있어도, 질문자가 물을 사실과 인용할 URL·섹션이 다르면 별도 청크 후보로 본다.
2. **따로 읽어도 주어와 맥락이 충분한가.** "그 행사는"처럼 앞 문단을 알아야 이해되는 문장을 떼어 내면, 임베딩과 BM25는 일부 단어를 잡더라도 생성 모델은 대상을 추측하게 된다.
3. **요약하거나 정리했다면 URL과 섹션을 더 엄격하게 확인한다.** 청크는 답변 자체가 아니다. 원문이 말하지 않은 연결이나 평가를 덧붙이면, 출처가 붙어 있어도 환각을 숨기는 재료가 된다.

- 120자는 세 확인을 통과시키기 위한 하한이지, 120자를 채우려고 주변 사실을 덧붙이라는 뜻이 아니다. 필요한 맥락을 넣은 뒤에도 서로 다른 주제가 한 청크에 들어간다면 나누는 편이 낫다.
- URL이 빠진 청크는 검색 점수가 높아도 사용자가 검증할 수 없다. section이 빠진 청크는 나중에 원문이 바뀌었을 때 무엇을 다시 임베딩해야 하는지 알기 어렵다.

> 청크 설계는 생성 모델의 기억을 늘리는 일이 아니다. 근거를 다시 꺼내 볼 수 있는 단위로 보관하는 일이다.

### 실습 2: 내 도메인에서 8~15청크 모으기

1. 내 도메인에서 공개 원문 후보를 찾고, URL과 페이지 주제부터 기록한다. 로그인이나 권한이 필요한 자료는 브라우저 정적 앱에서 사용자가 다시 확인할 수 있는 근거가 되기 어려우므로 공개 자료 후보와 따로 분류한다.
2. 자료를 읽고 최소 120자 이상의 독립된 사실 단위로 나눈 뒤, MC-001 같은 일정한 규칙으로 임시 ID를 붙인다. MC는 모두콘 예시의 접두어이므로 다른 접두어를 써도 되지만, 한 코퍼스 안에서는 규칙을 바꾸지 않는다.
3. 8~15개가 모이면 각 행에 `id`, `text`, `url`, `section`을 채우고, `text`만 읽어도 질문과의 관계를 판단할 수 있는지 서로 교차 검토한다.

- 목표는 37개를 빨리 따라 만드는 것이 아니라, 작은 코퍼스에서도 검색 경계가 어떻게 생기는지 확인하는 것이다.
- 아직 `vector`가 없어도 URL이 없는 행, 두 주제가 섞인 행, 너무 짧아 맥락을 잃은 행은 먼저 찾아낼 수 있다.
- 수집 일부를 에이전트에게 맡길 때도, 에이전트가 **실제로 확인한 URL**과 **확인하지 못한 추정**을 나눠 달라고 요청한다. 자동 수집 결과가 표에 들어갔다고 원문 검증이 끝난 것은 아니다.

**에이전트에게 자료 수집을 질문으로 맡기기**

"웹에서 자료를 찾아 JSON을 만들어라"라고 한 번에 시키기보다, 수집 후보와 청크 경계를 먼저 제안하게 하고 사람이 URL을 확인한 뒤 확정한다. "실제로 열어 보지 못한 URL을 만들지 말라"는 지시는 그럴듯한 가짜 링크가 검색과 출처 표시를 한꺼번에 오염시키는 일을 막는다.

```
당신은 공개 자료 기반 RAG 코퍼스의 수집 보조자입니다.
도메인: 모두콘 안내 챗봇
자료 범위: 2025 본행사, 2018~2024 역대 행사, 모두의연구소 소개
공개 자료 후보: [확인할 URL 목록]

다음 원칙으로 8~15개 청크 초안을 제안합니다.
1. 각 청크는 최소 120자의 독립된 사실 단위로 제안합니다.
2. id, text, url, section 필드를 모두 제시합니다.
3. URL을 실제로 확인하지 못했으면 추정하지 말고 [검증 필요]로 표시합니다.
4. 한 청크에 서로 다른 행사 연도나 무관한 주제를 섞지 않습니다.
5. 원문에 없는 평가, 날짜, 수치, 관계를 보태지 않습니다.
6. 마지막에 중복 가능 청크와 사람이 원문으로 확인할 항목을 목록으로 정리합니다.
```

결과를 받으면 먼저 URL을 열어 `text`가 원문과 맞는지 확인하고, 그다음에야 임베딩 대상 목록으로 옮긴다.

### 내 도메인에 적용하기

- 모두콘이 37청크에 이른 과정처럼, 먼저 본행사 자료만 모은 뒤 역대 회차와 주최 측 소개를 덧붙이는 식으로 확장해 볼 수 있다.
- 청크가 늘 때 같은 질문의 상위 검색 결과가 어떻게 바뀌는지 기록해 두면, 코퍼스가 커지는 것이 검색 품질에 주는 영향을 관찰할 수 있다.
- 문서는 시간이 지나면 낡는다. 출처·청크·임베딩을 어느 주기로 다시 점검할지 정한 **재수집 주기**를 PRD 항목으로 남겨 두는 것도 설계에 들어간다.

> 청크의 경계가 곧 검색의 경계다.

## 4. 임베딩과 벡터스토어 구축

### 브라우저 안에서 문장을 좌표로 바꾸기

**상황**: 모두콘 문서를 검색 재료로 바꾸려고 예전 스크립트를 그대로 돌리면, 그 경로는 BGE 384차원 벡터를 만든다. 숫자 배열은 멀쩡해 보이지만, 질문이 다른 공간에서 만들어졌다면 "가깝다"는 판단 자체가 성립하지 않는다. 문서와 질문의 출발점부터 맞춰야 한다.

- 문장을 검색할 수 있게 하려면 숫자 목록인 벡터로 바꿔야 한다.
- 사용 모델은 `onnx-community/embeddinggemma-300m-ONNX`다. 문장과 질문 하나하나를 **768차원 벡터** 하나로 바꾼다.
- 첫 방문에는 모델 파일 약 200MB를 받아야 하고, 첫 로드는 실측 5~15초가 걸릴 수 있다. 그래서 화면이 멈춘 것처럼 보이지 않게 진행 상태와 캐시 여부를 보여 줘야 한다.
- 로드가 끝난 모델은 행사 소개, 참가 방법, 발표 신청처럼 표현이 다른 문장 사이의 의미 관계를 좌표 사이의 거리로 다룬다.

> **임베딩은 답을 만드는 과정이 아니다.** 답의 근거 후보를 찾기 위한 색인 과정이다.

### 캐시는 다시 방문했을 때의 경험을 위한 약속

질문할 때마다 모델 파일을 다시 받으면 검색을 시작하기도 전에 사용자를 기다리게 만든다.

- **HTTP 캐시만 믿기 어려운 이유**: Hugging Face의 resolve URL이 서명된 CDN URL로 리다이렉트되면서 캐시 적중이 불안정할 수 있다.
- **방법**
  - 원래 URL을 키로 써서 Cache Storage에 직접 보관한다.
  - 캐시가 적중하면 완료 상태와 캐시 사용 여부를 바로 알린다.
  - Cache Storage도 실패할 수 있으므로, 한 번 재시도한 뒤에도 실패하면 그냥 다운로드를 이어 가는 경로를 남긴다. 브라우저 환경에 따라 저장된다고 단정하지 않는다.
- **목적**: 다시 찾은 사용자가 모델 준비가 아니라 질문 자체에 집중하게 하는 것이다.

### 기본 파이프라인이 멈추는 지점 우회하기

- **문제**: 브라우저에서 `pipeline()`을 바로 부르면 기본 q4 또는 q8 경로가 선택되는데, 이때 WASM ONNX Runtime이 `GatherBlockQuantized` 연산을 지원하지 않아 실패할 수 있다.
- **해결**: 모델을 포기하지 않고 역할을 나눈다.
  - 토크나이저는 transformers.js의 `AutoTokenizer`를 쓴다.
  - 추론 세션은 `model_no_gather_q4.onnx`와 데이터 파일을 ONNX Runtime에 직접 넘기고, WASM 실행 공급자를 지정한다.
- 이 우회는 문서 임베딩과 브라우저 질문 임베딩이 같은 모델 계열의 계산을 거치게 해 주는 조건이기도 하다.
- 에이전트에게는 오류 문구만 던지지 말고, 토크나이저와 ORT 세션을 나눠야 하는 이유와 `no_gather_q4` 파일을 써야 하는 조건을 함께 알려 줘야 한다.

```ts
// rag.ts의 핵심 경로
const tokenizer = await AutoTokenizer.from_pretrained(modelId);
const session = await ort.InferenceSession.create(modelUrl, {
  executionProviders: ["wasm"],
});
```

### 평균을 내고 길이를 맞춰야 비교가 공정하다

모델 출력의 `last_hidden_state`는 토큰마다 하나씩 나오므로, 문장 하나를 대표하는 벡터로 줄이는 규칙이 필요하다.

**모두콘 챗봇의 처리 순서**

1. **mean pooling**: `attention_mask`가 가리키는 실제 토큰만 평균 낸다.
2. **L2 정규화**: 벡터 길이를 1로 맞춘다.

- 이 순서를 건너뛰면 패딩 토큰이 문장 표현에 섞이거나, 문장 길이 차이가 점수에 지나치게 영향을 준다.
- 정규화된 벡터끼리는 **내적이 곧 코사인 유사도**라서, 검색할 때 길이 보정을 다시 할 필요가 없다.

**에이전트에게 분명히 알려 줄 것**

- 출력 텐서의 첫 값만 쓰지 말 것
- 마스크를 분모와 분자 양쪽에 반영할 것
- 0으로 나누는 경우를 막을 것

숫자로 바꾸는 과정에서 생긴 작은 생략이 검색 결과 전체를 한쪽으로 치우치게 만들 수 있다.

### 차원과 공간을 섞지 않는다

차원 수가 같거나 배열 모양이 비슷하다고 비교가 가능해지는 것은 아니다.

- 예전 BGE 경로는 384차원, 지금 모두콘 코퍼스는 Gemma의 768차원이다. 둘을 섞으면 계산이 실패하거나 의미 없는 거리가 나온다.
- 더 위험한 경우는 **차원이 우연히 같은데 서로 다른 모델의 공간을 섞는 것**이다. 숫자는 나오지만 그 가까움이 무슨 뜻인지 보장되지 않는다.
- 문서 벡터를 만들 때 쓴 모델, pooling 방식, 정규화 규칙을 질문 임베딩에도 똑같이 적용하고, 벡터스토어에는 이를 확인할 수 있는 생성 경로를 남긴다.
- 기존 스크립트가 있다는 이유만으로 다시 돌리지 말고, 현재 코퍼스의 차원과 생성 모델부터 확인한다.

### 실습 3: 문서 벡터스토어를 에이전트와 함께 만들기

현재 경로는 `embed-docs-browser-path.mjs`다.

- Node 환경에서 같은 모델의 feature-extraction pipeline을 쓴다.
- `dtype: "q4"`, `pooling: "mean"`, `normalize: true` 조건으로 문서 벡터를 만든다.
- 결과는 `app/public/moducon-docs.json`에 저장한다.
- 벡터스토어는 최상위 배열 안에 `id`, `text`, `url`, `section`, `vector`를 가진 청크를 담아야 하고, 만든 뒤에는 질문과 문서가 같은 공간에 있는지 검색으로 확인한다.

**에이전트에게 그대로 보낼 요청**

```
모두콘 공개 문서 청크 배열을 읽어 브라우저 RAG용 벡터스토어를 만드는
embed-docs-browser-path.mjs를 작성합니다.
onnx-community/embeddinggemma-300m-ONNX를 사용하고 dtype은 q4,
pooling은 mean, normalize는 true로 고정합니다.
각 청크의 id, text, url, section을 보존하고 vector를 추가하여
app/public/moducon-docs.json에 저장합니다.
기존 BGE 384차원 경로는 사용하지 말고,
생성 후 모든 vector가 768차원인지 검사하는 검증도 포함합니다.
```

- 요청을 보낸 뒤, 생성된 스크립트의 모델 ID, q4 설정, mean pooling, 정규화, 출력 필드를 한 줄씩 대조한다.
- 벡터 길이를 확인했다면 예전 스크립트의 결과물을 새 파일에 섞지 않는다. 문서와 질문이 모두 같은 Gemma 경로를 지난 다음에야 검색 점수를 읽는다.
- 이건 숫자를 좋아 보이게 하려는 조정이 아니라, 두 좌표 사이의 거리를 비교할 수 있는 조건을 되살리는 일이다.
- 확인은 차원 수 대조에서 끝내지 말고, 모델 ID, pooling, 정규화 규칙까지 문서 생성 쪽과 질문 처리 쪽이 같은지 본다. 그래야 상위 결과가 우연히 익숙한 표현을 고른 것인지, 실제로 비교 가능한 좌표에서 가까운 청크를 고른 것인지 구분할 수 있다.

남는 질문은 벡터 파일이 만들어졌느냐가 아니라, **실제 질문에서 관련 청크가 위로 올라오느냐**다.

### 실습 3: 검색 결과를 스팟체크로 읽기

> 💡 **스팟체크**: 표본 몇 개를 직접 골라 확인하는 방법이다.

생성 명령이 성공했다는 메시지만으로 벡터스토어가 맞다고 판단할 수 없다. `check_retrieval.py` 같은 점검 도구에 예상 질문을 넣고 top-1과 top-3에 어떤 청크가 오는지 읽는다.

```bash
python3 check_retrieval.py
```

- **문서에 근거가 있는 질문**(모두콘이 무엇인지, 참가 방법, 발표 신청): 관련 청크가 상위에 나오는지 확인한다.
- **문서 범위 밖 질문**: 관련 없는 청크가 억지로 정답처럼 올라오지 않는지 본다.
- 확인하려는 것은 모델의 지능이 아니라 문서 청크, 생성 모델, 정규화, 검색 점수가 제대로 이어져 있는지다.
- top-1이 기대와 다르면 바로 임계값을 바꾸지 말고, 질문과 문서가 같은 임베딩 경로를 지났는지, 청크의 사실 경계가 적절한지부터 거꾸로 점검한다.

**더 깊이 가 보기**

- `executionProviders`에 WASM 대신 WebGPU 백엔드를 지정해, 지원하는 브라우저에서 임베딩 준비와 계산이 어떻게 달라지는지 관찰할 수 있다.
- 모델 파일의 양자화 종류를 q4와 q8로 바꿔 가며 상위 검색 결과의 순서 변화를 기록하는 것도 같은 코퍼스로 해 볼 수 있는 실험이다.

> 질문과 문서가 같은 공간에 있어야 거리가 의미를 갖는다.

## 5. 가까운 청크 고르기: 하이브리드 검색

### 코사인 유사도는 방향이 얼마나 비슷한지를 본다

**상황**: "모두콘 발표 신청 방법"처럼 고유명사와 절차가 섞인 질문이다. 상위 청크가 질문의 의미와 어느 정도 닿더라도 "발표 신청"이라는 정확한 표기가 없다면, 답을 생성하기 전에 멈춰서 검색 결과를 검토해야 한다. 그럴듯한 첫 결과를 그대로 믿지 말고, 검색 기록에서 고유명사를 왜 놓쳤는지, 그걸 메울 검색 경로가 무엇인지 설명할 수 있어야 한다. 이 검토가 **검색 점수의 순위**와 **답변 근거의 충분성**을 구분하는 출발점이다.

- L2 정규화된 질문 벡터와 문서 벡터의 내적은 코사인 유사도로 읽을 수 있다.
- 두 벡터가 얼마나 같은 방향을 향하는지를 나타내므로, 문장 길이보다 의미 표현의 관계를 기준으로 후보를 정렬한다.
- 예: 사용자가 참가 절차를 자기 말로 묻고 문서는 다른 단어로 설명했더라도, 벡터 검색은 두 문장이 의미상 가깝다는 것을 잡아낼 수 있다.
- 하지만 점수 하나를 참일 확률처럼 읽으면 안 된다. 점수는 **현재 모델, 현재 청크, 현재 질문 사이의 상대적인 가까움**일 뿐이다.
- 어떤 문서가 답을 실제로 뒷받침하는지는 프롬프트의 근거 원칙과 출처 표시로 다시 제한해야 한다.

> 검색은 답변을 대신하는 판단이 아니다. 답변이 읽을 자료의 순서를 정하는 판단이다.

### 벡터 검색이 놓치는 정확한 표기를 BM25가 메운다

의미 검색은 표현이 달라도 가까운 문장을 찾는 데 쓸모 있지만, 특정 행사명, 고유명사, 정확한 ID, 코드처럼 **글자 자체가 중요한 질문**에서는 필요한 청크를 충분히 위로 올리지 못할 수 있다.

**모두콘 챗봇의 결합 방식**

1. 코사인 유사도 상위 10개를 먼저 고른다.
2. 아직 안 들어온 청크 중에서 BM25 상위 5개를 더한다.

| 검색 방식 | 무엇을 잡는가 | 무엇을 놓치는가 | 사용 범위 |
|---|---|---|---|
| vector | 표현이 달라도 가까운 의미 | 고유명사와 정확한 표기 | 코사인 상위 10개 |
| BM25 | 질문과 문서의 낱말 일치 | 다른 표현으로 쓴 같은 뜻 | 중복 아닌 상위 5개 |

BM25는 질문의 낱말이 문서에 어떻게 나타나는지를 반영하므로, 의미는 비슷하지만 표기가 다른 청크와 정확한 표기가 들어 있는 청크를 함께 검토하게 해 준다.

> **하이브리드 검색의 핵심**: 두 검색기를 경쟁시키는 것이 아니라, 실패하는 방식이 서로 다른 두 관찰 장치로 함께 배치하는 것이다.

### 점수의 단위는 맞추되, 근거의 강도와 헷갈리지 않는다

- BM25 원점수는 문서 집합과 질문에 따라 크기가 달라진다. 그래서 그 검색에서 나온 **최고 BM25 점수로 나눠 0~1 범위로 정규화**한다.
- 이 값은 벡터 점수와 같은 뜻이 아니다. UI에서 서로 다른 검색 방법의 상대적인 강도를 읽기 쉽게 만든 표기일 뿐이다.
- 결과 객체에는 `vector` 또는 `bm25` 방법과 점수를 함께 남겨, 어떤 청크가 어떤 경로로 들어왔는지 사용자가 확인할 수 있어야 한다.
- 프롬프트에 넣기 전에 중복을 없애지 않으면 같은 사실이 여러 번 반복되어 모델이 특정 청크를 과대평가할 수 있다.
- 반대로 BM25 후보를 전부 버리면 고유명사와 코드성 표기에 약한 검색기로 돌아가 버린다.

정규화와 방법 표시는 정답을 보장하지 않는다. 검색 판단을 검토할 수 있는 기록으로 바꿔 줄 뿐이다.

### 0.55는 문을 닫는 숫자가 아니라 말투를 바꾸는 신호다

최고 유사도가 0.55보다 낮다는 것은, 검색된 청크가 질문에 딱 맞는 근거가 아닐 수 있다는 신호다.

- 결과를 **막아 버리면** 사용자는 검색이 어떻게 실패했는지 알 수 없다.
- 평소처럼 **자신 있게 생성하면** 약한 연관을 사실처럼 말할 위험이 커진다.

**모두콘 챗봇의 처리**

- 근거 청크는 버리지 않고, 프롬프트를 보수적으로 바꾼다.
- UI에는 약한 근거 경고를 띄운다.
- 모델은 근거에 있는 내용만 짧게 답하고, 자료에 없는 부분은 없다고 말해야 한다.
- 사용자는 검색된 청크의 수, 방식, 점수를 열어 보고 스스로 판단할 수 있어야 한다.

0.55가 보편적인 정답이라는 뜻은 아니다. 지금의 코퍼스와 모델 조합에서 불확실성을 드러내기 위한 운영 규칙이다. 임계값은 숨은 자동 판정기가 아니라, **답변의 태도를 조절하는 공개된 경계**여야 한다.

### top-1이 기대와 다를 때 점검 순서

임계값을 조정해서 덮어 버리지 않는다.

1. 질문과 문서가 같은 임베딩 경로를 지났는가
2. 청크가 "발표 신청"이라는 사실 경계를 온전히 담고 있는가
3. 정확한 낱말을 BM25 후보가 메워 주었는가

- 벡터 후보만으로 놓친 표기를 BM25 청크가 끌어올리는 것이 보이면, 두 방법의 칩과 점수를 함께 남겨 판단 경로를 화면에 드러낸다.
- BM25는 벡터 점수를 더 높은 점수로 바꿔 주는 마법이 아니다. 질문에 있던 정확한 낱말을 다른 기준으로 찾은 결과일 뿐이다.
- "발표 신청"이 들어 있는 청크가 들어왔더라도, 그 청크의 URL과 section을 열어 질문에 답할 사실이 실제로 있는지 확인한 뒤에만 답변 근거로 넘긴다.

### 실습 4: 검색 결합을 에이전트에게 요구하기

- "관련 문서를 찾아 달라"보다 결과 순서, 중복 처리, 점수 표기, 약한 근거 처리까지 **계약으로 적는 편이 안전하다.**
- 에이전트가 코사인 결과만 돌려주거나 BM25 결과로 덮어써도 화면은 그럴듯해 보일 수 있다. 그래서 반환 타입에 `chunk`, `score`, `method`를 넣으라고 요구한다.
- 구현 뒤에는 이렇게 확인한다.
  - 행사 소개와 참가 방법 질문에서 vector 칩과 BM25 칩이 어떻게 섞이는가
  - 문서 밖 질문에서 약한 근거 경고와 보수적인 프롬프트가 함께 작동하는가

검색 결과는 모델에게만 넘기는 비공개 배열이 아니다. 사용자가 답의 출발점을 검토할 수 있게 해 주는 관찰 기록이어야 한다.

```
모두콘 벡터스토어 검색 함수를 구현합니다.
질문 임베딩과 문서 벡터의 코사인 유사도로 상위 10개를 고른 뒤,
중복되지 않은 BM25 상위 5개를 추가합니다.
BM25 점수는 해당 검색의 최고 점수로 나누어 0~1로 정규화합니다.
반환값마다 chunk, score, method("vector" 또는 "bm25")를 보존하고,
최고 유사도가 0.55보다 낮으면 결과를 버리지 말고 약한 근거 상태를 반환합니다.
```

**더 깊이 가 보기**

- top-k를 5, 10, 20으로 바꿔 같은 질문의 상위 근거와 답변 길이가 어떻게 달라지는지 기록해 볼 수 있다.
- 약한 근거 임계값 0.55를 낮추거나 높여서 답변의 보수성이 함께 움직이는지 관찰할 수 있다.
- 두 검색의 순위를 하나로 합치는 **Reciprocal Rank Fusion(RRF)** 같은 융합 방법을 찾아보고 지금의 정규화 방식과 비교해 볼 수도 있다.

> 검색 품질이 답변 품질의 상한선이다.

## 6. 프롬프트 조립과 로컬 LLM 스트리밍

### 프롬프트는 검색 결과를 답변의 근거로 바꾸는 경계

**상황**: 정적 Pages에 배포한 챗봇 주소에서 질문을 보내면, 화면은 공개되어 있어도 Ollama 호출이 막힐 수 있다. "정적 파일을 배포하면 서버가 로컬 모델 호출을 대신해 준다"는 생각은 틀렸다. 배포된 앱은 사용자 컴퓨터의 브라우저에서 돌아가고, 브라우저는 여전히 그 컴퓨터의 로컬 엔진을 직접 부른다.

이 실행 경계를 확인했다면, 연결 문제와는 별개로 모델이 어떤 근거로 답해야 하는지도 프롬프트에 분명히 적어야 한다. **배포 환경의 연결 조건과 답변 근거의 조건은 서로 다른 층에서 검증한다.**

검색된 청크를 그냥 이어 붙이는 것만으로는 모델이 자료 밖 내용을 덧붙이는 것을 막을 수 없다.

**`buildPrompt()`의 조립 순서**

1. 자료가 모두의연구소 컨퍼런스 모두콘의 공개 문서 청크라는 소개
2. 근거 원칙
3. 답 안에 근거 청크의 `[ID]`를 표시하라는 요구
4. 상대 시각 질문을 해석할 KST 현재 시각
5. 그 다음에야 `[자료]`와 `[질문]`

- 이 순서는 모델의 능력을 끌어올리는 주문이 아니다. 모델이 어느 범위에서 답하고 무엇을 인용해야 하는지를 문장으로 고정한 **계약**이다.
- 청크마다 `MC-xxx` 형식의 ID와 section을 남기면, 사용자는 답변 문장을 원문 청크까지 따라갈 수 있고, 모델도 막연한 "자료에 따르면" 대신 검토할 수 있는 근거를 남긴다.

### 약한 근거일 때의 문장은 그대로 지킨다

- 최고 검색 점수가 0.55보다 낮을 때는 일반 근거 원칙보다 더 엄격한 분기 문구가 필요하다. 검색 결과가 **있다는 사실**과 질문에 **맞는 근거라는 사실**을 구분하고, 모델이 빈틈을 상식으로 메우지 못하게 한다.
- "짧게 답하고 자료에 없는 부분은 없다고 말한다"는 조건은 답을 거부하려는 것이 아니다. 불확실한 검색에서 사실성을 지키기 위한 장치다.
- **KST 시간 컨텍스트**도 장식이 아니다. 지금, 올해, 다음 주 같은 상대 표현을 질문을 입력한 순간의 서울 시간 기준으로 해석하게 해 준다.

아래 구조는 그대로 조립하되, `[KST 시각]`, 청크 목록, 사용자 질문만 실행할 때의 값으로 바꾼다.

```
다음 자료는 모두의연구소의 컨퍼런스 '모두콘'에 대한 공개 문서에서 뽑은 조각입니다.
주의: 검색된 조각의 유사도가 낮습니다. 질문과 완전히 맞는 근거가 아닐 수 있으니,
근거에 있는 내용만 짧게 답하고 자료에 없는 부분은 없다고 말합니다.
근거가 된 조각의 [ID]를 답 안에서 표시합니다.
현재 시각은 [KST 시각]입니다. '지금', '올해', '다음 주' 같은 상대 표현은
이 시각을 기준으로 해석합니다.

[자료]
[MC-... | 섹션] 청크 텍스트

[질문]
사용자 질문
```

### Ollama 응답은 한 번에 받지 않고 조각으로 읽는다

- 로컬 엔진에는 `POST http://localhost:11434/api/chat`으로 `qwen3.5:2b`에 요청하고, 본문에 `stream: true`와 `think: false`를 넣는다.
- 스트리밍 응답은 완성된 JSON 하나가 아니라 **줄바꿈으로 구분된 JSON 조각**들이다.
- `ReadableStream`을 읽으면서 남은 문자열을 버퍼에 보관하고, 줄 단위로 파싱한 뒤, 조각마다 텍스트를 화면 답변에 이어 붙인다.
- 토큰당 약 50ms(실측)로 오는 응답을, 사용자는 빈 화면이 아니라 자라나는 문장으로 경험한다.
- 네트워크 오류와 JSON 파싱 실패는 답변 상태와 따로 표시한다.
- 요청을 취소할 때는 `AbortSignal`을 넘겨 이미 시작된 스트림을 멈춘다.

```ts
await fetch("http://localhost:11434/api/chat", {
  method: "POST",
  signal: controller.signal,
  body: JSON.stringify({
    model: "qwen3.5:2b",
    stream: true,
    think: false,
    messages,
  }),
});
```

> 스트리밍은 속도 자랑이 아니다. 지금 생성 중이라는 상태와, 그걸 멈출 수 있는 권리를 사용자에게 보여 주는 인터페이스다.

### 연결 상태와 CORS를 배포 환경까지 확인하기

- 채팅을 시작하기 전에 `GET /api/tags`로 Ollama 상태를 확인하면, 모델이 꺼진 상황을 생성 실패처럼 보이게 두지 않고 안내 배너와 재시도로 따로 처리할 수 있다.
- 로컬 개발 서버에서 되던 요청이 GitHub Pages 배포 뒤에도 저절로 되지는 않는다. 정적 페이지가 서버처럼 대신 호출하는 게 아니라 사용자 브라우저가 계속 자기 `localhost:11434`로 요청하기 때문에, Ollama 쪽에 `OLLAMA_ORIGINS` 설정이 필요하다.

```bash
# macOS
launchctl setenv OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# Windows
setx OLLAMA_ORIGINS "https://YOUR_ID.github.io"

# systemd 환경
systemctl set-environment OLLAMA_ORIGINS="https://YOUR_ID.github.io"
```

- 운영체제별로 설정한 뒤에는 앱을 재시작하고, 실제 Pages 주소에서 상태 확인과 스트리밍을 함께 점검한다.
- **브라우저**: Chrome과 Edge를 권장한다. Safari에서는 Ollama 연결과 임베딩 WASM이 불안정할 수 있다는 점을 시작 화면에 알려 두는 편이 좋다.
- 정적 파일을 올렸다고 Ollama가 인터넷 서버로 옮겨 간 것이 아니다. 배포된 앱을 연 사용자마다 브라우저가 자기 `localhost:11434`를 향하므로, 요청을 받는 로컬 Ollama가 Pages 출처를 허용해야 연결이 열린다.
- 이건 배포 오류 하나를 고치는 방법이 아니라, 프런트엔드가 어디서 돌고 모델이 어느 컴퓨터에서 응답하는지를 구분하는 **실행 구조**다.
- 연결 상태 배너와 재시도를 남겨 두면, 로컬 엔진이 꺼졌거나 출처 허용이 빠졌을 때 이를 검색이나 프롬프트 실패로 착각하지 않는다. 배포 주소와 로컬 엔진 사이의 경계를 화면에 보여 줘서, 사용자가 자기 환경에서 무엇을 점검해야 하는지 알게 하는 것이 제품의 책임이다.

### 실습 5: 챗봇 UI의 상태를 에이전트에게 명세하기

챗봇 UI는 입력창과 말풍선만으로 끝나지 않는다. 사용자는 아래 요소들을 보고 지금 답이 어느 단계에 있는지 읽을 수 있어야 한다.

- 로컬 엔진 선택 상태, Ollama 연결 여부, 임베딩 준비 상태, 검색 진행 상태, 생성 중지 동작, 출처 칩, 약한 근거 경고

에이전트에게는 예쁜 대화창이 아니라 **상태 전이와 실패했을 때 남겨 둘 내용**을 구체적으로 적어 준다.

- 스트리밍이 중간에 끊겨도 이미 받은 답변은 지우지 않는다.
- 출처 칩은 ID, section, 검색 방법, 점수를 보여 주고 원문으로 연결된다.

답변의 신뢰를 배지 하나에 맡기지 않고, 사용자가 근거와 과정을 직접 확인할 수 있게 하는 구조다.

```
Vite, React, TypeScript로 모두콘 RAG 챗봇 UI 골격을 만듭니다.
로컬 qwen3.5:2b 엔진 선택, GET /api/tags 연결 상태 배너와 재시도,
임베딩·하이브리드 검색·생성 단계 표시, 스트리밍 답변과 AbortSignal 중지 버튼을 구현합니다.
각 답변에는 출처 칩을 표시하고 칩에는 MC ID, section, vector 또는 bm25 방법, 점수를 보입니다.
최고 유사도가 0.55보다 낮으면 약한 근거 경고를 보이며,
스트리밍 오류가 나도 이미 받은 답변과 출처는 유지합니다.
Chrome과 Edge 권장, Safari 불안정 안내도 포함합니다.
```

**더 깊이 가 보기**

- 답변 모델을 더 큰 로컬 모델로 바꿔 볼 수 있다. ollama로 다른 모델을 받아 모델명만 바꾸면 같은 파이프라인에서 답변 리듬이 어떻게 달라지는지 볼 수 있고, 컴퓨터 사양에 따른 응답 속도의 한계도 함께 기록된다.
- 시스템 프롬프트 문구를 하나씩 바꿔 같은 질문 세트로 비교하는 A/B 실험, temperature를 바꿔 답변 일관성의 변화를 보는 실험도 자연스럽게 이어 갈 수 있다.

> 프롬프트의 문장 하나가 모델 행동의 경계다.

## 7. 답을 판정하기: LLM-as-a-Judge

### 답변 뒤에 평가자를 한 번 더 둔다

리허설에는 모두콘 자료와 관계없는 "내일 날씨 알려줘" 같은 **근거 없는 질문**을 넣는다. 챗봇이 확인할 근거가 없다고 말하는지, 날씨를 지어내지 않는지, 빈 출처를 꾸며 내지 않는지를 본다.

- 대화가 멈춘 것처럼 보이는 결과와 자료 경계가 제대로 작동한 결과를 구분하려면, 답변 본문과 출처 칩을 같이 읽어야 한다.
- 근거 없는 질문은 판정 배지보다 먼저, 검색·생성 단계의 경계가 실제로 지켜지는지를 드러내는 검증 입력이다.

리허설 기록에는 질문만 적지 말고 아래 내용을 나란히 적는다.

- 검색 결과가 비었는가
- 답변이 자료 밖 사실을 덧붙이지 않았는가
- 판정이 어느 필드로 그 판단을 드러냈는가

이 순서가 있어야 생성 단계의 조심스러운 문장과 판정 단계의 해석을 섞지 않고 볼 수 있다.

- 거부 문장이 있어도 엉뚱한 청크를 인용했다면 근거성과 인용은 다시 확인해야 한다.
- 답이 짧다는 이유만으로 실패라고 보지 말고, 그 질문에 답할 공개 자료가 있는지부터 묻는다.
- 판정 배지만으로 결론 내지 말고 답변 본문, 검색 근거, 평가 코멘트를 같은 기록 칸에서 비교한다.
- 이렇게 남긴 리허설은 예상 밖 질문이 들어왔을 때 무엇부터 읽을지 정해 주는 관찰 순서가 된다.

출처 칩이 보인다고 답변 전체가 근거에 충실하다고 판정할 수는 없다. 그래서 질문, 검색 근거, 생성된 답변을 함께 읽는 **별도의 평가자**를 답변 뒤에 둔다.

- 이 평가는 모델이 자기 문장을 완전히 객관적으로 증명하는 장치가 아니다. 근거성, 환각, 인용, 정당한 거부를 한 화면에서 관찰하게 해 주는 **교육용 계측 장치**다.
- 평가자는 답변을 다시 쓰거나 숨기지 않는다. 어떤 기준에서 통과했는지, 어디가 불확실했는지를 판정 배지와 짧은 코멘트로 남긴다.
- 판정 프롬프트는 평가 기준을 모호한 칭찬이나 인상으로 두지 않고, JSON 필드와 판단 대상을 분명히 적는다.
- 근거가 없는 질문에 답을 꾸미지 않고 없다고 말한 경우를 실패가 아니라 `refusal: true`로 따로 분리해야, 챗봇이 아무거나 답하는 도구가 아니라 확인 가능한 자료 안에서만 답하는 안내 도구가 된다.

### 판정 기준을 데이터 구조로 읽기

아래 프롬프트는 입력을 질문·근거자료·답변 세 가지로 고정하고, 여섯 필드만 JSON으로 돌려주게 한다. 그래서 화면 쪽은 설명 문장을 추측해서 해석할 필요 없이, 정해진 필드를 배지와 기록에 연결하면 된다.

```
당신은 RAG 챗봇 답변의 평가자입니다.
아래 [질문], [근거자료], [답변]을 읽고 다음 기준으로 JSON만 출력합니다.

grounded: 답변 내용이 근거자료에서 나왔는가 (true/false)
noHalluc: 근거에 없는 사실을 지어내지 않았는가 (true/false)
cited: 답변 안에 근거 조각의 [ID] 표시가 있는가 (true/false)
refusal: 근거에 답이 없어서 '없다'고 답한 경우 true, 그 외 false
score: 0-100 정수 (grounded·noHalluc·cited 반영)
comment: 한두 문장 평어 (한국어)

출력 형식: {"grounded":bool, "noHalluc":bool, "cited":bool, "refusal":bool, "score":int, "comment":"..."}
— JSON 외 텍스트 금지.

[질문] … [근거자료] … [답변] …
```

| 필드 | 뜻 | true / false의 의미 |
|---|---|---|
| `grounded` | 답변 내용이 검색 근거에서 나왔는지 | true면 근거에 닿음, false면 근거 밖 진술이 있음 |
| `noHalluc` | 근거에 없는 사실을 만들지 않았는지 | true면 지어낸 사실이 없음, false면 환각 가능성 |
| `cited` | 답변 안에 `[ID]` 인용이 있는지 | true면 추적 가능한 근거 표기가 있음, false면 출처 연결이 빠짐 |
| `refusal` | 근거가 없을 때 정직하게 거부했는지 | true면 정당한 거부, false면 답변했거나 다른 이유로 거부 |
| `score` | 세 핵심 기준을 반영한 정수 점수 | 높으면 충족한 기준이 많음, 낮으면 다시 읽어 볼 대상 |
| `comment` | 한국어 한두 문장 코멘트 | 긍정이면 통과 근거, 부정이면 확인할 결함을 설명 |

### 로컬 자기평가의 한계까지 함께 기록하기

로컬 엔진에서는 답변 생성에 쓴 `qwen3.5:2b`에게 같은 질문·근거·답변을 다시 보낸다. 이때 스트리밍과 사고 출력을 끄고, JSON 형식과 온도 0을 지정한다.

```
stream:false, think:false, format:"json", options:{temperature:0}
```

외부 API 키 없이 브라우저의 로컬 Ollama 호출만으로 평가하므로, 학생은 키 발급이나 서버 구성 대신 판정 결과가 생성 결과에 어떻게 붙는지에 집중할 수 있다.

- **한계**: 답변 모델과 평가 모델이 같은 2B 모델이라 독립 심사가 아니다. 미세한 사실 차이나 문맥 누락을 거칠게 판정할 수 있다는 한계를 화면과 기록에서 숨기지 않는다.
- **방어 처리**
  - 모델이 가끔 5점 만점처럼 점수를 내면, `score ≤ 5`일 때 `(score / 5) × 100`으로 환산해 점수 체계의 혼동을 막는다.
  - JSON 파싱이나 호출이 실패하면 `judgeError` 배지만 남기고, 이미 생성된 답변과 UI는 그대로 둔다.

### 사람 피드백과 함께 읽기

- 좋아요·싫어요가 판정 배지와 같은 방향이면, 자동 기준과 사용 경험이 일단 맞물린 사례로 본다.
- 서로 어긋나면, 판정 기준이 놓친 유용성이 있는지, 혹은 사용자가 놓친 근거가 있는지를 답변·출처·코멘트와 함께 다시 읽는다.

### 실습 6: 근거 없는 질문에서 정당한 거부 확인하기

1. 모두콘 공개 자료로는 답할 수 없는 날씨 질문을 넣고, 생성된 문장이 모르는 정보를 채워 넣지 않았는지 먼저 읽는다.
2. 판정 배지에서 `refusal: true`와 `grounded`, `noHalluc`, `cited`, `score`, `comment`가 어떤 조합으로 나오는지 본다. 정당한 거부가 품질 낮은 침묵이 아니라 근거 경계를 지킨 답변이라는 것을 확인한다.
3. 질문 원문, 답변의 핵심 문장, 판정 배지와 코멘트를 실습 기록에 함께 적는다. 점수 하나만 남기지 않고 판정이 나온 맥락을 보존한다.

```
내일 날씨 어때?
```

- 확인하려는 것은 날씨를 알아내는 능력이 아니라, 벡터스토어에 없는 정보를 만났을 때 검색·생성·판정이 각각 어느 경계에서 멈추는가다.
- `refusal: true` 배지는 질문을 피한 결함이 아니라, 근거 없는 날씨 정보를 만들지 않은 **정당한 거부**다. 이 배지가 실제 거부 문장, 그리고 비어 있는 근거 상황과 함께 나오는지 답변과 검색 근거를 다시 열어 확인한다.
- `refusal: true`가 안 보이거나 근거 없는 날씨 정보가 생성됐다면, 답변 문장만 손보기보다 검색 근거와 프롬프트의 근거 부재 분기부터 열어 원인을 기록한다.

**더 깊이 가 보기**

- 같은 답변을 로컬 judge와 Gemini judge 양쪽에 보내 판정하면, 점수와 코멘트가 어디서 갈리는지 볼 수 있다. 예시 구현은 처음부터 두 엔진을 판정자로 쓸 수 있게 설계되어 있다.
- judge 프롬프트의 기준 문구를 바꿔 판정 민감도가 달라지는지 보거나, judge의 판정을 사람이 다시 채점하는 **메타 평가** 실험도 같은 자료로 이어 갈 수 있다.
- 판정 배지는 답변마다 자동으로 쌓이므로, 답변 길이처럼 관찰 가능한 품질 신호와 함께 기록한다. 예를 들어 "답이 가끔 길다"는 인상은 질문 유형, 답변 길이, 판정 결과를 같은 표본에서 비교해야 개선 실험의 가설이 된다.

> 평가자를 만드는 일이 곧 답변을 만드는 일이다.

## 8. 스스로 세운 목표를 실험으로: 프롬프트 엔지니어링

### 스스로 세운 루브릭이 기준이 된다

답변 길이는 프롬프트·검색 설정을 검토할 때 볼 수 있는 관찰 항목이다. 하지만 답을 짧게 만들었더니 근거 청크 내용과 `[ID]` 표시가 빠졌다면 자료 경계가 흐려질 수 있으므로, **길이만으로 개선을 판단하면 안 된다.**

개선을 실험으로 검증하려면, 무엇이 좋아진 것인지를 도메인에 맞는 루브릭으로 먼저 정의해야 한다. 그래야 각 실행 행의 결과를 같은 기준으로 비교할 수 있다.

| 구분 | 역할 | 예 |
|---|---|---|
| PRD의 수용 기준 | 제품이 밖으로 나가기 전에 통과해야 하는 문 | 근거 없는 질문에서 정당한 거부와 판정 배지가 보이는가 |
| 루브릭 | 그 문을 통과한 뒤 프롬프트와 검색 설정을 비교할 때 쓰는 자 | 출처 인용, 도메인 밖 거부, grounded 비율 등 |

학생은 자기 자료와 사용자를 떠올리며 출처를 인용한 답, 도메인 밖 질문의 거부, grounded 비율, 짧은 답에서도 근거가 유지되는지를 지표로 삼을 수 있다.

| 지표 | 측정 방법 | 목표값 | 지금 값 |
|---|---|---|---|
| 출처를 인용한 답변 | 고정 질문의 `cited: true` 답 수 기록 | [목표값] | [실험 전 측정값] |
| 도메인 밖 질문의 거부 | 근거 없는 질문의 `refusal: true` 답 수 기록 | [목표값] | [실험 전 측정값] |
| 근거성 | 판정 배지의 `grounded: true` 비율 기록 | [목표값] | [실험 전 측정값] |
| 짧은 답변의 근거 유지 | 답변 길이와 `[ID]` 표시를 함께 검토 | [목표값] | [실험 전 측정값] |

- 목표값과 현재 값을 비워 두면, 남의 성공 수치를 베끼지 않고 실제 실행 결과로 칸을 채우게 된다.
- 이 표는 모델을 좋은 학생과 나쁜 학생으로 가르는 성적표가 아니다. 고정 질문 세트를 각 실행 행에서 같은 기준으로 보게 해 주는 관찰 기준이다.

### 한 번에 하나만 바꾼다

"답이 길다"는 반응을 들었다고 검색 결과 수와 프롬프트의 길이 지시를 동시에 고치지 않는다. 결과가 달라졌을 때 어떤 변경이 grounded, cited, 답변 길이에 영향을 줬는지 분리할 수 없기 때문이다.

**실험 한 바퀴**

```
1. 현재 설정을 기준 행으로 기록
2. 변수 하나만 바꾼 새 설정을 다음 행에 기록
3. 같은 질문 세트의 판정 배지와 답변 본문을 행끼리 비교
```

결과가 기대와 달라도 실패를 숨기지 않으면, 다음에 무엇을 바꿀지 고를 근거가 남는다.

**바꿀 수 있는 축** (한 번의 실험에서는 하나만 고른다)

| 축 | 변수 |
|---|---|
| 검색 | top-k, 최고 점수가 0.55보다 낮을 때 쓰는 약한 근거 문구, 벡터 검색과 BM25의 구성 |
| 프롬프트 | 근거 원칙 문구, 답변 길이 지시, `[ID]` 표시 규칙, 질문 시점에 맞춘 시간 컨텍스트 문구 |

0.55는 검색 결과를 버리는 차단선이 아니라, 근거에 있는 내용만 짧게 답하도록 프롬프트를 보수적으로 바꾸고 UI 경고를 띄우는 기준이라는 점도 기록해 둔다.

- 질문 세트도 실험 중간에 바꾸지 않는다. **정상 질문, 경계 질문, 근거 없는 질문을 각각 최소 세 개씩 Q1~Q9로 고정**하고 모든 실행 행에서 똑같이 돌린다.
- 답변마다 `grounded`, `noHalluc`, `cited`, `refusal`, `score`, `comment`를 모으되, 점수 하나로 결론 내지 않고 근거 청크와 실제 문장을 함께 읽는다.

> 두 축을 한꺼번에 바꾸면 좋아진 결과든 나빠진 결과든 원인을 찾을 수 없다. "한 번에 하나"라는 제약 자체가 실험의 신뢰를 지켜 준다.

### 실습 7: 내 루브릭으로 실험 한 바퀴 돌리기

1. 앞 표에서 내 서비스에 중요한 지표를 3~5개 고르고, 각 지표가 어떤 판정 필드나 사람의 검토와 연결되는지 적는다.
2. 정상·경계·근거 없는 질문을 각각 최소 세 개씩 골라 기준 질문 세트를 고정한다. 질문을 더 그럴듯하게 다듬거나 새 질문을 더하면 행끼리 비교하는 기준이 바뀌므로, 질문 원문과 실행 순서를 기록 파일에 그대로 남긴다.
3. 현재 설정으로 모든 질문을 돌려 답변, 근거 청크, 판정 배지, 루브릭 점수를 `README.md`에 기록한다.
4. 루브릭의 한 지표와 관련된 변수 하나를 고른다. 예: 답변 길이를 보려면 길이 지시만, 약한 근거에서의 보수성을 보려면 0.55 조건 문구만 바꾼다.
5. 그 변수만 바꾼 뒤 같은 질문 세트를 같은 순서로 다시 돌리고 judge 판정 필드를 모은다.
6. 새 설정과 루브릭 점수를 `README.md`에 기록하고, 기대와 다른 답변도 지우지 않은 채 다음 결정을 한 줄로 적는다.

판정 배지가 자동 채점 도구라 해도, 배지의 true/false가 실제 답변과 근거 청크의 관계를 잘 설명하는지는 학생이 다시 확인해야 한다.

**에이전트에게 실험 설계를 검토받는 지시문**

```
내 루브릭과 질문 세트를 읽고, 한 번에 하나의 변수만 바꾸는 실험 순서를 제안해 줘.
변경이 루브릭의 어느 지표에 영향을 줄지 예측도 함께.
측정되지 않은 예측은 [추정]으로 표시해 줘.
```

에이전트의 제안은 변경 후보를 정리해 주는 보조 자료일 뿐이다. 실제로 다시 돌려 판정 필드와 답변을 기록하기 전에는 개선의 증거가 되지 않는다.

### 실험 결과는 README에 남긴다

- 실험 결과는 내 저장소의 `README.md`에 정리한다.
- 무엇을 남길지는 스스로 정하되, 적어도 **어떤 설정으로 돌렸을 때 어떤 루브릭 점수가 나왔는지**는 나중에도 읽을 수 있어야 한다.
- 변경 이유, 기대와 달랐던 결과, 답변이나 근거 청크를 다시 읽으며 확인한 점도 필요한 만큼 적는다.
- 기록은 완성된 보고서가 아니라, 다시 실험할 때 그때의 판단과 결과를 되짚는 자료다.
- 고정 질문 세트(Q1~Q9 같은)로 같은 질문을 돌렸다는 사실이 결과 옆에 남아 있어야 결과끼리 비교할 수 있다.
- judge 판정 필드(`grounded`, `noHalluc`, `cited`, `refusal`, `score`, `comment`)는 루브릭 점수가 나온 근거이므로 결과와 함께 확인한다. 점수가 달라졌다면 그 판정과 실제 답변을 같이 읽어 변화가 무엇을 뜻하는지 판단한다.

**더 깊이 가 보기**

- 한 바퀴를 안정적으로 돌린 뒤에는 같은 답변을 로컬 judge와 Gemini judge에 각각 보내고, 엔진별 판정을 `README.md`의 같은 실험 기록에 함께 남길 수 있다.
- 두 판정이 다르면 어느 쪽이 맞는지 바로 정하지 말고, 사람이 답변·근거 청크·코멘트를 다시 읽어 루브릭 정의가 충분히 구체적인지 확인한다.
- 프롬프트 세 종류를 A/B 방식으로 비교할 때도 질문 세트와 나머지 설정은 고정하고, 각 프롬프트가 겨냥하는 지표만 다르게 두어야 비교가 성립한다.
- `README.md`에 실험 기록이 쌓이면 같은 기준 질문으로 얻은 지표 변화를 이어서 볼 수 있다. 한 번 실행에서 나온 우연한 차이를 큰 개선이라고 선언하지 않는다. 다시 돌린 기록이 늘수록 해석의 근거도 늘어나고, 그 기록이 배포 전 수용 기준과 배포 후 관찰을 잇는 출발점이 된다.

> 루브릭을 스스로 적는 순간, 개선은 감이 아니라 기록이 된다.

## 9. 내 도메인에서 동작하는 챗봇 제출하기

### 설계: 내 도메인의 PRD 완성하기

앞에서 초안으로 남겨 둔 PRD를 제출 직전에 완성본으로 마무리한다.

- 문서의 `[결정 필요]`를 하나씩 찾아 다음 내용으로 바꿔 적는다: 사용자, 해결하려는 질문, 사용할 자료의 범위, 답변의 근거 표시, 실패했을 때의 안내 문구.
- 빈칸을 남긴 채 구현을 시작하면, 나중에 고르는 코드가 제품의 약속을 대신 정해 버린다.
- 자료에 없는 질문에는 범위를 그럴듯하게 넓혀 답하지 않고, 자료 범위 밖이라고 밝힌 뒤 관련 자료를 요청하거나 답할 수 없다고 안내한다고 분명히 적는다. 이 기준은 거절 횟수를 줄이려는 것이 아니라, 사용자가 답변의 경계를 이해하게 하려는 약속이다.
- 수용 기준에는 어떤 답에 출처가 있어야 하는지, 어떤 경우의 거부가 정당한지도 적는다.
- 완성한 PRD를 처음 보는 사람이 읽고, 무엇을 물어도 되고 무엇을 기대하면 안 되는지 판단할 수 있는지 확인한다.
- 기능 목록에는 그 기능이 사용자의 판단을 어떻게 돕는지 이유를 붙인다.
- 자료를 누가 갱신하는지, 출처 링크는 누가 책임지는지도 적어 두면, 나중에 자료가 바뀌었을 때 무엇을 다시 검토해야 하는지 분명해진다.

### 구현: 모두콘 구조를 내 자료로 바꾸기

- 모두콘의 청크 배열을 내 자료의 사실 단위로 교체한다. 각 항목의 `id`, `text`, `url`, `section`, `vector` 스키마는 그대로 둔다.
- 소개와 페이지 문구도 PRD에서 확정한 사용자와 질문에 맞게 바꾼다.
- 임베딩은 `embeddinggemma-300m`으로 만들어 768차원 벡터 공간을 맞춘다. 자료 벡터만 바꾸고 질의 임베딩을 다른 모델로 만들면 검색 점수가 비교할 기준을 잃는다.
- 검색 순서와 답변 프롬프트의 출처·거부 규칙은 그대로 두어, 결과가 달라지면 그것을 내 자료의 차이로 읽을 수 있게 한다.
- 교체 작업을 에이전트에게 맡길 때도 **데이터 구조를 바꾸지 말라는 조건을 먼저** 준다.

```
**스키마와 검색·프롬프트 파이프라인은 변경하지 마세요.**
모두콘 예시 코드에서 청크 데이터와 소개·페이지 문구를 [내 도메인]으로 교체해 주세요.
청크는 [자료 경로]를 근거로 만들고 `id`, `text`, `url`, `section`, `vector` 필드를 유지하세요.
임베딩은 embeddinggemma-300m의 768차원으로 통일하고,
[도메인 밖 질문 처리 기준]을 문구에 반영하세요.
```

### 실험: 내 루브릭으로 한 바퀴

- 앞에서 정한 내 루브릭을 새 챗봇에 그대로 적용한다.
- 출처를 인용한 답, 도메인 밖 질문의 거부, 판정 배지의 grounded 여부, 짧은 답에서도 근거 표시가 남는지를 고정 질문 세트로 확인한다.
- 질문에는 자료를 직접 묻는 것, 여러 청크를 이어야 하는 것, 자료 밖을 묻는 것을 섞어 경계를 관찰한다.
- 한 번 실행할 때는 프롬프트 문구나 검색 설정처럼 변수 하나만 바꾸고, 나머지 조건과 질문 순서는 유지한다. 그래야 답변이 달라진 이유를 추측하지 않고 비교할 수 있다.
- **`README.md`에 기록할 것**: 실행 날짜 대신 실험 이름, 바꾼 변수, 고정 질문, 질문별 cited·refusal·grounded 판정, 관찰한 근거, 채택할지 되돌릴지에 대한 결정
- 실패한 답도 지우지 않아야 다음 수정에서 무엇을 지켜야 하는지 알 수 있다.
- 루브릭의 목표값과 실제 판정값을 나란히 남기면, "개선"이라는 말이 어떤 관찰에 근거하는지 동료와 사용자에게 설명할 수 있다.

### 배포: 내 주소로 공개하기

```bash
npm run build   # 정적 결과물 생성 → dist를 GitHub Pages에 올림
```

- 프로젝트 설정의 `base: './'` 덕분에 배포 주소 아래에서도 자산 경로를 상대 경로로 찾는다.
- **주의**: 정적 페이지가 답변을 대신 실행하는 것이 아니다. 페이지를 연 사용자의 브라우저가 `localhost:11434`의 Ollama `qwen3.5:2b`를 직접 부른다. 그래서 그 사용자 컴퓨터에서 Ollama가 돌고 있어야 하고, Pages 출처의 요청을 허용하도록 `OLLAMA_ORIGINS`를 설정해야 한다.
- 배포 주소에서 소개 질문과 도메인 밖 질문을 각각 넣어 자산 로드, 모델 연결, 출처 표시, 거부 안내를 확인한다.
- 주소가 열린다고 배포가 끝난 것이 아니다. 사용 조건을 갖춘 브라우저에서 실제 경로를 끝까지 따라가 본다.
- 연결에 실패했을 때 모델이 없다는 안내와 재시도 방법이 보이는지도 확인해, 사용자가 페이지 오류와 자기 실행 환경 문제를 구분할 수 있게 한다.

### 제출: 저장소와 안내 페이지

사용 조건은 숨기지 않고 적는다: Ollama 실행, 첫 방문 시 임베딩 다운로드 약 200MB, CORS 설정 필요. 안내 페이지는 결과를 자랑하는 자리가 아니라, 처음 보는 사람이 실행 전에 조건을 판단하는 자리다.

**사용자가 따라갈 순서** (README와 안내 페이지에서 같은 말로 쓰였는지 마지막으로 대조한다)

1. 배포 주소를 열고 서비스가 다루는 자료와 질문을 읽는다.
2. 내 컴퓨터에서 Ollama를 실행하고 `qwen3.5:2b`를 준비한다.
3. 첫 방문에는 임베딩 다운로드가 있을 수 있으니 확인하고 기다린다.
4. Pages 주소에서 호출하려면 `OLLAMA_ORIGINS`에 해당 출처를 허용한 뒤, 안내된 질문과 자료 밖 질문을 각각 넣어 본다.

| 제출물 | 담을 내용 |
|---|---|
| `README.md` | 서비스 소개, 설계 결정 요약, 실험 결과, 배포 주소와 사용 조건 |
| `PRD.md` | 누구의 어떤 질문을 자료 범위 안에서 다루는지, 도메인 밖 질문 처리 기준 |
| 코드 | 챗봇 구현 전체 |
| 배포 주소 | GitHub Pages 주소 |

### 마무리: 제출 뒤에 남는 것

이번에 만든 것은 자료를 넣으면 답이 나오는 화면만이 아니다. 다음 흐름을 한 번 끝까지 이었다.

```
PRD로 질문의 범위와 거절 기준을 정함
  → 같은 스키마와 임베딩 공간 안에서 자료를 교체함
  → 루브릭과 고정 질문으로 답변을 판정함
  → 사용 조건까지 안내함
```

- 저장소의 README는 사용자의 출발점이다. PRD는 바꿀 수 없는 약속과 다시 검토할 결정을 가르는 기준이다. 실험 기록은 다음 변경을 비교할 기준이다.
- 답변 하나가 좋아 보인다는 인상보다, 어떤 질문에서 어떤 근거와 판정이 나왔는지 남긴 기록이 챗봇을 설명할 수 있게 해 준다.
- 자료가 바뀌거나 사용자의 질문이 넓어지면 같은 고정 질문으로 다시 관찰하고, PRD의 범위와 안내 문구도 함께 고친다.
- 그렇게 쌓인 비교 기록은 새 기능을 급하게 붙이는 대신, 자료에 근거한 답변이라는 약속을 지키는 데 쓰인다.

> 제출은 끝이 아니라, 내 도메인에서 측정을 계속해 나가는 시작이다.
