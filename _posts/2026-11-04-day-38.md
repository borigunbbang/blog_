> **한 줄 요약** — 긴 컨텍스트를 여러 에이전트가 나눠 읽는 딥리서치 에이전트를 만들었다. 코디네이터가 목차를 짜서 절을 나눠 맡기고, 서브에이전트(리서처)는 담당한 절에 필요한 문서만 읽고 원고를 쓴다.

## 1. 딥리서치 에이전트란

긴 컨텍스트를 읽어야 할 때 사용하는 **멀티 에이전트** 구조다.

| 역할 | 하는 일 |
|---|---|
| **코디네이터** | 목차를 짜고 각 절을 나눠 맡긴다. 부족한 내용은 근거를 확인한 뒤 다시 요청한다 |
| **서브에이전트(리서처)** | 담당한 절에 필요한 문서만 읽고 원고를 작성한다 |

### 실습 목표

위키백과 문서 34건을 읽을 수 있는 딥리서치 에이전트 만들기.

- 여섯 개의 **빈 노드를 먼저 연결한 뒤 전체 흐름을 실행**한다 → 뼈대 작업
  - 실제 작업이 아닌 **파이프라인만 완성된 상태**
- 실행할 때마다 분기 수가 달라질 수 있기 때문에 그래프 설계를 미리 하지 않는다
  - LangGraph의 **Send** 사용: 실행 중 필요한 수만큼 노드를 병렬로 실행해 주는 기능

## 2. 여섯 개 노드

```
① 기획 → ② 배치 ──┬─ ③ 조사 ─┐
                  ├─ ③ 조사 ─┼→ ④ 점검 → ⑤ 종합 → ⑥ 평가
                  └─ ③ 조사 ─┘     │
                       ↑           │ 부족하면
                       └───────────┘ 다시 조사 요청
```

| # | 노드 | 하는 일 | 중요한 질문 |
|---|---|---|---|
| 1 | **기획** | 코디네이터가 질문을 받아 보고서의 목차를 구성한다 (절을 몇 개로 나눌지, 어떤 리서처에게 맡길지, 어떤 문서를 읽게 할지) | 무엇을 기준으로 작업을 나눌 것인지 |
| 2 | **배치** | 각 절을 담당할 서브에이전트를 실행한다. 여기서 그래프가 여러 갈래로 나뉜다 | 얼마나 세분화할 것인지 |
| 3 | **조사** | 서브에이전트가 실제로 작업한다 | 어떤 결과물을 돌려받을 것인가 |
| 4 | **점검** | 코디네이터가 제출된 원고를 검토하고 부족한 부분을 찾는다. 부족하면 다시 조사 요청 | 어떤 기준으로 판단할 것인지 |
| 5 | **종합** | 각 절의 원고를 하나로 합쳐 보고서를 완성한다 | |
| 6 | **평가** | 완성된 보고서가 요구사항을 충족하는지 검토한다 | |

## 3. 데이터셋: 한국어 위키백과 한국 근대사 문서 모음

### 채택 이유

1. **여러 문서를 함께 읽었을 때 답할 수 있어야 한다.**
   - 한 문서만으로 답할 수 있다면 작업을 나눌 필요가 없다.
2. **문서끼리 연결되어 있어야 한다.**
   - 예) 강화도 조약 문서 → 운요호 사건 → 개화파
   - 이런 링크가 있어야 서브에이전트가 문서를 읽은 뒤 다음 대상을 탐색할 수 있다.
3. **결과를 평가할 수 있어야 한다.**

코퍼스(문서 모음)를 다른 주제로 바꿔도 활용 가능한 방법으로 실습을 진행했다.

## 4. 라우팅 구조와 차이점

### 구조가 정해지는 시점

| | 라우팅 | 딥리서치 에이전트 |
|---|---|---|
| 구조 결정 | **코드를 작성할 때** 정해짐 | **질문이 들어온 뒤** 정해짐 |
| 동작 | 질문이 들어오면 정해진 분기 중 하나를 선택 → 구조 자체는 안 바뀜 | 질문에 따라 목차, 리서처 수, 담당 작업이 달라짐 |
| 장점 | 예측하기 쉽고 비용 절감, 디버깅 간단 | 질문에 맞는 대응 가능 |
| 단점 | | 비용이 많이 들 가능성 있음 |

> 무엇을 어떤 순서로 할지 **늦게 정할수록** 질문에 잘 맞는 답을 한다.

### 컨텍스트 길이 비교

- **라우팅**: 선택된 핸들러가 필요한 자료만 추려 **하나의 컨텍스트 윈도우**에서 답변 생성
- **서브에이전트 구조**: **여러 컨텍스트 윈도우를 병렬로** 활용
  - 각 서브에이전트가 독립된 컨텍스트 윈도우에서 원문을 읽고, 코디네이터에게는 작성한 원고만 전달

에이전트가 같은 맥락을 공유해야 하거나 에이전트 간 의존성이 높은 작업(ex. 코딩)은 서브에이전트 구조가 적합하지 않다.
→ 각 에이전트는 병렬로 돌아가서 **서로의 작업을 볼 수 없기 때문**

### 구조를 정하는 방법

```
모든 작업 경로를 미리 정할 수 있는가?
├─ YES → 라우팅 (Routing)
└─ NO  → 자료를 읽어봐야 다음 할 일이 정해지는가?
          ├─ YES → 딥리서치 에이전트 (코디네이터 + 리서처 에이전트)
          └─ NO  → 단일 에이전트
```

- **라우팅**: 질문의 유형이 정해져 있는 경우
- **서브에이전트 구조**: 질문을 매번 다른 관점으로 분석하고 해석해야 할 때

## 5. 기획 노드 채우기 — 문서 카드와 목차 배정

**역할**: 질문을 받은 후 목차를 구성하고, 각 절에 리서처 에이전트를 배정한 뒤 읽을 문서를 지정한다.

### 코디네이터에게 문서를 보여주는 방법

목차를 구성하려면 코디네이터도 문서(자료)를 읽어야 한다.

| # | 방법 | 특징 |
|---|---|---|
| 1 | 제목만 보여준다 | 실제 문서의 내용은 알 수 없음 |
| 2 | **제목 + 문서 앞 250자 카드** | 첫 문단에 정의가 담긴 자료에 적합 |
| 3 | 문서 한 건을 먼저 읽히고 목차 배정 | 실제 본문을 읽기 때문에 근거 확실. 단, 직렬 단계가 추가돼 병렬의 장점이 사라짐 (사전 조사 후 병렬로 실행되기 때문에 전체 시간 증가) |
| 4 | 문서 전체를 보여준다 | 물리적으로 불가능 |

→ **2번 방법 채택.** 2의 구조는 유지하되 앞 250자 대신 **미리 생성한 한 줄 요약**을 제공했다.

### 목차 배정

무엇을 읽을지 정하는 일이다.

- **시작 문서**를 코디네이터가 배정해 준다 → 리서처 에이전트가 각각 다른 문서를 읽을 수 있게 해주는 역할
- 시작 문서가 질문과 상관없으면, 다음 문서부터는 리서처가 스스로 다음 읽을 문서를 선택한다

### 검증 방법

카드를 제공하면 코디네이터가 정답에 가까운 문서를 배정하는지 확인한다.

| 지표 | 의미 | 기대 |
|---|---|---|
| **Hit rate (배정 정확도)** | 배정한 시작 문서 중 골든셋에 포함된 문서의 비율 | 카드를 제공하지 않았을 때보다 높아야 함 |
| **관련 없음 비율** | 리서처가 읽은 뒤 '관련 없음'으로 판단한 문서의 비율 | 배정이 잘못되면 높아짐 |
| **최다 문서 편중** | 특정 문서에 인용이 집중되는 정도 | 배정이 부정확하면 여러 에이전트가 같은 유명 문서로 몰리며 높아짐 |

세 가지는 ⑥ 평가 노드의 metrics에 정리한다.

> 리서처 에이전트는 엉뚱한 문서를 읽어도 그 내용을 바탕으로 **그럴듯한 원고를 작성**한다 → 질문과 각 절의 제목을 나란히 놓고 비교해야 확인 가능하다.

### 기획 노드 구성 코드

1. **Roster** — 리서처 에이전트 명단
   - 명단에는 절마다 '시간 순 담당', '인물 담당'처럼 역할을 부여하고 프롬프트에 반영한다
   - → 같은 문서를 보더라도 역할에 맞게 정보를 정리
   - 역할은 프롬프트 한 줄로 정의 가능하기 때문에 별도의 코드 작성은 필요하지 않다
   - roster에 각 역할을 적어놓고, 코디네이터는 목차를 구성할 때 질문에 맞는 역할을 roster에서 찾아 프롬프트에 적어 리서처에게 보낸다 → 각 리서처는 전달받은 역할에 맞는 자료를 탐색
2. **card** — 문서 카드를 만드는 함수
3. **plan** — 목차 생성

### 판단 항목

1. 절이 두 개 이상 생성되었는가
2. 각 절에 서로 다른 시작 문서가 배정되었는가 (같은 문서가 중복되면 코드가 바로잡도록 되어 있다)
3. 배정된 문서가 질문의 시대와 주제에 맞나? (엉뚱한 연도의 사건이 포함되었다면 카드가 제 역할을 하지 못한 것)

> 코드는 **형식과 문서 존재 여부만** 확인하고, 내용 검증은 점검·평가 노드에서 한다.

## 6. 배치 노드 — 폭과 깊이, 구역 나누기

1. 보고서를 몇 개의 절로 나누는가 → **폭 (절 수)**
2. 각 리서처가 문서를 몇 건까지 읽을지 → **깊이 (절 예산)**

```
한 번 실행할 때 읽는 문서 수 = 절 수 × 절당 읽기 예산
```

| 폭이 커지면 | 깊이가 커지면 |
|---|---|
| 보고서의 구성이 좋아짐 | 더 많은 자료를 살펴볼 수 있음 |
| 각 절의 주제가 명확 | 배정받은 링크를 따라가면 코디네이터가 미처 파악하지 못한 문서까지 찾을 수 있음 |
| 리서처가 좁은 범위에 집중할 수 있어 문장마다 근거를 붙이기 쉬워짐 | |

### 결정 검증 방법

절을 나누면 근거가 촘촘해지고, 읽기 예산을 늘리면 조사 범위가 넓어지는지 확인한다.

| 지표 | 의미 |
|---|---|
| **절당 실제 읽기 수** | 시작 문서 + 리서처가 추가로 선택한 문서의 수. 예산을 다 쓰지 않고 멈추는 경우가 많다면 읽기 예산을 늘려도 효과 없음 |
| **절당 글자 수** | 절 하나의 분량 |
| **최다 문서 편중** | 인용이 가장 많이 된 문서 하나가 전체 인용에서 차지하는 비율. 절 수가 적을수록 특정 문서에 의존하기 쉬워짐 |
| **중복률** | 같은 문서를 두 개 이상의 절에서 읽은 비율 |

> 잘못된 설정의 대표 증상 → **보고서는 길어지는데 근거율은 그대로**

### 피하기 목록

코디네이터가 리서처에게 '**이 문서는 피해**'라고 전해주는 목록 → 중복 방지

- 1바퀴: 시작 문서를 바탕으로 피하기 목록 작성
- 2바퀴부터: 리서처들이 읽은 목록을 바탕으로 작성

## 7. 조사 노드 — 반환 형식과 컨텍스트 격리

리서처 실행 후 각 에이전트가 코디네이터에게 **어떤 형태로 전달할지** 정하는 과정이다.

| # | 반환 형식 | 장점 | 단점 |
|---|---|---|---|
| 1 | 읽은 문서의 원문 그대로 | 정보 손실 X | 서브에이전트를 쓰는 의미가 없어짐. 코디네이터의 컨텍스트 윈도우를 초과할 가능성 높음 |
| 2 | 질문에 맞춘 요약 | 가장 가벼움. 글쓰기 작업이 코디네이터에 집중됨 | 앞부분에서 뒷부분으로 갈수록 근거 부족 |
| 3 | **담당한 절의 원고 + 자체 평가** | 원문으로 작성해서 근거를 정확하게 인용. 컨텍스트 분리 유지. 코디네이터가 자체 평가로 추가 조사 판단 가능 | 절 사이 내용이 겹치거나 다른 주장을 하면 판단하기 어려움 (서로 내용을 볼 수 없기 때문) |
| 4 | 절 원고 + 근거가 되는 원문 발췌 | 코디네이터가 인용의 정확성을 직접 검증. 신뢰성이 엄격한 작업에 적합 | 컨텍스트 윈도우 문제 |

### 컨텍스트 격리

> 비싼 원문은 **하위 에이전트의 컨텍스트 안에서만 소비**하고, 위로는 **압축된 결과만** 올리는 설계

- 요약 프롬프트에 '**관련 없으면 관련없음으로만 답**'이라고 적어 잘못된 요약을 방지할 수 있다.

### 검증 방법

리서처가 직접 원고를 작성하면 인용이 촘촘해지고 코디네이터의 컨텍스트 사용량은 줄어드는지 확인한다.

| 지표 | 계산 | 기준 |
|---|---|---|
| **격리율** | 코디네이터가 읽은 글자 수 ÷ 팀 전체가 읽은 글자 수 | 한 자릿수 퍼센트 목표. 30%를 넘으면 컨텍스트 격리 오류 |
| **절당 인용 수** | 각 절에 문서명이 몇 번 인용되었는지 | 인용이 하나도 없다면 자료 없이 작성했을 가능성이 높음 |
| **허위 인용** | 인용한 문서 목록 − 실제로 읽은 문서 목록 (차집합) | 0이 아니면 읽지 않은 문서를 근거로 사용한 것 |

→ 평가 노드에서 한 번에 확인한다.

### researcher 노드

배정받은 문서를 읽고 → 다음 후보를 찾아 읽고 → 읽기 예산을 소진하면 원고 작성.
이 과정이 **하나의 에이전트**로 동작한다.

**확인할 항목**

1. 절마다 3건의 문서를 읽었는지
2. 인용이 하나도 없는 절이 있는지
3. 허위 인용을 했는지
4. 같은 문서를 여러 절이 읽었는지
