업무 자동화에서 에이전트가 차지하는 위치와 워크플로 도구(n8n) 사용법을 7개 강의 순서대로 정리했다.

## 1. 다음 행동을 누가 정하는가

### 왜 이 질문부터 시작하나

배송 일정, 결제 실패, 반품 주소를 묻는 비슷한 문의를 매일 읽고, 담당 팀에 넘기고, 같은 내용을 표에 다시 옮기는 일은 AI에게 맡기고 싶은 대표적인 반복 업무다. 자동화의 목적은 이런 반복에 드는 시간과 실수를 줄이는 것이고, 규칙이 분명한 반복은 실제로 잘 맡길 수 있다.

하지만 맡긴 일이 예상하지 못한 예외를 만나면 문제가 생긴다.

- 잘못 분류된 문의가 여러 팀으로 전달된다.
- 멈춰야 할 작업이 계속 실행된다.
- 처리 결과만 남고, 왜 그렇게 처리됐는지는 찾기 어렵다.

그래서 먼저 정할 것은 "AI를 쓸까 말까"가 아니라 다음 세 가지다.

1. 무엇을 맡기는가
2. 어디에서 멈추게 하는가
3. 문제가 생기면 무엇을 확인하는가

이 강의는 도구 이름보다 이 세 가지를 정하는 기준을 다룬다. 목표는 반복 업무에서 맡길 부분과 사람이 판단할 부분을 나누는 것이고, 출발점은 **다음 행동을 누가 정하는가**라는 질문이다.

### 다음 행동을 정하는 세 가지 방식

opencode, Claude Code, Antigravity 같은 코딩 에이전트에 "저장소를 살펴보고 수정안을 만들어 줘"라고 맡기면, 도구는 파일을 읽고 → 명령을 실행하고 → 테스트 결과를 확인한 뒤 → 다음 행동을 고른다. 화면에는 최종 수정안만 남는다. 어떤 파일을 먼저 열었는지, 어느 명령을 골랐는지, 실패 뒤 왜 다시 시도했는지는 빠르게 지나가 다시 확인하기 어렵다. 지나간 과정을 다시 확인하려면 먼저 다음 행동을 누가 정했는지 알아야 한다. "에이전트"라고 불리는 도구들도 이 방식이 서로 다르다.

| 방식 | 다음 행동을 정하는 주체 |
|---|---|
| 사람이 직접 지시 | 사람이 다음 행동을 하나씩 정한다 |
| 워크플로 | 단계를 미리 연결해 둔 흐름(고정 그래프)이 정해 둔 순서와 조건대로 정한다 |
| 에이전트 | 앞선 결과를 읽은 모델이 쓸 도구와 다음 경로를 고른다 |

예: 고객 문의를 분류해 담당 팀에 알리는 업무

| 방식 | 업무가 진행되는 모습 | 문제가 생기면 확인할 것 |
|---|---|---|
| 사람이 직접 지시 | 사람이 메일을 읽고 기준을 적용해 알림을 보낸다 | 입력과 판단 기준 |
| 워크플로 | 수신 → 분류 → 담당 팀 찾기 → 알림 발송을 연결하고 조건을 정해 둔다 | 어느 조건에서 다른 경로로 갔는지 |
| 에이전트 | 내용이 모호한 문의에서 조회 도구를 쓸지, 추가 정보를 요청할지, 후보를 다시 찾을지 모델이 고른다 | 준 도구, 도구가 돌려준 결과, 반복 한도, 승인 규칙 |

세 경우 모두 화면에는 "담당 팀에 알림을 보냈다"는 결과만 남을 수 있다. 결과가 같아 보여도, 문제가 생겼을 때 원인을 찾을 곳은 방식마다 다르다.

### 결정권이 옮겨 가는 그림

강의 도식 "다음 행동을 누가 선택하는가"의 내용이다.

```
사용자 ──직접 지시──▶ 고정 그래프 ──동적 선택──▶ 모델
(단계·도구를 지시)    (조건이 지정)              (도구·경로를 선택)
                                                  │  ▲
                                             실행 │  │ 재선택
                                                  ▼  │
                                      도구 실행 결과(파일·응답·오류)
```

- 화살표는 데이터가 움직이는 방향이 아니라, **다음 행동을 정할 권한이 옮겨 가는 방향**이다.
- 모델과 도구 실행 결과 사이의 "실행"·"재선택"은 모델이 도구를 실행하고 → 결과를 읽고 → 다음 행동을 다시 고르는 반복을 뜻한다.

### 워크플로와 에이전트는 제품이 아니라 단계에 붙이는 이름

한 도구 안에서도 단계마다 다음 행동을 정하는 주체가 달라질 수 있다.

- 대화창에서 메일, 캘린더 같은 외부 서비스를 연결해 실행할 수 있다.
- 워크플로 한가운데 모델의 판단이 들어갈 수 있다.
- 코딩 에이전트에도 사람이 승인하는 절차가 있을 수 있다.

Anthropic은 *Building effective agents*에서 이렇게 나눈다.

- **워크플로(workflow)**: 코드 경로가 미리 정해진 경우
- **에이전트(agent)**: 모델이 과정과 도구 사용을 그때그때 이끄는 경우

이 구분은 어느 쪽이 더 낫다는 뜻이 아니다. 워크플로의 고정 경로는 검토하고 똑같이 다시 실행해 보기(재현)에 유리하다. 에이전트의 그때그때 선택은 예외가 많은 업무에 도움이 된다. 대신 모델 호출이 늘어 비용이 커지고, 앞 단계의 오류가 다음 단계로 이어질 수 있다.

> 모델에 선택을 더 맡길수록 도구 권한, 반복 한도, 사람이 확인하고 승인하는 지점을 더 분명히 정해야 한다.

| 방식 | 특징 | 확인할 것 |
|---|---|---|
| 사람이 직접 지시 | 대화창에서 하나씩 요청하며 조사, 파일, 코드, 연결 도구를 쓴다. 어떤 연결 도구를 거쳤는지, 어떤 권한으로 실행했는지가 화면 어디에 보이는지는 제품마다 다르다 | 입력한 내용이 어떤 연결 도구와 외부 서비스로 가는지, 실행 기록을 어디까지 볼 수 있는지 |
| 워크플로 | 시작 조건(트리거), 단계(노드), 분기, 실행 이력을 이은 경로가 화면에 보인다. "새 문의를 분류하고 특정 조건에서 알린다"는 경로는 설계한 그래프가 정한다. 그래프 중간에 모델을 넣어도 전체가 곧바로 에이전트 방식이 되지는 않는다 | 모델이 판단하는 범위, 모델 노드에 들어가는 입력과 그 결과를 받는 다음 노드, 실행 권한 |
| 에이전트 | 저장소, 터미널, 테스트처럼 개발 환경의 실제 도구를 다룬다. 제품마다 제공 범위는 다를 수 있다 | 어떤 파일 경로가 읽기 전용인지, 파일 변경과 외부 통신은 어디서 승인하는지, 테스트 결과가 다음 선택에 다시 반영되는지 |

### 이 강의에서 쓰는 세 용어

| 용어 | 뜻 |
|---|---|
| 자동화 | 규칙이 분명한 반복을 도구에 맡기는 일 전체. 세 방식 중 하나를 가리키는 말이 아니다 |
| 워크플로 | 여러 단계를 사람이 설계해 연결하고, 정해 둔 순서와 조건대로 실행하는 방식 |
| 에이전트 | 판단이 필요한 곳에서 모델이 다음 행동을 고르는 방식 |

## 2. 자동화 규칙과 워크플로 비교 기준

### 자동화할 일 고르기: 규칙으로 적을 수 있는가

자동화에 맡길 일은 그 일을 규칙으로 적을 수 있는지로 고른다. 일을 설명할 때 "무조건", "항상", "매번"을 쓸 수 있다면 규칙이 비교적 선명하다. 아래 일은 조건과 결과를 이어 적을 수 있다.

- 새 문의에 접수 번호를 붙인다.
- 매일 아침 전날 매출을 표에 옮긴다.
- 첨부가 없는 신청서에는 안내를 보낸다.

반대로 "친절하게 답한다", "중요한 메일부터 본다"에는 사람의 판단이 들어간다.

> 💡 **규칙인지 확인하는 방법**: 이 일을 처음 맡는 동료에게 가르친다고 생각해 본다. 동료가 "이 경우엔 어떻게 해요?"라고 물었을 때 "알아서 해 주세요"라고 답하게 된다면, 그 부분은 아직 규칙이 아니다.

> 자동화는 적어 둔 규칙만 실행한다. 적지 않은 빈틈을 스스로 메우지 않는다.

### 그래프와 워크플로

업무는 한 번의 행동으로 끝나지 않는 경우가 많다. 문의를 받고 → 분류하고 → 답을 고르고 → 기록하고 → 필요하면 담당 부서로 넘긴다. 이렇게 여러 행동을 이어 놓은 설계도를 **그래프**라고 한다.

| 그래프의 요소 | 뜻 |
|---|---|
| 노드(node) | 행동 하나를 나타내는 점 |
| 연결선 | 노드 사이의 흐름을 나타내는 화살표 |
| 트리거(trigger) | 그래프 실행을 시작하게 하는 노드 |
| 분기 | 조건에 따라 흐름이 갈라지는 지점 |
| 실행 기록 | 그래프가 실행될 때마다 노드별 입력과 출력이 남는 기록 |

그래프가 순서를 정하는 워크플로에서는 사람이 경로를 미리 정한다. 예: 새 문의를 분류한 뒤, 환불 문의는 담당 부서로 보내고 나머지는 일반 답변 흐름으로 보낸다. Anthropic은 워크플로를 "미리 정의된 코드 경로로 LLM과 도구가 조율되는 시스템"이라고 정의한다. 그래서 워크플로에서는 모델을 넣더라도 실행 순서와 분기는 사람이 정하고, 실행 기록으로 그 순서를 다시 검토할 수 있다.

### 도구를 비교하는 다섯 가지 질문

도구 소개 페이지에는 기능 수, 연결할 수 있는 서비스 수, 모델 이름이 먼저 보인다. 하지만 기능 수만으로는 업무에 쓸 때의 위험을 판단할 수 없다.

- 연결이 많아도 입력을 어디서 읽었는지 알 수 없다면, 잘못된 요약을 고치기 어렵다.
- 기능이 적어도, 읽기 전용 공개 데이터로 검토용 초안을 만드는 일이라면 더 안전할 수 있다.

그래서 도구는 기능 수 대신 다음 다섯 질문으로 비교한다.

| 질문 | 확인할 것 |
|---|---|
| 통제 | 누가 시작, 중지, 승인, 쓰기 권한을 정하는가 |
| 관측 | 입력, 도구 호출, 응답, 실패 지점을 기록으로 되짚을 수 있는가 |
| 이식성 | 프롬프트, 연결 규칙, 코드, 비밀값(API 키·비밀번호 같은 값)을 다른 환경으로 옮길 때 무엇을 다시 준비해야 하는가 |
| 비용 | 구독, 모델 처리량, 실행 횟수 중 어떤 단위로 요금이 계산되는가 |
| 데이터 경로 | 입력, 로그, 모델, 결과, 비밀값이 어느 서비스와 저장 위치를 지나는가 |

### 예시 업무로 다섯 질문 채워 보기

예시 업무: 매일 아침 공개 데이터(개인 정보가 없는 공개 API)에서 정보를 읽고 세 문장 요약을 받는다. 같은 업무라도 어느 방식에 두느냐에 따라 누가 무엇을 승인하는지, 확인할 기록이 달라진다.

| 방식 | 통제 | 관측 | 이식성 | 비용 | 데이터 경로 |
|---|---|---|---|---|---|
| 사람이 직접 지시 | 사람이 매일 대화에서 요청한다. 예약·연결 기능이 있다면 켜고 끄는 권한을 확인한다 | 요약과 별도로 공개 데이터의 원본 응답을 저장하거나 다시 열 수 있는지 확인한다 | 대화 지시와 연결 설정을 다른 계정이나 도구로 옮길 수 있는지 확인한다 | 플랜의 사용량 한도와 연결 도구 사용량이 같은 한도인지 확인한다 | 공개 데이터, 대화 내용, 연결 도구 입력이 각각 어느 제공자에게 가는지 확인한다 |
| 워크플로 | 정해 둔 시각의 실행과 요약 전송을 고치거나 멈추는 권한을 확인한다. 발송은 별도 승인을 거치게 설정한다 | 실행마다 요청, 응답, 분기, 오류를 실행 기록에서 확인한다 | 워크플로를 내보낸 뒤에도 비밀값을 다시 넣어야 하는지, n8n 버전이 다르면 노드 설정이 달라지는지 확인한다 | 하루 한 번의 전체 워크플로 실행이 어떤 단위로 계산되는지 확인한다 | 호스팅 위치, 실행 로그, 외부 모델, 공개 API 사이의 데이터 이동을 확인한다 |
| 에이전트 | 일정 설정, 코드 변경, 파일 저장, 메시지 발송에 필요한 승인 경로를 각각 확인한다 | 실행 명령, 코드 변경, 표준 출력, 오류를 사람이 똑같이 다시 실행해 볼 수 있는지 확인한다 | 저장소의 코드와 환경 변수 중 다른 컴퓨터에서 다시 준비할 내용을 확인한다 | 계정 사용량, 모델 처리량, 실행 환경 비용을 각각 확인한다 | 공개 데이터 요청, 로컬 파일, 환경 변수, 모델 입력, 원격 저장소에 올라가는 파일이 각각 어디로 가는지 확인한다 |

표를 채우다 보면 공식 문서로 답할 수 없는 칸이 생긴다. **그 칸이 바로 도구를 업무에 쓰기 전에 확인해야 할 항목이다.** 행에 ChatGPT, n8n, Claude Code처럼 실제 제품을 더해 같은 다섯 질문으로 비교할 수 있고, 공식 문서에서 확인하지 못한 가격, 연결 수, 기능 차이는 그 칸에 "미확인"이라고 적는다.

### 같은 그래프형 도구라도 요금 세는 단위가 다르다

| 도구 | 세는 단위 | 트리거 + 액션 4개짜리 워크플로를 한 번 실행하면 |
|---|---|---|
| n8n | 워크플로 전체가 한 번 실행되면 노드 수와 관계없이 execution 1회 | execution 1회 |
| Zapier | 실행된 액션 단계마다 task 1개 | task 4개 |

그래서 요금표의 숫자만 나란히 놓고 비교하면 안 된다.

n8n의 AI Agent 노드처럼, 연결된 도구 중 무엇을 호출할지 모델이 고르는 노드도 있다(5강에서 사용). 이런 노드를 쓸 때는 두 가지를 확인한다.

1. 연결한 도구가 조회만 하는지, 메일 발송이나 삭제처럼 외부 상태를 바꾸는지
2. 실행 기록에서 모델이 어떤 도구를 어떤 입력으로 호출했는지

## 3. n8n에서 워크플로 만들고 실행 기록 확인하기

### 자동화 도구의 종류

반복 업무를 덜어 주는 도구는 다음 행동을 누가 정하는지, 과정이 어디까지 보이는지, 무엇에 비용이 붙는지가 서로 다르다.

| 방식 | 예 | 다음 행동을 정하는 것 | 특징 |
|---|---|---|---|
| 대화창 | ChatGPT, Claude | 사람의 요청과 대화 맥락 | 답은 바로 돌아오지만, 답을 만들 때 어떤 외부 서비스나 도구를 호출했는지는 대화 화면만으로 알기 어렵다 |
| 노코드 자동화 서비스 | Zapier | 사람이 미리 정한 "트리거(이런 일이 생기면) → 액션(이렇게 한다)" 규칙 | 수천 개 앱을 연결한다. 성공적으로 실행된 액션 단계 수(task)로 요금이 달라져서 비용과 실행 기록을 함께 봐야 한다 |
| 시각적 시나리오 편집기 | Make(이전 이름 Integromat) | 사람이 미리 정한 규칙 | 흐름을 그래프처럼 그리고 필터, 반복, 오류 처리 분기를 시나리오 안에서 조립한다. 2025년 8월 27일부터 요금 단위가 operation에서 credit으로 바뀌었고, 기존 operation은 1:1로 credit으로 바뀌었다 |
| 그래프형 도구 | n8n, Node-RED | 노드와 연결선으로 정한 경로 | 다음 행동과 데이터의 이동 경로가 화면에 보인다 |
| 코드, 코딩 에이전트 | 코드, 터미널, 저장소 | 코드 또는 에이전트 | 더 세밀한 규칙을 정할 수 있지만, 흐름과 기록을 한 화면에서 모두 보기는 어려울 수 있다 |

Zapier와 Make에서는 사람이 미리 정한 규칙이 다음 행동을 대신 수행한다. n8n도 같은 방식이지만, 소스 코드가 공개되어 있어 내 컴퓨터에 직접 띄워 볼 수 있다.

### 관찰 도구로 n8n을 쓰는 이유

n8n은 2019년 베를린에서 공개된 워크플로 자동화 도구다. 이름은 노드(node)와 자동화(automation)를 합친 **nodemation**을 줄인 것이다. 이 수업에서 n8n을 관찰 도구로 쓰는 이유는 다음과 같다.

1. 화면에서 노드를 이어 흐름을 그리면, 그 그래프가 그대로 실행된다.
2. 메일, 폼, 스프레드시트, 채팅 같은 외부 서비스와 공개 API를 노드로 묶을 수 있다.
3. 실행할 때마다 어느 노드가 무엇을 주고받았는지 기록이 남는다. 그래서 흐름과 데이터의 이동을 화면에서 따라갈 수 있다.
4. 소스 코드를 공개하는 **fair-code** 방식이라 나중에 내 컴퓨터나 서버에 직접 띄울 수 있다. 클라우드 서비스가 중단돼도 내 환경에서 흐름을 계속 실행할 수 있다.

n8n은 2025년 한 해에 GitHub 별이 11만 개 넘게 늘었다. 사용자가 많다고 믿을 수 있는 도구라는 뜻은 아니다. 다만 다른 사람이 공유한 워크플로 템플릿과 커뮤니티 질문·답변을 찾기 쉬워, 강의가 끝난 뒤 혼자 쓸 때 도움이 된다.

> 💡 **인스턴스**: 실행 중인 n8n 서버 하나. 수업에서는 미리 마련된 수업용 인스턴스에 접속하므로, 설치 없이 계정만 만들면 바로 워크플로를 만들 수 있다.

### 실습: 두 노드 워크플로 만들고 실행 기록 확인하기

공개 정보를 읽는 짧은 흐름을 만들고, 화면에서 설계한 흐름과 실행 뒤에 남은 기록을 나란히 본다. 목표는 두 가지를 구분하는 것이다.

- **실행 기록으로 확인할 수 있는 것**: 요청, 응답, 상태 코드
- **화면만으로는 알 수 없는 것**: 데이터가 저장되는 위치, 계정 권한

강의 그림: n8n 편집 화면에 Manual Trigger → HTTP Request(Wikipedia 요약 요청) 두 노드가 이어져 있다. 연결선은 사람이 정한 순서이고, 아래쪽 Execute workflow 버튼은 수동으로 실행하는 지점이다.

**1단계. 계정 만들고 로그인하기**

1. 수업용 인스턴스의 설문 폼에서 안내받은 진입 정보로 계정을 만든다.
2. 접속 주소에서 그 계정으로 로그인한다.
3. 로그인 뒤 화면에 표시되는 n8n 버전을 그대로 기록해 둔다.

로그인에 실패해도 개인 가입, 초대 수락, 비밀번호 설정처럼 다른 인증 방법을 짐작해서 시도하지 않는다. 여러 방식으로 계정을 만들면 어떤 계정이 어떤 권한으로 무엇을 했는지 기록에서 구분하기 어려워진다. 대신 멈춘 화면, 오류 문구, 접속한 주소를 기록한다.

**2단계. 두 노드 흐름 만들기**

1. 새 워크플로를 만든다.
2. **Manual Trigger** 노드를 추가한다. 이 트리거는 Execute workflow 버튼으로 실행할 때만 흐름을 시작하므로, 흐름이 어디서 시작되는지 화면에서 확인할 수 있다.
3. **HTTP Request** 노드를 추가하고 URL에 `https://en.wikipedia.org/api/rest_v1/page/summary/N8n`를 넣는다. 인증 없이 읽을 수 있는 공개 API다.
4. 상태 코드도 출력에서 보려면 HTTP Request 노드의 Options에서 **Include Response Headers and Status**를 켠다. 기본 설정에서는 응답 본문만 출력된다. 이 옵션을 켜면 출력이 `statusCode`, `headers`, `body`로 나뉘고, 응답 필드는 `body` 안에 들어간다.
5. 두 노드를 연결한 뒤 Execute workflow를 누른다.

**3단계. 실행 기록 확인하기**

1. 편집 화면 위쪽의 **Executions** 탭에서 방금 실행한 기록을 연다. 실행 기록 하나는 워크플로 전체가 한 번 실행된 단위이므로, 노드를 편집하는 화면과 실행 한 건을 구별해서 본다.
2. HTTP Request 노드의 출력에서 HTTP 상태 코드와 서버가 돌려준 원본 응답을 찾는다.
3. 원본 응답에서 `title`, `description`, `timestamp`, `content_urls` 필드를 찾는다.

| 관찰 질문 | 확인한 화면 위치 또는 값 |
|---|---|
| Manual Trigger와 HTTP Request 노드를 찾았는가 | |
| 실행은 어디에 기록되는가 | |
| 원본 응답은 어디에 보이는가 | |

### 같은 방식으로 만들 수 있는 흐름

- 설문 폼의 응답을 스프레드시트로 옮긴다.
- 정해진 시각에 공개 API를 읽어 요약을 남긴다.
- 새 메일이나 폼 접수를 감지해 알림을 보낸다.
- 웹페이지의 변화를 확인한다.

다만 n8n에 그 서비스의 노드가 있다는 것만으로 업무를 맡겨도 되는 것은 아니다. 연결할 서비스에 어떤 권한을 주는지, 실패했을 때 무엇이 기록되는지, 사람이 어느 단계에서 결과를 다시 확인할지를 함께 정해야 한다.

## 4. 코딩 에이전트로 n8n 워크플로 만들기

3강에서는 화면에서 흐름을 만들었다. 이번에는 같은 흐름을 코딩 에이전트에게 맡기고, 워크플로 정의와 실행 기록이 어디에 남는지 화면에서 만든 경우와 비교한다.

> 일을 맡긴다는 것은 명령을 대신 실행하게 하는 데서 끝나지 않는다. 결과와 실행 기록을 누가 확인할지도 함께 정하는 것이다.

에이전트가 화면 작업보다 빨리 끝내도, 속도만으로 결과를 믿지 않는다. 에이전트가 한 일과 학생이 확인한 일을 나눠 적어 두면, 6강 판정문의 "확인한 사실"을 채우는 근거가 된다.

| 누가 | 하는 일 |
|---|---|
| 에이전트 | CLI(명령줄 도구) 호출, 워크플로 생성과 조회 |
| 학생 | 생성 전 JSON 검토와 승인, 생성 결과와 실행 근거 확인 |

### 준비

- 코딩 에이전트(Claude Code 등)가 설치돼 있어야 한다.
- npx는 Node.js에 들어 있다. 터미널에서 `node -v`를 실행해 버전이 나오지 않으면 Node.js를 먼저 설치한다.

### 1단계. API 키 발급하기

n8n 화면의 **Settings → n8n API**에서 API 키를 발급한다. API 키는 워크플로 목록 조회·생성·삭제와 실행 기록 조회에 쓰인다. 발급한 키는 에이전트에게 보내는 요청문, 공유 화면, 캡처에 남기지 않는다.

### 2단계. CLI 설정과 연결 확인하기

터미널에서 `npx @n8n/cli`로 설치 없이 n8n CLI를 실행한다. 인스턴스 주소와 API 키를 설정한 뒤 워크플로 목록을 확인한다. `<발급한 API 키>` 자리에는 꺾쇠까지 지우고 1단계에서 받은 키를 넣는다.

```bash
npx @n8n/cli config set-url <인스턴스 주소>
npx @n8n/cli config set-api-key <발급한 API 키>
npx @n8n/cli workflow list
```

설정한 주소와 키는 내 컴퓨터의 `~/.n8n-cli/config.json`에 저장된다. `workflow list` 결과에 3강에서 만든 워크플로가 보이는지 확인한다.

### 3단계. 공식 스킬 설치하기

n8n CLI에는 코딩 에이전트에게 CLI 사용법을 알려 주는 공식 스킬이 들어 있다. 공식 스킬이 다루는 것은 워크플로 조회와 생성, 활성화, 실행 기록 확인, 연결 정보 관리, `--jq`로 값 고르기다. 다음 명령은 Claude Code에 스킬을 전역(모든 프로젝트에서 쓰게) 설치한다.

```bash
npx @n8n/cli skill install --global
```

| 코딩 에이전트 | 스킬 설치 방법 |
|---|---|
| Claude Code | 위 명령 (`--global` 없이 실행하면 현재 프로젝트에만 설치) |
| Cursor | `npx @n8n/cli skill install --target=cursor` |
| Windsurf | `npx @n8n/cli skill install --target=windsurf` |
| opencode, Antigravity | 공식 스킬 설치 대상이 아니며, 같은 CLI를 도구로 사용한다 |

### 4단계. 에이전트에게 워크플로 생성 맡기기

연결 확인 → 정의 검토 → 생성 → 기록 조회의 순서를 한 요청에 담는다. 요청에는 생성 전에 검토할 내용을 분명히 적는다.

```
먼저 workflow list로 이 인스턴스의 연결 상태를 확인해 줍니다. 이어서 Manual Trigger →
HTTP Request(https://en.wikipedia.org/api/rest_v1/page/summary/N8n) 워크플로 정의를
wf.json으로 만들고, 생성 명령을 실행하기 전에 JSON의 노드와 연결을 보여 줍니다.
확인했다는 답을 받은 뒤 생성합니다.
```

에이전트가 보여 준 `wf.json`에는 다음 내용이 들어간다.

| 키 | 들어가는 내용 |
|---|---|
| `name` | 워크플로 이름 |
| `nodes` | 노드의 id, 이름, 종류, 버전, 위치 |
| `connections` | 노드 사이의 연결 |
| `settings` | 워크플로 설정 |

두 노드의 이름, HTTP Request의 URL, 연결을 검토한 뒤에만 생성을 승인한다. **JSON에 적힌 URL로 실제 요청이 나가기 때문이다.** 승인하면 에이전트가 `workflow create --file=wf.json`으로 워크플로를 만든다. 생성 뒤에는 n8n 화면에서 같은 이름의 워크플로를 열어 노드와 연결을 다시 대조한다.

### 5단계. 화면에서 실행하고 에이전트로 실행 기록 조회하기

CLI에는 새 실행을 시작하는 명령이 없다. 그래서 Manual Trigger 워크플로의 첫 실행은 n8n 화면에서 Execute workflow로 한다. 실행한 뒤 에이전트에 "방금 실행을 찾아 상태코드와 원 응답을 보여 줘"라고 요청하면, 에이전트는 `execution list`와 `execution get <실행 ID>`로 기록을 찾아 보여 준다.

- HTTP Request 노드는 응답 상태 코드가 2xx(200번대)일 때만 성공으로 끝난다. 그래서 실행 상태가 `success`이면 2xx 응답을 받은 것이다.
- 상태 코드 값 자체는 3강 2단계의 Include Response Headers and Status 옵션이 이 워크플로에도 켜져 있어야 출력에 나타난다.
- 상태 코드와 원본 응답이 어느 노드 출력에 보이는지는 화면에서 다시 확인한다.

### 더 알아보기: MCP 서버로 실행까지 맡기기

MCP(Model Context Protocol)는 AI 애플리케이션이 외부 도구와 데이터에 연결하는 방식을 정한 표준 규약이다. n8n은 인스턴스 단위의 MCP 서버도 제공한다. 인스턴스 설정에서 MCP 서버를 켜면, CLI로는 할 수 없던 워크플로 실행까지 코딩 에이전트에게 맡길 수 있다(켜고 연결하는 구체적인 절차는 강의에서 다루지 않음).

| MCP 도구 | 하는 일 |
|---|---|
| `validate_workflow` | n8n Workflow SDK 코드를 워크플로로 바꿔 오류가 있는지 검사한다 |
| `create_workflow_from_code` | 검증한 SDK 코드로 워크플로를 만든다 |
| `execute_workflow` | 워크플로를 실행한다. manual 모드를 지정하면 아직 게시하지 않은 버전을 실행한다 |
| `test_workflow` | 외부 서비스 대신 고정 데이터(pin data)를 넣어 워크플로를 실행하고 결과를 기다린다 |
| `get_workflow_execution` | 실행 기록을 조회한다. 각 노드의 실행 상태와 출력 데이터를 확인할 수 있다 |

MCP가 보여 준 JSON도 원본 응답과 대조해 확인한다.

## 5. 워크플로에서 에이전트 사용하기

앞의 두 실습에서 만든 워크플로는 정해 둔 순서대로만 실행됐다. 이번에는 워크플로 중간에 AI가 판단하는 단계를 넣는다. 메일을 가져오고 시트에 기록하는 순서는 그래프가 정하고, 메일을 요약하는 단계만 모델이 맡는다. 1강에서 본 것처럼, 그래프 중간에 모델을 넣어도 워크플로 전체가 에이전트 방식으로 바뀌지는 않는다.

### AI Agent 노드의 구성

AI Agent 노드는 대화 모델에게 작업을 맡기는 노드다. 노드 아래의 연결 단자에 다른 노드를 붙여 쓴다.

| 연결 단자 | 연결할 노드 | 역할 |
|---|---|---|
| Chat Model | 대화 모델 노드 (이 실습에서는 Google Gemini Chat Model) | 입력을 읽고 문장을 만든다. **반드시 연결**해야 한다 |
| Memory | Simple Memory 등 | 이전 대화를 저장해 다음 요청에서 이어 쓴다. 선택 사항 |
| Tool | HTTP Request Tool 등 | 모델이 아직 모르는 사실을 읽어 오거나 작업을 실행한다. 선택 사항 |

### 실습: 오늘 받은 메일을 요약해 Google Sheets에 정리하기

Gmail에서 오늘 받은 메일을 가져와 AI가 요약하고, 그 결과를 Google Sheets에 정리하는 워크플로를 Claude Code에게 맡겨 만든다. 4강 실습처럼 학생은 생성 전에 워크플로 정의를 검토하고, 실행 뒤에는 요약이 원래 메일과 맞는지 확인한다.

완성할 워크플로의 구조(강의 도식 "오늘 받은 메일을 요약해 시트에 정리하는 워크플로"):

```
1. Manual Trigger  : 실행 시작
2. Gmail           : 오늘 메일 가져오기        (자격 증명: Gmail OAuth2)
3. AI Agent        : 메일마다 요약            (Chat Model 단자에 Gemini Chat Model 연결,
                                               자격 증명: Gemini API key)
4. Google Sheets   : 요약을 행으로 추가        (자격 증명: Sheets OAuth2)
```

순서는 그래프가 정하고, 3번 AI Agent 노드만 모델이 판단한다. 괄호 안은 그 노드에 연결할 자격 증명(로그인 정보)이다. Claude Code가 만든 워크플로는 트리거 종류가 다르거나 노드가 더 있을 수 있으므로, 4단계에서 이 구조와 비교한다.

**준비**

- 4강에서 설정한 Claude Code, n8n CLI, 공식 스킬이 필요하다.
- 요약 결과를 기록할 Google 스프레드시트를 하나 만들어 둔다.
- Gmail과 Google Sheets에 연결할 Google 자격 증명은 별도 안내 문서 "Google 자격 증명 만들기"를 따라 만든다. 수업 인스턴스는 직접 운영하는 n8n이므로 Google Cloud에서 OAuth 클라이언트를 직접 만들어야 한다.

> ⚠️ **주의: Gemini API 무료 등급과 메일 데이터** — 이 실습은 메일 내용을 Gemini API에 보낸다. 무료 등급에 보낸 내용과 생성된 응답은 Google이 제품 개선에 쓸 수 있고, 사람 검토자가 읽을 수도 있다. Google은 무료 등급에 민감한 정보, 기밀 정보, 개인 정보를 보내지 말라고 안내한다(출처: Gemini API Additional Terms of Service). 2강의 데이터 경로 질문으로 어떤 메일 내용이 어디로 가는지 확인하고 실습한다.

**1단계. Gemini API 키를 n8n에 등록하기**

1. Google AI Studio의 API 키 페이지(`https://aistudio.google.com/apikey`)에서 API 키를 발급한다.
2. n8n 화면에서 새 자격 증명을 만들고 **Google Gemini(PaLM) Api**를 고른다.
3. Host는 기본값 `https://generativelanguage.googleapis.com`을 그대로 두고, API Key에 발급한 키를 넣어 저장한다.

API 키와 Google 계정 정보는 Claude Code에게 보내지 않고 n8n 화면에서 직접 등록한다. Claude Code가 자격 증명을 만들겠다며 키를 요청하면, 화면에서 직접 등록하겠다고 답한다.

**2단계. Google 자격 증명 등록하기**

별도 안내 문서를 따라 n8n에 Gmail OAuth2 API와 Google Sheets OAuth2 API 자격 증명을 만든다.

**3단계. Claude Code에 워크플로 만들기 요청하기**

```
n8n에 gmail 받아서 오늘 받은 메일만 ai가 요약해서 google sheet에 정리해주는 워크플로 짤 수 있어?
ai는 google ai 무료 api키 쓸 꺼야. 요약은 AI Agent 노드로 해 줘.
생성 전에 워크플로 JSON을 보여 주고, 내가 확인했다고 답하면 생성해 줘.
```

Claude Code가 워크플로 JSON을 보여 주면, 4단계의 표로 검토한 뒤 확인했다고 답해 생성을 승인한다. 시트 이름이나 열 구성을 물으면 준비한 스프레드시트에 맞춰 답한다.

**4단계. 생성 전에 워크플로 정의 검토하기**

| 확인할 것 | 이유 |
|---|---|
| 트리거가 수동 실행인지, 정해진 시각에 실행되는지 | 수동 실행이면 버튼을 누를 때만 실행된다. 정해진 시각 실행이면 워크플로를 켜 둔 동안 자동으로 실행되어 실행 기록이 계속 쌓인다 |
| Gmail 노드가 "오늘 받은 메일"을 어떻게 고르는지 | Received After 필터로 오늘 0시 이후를 고르는지, 검색어로 최근 24시간을 고르는지에 따라 결과가 다르다 |
| Gmail 노드의 Read Status 설정 | 기본값은 읽지 않은 메일만 가져온다. 이미 읽은 오늘 메일이 빠질 수 있다 |
| 요약에 메일 본문이 들어가는지 | Gmail 노드의 Simplify 옵션이 켜져 있으면 제목, 보낸 사람 같은 머리말 위주로 출력돼 본문이 요약에 들어가지 않을 수 있다 |
| 요약 단계에 쓴 노드와 모델 | 요청한 대로 AI Agent 노드인지, 그 Chat Model이 Google Gemini Chat Model인지 확인한다 |
| Google Sheets 노드의 작업과 대상 시트 | 행을 추가하는지, 준비한 스프레드시트와 열 이름이 같은지 확인한다 |
| 메일을 보내거나 지우는 노드가 없는지 | 이 업무는 메일을 읽기만 한다. 외부 상태를 바꾸는 노드가 있으면 생성을 승인하지 않는다 |
| JSON에 API 키나 비밀번호가 없는지 | 자격 증명은 이름으로만 연결되고, 실제 값은 n8n 화면에서 등록한다 |

**5단계. 화면에서 자격 증명을 연결하고 실행하기**

1. n8n 화면에서 생성된 워크플로를 연다.
2. Gmail, Google Gemini Chat Model, Google Sheets 노드마다 1·2단계에서 만든 자격 증명을 고른다.
3. Execute workflow로 실행한다.

오늘 받은 메일이 많으면 모델 호출도 메일 수만큼 늘어나고, 무료 등급의 호출 한도에 걸릴 수 있다.

**6단계. 실행 기록과 결과 확인하기**

Executions 탭에서 실행 기록을 열고 다음 표를 채운다. 요약은 모델이 만든 문장이라 원래 메일과 다를 수 있다. 실행 기록에서 요약 노드의 입력(메일 내용)과 출력(요약)을 나란히 놓고, 빠지거나 바뀐 내용이 있는지 확인한다.

| 관찰 질문 | 확인한 값 |
|---|---|
| Gmail 노드가 가져온 메일 수 | |
| 요약 단계에 쓴 노드와 모델 | |
| 메일 한 통을 골라 원래 내용과 요약을 대조한 결과 | |
| 스프레드시트에 추가된 행 수 | |

### 흐름을 판정하는 기준

지금까지 화면, CLI, 코딩 에이전트로 워크플로를 만들고 실행 기록을 봤다. 이 관찰을 내 업무의 판정에 쓰려면 두 가지를 함께 본다.

1. 실행 기록에 무엇이 남는가
2. 워크플로가 어떤 계정 권한으로 무엇을 읽고 쓰는가

먼저 업무를 한 문장으로 좁힌다. 이 강의의 예시 업무는 "매일 공개 API에서 정보를 읽어 짧은 요약을 만듭니다"로 정리할 수 있다.

| 업무 문장 | 드러나는 것 |
|---|---|
| "고객 지원 자동화" | 입력과 확인 범위가 넓어 판정하기 어렵다 |
| "매일 오전 새로 들어온 공개 문의를 읽고 담당자가 확인할 세 줄 요약을 만듭니다" | 읽는 대상, 결과를 받는 사람, 사람이 확인하는 지점이 드러난다 |

업무 판단의 순서(강의 흐름도):

```
1. 반복 업무를 한 문장으로 적는다
2. 입력과 산출물(결과물)을 적는다
3. 허용할 권한과 검증 신호(결과가 맞는지 확인할 표시)를 적는다
4. "지금 근거로 판정할 수 있는가?"
      ├─ 검증 가능 → 도입 : 작은 범위로 시작한다
      ├─ 미확인     → 보류 : 빈 사실을 확인한다
      └─ 통제 불가 → 거절 : 현재 조건에서는 멈춘다
```

판정문은 6강에서 작성한다.

### IF 노드로 분기 만들기

지금까지의 워크플로는 입력이 들어오면 같은 순서로 노드를 실행했다. 실제 업무에서는 받은 값의 상태에 따라 다음 행동이 달라져야 한다. n8n의 **IF 노드**는 정해 둔 조건을 검사해 실행 경로를 true와 false로 나눈다.

3강의 Manual Trigger → HTTP Request 워크플로 뒤에 IF 노드와 AI Agent 노드를 이어 붙인다. IF 노드는 공개 API 응답에 title과 description이 모두 있는지 검사한다.

```
HTTP Request(Wikipedia API) → "title과 description이 모두 있는가?"
      ├─ TRUE  → AI Agent (한 문장 요약)
      └─ FALSE → 확인 필요 기록 또는 담당자 검토
```

1. HTTP Request 노드 뒤에 IF 노드를 추가한다.
2. 첫째 조건으로 title이 비어 있지 않은지 확인한다.
3. 둘째 조건으로 description이 비어 있지 않은지 확인한다.
4. 두 조건을 모두 만족해야 true 경로로 보내도록 설정한다.
5. true 경로에 AI Agent 노드를 연결해 한 문장 요약을 만들게 한다. Chat Model에는 앞 실습에서 만든 Google Gemini 자격 증명을 쓴다. 프롬프트는 **Define below**로 바꾸고, 요약할 title과 description을 프롬프트에 넣는다.
6. false 경로에는 처리를 멈추거나 확인이 필요하다는 결과를 남기는 노드를 연결한다.

HTTP Request 노드에서 Include Response Headers and Status 옵션을 켰다면 응답 필드는 body 안에 있으므로 `body.title`, `body.description`을 검사한다.

> IF 노드의 분기는 AI의 판단이 아니라, 같은 입력에는 언제나 같은 결과를 내는 명시적인 규칙이다.

다음처럼 조건을 값으로 분명하게 적을 수 있을 때 알맞다.

- 필드가 비어 있는가
- 상태 코드가 200인가
- 점수가 기준 이상인가

실행 기록에서는 어떤 조건이 참이었고 어느 경로가 실행됐는지 확인할 수 있다. IF 노드는 잘못된 입력이 다음 단계로 넘어가지 않도록 막는 역할도 한다. 그래서 false 경로를 비워 두기보다 오류 기록, 재시도, 사람의 확인 단계와 연결하는 편이 좋다. false 경로에서 무엇을 할지도 워크플로를 만들 때 함께 정한다.

### 에이전트가 다음 행동을 선택하게 하기

모든 업무 조건을 "값이 비어 있는가"처럼 미리 나열할 수는 없다. 다음과 같은 판단이 필요하면 AI Agent 노드를 쓴다.

- 입력 문장의 의도를 해석한다.
- 현재 정보만으로 답할 수 있는지 판단한다.
- 필요한 도구를 고른다.

AI Agent 노드에 조회 도구를 연결하면, 모델은 질문을 읽고 도구를 호출할지 판단한다. 새로운 사실이 필요하면 도구를 호출하고, 이미 받은 내용을 다른 형식으로 바꾸는 요청이라면 대화 맥락의 정보만 쓴다.

예: Wikipedia 요약 API를 조회 도구로 연결했다면

- "N8n 문서의 제목과 설명은 무엇인가" → 도구를 호출한다.
- 이어서 "방금 받은 제목과 설명을 한 문장으로 정리해 줘" → 도구를 호출하지 않아도 된다.

실행 기록의 도구 호출 여부로 둘을 구별할 수 있다. 이처럼 에이전트는 고정된 한 경로를 실행하는 대신, 목표와 현재 상태를 바탕으로 다음 행동을 고른다.

AI Agent가 다음 행동을 고르는 방식(강의 도식):

```
사용자 요청 → AI Agent가 다음 행동을 판단
      ├─ 새 사실 필요 → 조회 도구 호출 → 결과 확인 → 답변
      ├─ 정보 충분   → 도구 호출 없이 형식만 바꿔 답변
      └─ 근거 부족   → 부족한 정보를 표시하거나 사람에게 확인 요청
```

조회 도구를 여러 개 연결하면 더 다양한 질문을 처리할 수 있다. 예를 들어 문서 정보를 읽는 도구와 서비스 상태를 확인하는 도구를 함께 연결하면, 에이전트는 질문에 필요한 도구를 골라 호출한다. 한 번의 호출로 정보가 부족하면 결과를 확인한 뒤 다른 도구를 호출하거나 질문을 좁힐 수도 있다.

다양한 질문을 처리하게 하려고 에이전트에게 모든 권한을 줄 필요는 없다. 허용한 도구 안에서 다음 행동을 고르게 하면 된다.

- 처음에는 공개 데이터를 읽는 **조회 도구**만 연결하고, 호출 횟수와 처리 범위를 작게 제한한다.
- 발송, 수정, 삭제처럼 외부 상태를 바꾸는 **변경 도구**가 필요하면, 사람 승인(human-in-the-loop, HITL)이나 별도의 IF 조건을 통과한 뒤에 실행하도록 한다.

### IF 노드와 AI Agent 노드 비교

IF 노드와 AI Agent 노드는 서로를 대신하지 않는다. IF 노드는 명시한 조건을 안정적으로 판정하고, AI Agent는 모든 경우를 미리 규칙으로 적기 어려운 요청을 해석한다.

| 구분 | IF 노드 | AI Agent 노드 |
|---|---|---|
| 판단 기준 | 미리 작성한 조건 | 입력의 의미와 현재 맥락 |
| 같은 입력의 결과 | 같은 경로로 분기한다 | 모델과 도구 결과에 따라 달라질 수 있다 |
| 알맞은 업무 | 값, 상태, 수치 검사 | 의도 해석, 도구 선택, 요약 |
| 확인할 기록 | 조건 결과와 실행 경로 | 도구 호출, 도구 결과, 최종 답변 |
| 주요 통제 | 조건식과 예외 경로 | 도구 권한, 지시문, 호출 범위, 사람 승인 |

> 💡 분명한 규칙은 IF 노드에 맡기고, 해석이 필요한 부분은 제한된 도구를 가진 AI Agent에 맡긴다. 실행 기록에서 분기 조건과 도구 호출을 함께 확인할 수 있다면, 어떤 결과가 규칙에 따른 것이고 어떤 결과가 AI의 판단에 따른 것인지 구별할 수 있다.

## 6. 업무 판정: 도입, 보류, 거절

화면 조립, 에이전트 위임, 실행 기록 대조에서 관찰한 사실을 업무 판정으로 정리한다. 도구 소개나 써 본 느낌이 아니라, 실행 기록과 관찰 표에 적은 사실을 근거로 고르기 위해서다. 무엇을 맡길지뿐 아니라 어디까지 맡기고 무엇을 계속 확인할지도 함께 정한다.

| 판정 | 고르는 경우 |
|---|---|
| 도입 | 필요한 기능, 책임 범위, 확인 절차가 업무 조건 안에서 확인됐을 때 |
| 보류 | 쓸모는 보이지만 안전성, 권한, 운영 조건처럼 아직 확인하지 못한 사실이 남았을 때 |
| 거절 | 확인한 위험이나 비용이 업무의 목적과 맞지 않아, 현재 조건에서는 맡기지 않기로 정했을 때 |

어느 판정이든 근거와 다시 살필 조건을 함께 적어 둔다. 그 조건이 확인되면 같은 판정문을 고쳐 다시 판정할 수 있다.

### 판정문 작성하기

판정문은 한 쪽 분량이다.

| 항목 | 작성 기준 |
|---|---|
| 검토할 업무 | 한 문장으로 적는다 |
| 확인한 사실, 미확인 사실 | 둘을 나눠 적는다. 앞 실습에서 채운 관찰 표와 실행 기록을 확인한 사실의 근거로 쓴다 |
| 판정 | 도입, 보류, 거절 중 현재의 선택을 적는다 |
| 재검토 조건 | 어떤 사실이 확인되면 선택을 바꿀 수 있는지 적는다 |

예시: 공개 API를 읽고 내부 메모를 만드는 업무

| 항목 | 예시 |
|---|---|
| 검토할 업무 | 공개 API를 읽고 내부 메모를 만든다 |
| 확인한 사실 | 실행 기록에 상태 코드와 원본 응답이 남는다. 도입을 검토할 근거가 된다 |
| 미확인 사실 | 데이터 보관 위치, 쓰기 권한 |
| 판정 | 보류 |
| 재검토 조건 | 운영 환경과 보관 위치를 확인한다. 쓰기 권한의 범위까지 확인되면 그 기록을 바탕으로 도입 여부를 다시 검토한다 |

### 같은 업무도 판정이 다를 수 있다

어떤 업무에서는 실행 기록이 충분한 근거가 되지만, 다른 업무에서는 보관 위치나 권한 범위를 먼저 확인해야 한다. 판정의 차이는 무엇을 관찰했고 무엇이 아직 확인되지 않았는지에서 생긴다. 그래서 판정문에는 결론과 함께 근거를 적는다. 같은 업무를 다르게 판정했다면 근거를 나란히 놓고 무엇이 다른지 비교할 수 있다.

## 7. n8n 셀프 호스팅 (선택 심화)

필수 내용은 6강의 판정까지다. 이 강의는 판정한 워크플로를 직접 운영해 볼 학생을 위한 선택 심화로, 수업 인스턴스에 있던 워크플로와 실행 기록을 내 컴퓨터나 서버로 옮길 때 어떤 운영 책임이 생기는지 확인한다.

### 셀프 호스팅과 운영 책임

**셀프 호스팅**은 다른 회사가 운영하는 환경 대신 내가 관리하는 컴퓨터나 서버에서 n8n을 실행하는 것이다. n8n은 Sustainable Use 라이선스를 따르는 fair-code 소프트웨어여서 이렇게 직접 실행할 수 있다.

| 환경 | 운영 주체 |
|---|---|
| n8n Cloud | n8n |
| 수업 인스턴스 | 수업 운영 환경 |
| 셀프 호스팅 | 나 |

- 셀프 호스팅에서는 실행 환경, 데이터 보관, 업데이트, 장애 대응을 내가 관리한다.
- 워크플로 정의, 실행 기록, 연결에 쓰는 비밀값이 어디에 남는지 확인한다.
- 백업, 삭제, 접근 권한 회수를 내가 설계하고 확인한다.

> 데이터가 내 컴퓨터에 있다고 해서 안전하다고 판단하지 않는다. 그 컴퓨터에 누가 접근하는지, 백업이 있는지, 비밀값이 어디에 저장되는지를 따로 점검한다.

### 셀프 호스팅 구성 요소

| 구성 요소 | 뜻 | 쓰는 경우 |
|---|---|---|
| 127.0.0.1:5678 | 127.0.0.1은 지금 쓰는 컴퓨터 자신을, 5678은 n8n 화면이 열리는 기본 포트(창구 번호)를 가리킨다 | 혼자 살펴보는 로컬 실행. 도메인과 HTTPS 없이 시작하며, 컴퓨터를 끄면 n8n도 멈춘다 |
| 도메인, HTTPS | 다른 사람이 인터넷으로 접속할 주소, 통신 암호화, 누가 접속할 수 있는지를 관리한다 | n8n을 외부에 공개할 때 |
| Docker, 컨테이너 | Docker는 앱과 실행에 필요한 환경을 컨테이너라는 독립된 실행 단위에 함께 담아 실행한다. 운영체제마다 필요한 프로그램을 따로 맞추는 수고를 줄인다 | 같은 이미지로 내 컴퓨터와 서버에서 비슷한 조건으로 실행할 때. 셀프 호스팅을 시작할 때 널리 쓴다 |
| 볼륨 | 컨테이너 바깥에 데이터를 남겨 두는 저장 공간 | 이미지를 바꾸거나 컨테이너를 다시 띄운 뒤에도 워크플로와 설정을 이어서 쓸 때 |
| SQLite | n8n의 기본 데이터베이스로, 데이터를 내 컴퓨터의 파일 하나에 저장한다 | 혼자 관찰하거나 가볍게 실습할 때 |
| PostgreSQL | 따로 실행하는 데이터베이스 프로그램에 데이터를 저장한다 | 여러 사람이 계속 쓰거나 백업과 복구를 운영해야 할 때 권장 |
| Redis, queue mode | 기본 구성에서는 실행 프로세스 하나가 모든 작업을 처리한다. queue mode에서는 Redis가 작업 대기열을 관리하고 여러 실행 프로세스가 작업을 나눠 처리한다 | 실행이 많이 겹칠 때. 처리량은 늘지만 Redis와 실행 프로세스 상태, 실패한 작업 기록까지 확인할 대상도 늘어난다 |
| Kubernetes(k8s) | 컨테이너를 여러 서버에 배치하고, 멈춘 컨테이너를 다시 실행하며, 접속량에 따라 컨테이너 수를 조절한다. n8n은 Kubernetes용 Helm 차트 배포를 지원한다 | 여러 서버에서 지속적인 서비스를 운영할 때. 개인 로컬 환경에는 관리할 것이 너무 많아 쓰지 않는다 |

컨테이너와 볼륨은 역할이 다르다. 컨테이너를 지우고 새로 만들면 그 안의 임시 파일도 함께 삭제되므로, n8n 데이터는 볼륨에 연결해 둔다. 볼륨이 실제로 저장되는 위치와 백업 방법은 Docker 설정과 운영체제에 따라 다르므로 직접 확인한다.

### 상황별 구성 고르기

구성은 규모가 아니라 **운영 책임**에 따라 고른다. 아래쪽 구성일수록 관리할 대상이 늘어난다. 내 워크플로가 멈췄을 때 누가 확인하고 복구할 수 있는지에 맞춰 고른다.

| 상황 | 검토할 구성 | 함께 확인할 운영 책임 |
|---|---|---|
| 혼자 관찰 | 로컬 실행 + SQLite | 컴퓨터와 데이터 파일의 보관과 백업 |
| 소규모 팀 | Docker + PostgreSQL | 접근 권한, 데이터베이스 백업, 업데이트 |
| 실행이 많이 겹침 | Docker + PostgreSQL + Redis queue mode | 대기열, 실행 프로세스 상태, 실패한 작업의 기록 |
| 여러 서버를 운영 | Kubernetes 배포 | 배포 상태, 장애 복구, 권한과 비용 |

### 실습(선택): 로컬에서 Docker로 n8n 띄우기

**준비**: Docker가 설치돼 있고 실행 중이어야 한다. Windows와 macOS에서는 Docker Desktop을 실행해 둔다.

**1단계. 코딩 에이전트에게 실행 요청하기** — 목적과 조건을 함께 전달한다.

```
로컬에서 n8n을 Docker로 띄워 줘. 포트는 5678로 열고, 데이터는 볼륨에 남겨 줘.
실행 뒤에 확인할 주소와 생성된 파일·볼륨도 설명해 줘.
```

제안된 설정을 그대로 믿지 않고, 사용한 이미지, 포트, 볼륨을 다시 읽어 확인한다. n8n 공식 문서의 Docker 실행 예는 다음과 같다. 에이전트가 제안한 명령과 비교해 본다.

```bash
docker volume create n8n_data
docker run -it --rm --name n8n -p 5678:5678 -v n8n_data:/home/node/.n8n n8nio/n8n
```

| 옵션 | 하는 일 |
|---|---|
| `-p 5678:5678` | 내 컴퓨터의 5678 포트를 컨테이너의 n8n 화면에 연결한다 |
| `-v n8n_data:/home/node/.n8n` | n8n 데이터를 n8n_data 볼륨에 저장한다 |
| `--rm` | 컨테이너가 멈추면 컨테이너를 지운다. 데이터는 n8n_data 볼륨에 남는다 |

공식 문서는 Docker Compose를 이용한 설치를 권장한다. 위 명령은 로컬에서 살펴보기 위한 최소 구성이다.

**2단계. 실행 확인하기**

1. 브라우저에서 `http://127.0.0.1:5678`을 열어 n8n 화면이 보이는지 확인한다.
2. 새 터미널에서 `docker ps`를 실행해 n8n 컨테이너가 계속 동작하는지 확인한다.
3. 화면이 열리지 않으면 포트 충돌, 컨테이너 중지, 이미지 내려받기 실패처럼 확인할 수 있는 원인부터 살펴본다.
4. 비밀번호나 API 키가 요청문, 터미널 기록, 공유 화면에 남지 않았는지 확인한다.
