> **한 줄 요약** — 점검(재위임 루프)·종합·평가 노드를 채워 딥리서치 에이전트를 완성했다. 리서처의 자기 신고와 라운드 제한으로 재위임 루프를 설계하고, 정답표 없이 쓸 수 있는 평가 지표로 장치를 하나씩 끄는 소거 실험을 진행했다.

## 1. 진행 상황

지난 시간까지 **① 기획 → ② 배치 → ③ 조사**를 구현했다.

코디네이터가 목차를 작성해 각 절의 조사 작업을 나누면, 4개의 서브에이전트가 `Send`를 통해 동시에 실행되어 문서를 읽고 각 절의 원고를 작성한다.

### 학습 목표

1. **자기 신고**와 **라운드 제한**을 활용해 재위임 루프의 실행 및 종료 조건을 설계할 수 있다.
2. 정답표 없이 **근거 비율, 허위 인용, 편중, 중복률**을 기준으로 보고서의 품질을 평가하는 지표를 만든다.
3. 장치를 하나씩 비활성화하는 **소거 실험**으로 각 장치의 효과를 확인하고, 평가 지표가 발견하지 못하는 문제를 직접 보고서를 읽으며 찾아낼 수 있다.

### 전체 구조

```
                    ┌─ 리서치 1 ─┐
질문 → 기획 → 배치 ──┼─ 리서치 2 ─┼→ 점검 → 종합 → 평가
                ↑   ├─ 리서치 3 ─┤    │
                │   └─ 리서치 4 ─┘    │
                └──── 수정 필요 ───────┘
```

## 2. 점검 노드 — 자기 신고와 재위임 루프

이 절에 **수정이 필요한지**를 판단하는 노드다.

> 판단을 내리는 쪽이 원고를 직접 읽어야 할까?
> → 정확도는 높아지지만 **에이전트 간 정보 격리가 깨진다.**

### 판단 방법 비교

| # | 방법 | 장점 | 단점 |
|---|---|---|---|
| 1 | **코드 규칙**으로 판단 (예: 인용 수가 k개 미만이면 부족) | 결정적. 같은 원고에는 항상 같은 판단. LLM 호출 X, 추가 비용 X | 무엇이 부족한지 모름 → 찾아야 할 것이 구체적이지 않아 같은 내용을 반복할 가능성 |
| 2 | **리서처가 스스로 신고** | 직접 작성한 리서처가 근거 부족을 판단 가능. 부족한 부분을 구체적인 문장으로 전달 가능. 기존 원고에 '충분/부족' 필드만 추가 → 별도 LLM 불필요 | 모델은 자기 작업을 높게 평가하는 경향. '부족'의 기준을 이해하지 못할 가능성 |
| 3 | **코디네이터가 읽고 직접 판단** | 전체 원고를 보기 때문에 더 정확 (중복·오류 발견이 쉬움) | 에이전트 간 정보 격리가 깨짐 |
| 4 | **별도의 판정 모델**로 평가 (원고 + 참고 자료 전달) | 문장마다 근거를 확인하면 사람의 검수에 가까워짐 | 평가 과정 자체가 또 하나의 불확실한 단계가 됨 (LLM이기 때문) |

→ **2번 채택.** 무엇이 부족한지 알 수 있으면서 추가 비용이 없는 선택지다.
재위임에는 "이 부분의 근거가 부족하니 관련 자료를 찾아라" 같은 **구체적인 지시**가 필요하기 때문이다.

### 재위임이 효과를 내기 위한 조건

한 번의 조사로 끝내는 방식 vs 부족한 부분을 찾아 한 번 더 조사하는 **재위임** 방식.
재위임이 의미 있으려면:

1. 첫 번째 라운드에서 모든 자료를 확인할 수 없어야 한다.
2. 두 번째 라운드에서는 첫 라운드에서 놓친 부분을 파악해 필요한 자료를 **선택적으로** 조사해야 한다.

### 검증 방법

자기 신고로 시작된 재위임 루프가 실제로 부족한 부분을 보완하는지 확인한다.

| 지표 | 확인 내용 | 이상 신호 |
|---|---|---|
| **재위임된 절 수** | 질문 하나당 몇 개의 절이 '부족'으로 신고됐는지 | 0에 가까우면 자기 신고가 거의 발생하지 않아 루프가 작동하지 않음 |
| **재위임 전후 절 길이·인용 수** | 재위임된 원고가 길어지고 인용이 늘었는지 | 수치가 그대로면 추가 조사 내용이 원고에 반영되지 않은 것 |
| **2라운드에서 새로 읽은 문서 수** | 재위임된 리서처가 실제로 새 문서를 조사했는지 | 재조사 기회가 있었는데도 새 문서가 없다면 조사 후보가 모두 소진된 것 |

세 가지는 리서처 에이전트의 로그를 **1라운드 / 2라운드로 나눠 비교**하면 확인할 수 있다.

> **로그는 바쁜데 결과물은 그대로**라면 문제가 있다.
> 대부분 1라운드와 2라운드의 후보가 동일할 때 문제가 생긴다 → 재위임 지시에 **무엇이 부족한지 구체적인 정보**가 필요하다.

### review 노드

리서처의 신고를 모아 **부족한 절 목록**을 만드는 역할.
코디네이터는 원고 품질을 직접 판단하지 않고, **신고 내용을 집계해 재조사 대상만 결정**한다.

처리해야 할 것:

1. **중복 신고 처리** — 재위임 과정에서 같은 절이 여러 번 제출되면 가장 마지막에 제출된 원고만 반영
2. **라운드 제한** — 코드의 최대 바퀴 설정으로 재위임 횟수를 제한해 무한 루프 방지
3. **재조사 지시 전달** — 부족한 부분을 구체적으로 정리해 다음 라운드의 조사 지시에 포함

### 루프 종료 조건

| 기준 | 조건 | 의미 |
|---|---|---|
| **내용 기준** | 더 이상 '부족'으로 신고된 절이 없을 때 | 완성 |
| **횟수 기준** | 설정한 최대 라운드를 다 돌았을 때 | 강제 종료 |

**두 가지를 함께 쓰는 이유**

- **횟수만** 있으면 → 이미 내용이 충분한데도 횟수를 채우느라 불필요한 토큰을 낭비할 수 있다. 반대로 횟수 안에 조사가 불충분해도 그냥 종료될 수 있다.
- **내용 기준만** 있으면 → LLM이 만족할 때까지 끝없이 재조사할 위험이 있다.

## 3. 종합 노드 — 편집 범위와 보고서 완성

네 개의 원고를 이어 붙이면 보고서가 완성된다.
다만 **문체 통일, 중복 내용 정리**를 위해 원고를 다시 작성·검토할지 고민이 필요하다.

원고를 다시 작성할 때의 문제점:

1. 에이전트 간 정보 격리가 깨진다.
2. 재작성 과정에서 인용이 누락될 수 있다.

### 편집자가 리서처의 원고를 어떻게 처리할까?

| # | 방법 | 장점 | 단점 |
|---|---|---|---|
| 1 | **원고는 그대로 이어 붙이고 머리말·맺음말만 작성** | 컨텍스트 윈도우 관리. 인용 보존 | 문체와 문장 흐름이 제각각. 중복 가능성 |
| 2 | 모든 절을 읽고 편집자가 보고서 전체를 다시 작성 | 흐름이 자연스러움 | 정보 격리가 깨지고 인용 정확성이 떨어짐. 허위 인용 가능성 |
| 3 | 절마다 별도의 편집자에게 보내 수정 | 정보 격리 유지, 문장 다듬기 가능 | 절 사이의 문제(중복, 내용 모순)는 해결 못 함. LLM 호출 비용만 증가 |
| 4 | 원고 수정 없이 그대로 이어 붙임 | 추가 LLM 호출 0 → 비용 최소. 인용 보존 | 전체 흐름이 부족. 리서치 보고서보다는 여러 조사 메모에 가까움 |

→ **1번 채택.** 이유는 **인용의 정확성**.
단점인 내용 중복·모순은 기획 단계에서 목차를 내용별로 나눴기 때문에 겹칠 가능성이 낮다고 판단했다.

### Synthesize 작업

1. **중복 원고 정리** → 가장 마지막 원고 사용
2. **절 순서 정렬**
3. **보고서 완성** — 편집자가 작성한 머리말·맺음말을 각 절의 원고와 이어 붙임

> 편집자(종합 노드 안에서 머리말·맺음말을 쓰는 LLM)에게는 **절 제목 + 첫 90자만** 전달한다.

완성된 보고서에서 확인할 점:

1. 인용이 하나도 없는 절이 있는지
2. 질문 범위를 벗어난 절이 있는지

## 4. 평가 노드 — 정답표 없는 평가 지표

구현한 기능을 하나씩 비활성화한 뒤 비교하는 실험(**소거 실험**)으로 각 기능이 실제로 효과가 있는지 확인한다.
여기서 쓰는 평가 지표가 곧 소거 실험에 사용할 지표(Metric)다.

### 평가 지표의 세 가지 조건

1. 설정을 바꿔도 **평가 기준은 동일**해야 한다.
2. 같은 입력에는 **항상 같은 결과**가 나와야 한다.
3. **어떤 기능이 문제를 일으켰는지** 파악할 수 있어야 한다.

### 평가 방법 비교

| # | 방법 | 한계 |
|---|---|---|
| 1 | 글자 수와 인용 개수 측정 | 장치를 껐을 때 지표가 어느 방향으로 변해야 하는지 판단 불가. 보고서가 짧아진 게 품질 저하인지, 불필요한 내용이 줄어든 건지 알 수 없음 |
| 2 | **네 가지 항목 측정** (근거 비율, 허위 인용, 읽고 안 쓴 문서, 최다 문서 편중) | 각 지표가 특정 장치의 성능과 연결됨 ↔ 글의 품질 자체는 판단 불가 |
| 3 | 모델에게 보고서 채점 | 매번 같은 점수를 보장할 수 없음 |
| 4 | 사람이 직접 판단 | 자동화 불가능 |

→ **2번 채택.** 장치를 껐을 때 "문서 편중이 먼저 높아진다"처럼 **구체적인 변화**를 확인할 수 있다.

**한계** — 인용이 실제로 해당 문장의 근거가 되는지는 확인할 수 없다.
→ **오귀속 문제**: 실제로 읽은 문서라도 엉뚱한 문장에 연결될 수 있다.

### 지표별 평가 영역

| 지표 | 평가 대상 | 내용 |
|---|---|---|
| **최다 문서 편중, 중복률** | 배정 구역 | 인용이 특정 문서에 집중되어 있는지, 같은 문서를 여러 절에서 중복해 읽었는지 |
| **읽고 안 쓴 문서** | 배정 품질 | 문서를 읽었지만 최종 보고서에서 한 번도 활용하지 않은 경우 → 코디네이터가 적절하지 않은 문서를 배정했을 가능성 |
| **근거 비율** | 조사 깊이, 재위임 효과 | 전체 문장 중 '문서명' 인용이 포함된 문장의 비율. 절반이 안 되면 자료에 근거하지 않은 내용이 많다는 의미 |
| **허위 인용** | 반드시 확인 | **무조건 0이어야 한다** |

### 평가 기준

- **허위 인용** → 명백한 실패
- 그 외에는 보고서의 품질을 비교해 우선순위를 정한다.
  - 자동 측정 지표는 **걸러내는 용도**로만 쓰고, 결과물은 **사람이 최종 판단**한다.

> **단일 에이전트**는 문서 한 건만 읽어도 답할 수 있는 질문에 적합하다. 이런 질문은 오히려 문서를 많이 읽을수록 정확도가 떨어진다.

## 5. 소거 실험 결과

| 끈 장치 | 결과 |
|---|---|
| **배정·구역** | **가장 나빠짐** (질문이 바뀌어도 일관됨). 중복률·문서 편중 상승, 읽은 문서 수 감소. LLM 호출 수 증가 → 여러 에이전트가 같은 문서를 반복해서 읽었다는 뜻 |
| **역할** | 질문에 따라 다름. 질문이 역할을 요구할 때만 효과 있음 |
| **재위임** | 이번 실험에서는 효과 없음 |

### 재위임이 효과가 없었던 이유

재위임 발생 → 두 번째 원고가 기존 원고를 **덮어씀** → 인용이 빠질 가능성 증가

**해결 방법** — 두 번째 원고가 첫 번째를 무조건 덮어쓰지 않게 한다. 둘 중 더 좋은 쪽을 선택하거나, 두 개를 비교해 합치면 품질 저하를 줄일 수 있다.

### 실험 설계 원칙

- 비활성화 스위치는 **설정 딕셔너리 한 곳**에 모으고, **한 번에 하나씩만** 끈다.
- 평가 기준이 정답표에 의존하지 않아야 설정을 바꿀 때마다 평가 기준을 새로 만들 필요가 없다.

## 6. 결과 해석 — 지표가 못 잡는 문제 찾기

1. **`인용점검()`** — 표시되는 문장과 해당 문서의 첫머리를 대조한다.
   → 자동 평가 지표가 발견하지 못하는 문제를 확인
2. **`흐름()`** — 최종 보고서에 포함되지 않은 절이 있는지 확인한다.
3. **`목록()`** — 배정 구역 설정을 끈 경우의 문서 편중을 확인한다.
   → 특정 사건에 내용이 집중되어 있음을 알 수 있다.
4. **Q1 보고서 읽기** — 답변에 필요한 내용이 문서 한 건에 있는 경우, 보고서가 지나치게 길어질 수 있다.
   → 멀티 에이전트 구조를 쓸지 판단하는 근거

> 문장에 인용이 붙어 있는데 내용은 **다른 사건**인 경우 → **오귀속은 자동으로 잡히지 않는다.** 사람이 직접 읽어야만 찾을 수 있다.
