## 백엔드의 구성

서버단에서 돌아감 — 백엔드(서버 안에서 돌아가는 프로그램), 서버(DB)

## 네트워크의 기본

> 💡 이름을 주소로 - 도메인과 DNS · 그 주소엔 무엇이 - 서버와 호스팅(그 서버가 사는 곳: 내부망/외부망) · 어느 문으로 - 포트와 방화벽 · 무슨 말로 - HTTP와 HTTPS(그리고 데이터가 여행하는 법)

### IP

- 컴퓨터가 실제로 통신할 때 사용하는 주소
- 국가별로 IP 주소 할당량이 존재

### 도메인

- 사람을 위한 이름, 사람이 보기 쉽게 만든 주소
- 서버를 옮겨도 주소는 그대로
- 한 사이트에 여러 사람이 접속해도 여러 서버로 나눌 수 있음, 지역별로 가까운 서버로 안내
- 서브 도메인의 구조화: 하나의 도메인 아래 여러 서브 도메인을 구분해서 둘 수 있고, 각 서브 도메인마다 다른 서버로 연결 가능
- 신뢰할 만한 사이트임을 인증: 도메인과 연결된 내 PC(IP)가 인증받는 게 아니라 HTTPS 자물쇠(인증서)가 도메인에 발급됨
- 호스팅 업체가 바뀌어도 내 도메인은 바뀌지 않음

### DNS (Domain Name System)

IP와 도메인 연결 시스템. 사람이 읽는 도메인 이름을 IP 주소 등 네트워크 정보로 찾아주는 시스템

### 서버 / 호스팅

- 서버: 내 파일과 데이터를 올려두고 24시간 켜져 있는 컴퓨터
- 호스팅: 늘 켜져 있는 컴퓨터를 빌려 쓰는 것 (클라우드 서비스 — 아마존, 구글과 같은 서비스)

### 네트워크 — 내부망과 외부망 / 공유기

**외부망(WAN)**: 전 세계의 네트워크

- 공인 IP: KT가 공인 IP 100개를 받았다고 100명만 접속 가능한 게 아님. IP에 100명이 동시 접속하는 게 아니라서 IP를 돌려막음 ⇒ 유동 IP. 고정 IP는 별도 가입(더 비쌈)
- 케이블TV 업체는 공인 IP 할당이 더 적음 (예: 5개로 100명 이용) → 공유기 사용. 아파트 하나에 공인 IP 가진 공유기 하나 놓고 사용하는 식이며, 이런 경우 다른 곳에서 내부 IP로 접근 불가(공유기 세팅이 불가하기 때문)

**내부망(LAN)**: 내부 IP

- 전 세계 인터넷망은 공인 IP까지만 접근 가능, 내부 IP는 접근 불가 ⇒ 사설 IP는 인터넷에서 직접 라우팅할 수 없음
- 접근하려면 공유기 세팅 → 공유기 포트별로 컴퓨터 포트와 연결 세팅해놓음 (포트포워딩)

### 포트와 방화벽

- 한 대의 서버 컴퓨터로 여러 가지 통신을 할 수 있는 문
- IP가 건물 주소라면 포트는 그 건물 안의 호실 번호
- 방화벽: 포트를 관리

### HTTP / HTTPS

통신 규약 / 브라우저와 서버의 공통 언어. HTTP는 보안에 취약 → 보안을 강조한 게 HTTPS

**HTTPS**

- 공개키: 내용물을 넣고 잠글 수만 있음(풀 수는 없음). 잠그는 역할만 하는 키 → 해커가 탈취해도 잠그는 키라 열 수 없음
- 개인키: 공개키로 잠근 것을 열 수 있는 키 → 서버만 가지고 있음
- 세션키: 내 컴퓨터와 서버 사이에 데이터를 주고받을 때 자물쇠를 채워서 주고받는 키
  - 공개키 ↔ 개인키로만 소통하면 느림
  - 흐름: 서버가 공개키를 접속한 PC들에게 뿌림 → 개인 컴퓨터는 세션키를 공개키로 잠근 후 서버에 전달 → 서버가 세션키 정보를 얻음 → 그 이후부터는 세션키로만 대화 (세션키는 외부로 유출된 적 없음)
  - ⇒ 이 첫 인사 과정을 **TLS 핸드셰이크**라고 함

> 💡 HTTP 상태 코드 - 인터넷의 신호등
> - 2xx = 성공, 초록불, 통과
> - 3xx = 다른 데로, 노란불, 우회(주소가 옮겨졌을 때)
> - 4xx = 요청(나)의 잘못, 주소를 틀렸거나 권한이 없음
> - 5xx = 서버의 잘못, 서버가 터짐

| 코드 | 뜻 | 한마디로 |
|---|---|---|
| 200 OK | 성공 | "다 잘됐어" (잘 되면 눈에 안 보이는 코드) |
| 301/302 | 주소 이동 | "그 페이지 저쪽으로 옮겼어" (자동으로 새 주소로 보냄) |
| 401 Unauthorized | 로그인 필요 | "누구세요?" (아직 로그인 안 함) |
| 403 Forbidden | 권한 없음 | "누군지 알지만, 넌 안 돼" (VIP 바운서) |
| 404 Not Found | 없는 페이지 | "그런 페이지 없어" (인터넷에서 제일 유명한 에러) |
| 429 Too Many Requests | 너무 많은 요청 | "천천히 좀" (짧은 시간에 너무 자주 요청) |
| 500 Internal Server Error | 서버 오류 | "네 잘못 아냐, 내가 터졌어" |

### 패킷 / TCP·IP

- 패킷: 데이터 전송할 때 한 번에 통으로 보내는 게 아니라 잘게 쪼개서 전송함
- TCP/IP: 데이터를 쪼개 주소를 붙이고 순서를 맞추는 공통 규칙
  - IP = 목적지 주소를 보고 보내는 역할
  - TCP = 데이터가 제대로 갔는지 관리하는 역할

## 백엔드와 API

**백엔드**: 요청을 받아서 처리하고 응답을 돌려주는 일을 함. 프론트(브라우저)가 "이 상품 목록 줘", "이 주문 접수해 줘"라고 요청을 보내면, 백엔드는 그걸 해석하고 → 규칙을 검사하고 계산하고 데이터를 읽거나 쓰고 → 결과를 응답으로 돌려줌.

API가 '창구들이 모여 있는 서비스 전체(또는 인터페이스 집합)'라면, 엔드포인트(Endpoint)는 그 안에 있는 '개별 창구 하나하나'를 의미.

**API (Application Programming Interface)**
- 개념: 서버와 클라이언트가 서로 소통할 수 있도록 열어둔 전체 인터페이스/규약
- 비유: 식당의 '메뉴판 전체' 또는 고객을 맞이하는 '상담 센터 전체'
- 예시: "우리 서비스는 사용자 관리 API와 결제 API를 제공합니다."

**엔드포인트 (Endpoint)**
- 개념: API 내부에서 특정 기능이나 데이터에 접근할 수 있는 개별 주소(URL) + 요청 메서드(HTTP Method)의 조합
- 비유: 메뉴판 안의 '개별 메뉴(예: 김치찌개 주문 창구)' 또는 상담 센터의 '내선 번호(예: 1번 대출 상담, 2번 예금 상담)'
- 예시: `GET /products` (상품 목록 조회 창구), `POST /login` (로그인 처리 창구)

- 백엔드에서 열어주는 통로(창구): 엔드포인트. 주소(URL) + 동작(HTTP 메서드) ⇒ 프론트엔드와 백엔드가 주고받음
- 백엔드가 밖에 공개한 창구들의 묶음이 API
- 웹이 간단할 때는 URL로만 대화했는데, 웹이 복잡해지며 다양한 정보를 넣는 대화법으로 바뀜 ⇒ API의 동작

### CRUD

만들기(Create), 읽기(Read), 고치기(Update), 지우기(Delete) — 대부분의 서비스가 데이터에 대해 하는 일. HTTP method와 일치.

- **Read (조회) — GET**: 서버에 있는 데이터를 읽어와 화면에 보여줌. 데이터를 변경하지 않으므로 몇 번을 호출해도 안전. (예: 쇼핑몰 상품 목록 보기, 블로그 게시글 읽기)
- **Create (생성) — POST**: 서버에 새로운 데이터를 등록. (예: 회원가입 제출, 게시글 작성, 장바구니에 상품 추가)
- **Update (수정) — PUT / PATCH**: 이미 존재하는 데이터의 내용을 변경 (PUT은 전체 덮어쓰기, PATCH는 일부 수정). (예: 회원 정보 수정, 댓글 수정)
- **Delete (삭제) — DELETE**: 서버에서 특정 데이터를 삭제. (예: 게시글 삭제, 장바구니 상품 빼기)

- JSON: 데이터를 실어서 보내는 형태 ⇒ 일반적으로 표준으로 사용
- 백엔드도 프레임워크를 사용 (우리는 뼈대만 잡고 실제 코드는 AI에게 맡길 것)

## 보안 이야기

프론트엔드에 표시되는 모든 정보는 콘솔에서 조작 가능 → 누구나 조작 가능 → 중요한 정보는 프론트엔드가 아닌 백엔드에서 확인(검증)해야 함

### AI가 짠 코드의 약점

- 보안: AI가 짠 코드는 보안 결함이 있는 경우가 많음. 구체적으로 일을 시키지 않으면 결함이 생길 수 있음

**자주 일어나는 보안 이슈**

- 프론트엔드에서 받은 사용자 이름을 백엔드가 단순 문자열로만 처리하면, 이름값에 백엔드에 영향을 줄 수 있는 명령어가 들어갈 수 있음
  - → AI에게: "사용자 입력을 검증하고, 비밀번호는 해시로 저장하고, 모든 통신은 HTTPS로 해줘. 흔한 보안 취약점(입력값 주입, XSS)을 막아줘."
- 비밀번호·API 키를 코드에 그대로 적어 GitHub에 올리는 경우 (AI가 GitHub의 코드를 많이 학습해서 생기는 이슈) → 해결책: 환경변수
  - → AI에게: "API 키와 DB 접속 정보는 코드에 넣지 말고 환경변수로 빼줘. `.env` 파일은 깃에 안 올라가게 해줘."
- ⇒ 코드 = 공개해도 되는 것 / 환경변수 = 절대 공개하면 안 되는 것(비밀번호·키)

### 해시와 솔트

- 해시: 중요한 값을 원본 그대로 저장하지 않고 해시값으로 바꿔서 저장. 한쪽으로만 계산되는 방식
  - 가역적(결과값을 보고 되돌릴 수 있음) ↔ 비가역적(결과값을 봐도 유추할 수 없음) → 해시는 비가역적
- 솔트: 랜덤값
- AI에게: "비밀번호는 솔트를 섞어 bcrypt로 해시해서 저장해줘"

### 쿠키와 세션

- 쿠키: 브라우저에 저장되는 작은 데이터
- 세션: 서버가 사용자의 로그인 상태 등을 기억하기 위해 서버 측에 저장하는 정보
- 세션은 서버에만 남겨놓고, 내 컴퓨터가 요청할 땐 쿠키 값만 보냄
- 흐름: ① 로그인하면 서버가 세션을 만들고 고유 번호(세션 ID)를 발급 → ② 그 번호를 쿠키로 브라우저에 줌 → ③ 이후 요청마다 브라우저가 그 쿠키를 함께 보냄 → ④ 서버가 번호로 나를 알아봄

## 배포

내 서비스를 서버에 올려 누구나 들어올 수 있게 하는 것 (프론트엔드 / 백엔드 / DB)

- 백엔드는 서버에 배포
- 프론트엔드는 내 컴퓨터(개인 PC)에서 돌아감 ⇒ 주소에 접근하면 바로 다운로드받아져서 PC에서 실행하면 웹브라우저 페이지가 보임

### CORS

사용자의 브라우저가 출처가 불분명한(주소가 다른) 웹사이트의 위험한 요청으로부터 사용자를 보호하기 위한 안전장치. AI에게: "내 프론트 주소에서 오는 요청을 허용(CORS)해줘"

### 공개 서버 vs 호스팅

- **공개 서버(Public Server)**: 인터넷에 연결되어 누구나 URL만 치면 들어올 수 있는 물리적/가상 컴퓨터 그 자체 (비유: 건물)
- **호스팅(Hosting)**: 그 공개 서버의 일정 공간을 빌려서 자기 사이트를 운영할 수 있도록 제공하는 서비스/행위 (비유: 건물 안 상가를 임대해 주는 서비스)

### 터널

내 컴퓨터가 바깥 서비스로 먼저 연결을 맺어 그 통로로 손님을 받는 방식

| 도구 | 특징 | 무료 한도 · 주의 | 언제 |
|---|---|---|---|
| Cloudflare Tunnel | 포트 개방 불필요, 정식 주소·인증서까지 | 대역폭 무제한·무료. 초기 설정 약간 필요 | 가장 든든한 상시용 |
| ngrok | 한 줄 명령으로 즉시 공개 주소 | 무료는 고정 주소 1개·동시 3개 제한, 첫 방문 때 경고 페이지가 한 번 뜸 | 잠깐 시연·테스트 |
| Tailscale Funnel | 내 기기끼리 사설망으로 묶고 일부만 공개 | 무료·고정 주소. HTTPS 포트만 | 개인·팀 내부 공유 |

- **깃허브(Pages 등 클라우드 배포)**: 내 컴퓨터에서 작업하던 결과물(코드/빌드 파일)을 깃허브 서버로 전부 복사해서 전달. 내 컴퓨터를 꺼도 깃허브 서버가 24시간 대신 돌려주므로 남들이 볼 수 있음
- **내 포트 개방 / 터널링(ngrok 등)**: 코드를 다른 곳에 복사해두지 않고, 지금 내 컴퓨터에서 실제로 실행 중인 화면을 그대로 밖에서 들여다볼 수 있게 임시 창문만 열어두는 것. 내 컴퓨터나 프로그램을 끄면 접속 불가

### 배포 방식 비교

**1. 일반적인 URL 서비스 (클라우드 배포)**

- 방식: 코드를 클라우드 서버(Vercel, AWS 등)로 완전히 이사(업로드)
- 작동: `https://my-site.com` 같은 일반 URL로 접속하면, 24시간 켜져 있는 클라우드 서버가 파일이나 데이터를 보내줌
- 내 컴퓨터 상태: 끄든 켜든 상관없이 잘 돌아감
- 쓰는 이유: 안정적이고 빠르며 24시간 언제나 접속 가능

**2. 터널을 이용한 URL (ngrok, Cloudflare Tunnel 등)**

- 방식: 코드는 이사시키지 않고 내 컴퓨터에만 둔 채, 밖에서 내 컴퓨터로 들어오는 임시 파이프(터널)만 하나 연결
- 작동: 터널이 만들어 준 임시 URL로 접속하면, 터널을 지나 지금 켜져 있는 내 컴퓨터로 들어와 화면을 받아감
- 내 컴퓨터 상태: 끄면 터널도 끊겨서 접속 불가
- 쓰는 이유: 배포 과정을 거치지 않고 지금 개발 중인 화면을 누군가에게 즉시/임시로 보여주거나 테스트할 때

- **집 서버가 맞을 때**: 원리 학습, 취미, 가족·집안 내부용, 데이터를 집 밖에 두기 싫을 때, 다운타임을 감수할 수 있을 때
- **클라우드가 나을 때**: 남에게 안정적으로 24시간 보여줘야 할 때, 포트폴리오·상용 서비스, CGNAT라 집에선 안 될 때, 관리 부담을 줄이고 싶을 때
